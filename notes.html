    The Internet and the World Wide Web are not the same thing

    The Internet is the wiring of the world: cables, radio links, routers and billions of connected devices, plus the rules (protocols) that move data between them. It is a network of networks: your phone joins the home router, the router joins an Internet service provider, and providers join bigger networks across the globe. No single company owns it and no single computer is it.

    • Data travels in small packets, each labelled with its destination address; routers pass them on like road junctions.
    • TCP/IP holds it together: IP addresses and moves packets; TCP makes sure they all arrive in order.

    The World Wide Web (the Web, WWW) is one service that runs on top of the Internet: web pages written in HTML, joined by hyperlinks, fetched with HTTP and named by URLs. HTML, HTTP and URLs were invented together at CERN in 1989-91, long after the Internet began. Many other services share the same roads but are not the Web, because they use their own protocols and are not made of web pages.

    ActivityUses the Internet?Part of the Web?Reason
    Reading a news site in a browserYesYesHTML pages delivered by HTTP
    Sending email from a mail programYesNoUses mail protocols (SMTP, IMAP)
    Playing an online multiplayer gameYesNoUses a game protocol, no web pages
    Using a video-streaming app, or a WhatsApp chat or callYesNoStreaming and messaging protocols
    Internet = the infrastructure (devices + routers + cables + TCP/IP). Web = one service on it (HTML pages + links + HTTP). Every website is on the Internet, but not everything on the Internet is a website. Email, games and streaming prove the Web is only one of several Internet services.
    Trap: Calling the Web the infrastructure and the Internet a service on it is backwards. Saying the two words mean one identical system is false: you can email or game without touching the Web. Saying "the Internet speaks only HTTP and the Web speaks only TCP/IP" swaps the protocols: HTTP belongs to the Web, TCP/IP to the Internet, and HTTP itself travels over the Internet's TCP/IP family of protocols. The Internet is also not one giant computer, not a website holding every page, and not a search engine (a search site like Google is itself one website on the Web). Email and games do not run on HTML either.

    Client and server: who asks, who answers

    Every web visit is a conversation between two programs. This is the client-server model. The client asks; the server answers.

    PartWhat it isIts jobNot its job
    ClientThe browser (Chrome, Edge, Firefox, Safari) or a phone appBuilds and sends the HTTP request; receives the reply; renders HTML into pixels on screenHolding the site's database
    ServerA program on a computer in a data centreStores data, runs logic and responds to requestsDrawing pixels for the user; typing the URL (the user does that)
    DNSDomain Name System, the phone book of the InternetTurns a domain name into an IP addressSending the page request or the page
    DatabaseSits behind the serverKeeps records and answers only the serverTalking to the browser directly
    Food-delivery app: your phone (client) shows menus and sends each tap as a request. The company server looks up the restaurant list in its database, works out the delivery time and replies with JSON. The phone never holds the whole database.

    What the server sends back is a response: a status code plus the content, usually HTML for a page or JSON for data (sometimes an image or PDF). It is text, not a picture of the page; the browser interprets and draws it.

    Trap: The browser is the client even though it "shows" the page: roles depend on who asks. A server reply never contains your keystrokes, a copy of your browser's cache or history (both live on your own device), or a newly bought domain name (domains come from a registrar, not inside a page). Scrambling what the user types on the keyboard is not the server's job; HTTPS protects data while it travels between the two ends. Moving packets between networks is the routers' job, not the web server's.

    HTTP and HTTPS

    HTTP = HyperText Transfer Protocol. It is the protocol used to exchange web requests and responses: a fixed set of rules for how a request and a reply are worded, so any browser can talk to any server. In HTTP/1.1, the version shown here, the messages are plain text (newer HTTP/2 and HTTP/3 pack the same requests into binary frames):

    Browser sends:
GET /timetable.html HTTP/1.1
Host: www.citycollege.org

Server replies:
HTTP/1.1 200 OK
Content-Type: text/html

<!DOCTYPE html><html lang="en"> ...
    • GET asks for a resource; POST sends data (such as a form) in the body.
    • Status codes by first digit: 2xx success (200 OK), 3xx redirect, 4xx client error (404 Not Found), 5xx server error.
    FeatureHTTPHTTPS
    Full formHyperText Transfer ProtocolHTTP Secure
    Data on the wayReadable text; anyone on the path (cafe Wi-Fi, ISP) can read or change itEncrypted with TLS (Transport Layer Security); a certificate proves the server is genuine
    Default port80443
    Address bar"Not secure" warningPadlock or site-info icon (no warning)
    HTTPS = the same HTTP conversation in a sealed envelope: HTTP plus TLS encryption of the data in transit. Only the scheme and the default port (443) change; the path, the HTML or JSON content and the server code stay the same.
    Trap: HTTP is a protocol. It is not the physical cables (that is infrastructure), not a language for querying databases (that is SQL), and not a markup language for building pages (that is HTML). HTTPS does not compress or shrink files, does not fit layouts to phone screens (that is responsive CSS), and does not add server-side scripting (PHP or Node.js code runs with or without it).

    The request-response cycle, step by step

    1. Click: the user clicks a link or types a URL.
    2. (DNS lookup: the browser turns the domain name into an IP address.)
    3. Request: the browser (client) sends an HTTP request to that server.
    4. Server processes: it reads a file, or runs code and queries its database.
    5. Response: it sends back a status code and the content (HTML or JSON).
    6. Render: the browser draws the page, requesting each CSS file, image and script the HTML mentions (unless already cached).
    Click, then request, then server processes, then response, then render. This order never changes.
    Trap: Reject any order where the request comes before the user acts, the response comes before the request, or the server processes before anyone clicks.

    Reading a URL part by part

    A URL (Uniform Resource Locator) is the address the browser requests. Read it like a postal address: how to deliver, which building, which room, plus a note.

    https://lib.citycollege.org/books/find.html?title=html&year=2026
|       |                  |               |
|       |                  |               +-- query string (extra data)
|       |                  +-- path (which file)
|       +-- domain (which server)
+-- protocol (how to fetch)
    PartExampleJobHow to spot it
    Protocol (scheme)httpsHow to fetch: http or https (also mailto, tel)Before ://
    Domain (host)lib.citycollege.orgWhich server; DNS turns it into an IP addressAfter ://, up to the first /
    Path/books/find.htmlWhich resource on that server, like a folder pathStarts with /, runs up to ?
    Query string?title=html&year=2026Extra name=value parameters for the server, joined by &Starts with ?, runs up to # or the end
    Port (optional):8080 (not in this URL)Which "door" on the server; defaults are 80 (HTTP) and 443 (HTTPS)Right after the domain
    Fragment (optional)#reviews (not in this URL)Jumps to the element with that id; never sent to the serverStarts with #
    Worked example: https://results.techuni.ac.in/sem3
    Protocol = https; domain = results.techuni.ac.in (the whole host name); path = /sem3; no query string.
    Add ?roll=45 to the end and that new piece is the query string; the path stays /sem3.
    Trap: The domain is the full host name, not just its last label. In results.techuni.ac.in the ending in is only the top-level domain (India's country code). https:// with its colon and slashes marks the protocol; it is never the path. A path always begins with / and a query string always begins with ?.

    An absolute URL has the protocol and domain and means the same thing anywhere; a relative URL such as find.html is completed by the browser from the current page's address.

    The skeleton, the doctype and the root element

    Every HTML5 page starts with the same skeleton. Learn it once and reuse it in every file.

    <!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Hostel Mess Menu</title>
</head>
<body><h1>This Week's Menu</h1></body>
</html>
    • Line 1, <!DOCTYPE html>, tells the browser to use the modern HTML5 parsing rules (standards mode). It is a declaration, not an element, and has no closing tag. Case does not matter: <!doctype html> works too. Leave it out and the browser drops into quirks mode, copying 1990s layout rules, so spacing and box sizes go subtly wrong.
    • <html> is the root element: the single container that holds everything else. It has exactly two children, <head> first and then <body>. Head and body are siblings inside html, so neither is the root. The doctype sits above html but is not an element at all, so it cannot be the root either.
    • lang="en" on html declares the language the content is written in (hi = Hindi, pa = Punjabi). Screen readers use it to choose the right pronunciation; browsers use it to offer translation and to pick spell-check and hyphenation rules. It does not translate the page, restrict fonts or stop anyone typing other characters.
    Trap: <!DOCTYPE HTML5>, <html5> and <meta doctype="html5"> do not exist. The HTML5 doctype carries no version number, just the word html. A doctype is never a meta tag and never an element.

    The browser reads the page as a tree

    The browser does not keep your file as one long string, a flat list of separate tags, or a grid of rows and columns. It parses the markup into a nested tree of elements, called the DOM (Document Object Model). Every element is a node with one parent and possibly children; CSS and JavaScript work by walking this tree, and DevTools (F12, Elements panel) shows it.

    html
 +-- head
 |    +-- meta
 |    +-- title
 +-- body
      +-- h1

    Because it is a tree, nesting must be clean: last opened, first closed. <p><em>hi</em></p> is right; <p><em>hi</p></em> crosses over and forces the browser to guess.

    Head or body: one question decides

    The head holds metadata, information about the page; nothing in it is drawn on the page. The body holds everything the reader sees or uses. Ask one question: is it drawn on screen? Yes means body; information about the page means head.

    Belongs in head (invisible)Belongs in body (visible)
    <title>Exam Cell</title><h1> to <h6> headings
    <meta charset="UTF-8"><p> paragraphs
    <meta name="viewport" ...><img> photos, <video>
    <meta name="description" ...><table>, <form>, lists
    <link rel="stylesheet" href="site.css">, <link rel="icon"><header>, <nav>, <main>, <footer>
    <style> blocks<a> links, <button>

    <script> may go in either place: in the head with defer (so it waits until the page is parsed), or just before </body>. It is never drawn, so it is the one common exception to the rule.

    Trap: a heading, paragraph or image placed in the head is a mistake, however small. The browser quietly ends the head and pushes it into the body, and the page is invalid. Title, meta and a stylesheet link are all correct in the head. And <head> is not <header>: header is a visible banner inside the body.

    The three meta tags to know

    <meta> is a void element (no closing tag) that supplies one piece of metadata. Each of these three has exactly one job:

    <meta charset="UTF-8">Declares the character encoding: how the browser turns the file's bytes into charactersRupee signs, accents and Hindi text display correctly instead of junk such as â‚¹
    <meta name="viewport" content="width=device-width, initial-scale=1.0">Lays the page out at the phone's real width, 100% zoomWithout it a phone shows a tiny, shrunken desktop page
    <meta name="description" content="...">A short summary of the pageTypically shown as the summary text under the clickable headline in search results
    • charset is not about fonts (fonts are CSS font-family), not about phones (viewport) and not the search summary (description). Put it first in the head.
    • The description is not shown in the browser tab (that is the title) or as a heading on the page (that is h1). It is not invisible either: people read it on the search results page, where a good one wins the click. Engines sometimes show other text from the page instead.

    Trap: swapping the roles (calling h1 metadata and title the visible content) gets it backwards, and a document may not have several title elements.

    Elements versus attributes

    Elements express meaning; attributes configure them. The element says what the thing is (an image, a link, a heading). Attributes add the details (which file, where to go, which language). The two are not interchangeable, and the reversed sentence (attributes give meaning, elements configure) is backwards.

    Trap: a pair such as target="_blank" or alt="..." written inside an opening tag is an attribute. It is not the content (that sits between the tags), not the closing tag, and not a CSS declaration. A CSS declaration looks like color: red; (property, colon, value) and belongs in a stylesheet.

    Global attributes can be applied to almost any element: id (a unique name for one element), class (a reusable group name), style, title (tooltip), lang, hidden and data-*. Most other attributes belong to one family of elements:

    AttributeUsed on (main cases)Means
    href<a>, <link>, <area>, <base>A destination or address to go to
    src<img>, <video>, <audio>, <source>, <script>, <iframe>A file to load and embed

    So for an attribute that works on almost any element, choose a global one such as id; href, src and action are tied to links, embedded files and forms.

    Block-level and inline elements

    Block-level elements start on a new line and stretch across the full width, stacking like bricks. Inline elements flow inside a line of text and take only the width of their content, like one bold word in a sentence. CSS can change either, but these are the defaults.

    Block-level by defaultInline by default
    <div>, <p>, <h1> to <h6>, <ul>, <li>, <section>, <table>, <form><span>, <a>, <strong>, <em>, <b>, <code>, <img>, <label>

    <div> and <span> carry no meaning: div is the generic block container and span the generic inline one, for a few words inside a line.

    <p>Last date: <span class="due">31 March</span> for fee payment.</p>

    The span lets CSS colour just the date without breaking the line. Usually inline goes inside block. The main exception is <a>, which in HTML5 may wrap block content such as a whole card. A <p>, however, can never contain a <div>, so the browser closes the paragraph early.

    Repairing a broken fragment

    Broken:

    <h2>Canteen Menu<h3>
<img src="thali.jpg">
<a>Order online</a>

    Fixed:

    <h2>Canteen Menu</h2>
<img src="thali.jpg" alt="Veg thali with rice, dal and roti">
<a href="order.html">Order online</a>

    Three faults, three targeted fixes: (1) the heading was never closed and a second heading was opened instead, so write the closing tag that matches the opening name; (2) the image has no alt, so screen readers and search engines cannot tell what it shows; (3) the link has no href, so it goes nowhere.

    Trap: half-fixes look finished but are not. A closing tag must repeat the opening name exactly: <h2> closes with </h2>, never </h3>. An empty href="" only points back to the current page. Deleting the link text, the image's src or the heading loses content, and unrelated markup (a div for the heading, a title in the body, a bordered table) fixes nothing. Fix the real fault and keep the content.

    Textbook chapters 6, 7, 12

    Headings build the outline, not the font size

    HTML has six heading levels, <h1> (highest) to <h6> (lowest). They are the page's contents list: h1 the title, h2 the chapters, h3 the sections inside a chapter. Bigger text is only a side effect. Screen-reader users jump from heading to heading, and search engines read headings to learn what the page is about.

    • Exactly one h1 per page, naming the page's main topic. Not one per paragraph, not "as many as look nice", and never none: headings are structure, not decoration. A second h1 is not a syntax error, but it blurs which topic is the main one.
    • Do not skip levels. After h1 comes h2, then h3. Jumping from h1 straight to h4 leaves holes in the outline that screen-reader users and search engines both rely on.
    • Never pick a level for its size. Want a smaller subheading under an h2? Use h3 and shrink it with CSS.
    <h1>City Public Library</h1>
<h2>Timings</h2>
<h3>Weekend hours</h3>
<h2>Membership</h2>
    Trap: "Skipping to h4 is wrong because browsers will not display it." False. Browsers render all six levels, <h4> is fully valid in HTML5, and headings do not have to sit inside a single <section>. The real fault is the broken outline. Faking a heading with <p><b> or <div class="h2"> throws the outline away completely.

    Meaning versus looks: strong/b and em/i

    Logical (semantic) elements say what text means; physical (presentational) elements only say how it looks. Both families exist in HTML5 and look identical on screen, so choose by meaning: a screen reader can act on meaning, never on "make this bolder".

    ElementWhat it meansTypical use
    <strong>Strong importance, seriousness or urgencyA safety warning, a deadline
    <b>Bold ink to draw the eye, with no extra importanceA product name or keyword
    <em>Stressed emphasis that changes how the sentence is spoken and what it meansI asked for <em>tea</em>, not coffee.
    <i>A different kind of text, with no stressA species name, a technical term, a foreign phrase
    <u>A non-textual annotation, such as marking a misspellingRarely; underlined text looks like a link
    <small>Fine print and side comments"Taxes extra", a copyright line
    <p><strong>Warning:</strong> unplug the iron after use.</p>
<p>Our new model is the <b>Nova X</b>.</p>
<p>The tiger is <i>Panthera tigris</i>.</p>
    strong = "say it with urgency"; b = "heavier ink". em = "stress this word"; i = "a different voice". Both strong and b are current HTML5 elements, and they do not mean the same thing.
    Trap: Swapping the pair ("<b> means important, <strong> is just bold") or believing <strong> was removed from HTML5. For stressed emphasis, <i> is wrong (no stress), <u> is wrong (not emphasis at all) and <small> is wrong (fine print). Use <i> for "a different kind of text", never just to get italics.

    A link is an <a> (anchor) element. Its href attribute (hypertext reference) holds the destination; the words between the tags are the clickable link text. No href, no link. Do not confuse it with <link>, which sits in the head and attaches resources such as a stylesheet or the tab icon; it never makes anything clickable.

    Email and phone links: mailto: and tel:

    Two special schemes hand the click to another app on the visitor's device:

    • mailto: opens the visitor's email program with a new message to that address.
    • tel: lets a phone user dial the number with one tap. Include the country code (+91 for India).
    • sms: also exists, but it opens a text message rather than a call.
    <a href="mailto:office@school.example">Email the office</a>
<a href="tel:+911234567890">Call the office</a>
    Trap: The schemes are spelled exactly mailto: and tel:. Look-alikes such as email:, mail:, send:, call:, phone: and dial: are not recognised, so the browser has no app to hand them to and the click does nothing useful.

    Opening a new tab safely: target and rel

    • target="_blank" opens the link in a new tab (the default, _self, reuses the tab). Use it sparingly: the new tab has no Back history, so the visitor cannot press Back to return to your page.
    • rel states the relationship between this page and the linked one. Rule: whenever a new tab shows an outside or untrusted page, pair it with rel="noopener noreferrer".
    • noopener: the new page cannot reach back through window.opener and control your tab (for example, quietly swapping it for a fake login page). noreferrer: the new site is not told which page the visitor came from.
    <a href="https://shop.example.net" target="_blank"
   rel="noopener noreferrer">Visit the partner shop (opens a new tab)</a>
    The HTML standard and today's browsers already treat target="_blank" as if noopener were written. Adding rel="noopener noreferrer" yourself is still the recommended habit: it protects visitors on older browsers, and noreferrer also hides which page the visitor came from. It is a safety measure; it does not make the link load faster.
    Trap: rel="stylesheet" belongs on <link> for attaching CSS. The download attribute saves a file instead of opening it, which gives no protection. There is no referrer="none" attribute; the real one is called referrerpolicy.

    Link text that names the destination

    Screen-reader users often call up a list of every link on the page; "click here, more, here, »" tells them nothing. Search engines also read link text as a label for the page it points to. So link text should say where the link goes or what it gets you, and make sense on its own.

    <img> is a void element (no closing tag). Treat two attributes as mandatory: src, the resource location (a relative path or a full URL), and alt, a meaningful text alternative. In short: src says where the file is, alt says what the image means.

    • src remains the fallback for browsers that ignore srcset.

    Trap: srcset is not the alt text (that is alt), not a CSS class (that is class), and it does not push the image to load last (delaying off-screen images is loading="lazy"). It is a list of candidate files.

    Raster versus vector: why a logo should be SVG

    A JPG or PNG is a raster image: a grid of coloured pixels. Enlarge it and the browser has to invent pixels that were never stored, so edges turn blurry or blocky. An SVG (Scalable Vector Graphics) file stores drawing instructions instead, such as "circle, centre here, this radius, orange". The browser redraws those instructions at whatever size is needed, so the picture remains crisp however far you zoom and on any size of screen.

    Photo versus knitting pattern: enlarge a photo and you see grain; knit the pattern in thicker wool and you get the same design, bigger and just as neat. So logos, icons and diagrams are SVG; photographs stay JPG.

    Claim about SVGVerdict
    Looks equally crisp on a phone, a laptop and a projectorTrue: the real reason to choose it for a logo
    Guaranteed to weigh less than the JPG versionFalse: simple shapes are tiny, but a very detailed drawing can outweigh a photo
    Can show colours that JPG cannotFalse: both can show millions of colours; colour range is not the reason
    Protected from being saved or copiedFalse: it is plain text that anyone can save

    Use it as a file (<img src="badge.svg" alt="Robotics Club">) or inline as an <svg> element that CSS and JavaScript can style. Inside inline SVG, end every shape with />; an unclosed shape swallows the shapes after it.

    The canvas: width, height and viewBox

    • width and height set how big the drawing appears on the page.
    • viewBox="min-x min-y width height" defines the drawing's own grid of units (its coordinate system): the graph paper every shape is measured on. The browser then maps that grid onto the rendered size.
    • The origin (0,0) is the top-left corner and y grows downward, unlike school graphs.
    • Anything outside the viewBox is clipped: silently not drawn, no error.
    • preserveAspectRatio (default xMidYMid meet) decides how the grid is fitted and centred when the proportions differ.
    <svg viewBox="0 0 200 100" width="400">
  <rect x="0" y="0" width="100" height="50"/>
</svg>
    200 units are spread across 400 px, so 1 unit = 2 px and the 100-unit rectangle shows 200 px wide. The numbers inside never change; only the scale does.
    Trap: viewBox holds no colours, no outline width and no timing; it only sets up the coordinate grid. Colours come from fill and stroke.

    Wrong vocabulary is not an error message; the browser simply ignores attributes a shape does not understand.     Trap: there is no <triangle>, <oval> or <arc> element. A triangle is a polygon with three points, an oval is an ellipse, an arc or curve is a path.
    Why a line needs a stroke: a <line> has no inside (no area), so fill has nothing to colour, and the default stroke is none. A line with no stroke therefore paints nothing. The markup is still perfectly valid (nothing rejects it), lines do not default to white, and the stroke never decides the length: the endpoints x1, y1, x2, y2 do.

    <polyline points="10,90 50,10 90,90" fill="none" stroke="red"/>  <!-- open ^ -->
<polygon  points="10,90 50,10 90,90" fill="none" stroke="red"/>  <!-- closed triangle -->

    Give a polyline fill="none": the default fill is black, which would colour the wedge between its points.

    Painting: fill and stroke

    Memory hook: fill is paint poured inside; stroke is the pen line around the edge. So fill paints the interior and stroke paints the edge line, never the other way round. Neither sets size, transparency or rotation. Both take any CSS colour; fill="none" makes a shape hollow.

    The path language: M, L, H, V, Q, Z

    <path> can draw anything. Its d attribute is a list of commands, each a letter followed by numbers.

    CommandMeaning
    M x yMove the pen to (x, y) without drawing; this starts a new shape
    L x yStraight line to (x, y)
    H x / V yHorizontal line to x / vertical line to y
    Q cx cy x yCurve to (x, y), bent toward the control point (cx, cy)

    Uppercase letters are absolute: "go to this point on the grid". Lowercase letters are relative: each number is an offset from where the pen is now. Lowercase is valid, is used in a path's d attribute, and normally lands somewhere different from the uppercase version.

    <path d="M10 90 L50 10 L90 90 Z"/>    <!-- absolute -->
<path d="M10 90 l40 -80 l40 80 z"/>   <!-- relative: same triangle -->
    From (10,90), l40 -80 means 40 right and 80 up, landing on (50,10). Then l40 80 lands on (90,90), and z seals the third side back to the M point (10,90).
    Trap: Z has nothing to do with zooming, erasing the last command or layering. Z draws a straight segment back to where the current shape began (the last M point), sealing the outline. In a path with a single M, that is simply the starting point. Layering in SVG comes from source order: later elements paint over earlier ones.

    Text, groups and accessibility

    • <text x="40" y="90">Lab 3</text> places a label; <g> groups shapes so they move or are styled together.
    • Inline SVG has no alt attribute: give it role="img" plus aria-label, or aria-hidden="true" if purely decorative.

    Native media in HTML5

    Before HTML5, playing sound or film needed a plug-in such as Flash. Now the browser plays media itself and supplies the play button, volume and progress bar. <audio> and <video> follow one pattern:

    • The element itself is paired: it always needs its closing tag.
    • One or more <source> children (void) point at the media files.
    • Optional <track> children (void) add captions.
    • Text between the tags is shown only by a very old browser that does not understand <audio>/<video> at all. If no source format is playable, a modern browser shows an empty player instead, not the text. Audio and video have no alt attribute, and there is no <fallback> element.

  <source src="anthem.ogg" type="audio/ogg">

</audio>

    For audio that carries information (a lecture, an announcement), also provide a transcript.

    allowGrants powers: fullscreen, camera, microphone, geolocation, autoplay
    sandboxRemoves powers; tokens such as allow-scripts or allow-forms give single ones back
    Why every iframe needs a title: a screen reader announces the title when the user reaches the frame, so they know what is inside ("Map showing the central library"). Without it they hear only "frame". Nothing is printed above the frame, the frame loads without it, and picture quality is unaffected.

    Embedding responsibly

    Embedding is a trade. The other site's scripts run in your visitor's browser, so a third-party frame can drop cookies, follow your visitors from site to site, and make your page load more slowly. Habits that limit the damage:

    • Embed only from trusted sources, and add loading="lazy" so off-screen frames cost nothing.
    • Use sandbox to grant only what the widget needs. An empty sandbox blocks scripts, forms and pop-ups, so a widget that dies after you add it has lost its scripts: add allow-scripts.
    • Use allow to switch on fullscreen or camera only where needed.
    • A big site that shows a blank frame is refusing to be framed (an X-Frame-Options or Content-Security-Policy header). Nothing in your HTML overrides it; use the site's official embed address, such as a video site's /embed/ link.
    Trap: an iframe leaves your own stylesheet working, leaves the browser's Back button working, and keeps your page as normal HTML. The genuine costs are privacy (cookies, tracking) and speed.

    7Semantic elements and page structure

    Textbook chapters 13, 14

    What "semantic" means

    Definition. A semantic element is one whose name describes the meaning and purpose of its content. <nav> says "these are navigation links"; <footer> says "this is closing information". A non-semantic element such as <div> or <span> says nothing about its content: it is just a box.

    On screen, <div class="header"> and <header> look the same: both are plain block boxes. The difference is for machines:

    • Screen readers announce semantic regions as landmarks, so a blind user jumps with one key to the main content, menu or footer. On an all-div page they must hear the whole menu on every visit.
    • Search engines tell real content apart from repeated boilerplate.
    • Developers read the page structure from the tag names alone.
    <!-- just boxes: no meaning -->
<div class="menu">...</div>
<div class="content">...</div>

<!-- same look, now a map machines can read -->
<nav>...</nav>
<main>...</main>
    Semantic means meaning, not looks. The gain is machine-readable structure for screen readers and search engines.
    Trap: Semantic elements do not add a special colour or style, do not render or load faster than a <div>, and do not make the file automatically smaller. Most of them (<header>, <nav>, <section>, <article>, <aside>, <footer>) may appear many times; the one-per-page rule applies only to <main>.

    <main>The dominant content unique to this pageOne per page (never more than one visible)The sections, articles and related asides

By contrast, <section>, <article> and <div> may appear as often as the content needs.

    Trap: <header> is not <head>. <head> holds invisible metadata (charset, title, CSS links); <header> is visible introductory content inside <body>. <title> is only the text on the browser tab, and HTML has no <top> element at all.

    nav: wrap the whole group once

    <nav> marks a navigation region, not a single link. Put one <nav> around the whole group, usually around a list of links. Main menus, breadcrumbs, pagination links and a table of contents are each a group of links, so each gets its own <nav>. When a page has two or more, give each an aria-label so a screen reader can tell them apart.

    <nav aria-label="Breadcrumb">
  <ol>
    <li><a href="/">Home</a></li>
    <li><a href="/shoes/">Shoes</a></li>
    <li><a href="/shoes/running/" aria-current="page">Running</a></li>
  </ol>
</nav>
    Trap: One <nav> per link is wrong: nav marks the group, and a dozen tiny landmarks make the screen reader repeat "navigation". Also false: "nav may hold only images" (it holds lists, text, anything) and "nav cannot go inside header" (the main nav inside the page header is normal). <menu> is not navigation: in HTML it is a toolbar-style list of commands with no navigation landmark. A link group does not turn into an <aside> or a <header> because of where it sits.

    section, article, aside or div?

    Ask these questions in order:

    1. Would the block still make sense on another website or in a news feed? <article>.
    2. Related to the main content but removable without loss? <aside>.
    3. A themed part of this page with its own heading? <section>.
    4. None of these; it exists only for CSS? <div>.
    ContentElementWhy
    A recipe that a food blog could republish whole<article>Stands alone
    The "Our menu" block of a cafe home page, with an h2<section>Themed part of this page
    A "You may also like" column beside a story<aside>Related, not essential
    A wrapper only so CSS can make two columns<div>No meaning to convey
    Copyright line and phone number at the bottom<footer>Closing information
    Breadcrumbs, main menu, page numbers<nav>Groups of navigation links

    A "related stories" sidebar is an <aside>: extra content next to the story. It is not the site's navigation (<nav>), not the closing information (<footer>) and not the introduction (<header>).

    section vs article in one line: <section> groups thematically related content of this page; <article> is complete enough to be distributed independently. They are not the same, and neither is limited to one per page. An article may contain sections, and a section may contain articles.

    Every section should have a heading. The heading lets assistive technology summarise the section and lets users jump between sections by heading. The page renders and takes CSS perfectly well without one; the heading is for meaning, not display. If a block has no natural heading, it was probably never a section: use a <div>.

    div is still right as a generic styling wrapper with no meaning of its own: a grid container, a card shell, a box for a background colour. It is the wrong choice for anything a semantic element already describes, such as a copyright notice (footer), the main menu (nav) or a blog post (article).

    Trap: The two definitions are often swapped. It is article that is independently distributable and section that is a thematic group. A missing heading does not stop a section from rendering, does not block CSS and does not hide it from search engines; it only makes the section harder to navigate.

    Assembling the page skeleton

    A page is a tree: <html> holds the invisible <head> and the visible <body>; the body holds the regions, in reading order; CSS arranges them into columns later.

    <body>
  <header><h1>City Library</h1> <nav>...</nav></header>
  <main>
    <section><h2>New arrivals</h2>
      <article><h3>Review: a mystery novel</h3>...</article>
    </section>
    <aside><h2>Events this week</h2>...</aside>
  </main>
  <footer>&copy; 2026 City Library <address>12 Mall Road</address></footer>
</body>
    • Page header: logo or site title and usually the main nav (header > nav).
    • Where articles and asides go: in the usual skeleton they sit inside the main region. Never inside <head> (metadata only) and not inside the page header or footer. (A site-wide sidebar placed beside main is also valid, but asides about the page content belong in main.)
    • Page footer last: copyright, contact details in <address>, small print. This is closing information, not a related extra (aside), not a link group (nav) and not a themed block (section).
    • Repeats: <header> and <footer> may appear again inside an article (byline on top, tags below). Only main is limited: never more than one visible main per page.
    • Headings follow regions: one h1 in the page header, an h2 per section, an h3 per article.

    8Accessibility: POUR, WCAG, ARIA and keyboard access

    Textbook chapters 15, 20

    What web accessibility is

    Web accessibility is the practice of building sites that people with visual, auditory, motor or cognitive disabilities can perceive, understand, navigate and use. In short: nobody is locked out.

    • Visual: blind users hear the page through a screen reader (NVDA, JAWS, VoiceOver, TalkBack); low-vision users zoom or magnify.
    • Auditory: deaf users need captions and transcripts.
    • Motor: some users cannot hold a mouse and use only the keyboard, a switch or voice control.
    • Cognitive: clear language, consistent menus and helpful error messages.

    It helps everyone: captions on a noisy bus, good contrast in sunlight, keyboard shortcuts for power users. Most of it is simply correct HTML: lang, real headings, alt text, labels, landmarks and native controls.

    Trap: Accessibility is not a speed target, not a search-ranking trick and not "works only in the newest browser". A fast, top-ranked page can still be unusable for a blind or keyboard-only visitor.

    WCAG and its conformance levels

    WCAG stands for Web Content Accessibility Guidelines, the international standard published by the W3C through its Web Accessibility Initiative (WAI). Versions: 2.0 (2008), 2.1 (2018), 2.2 (2023); each later version adds criteria to the earlier one (2.2 also dropped one obsolete rule, 4.1.1 Parsing). Structure: 4 principles (POUR), then guidelines, then testable success criteria, each given a level.

    LevelMeaningExample criteria
    AThe minimum; without it some users cannot use the page at allImages have text alternatives; everything works by keyboard; captions on recorded video
    AAThe usual target required by most laws and organisationsNormal text contrast at least 4.5:1; visible focus; captions on live video
    AAAThe highest; not required for whole sites because some content cannot meet itContrast 7:1; sign-language video

    Levels are cumulative: AA means every A and every AA criterion passes. When a policy says "WCAG 2.x compliant" it almost always means Level AA. India's RPwD Rules 2017 require government sites to follow GIGW, which adopts WCAG 2.1 Level AA; the US Section 508 and the EU's EN 301 549 also point to WCAG Level AA.

    Trap: Made-up expansions built from words like "World", "Code", "Compliance", "Grading" or "Generator" are wrong: it is Web Content Accessibility Guidelines. There are only three levels, A, AA and AAA; there is no Level B. Level A is only the floor, and AAA is the ideal, not the normal legal target.

    POUR: the four principles

    PrincipleThe question it asksTypical checksA scenario that tests it

    OperableCan users work every control?Keyboard-only use, visible focus, skip links, enough time, nothing flashing more than 3 times a secondFinishing a checkout with only Tab and Enter
    UnderstandableCan users understand the content and the controls?Page language declared, consistent navigation, labels, clear error messagesA form says "Enter a 6-digit PIN code" instead of just "Invalid"
    RobustDoes it keep working across browsers, devices and assistive technologies?Standard HTML, native elements, correct name, role and value for every controlThe same form works in Chrome, Firefox, on a phone and with a screen reader
    Scenario trick: sensing = Perceivable; doing, pressing keys = Operable; making sense = Understandable; works everywhere, with any tool = Robust.
    Trap: A keyboard-only test is about operating the page, so it is Operable, not Perceivable (nothing is hidden from the senses) and not Understandable (the user already knows what to do). "Keeps working across browsers, devices and assistive technology" is Robust, not Operable.

    Keyboard access and tabindex

    Many users never touch a mouse. Tab moves to the next control, Shift+Tab to the previous one, Enter follows a link or presses a button, Space toggles a checkbox or presses a button, and the arrow keys move inside radio groups and menus. Native links (<a href>), buttons and form controls are focusable and keyboard-operable for free; a <div onclick> is not. Never remove the focus outline without a replacement. A skip link at the top (<a href="#main">Skip to main content</a>) lets keyboard users bypass the menu.

    ARIA: role, aria-label, aria-hidden and the first rule

    ARIA (WAI-ARIA, Accessible Rich Internet Applications) is a W3C set of HTML attributes that tell assistive technology what an element is, what it is called and what state it is in, where plain HTML cannot say it. ARIA changes what is announced, never how the element behaves: role="button" on a <div> makes a screen reader say "button", but the div still ignores Enter and Space and is not in the Tab order.

    First rule of ARIA: if a native HTML element already has the meaning and behaviour you need, use it instead of rebuilding it with ARIA. A real <button> beats <div role="button">. Adding role="button" to a <button> is redundant, and giving a native element a role that contradicts it is worse. ARIA is a fallback for gaps, not a newer replacement for semantic HTML.

    The form element: where and how the data travels

    A <form> collects what the user enters and sends it to a server. When the submit button is pressed, the browser takes every control that has a name, pairs that name with the current value (name=value) and sends the pairs.     • action = where: the URL the form data is sent to. Leave it out and the form submits to the current page.
    • method = how: get (the default) or post.

</form>

So "age 21 to 65" is min="21" max="65", while minlength="8" on a password means at least 8 characters (not at most, not exactly, not digits only, nothing to do with time).     An empty box passes both minlength and pattern: they only judge a value that is actually there. That is why they are paired with required.

    <label for="sub">Subject code</label>
<input id="sub" name="sub" required pattern="[A-Z]{2}[0-9]{3}"
       title="Two capital letters then 3 digits, e.g. CS101">

    Type cs1 and the browser blocks the form; its message shows the title text as the hint about the expected format. The title is not the server's key (that is name), not a default value (that is value) and no replacement for a <label>.

    What type="email" really checks

    Browsers follow the HTML Living Standard: one or more allowed characters (letters, digits and symbols such as . + _ -, but no spaces), one @, then a domain made of one or more labels of letters, digits and hyphens, separated by dots. A dot after the @ is allowed but not required.

    Value in <input type="email" required>Result
    user.k@campus.ac.inValid: dots are fine on both sides of the @
    user@campusValid: the form submits normally
    user@Blocked: nothing after the @
    usercampus.ac.inBlocked: no @ at all
    user k@campus.inBlocked: a space inside
    (empty)Blocked by required
    Trap: many notes say an address with no dot after the @ (like name@college) is rejected. Real browsers accept it and submit normally. When a value really is invalid, the browser stops the form; it never "corrects" the address and never silently drops the field from the data.

    For a stricter rule, add a pattern; it is checked on top of the email check:

    <input type="email" name="mail" required
       pattern=".+@.+\..+" title="Use a full address such as name@college.edu">

    Now user@campus is blocked, because the pattern demands a dot after the @.

    Client-side versus server-side validation

    Client-side checks are the guard at the gate: quick and polite, but they can be walked past. Server-side checks are the lock on the door.

    Client-side (browser)Server-side (backend)
    Runsin the browser, before anything is senton the server, after the data arrives
    Written inHTML attributes, JavaScriptbackend code (PHP, Python, Java...), not HTML
    Feedbackinstant, no reloadonly after a round trip, so slower
    Can the user bypass it?Yes: DevTools can delete required, or a request can be sent without the formNo: it runs on the site's own machine, out of the user's reach

    Always do both. Client-side validation improves the experience but never replaces the server check, is not more secure, and does not run on the server.

    Textbook chapter 19

    When to use a table, and what each part does

    Use a table only for tabular data: information whose meaning comes from its position, where a row meets a column. A bus timetable (stop by time), a fee chart (course by year), a results sheet (team by event). If you only want boxes side by side, that is layout, and layout is CSS's job (see the last part of this section).

    ElementIts jobIt is NOT
    <table>The container for the whole grida page-layout tool
    <caption>A visible title for the whole table, read out first by screen readers. Must be the first child of <table>.a column width, a totals row, or a tooltip on each cell (tooltips come from the title attribute)
    <thead>, <tbody>, <tfoot>Sort the rows into sections: heading rows, data rows, and summary rows such as totalsa single row (each group holds tr rows), a way to merge cells, a border, or a shortcut that lets you skip tr
    <tr>One horizontal row; every cell must sit inside a rowa column (HTML builds a table row by row; no tag holds a column of cells)
    <th>A header cell: names what its column or row containsjust "bold text" (bold and centred is only its default look)
    <td>A data cell: holds one valuea heading
    Memory hook: tr = table row, th = table header, td = table data. A table holds rows, rows hold cells, cells hold content. The group tags sit between table and tr: they group rows, they never replace them.

    Why group rows at all? CSS can style the heading section differently from the body, a long table's heading rows can repeat on every printed page, and screen readers can tell heading rows from data rows.

    The correct order, in one example

    Children of <table> go in this order: caption, then colgroup (optional), then thead, tbody, tfoot.

    <table>
  <caption>Canteen prices</caption>
  <thead><tr><th scope="col">Item</th><th scope="col">Rs</th></tr></thead>
  <tbody>
    <tr><th scope="row">Samosa</th><td>15</td></tr>
    <tr><th scope="row">Tea</th><td>10</td></tr>
  </tbody>
  <tfoot><tr><th scope="row">Both</th><td>25</td></tr></tfoot>
</table>

    Browsers draw no borders by default; add them in CSS (th, td { border: 1px solid #999; }), not with the old border attribute. If you leave out <tbody>, the browser quietly adds one.

    Trap: <table><td>5</td></table> is invalid: the cell is not inside a <tr> (the browser patches it, but the source is still wrong). A caption placed after <thead> or outside </table> is also wrong.

    Merging cells: colspan and rowspan

    • colspan="n": the cell stretches sideways across n columns.
    • rowspan="n": the cell stretches downwards across n rows.

    Both go on a <td> or <th>, and n counts grid cells, not pixels. Like knocking down a wall between two rooms: one bigger room, so the plan stops showing two.

    Counting rule: every row must add up to the table's column count, spans included. The row below a rowspan cell leaves that cell out, because the slot is already filled from above.

    <!-- 3 columns: Department | Lab | Day -->
<tr><th rowspan="2">Physics</th><td>Optics</td><td>Mon</td></tr>
<tr><td>Mechanics</td><td>Thu</td></tr>
<tr><td colspan="3">All labs close at 5 pm</td></tr>
    Count it. Row 1: Physics + 2 cells = 3. Row 2: only 2 cells are written, because Physics (rowspan) still fills the Department slot: 1 + 2 = 3. Row 3: one cell with colspan="3" = 3. One label (Physics) heading two rows that sit one under the other is exactly the rowspan job. So colspan="2" covers two columns side by side, and rowspan="2" covers two rows top to bottom.
    Trap: colspan never means rows, whole tables or pages, and neither attribute takes pixels. span is not a merge attribute for cells: it belongs on <col> and <colgroup>, where <col span="2"> styles two whole columns at once. scope (any value, including rowgroup) only says which cells a header describes; it merges nothing. Under a rowspan cell, do not repeat the cell or add an empty one: either makes the row one column too wide.

    <colgroup> and <col> sit after the caption and before thead, and let you give a whole column a width or background without repeating it on every cell.

    Tables a screen reader can read

    A sighted reader glances up to the column heading and left to the row heading. A screen reader reads one cell at a time, so the markup must say which headings belong to each value. Done right, a cell is announced as "Relay, Blue House, 38", not a bare "38". Three tools:

    1. Use th for every heading cell, column and row headings alike; td is only for values.
    2. Put scope on each <th> to say which cells it labels.
    3. Add a <caption>, so the user hears what the table is about before hearing dozens of numbers.
    scope valueThe header labels...
    colthe whole column it heads (every cell under it)
    rowthe whole row it starts
    colgroup / rowgroupa group of columns (a colgroup) / every row of its thead, tbody or tfoot
    <table>
  <caption>Sports day: points by house</caption>
  <tr><td></td><th scope="col">100 m</th><th scope="col">Relay</th></tr>
  <tr><th scope="row">Red House</th><td>42</td><td>30</td></tr>
  <tr><th scope="row">Blue House</th><td>35</td><td>38</td></tr>
</table>

    For complex tables with two levels of headings, give each <th> an id and list them on the data cell: <td headers="relay blue">. scope handles simple tables; headers handles the rest.

    A data table that sounds confusing when read aloud is fixed by its markup, not its looks: <th> for headings + scope + a <caption>.
    Trap: bigger fonts, bold text and background colours change only what sighted people see; a screen reader ignores them. Rebuilding the grid from <div>s throws away the row and column links entirely. Sprinkling colspan merges cells and wrecks the grid without adding a single heading. And scope="col" labels every cell in its column, not just the one cell beneath the heading and not the whole table (naming the whole table is the caption's job).

    Never use a table for page layout

    Before CSS, whole pages were built inside tables: a row for the banner, cells for the menu and articles. Today that is wrong. Layout tables hurt accessibility and block responsiveness; tables are meant for tabular data only.

    • Accessibility: a screen reader may announce "table, 2 columns" and read out row and column positions that mean nothing (browsers try to guess layout tables, but the guess is unreliable).
    • Responsiveness: a table's grid does not reflow into one column on a phone unless extra CSS tears the table apart; left alone, the cells stay side by side, squeezed or scrolling sideways.
    • Meaning: the markup claims the page is data when it is not.

    The modern way is semantic regions (<header>, <nav>, <main>, <aside>, <footer>) arranged with CSS Flexbox or Grid.

    Trap: the reason is not that tables cannot hold images (a cell can hold images, links, lists, even a form), not that browsers dropped <table> (it is a current, fully supported element and the right choice for data), and not speed (tables do not "always" load slower than divs, and speed is not the objection). The real problems are accessibility and reflow.

    If you inherit a layout table you cannot rewrite (old HTML emails are the classic case), <table role="presentation"> tells assistive technology to ignore its data meaning. It changes nothing on screen: it does not hide borders, make the table sortable or make the cells stack on a phone.

    11Responsive content structuring

    Textbook chapter 21

    What responsive means

    A responsive page is one HTML document that adapts to whatever screen shows it, from a 360-pixel phone to a wide monitor: text reflows, columns stack, images shrink. There is no separate mobile site. Think of water: it takes the shape of any glass you pour it into. Three things work together:

    1. HTML with a clean, logical structure (this section);
    2. CSS media queries that rearrange it for each screen width (Unit 3);
    3. images and videos that can scale.

    The viewport meta tag

    Mobile browsers were built when the Web was all desktop pages. So, by default, a phone pretends its screen is about 980 pixels wide, lays the page out at that width, then zooms out to squeeze it onto the small screen. The result is a miniature desktop page whose text is too small to read without pinching. One line in the <head> stops the pretending:

    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    • width=device-width: lay the page out at the device's real screen width.
    • initial-scale=1.0: open at 100% zoom, not zoomed out.

    Without it, CSS media queries also measure the fake 980-pixel width, so phone-only styles never switch on. That is why the viewport tag is the one meta tag that phones need to show a page at its real size.

    Meta tagWhat it doesMakes the page fit a phone?
    <meta charset="UTF-8">Sets the character encoding, so the rupee sign ₹ and Hindi letters display correctlyNo (but still needed on every page)
    <meta name="description" content="...">A summary that search engines may show under the linkNo
    <meta name="author" content="...">Records who wrote the pageNo
    <meta name="viewport" content="...">Sets the layout width and starting zoom on mobileYes
    Trap: a page with no viewport tag still loads normally, and nothing on it is hidden. The browser does not swap in some built-in "mobile stylesheet" either; it simply shows the desktop layout shrunk down. Also, never add user-scalable=no or maximum-scale=1: blocking zoom hurts people with weak eyesight.

    Mobile-first and logical source order

    Mobile-first means you start with the smallest screen, then add improvements as screens get bigger: first a single column that works on a phone; when there is more room, CSS adds a second column, then a third. Working the other way (desktop-first: shrinking a big design down) gives cramped, compromised phone pages. Mobile-first also forces good priorities: only the important content fits a small screen, so you decide what matters first. It does not mean "desktop only", and it has nothing to do with print layouts.

    The single-column phone view is simply the HTML in the order it was written. So logical source order is the foundation: header, navigation, main content, related content, footer. Get the order right and the page already works on a phone before any CSS exists; screen readers and search engines read it in that order too.

    <header>Tech fest</header>
<nav>Events | Register</nav>
<div class="cols">
  <main>Schedule and venues</main>
  <aside>Sponsors</aside>
</div>
<footer>Organising team</footer>

    On a phone these simply stack. Later, one CSS rule puts main and aside side by side only when there is room, without touching the HTML:

    @media (min-width: 700px) {
  .cols { display: flex; }
}

    Flexible, scalable media

    A 1600-pixel photo shown at its full 1600 pixels overflows a 390-pixel phone and drags the whole page sideways. In a responsive page, images and videos must be able to shrink and grow with the box that holds them; they are never locked to a pixel width wider than a small screen. The standard CSS rule:

    img, video { max-width: 100%; height: auto; }
    • max-width: 100%: never wider than the box it sits in.
    • height: auto: the height follows, so the picture keeps its shape instead of stretching.

    Keep writing width and height attributes on <img>: they tell the browser the image's proportions so the page does not jump while it loads, and the CSS above still lets it shrink.

    Trap: the wrong habit is fixing the displayed size in pixels so the image cannot shrink. Hiding images on phones, swapping them for text, or sending them only to desktops removes content; responsive design keeps the content and resizes it.

    Shrinking a huge file still downloads the huge file. srcset lists several sizes, sizes says how wide the image will appear, and the browser picks the smallest file that is still sharp. <picture> can even give phones a differently cropped image.

    <img src="gate-800.jpg" alt="College main gate" width="800" height="450"
     srcset="gate-400.jpg 400w, gate-800.jpg 800w, gate-1600.jpg 1600w"
     sizes="(max-width: 600px) 100vw, 800px">

    A wide data table cannot become one column without losing its meaning, so let it scroll inside its own box while the page stays still: wrap it in <div class="scroll-x"> and give that class overflow-x: auto in CSS.

    Testing: in Chrome press F12, then Ctrl+Shift+M for device mode, and drag the width; then try a real phone, because emulators do not reproduce touch or slow networks. A page passes when no sideways scrollbar appears at any width, text is readable without zooming, images fit and every control can be tapped.
