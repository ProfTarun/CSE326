Website Performance Fundamentals

A page can have perfect HTML, tidy CSS and bug-free JavaScript and still fail its visitors: a white screen for six seconds on a phone, a button that freezes when tapped, text that jumps as you reach for a link. This chapter is about the speed a visitor feels: what makes pages slow, how a browser builds a page, the three numbers Google scores, and the fixes that make a site quick.

  • List the common causes of a slow page and match each to a fix.
  • Explain the browser's loading steps, why CSS blocks rendering and a plain script blocks parsing, and choose between defer and async.
  • Optimise an image: size, format, compression, srcset/sizes, width/height, lazy-loading below the fold.

74.1 What "fast" means to a visitor

Ask a friend whether a website is fast and they will say how it felt: "it took ages to show anything", "I tapped and nothing happened", "the page jumped and I clicked the wrong thing". Website performance is those three: how quickly a page becomes useful, how quickly it reacts, and whether it stays still while loading.

PillarThe visitor's questionIt fails when…
Loading speed"How soon do I see the main content?"The big photo or headline appears seconds late
Responsiveness"When I tap or type, does it react?"A click takes half a second to show a change
Visual stability"Does it stay where I put my finger?"Text and buttons jump as photos arrive

Figure 74.1 shows one page built two ways, drawn like the filmstrip of snapshots Lighthouse shows for your own page.

Picture this. At a dhaba outside the LPU gate, three things decide whether you come back: how long the first plate takes to arrive, whether the waiter answers when you call, and whether somebody shifts your plate mid-meal so your hand lands in the dal. A web page is judged on the same three.

Why it matters

  • People leave. Google's research on mobile pages found that as load time grows from one second to three, the chance of a bounce rises by 32%.
  • Data costs money. On a prepaid pack with a daily limit, a 6 MB page opened ten times is 60 MB of somebody's day.
  • Phones are slower than your laptop. A mid-range phone runs JavaScript several times more slowly, and mobile networks add a pause to every file. Test for the budget phone in a hostel corridor.
  • Search engines notice. Google counts the Core Web Vitals (Section 74.4) among its "page experience" signals, though relevant content matters most (Chapter 11).
Quick check: what are the three things a visitor feels when they say a page is "slow"?

Loading speed (how soon the main content appears), responsiveness (how quickly it reacts to taps and typing) and visual stability (whether content stays still).

74.2 What makes websites slow

The same few causes turn up again and again. One word first: page weight is the total size of every file a page downloads (HTML, CSS, JavaScript, images, fonts). One phone-camera photo is often 3–5 MB; a whole well-built page can be under 1 MB.

CauseTypical exampleWhat the visitor feelsFirst fix
Large imagesA 4 MB photo shown 400 px wideThe main picture arrives late; data used upResize, compress, WebP (74.5)

Too many requests40 small files, each with overheadWaiting adds up, file by fileCombine and remove files (74.6)

Two things make every cause worse on a phone. The network has latency: each new file can wait a tenth of a second or more before data flows, so forty tiny files keep paying that wait. And the processor is slower, while JavaScript costs twice: to download, then to compile and run. 300 KB of JavaScript keeps a phone busy far longer than a 300 KB photo.

Key idea. Most slow student projects have two problems: a giant photo straight from the phone camera, and scripts in the <head> without defer. Fix those two and most of the page is fixed.

74.3 How the browser turns files into a page

To see why those causes hurt, follow the browser from "you pressed Enter" to "you see the page": the critical rendering path, in six simplified steps.

  1. Request the HTML: GET / → index.html.
  2. Parse the HTML into the DOM. The parser reads top to bottom and builds the element tree of Chapter 55.
  3. Discover the other files from <link>, <script> and <img> tags.
  4. Build the CSSOM, then the render tree. The CSS becomes the CSSOM, combined with the DOM into the render tree: the visible elements only (no display: none), with final styles.
  5. Download the remaining resources: images, fonts and scripts, several at a time.
  6. Lay out and paint. Layout works out every box's size and position; paint fills in the pixels.

HTML becomes a tree, CSS a list of rules; together they decide what is visible and how it looks; then the browser works out where every box goes and only then colours in pixels. Delay any step and you delay what the visitor sees.

Two rules that decide when the first pixel appears

CSS is render-blocking. Nothing is painted until the stylesheets in the <head> arrive. That is deliberate: otherwise you would see unstyled text leap into place (a flash of unstyled content). So do not move CSS to the bottom; keep it small.

A plain script blocks parsing. Meeting <script src="app.js">, the parser stops, waits for the download, runs the script, and only then carries on, because a script may change the page being read. In the head, that means a white screen throughout. Parsing and scripts share the main thread, which does one job at a time.

Watch it. The head script below pretends to be a big file by keeping the main thread busy for 1.5 seconds; the preview stays blank until it lets go.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>Parser order</title>
  <script>
    console.log("1. Script in the head. Is the heading there yet?", document.querySelector("h1") !== null);
    // pretend this is a big script: the parser cannot read on until it finishes
    const stopAt = performance.now() + 1500;
    while (performance.now() < stopAt) {}
    console.log("2. Head script finished after 1.5 s. Only now can the body be read.");
  </script>
</head>
<body>
  <h1>Hello from the body</h1>
  <script>
    console.log("3. Script after the heading. Is the heading there now?", document.querySelector("h1") !== null);
    document.addEventListener("DOMContentLoaded", () => {
      console.log("4. DOMContentLoaded: all the HTML has been read");
    });
    window.addEventListener("load", () => {
      console.log("5. load: the picture and every other file have arrived too");
    });
  </script>
  <img src="media/campus.svg" alt="Campus scene" width="300" height="150">
</body>
</html>

The console prints five lines in order. Line 1 says false: the body has not been read, so the heading does not exist yet. Line 3 says true. Lines 4 and 5 are the Network panel's blue and red lines (Section 74.7): DOMContentLoaded when all the HTML is parsed, load when every other file has arrived too.

defer and async: download now, run later

Two attributes on an external script remove the blocking: both download the file in parallel while the parser keeps reading. They differ in when the script runs (Figure 74.3 and the table).

Written asRunsOrder kept?Use it for
<script src="app.js">At once; parsing stops for download and runYesAlmost never in the head
<script src="app.js" defer>After all the HTML is parsedYes, page orderYour own scripts
<script src="stats.js" async>As soon as it arrivesNo, arrival orderIndependent scripts (analytics)
<script type="module" src="main.js">Like defer, automaticallyYesModule code (Chapter 73)

Small print: defer and async work only on scripts with a src; an ordinary inline <script> ignores them. A script at the end of <body> also avoids blocking, but may start downloading later than a deferred one in the head.

defer: "fetch it now, run it when the page has been read, in order". async: "fetch it now, run it whenever it turns up".

Quick check: app.js uses a function defined in helpers.js. Should both get defer or async?

defer, with helpers.js written first: deferred scripts run in page order, so the helper exists when app.js runs. With async, app.js might run first and fail because the helper is not defined.

74.4 Core Web Vitals: three feelings, three numbers

To measure feelings, Google defined one number per pillar, the Core Web Vitals: the dhaba's first plate, the waiter's answer, the plate that must not move.

VitalMeasuresPillarGoodNeeds improvementPoor
LCP — Largest Contentful PaintWhen the biggest image or text block in the first screen appearsLoading≤ 2.5 s2.5–4.0 s> 4.0 s
INP — Interaction to Next PaintHow long the page takes to visibly answer taps, clicks and keysResponsiveness≤ 200 ms200–500 ms> 500 ms
CLS — Cumulative Layout ShiftHow much visible content moves around unexpectedlyVisual stability≤ 0.10.1–0.25> 0.25

LCP: when does the main thing appear?

The browser watches the images and text blocks in the first screenful (the viewport) and notes when the largest is painted, usually the hero photo or main heading. That moment is the LCP. It is late when the hero is heavy or lazy-loaded, when render-blocking files delay every paint, or when the server is slow.

Quick check: a page's hero image appears at 3.1 s for most visitors. Is its LCP good, needs improvement, or poor?

Needs improvement: it is between 2.5 s and 4.0 s. Compress and resize the hero, do not lazy-load it, and serve it at its displayed size.

INP: when I tap, does it answer?

Taps and key presses are handled by the main thread, one job at a time; if it is busy with long JavaScript, your tap waits in a queue. INP times each interaction from the input until the browser paints the next frame, and reports one of the slowest of the visit (a few extreme outliers are ignored on busy pages). That time has three parts:

  1. Input delay: waiting for the main thread to finish what it was doing.
  2. Processing: running your event handler.
  3. Presentation: recalculating layout and painting the change.

A job holding the main thread for more than 50 ms is a long task. INP replaced FID (First Input Delay, only the waiting part of the first interaction) in March 2024; older notes may still mention FID.

Feel it yourself. The red button does 600 ms of busy work before it answers. Click it, then at once click the green one:

  body { font-family: system-ui, sans-serif; padding: 14px; }
  button { font: inherit; padding: 10px 16px; margin-right: 8px; border: 0;
           border-radius: 8px; color: #fff; cursor: pointer; }
  #fast { background: #138808; }
  #slow { background: #C42B2B; }
  #out  { margin-top: 14px; font-weight: 700; color: #0B2545; }
</style>
<button id="fast">Fast button</button>
<button id="slow">Slow button</button>
<p id="out">Click a button. Then click Slow and, straight away, Fast.</p>
<script>
const out = document.querySelector("#out");

// keeps the main thread busy for ms milliseconds, like a heavy calculation
function busy(ms) {
  const end = performance.now() + ms;
  while (performance.now() < end) {
    // nothing else on the page can happen while this loop runs
  }
}

function report(name, event, start) {
  const waited = Math.max(0, Math.round(start - event.timeStamp));
  const ran = Math.round(performance.now() - start);
  console.log(`${name}: waited ${waited} ms to start, then ran for ${ran} ms`);
  out.textContent = `${name} answered after about ${waited + ran} ms.`;
}

document.querySelector("#fast").addEventListener("click", (event) => {
  const start = performance.now();
  report("Fast button", event, start);
});

document.querySelector("#slow").addEventListener("click", (event) => {
  const start = performance.now();
  busy(600);
  report("Slow button", event, start);
});
</script>

Alone, Fast waits and runs about a millisecond; Slow runs 600 ms. Click Fast while Slow is busy and Fast reports it waited hundreds of milliseconds: the input delay part of INP, caused by another job's long task. (event.timeStamp is the moment of the click, so start - event.timeStamp is the time queued.)

CLS: does it stay still?

A layout shift is visible content moving without the visitor asking: the paragraph you are reading slides down because an image above it arrived. A jump scores more the more of the screen moves and the further it moves. Jumps less than a second apart form a burst, and CLS reports the worst burst of the visit, with no unit: 0 means nothing moved. Movement within half a second of a tap or key press is expected, so not counted. (Half the screen dropping by a quarter of the screen touches three quarters of it: 0.75 × 0.25 = 0.1875.)

Usual causes: images and videos without width and height; adverts and "Accept cookies" banners pushed in with no space kept; web fonts swapping in at another size. Fixes: dimensions on every image and video, min-height or aspect-ratio for late arrivals, new content below the reader, and animation with transform, not top or height (Chapter 38).

Tell the browser every picture's size before it arrives, and never push new things in above what the visitor is reading. Then CLS stays close to 0.

Watch a shift. Both photos "arrive" two seconds after Run; until then each is a blank 1-pixel stand-in (the long data: value). Only the right one has width and height.

Real visitors, not one test: the 75th percentile

A page passes only when at least 75% of real visits are "good" on all three: the 75th percentile of LCP must be at most 2.5 s, of INP 200 ms, of CLS 0.1.

74.5 Images: the biggest, easiest win

Images are usually the heaviest part of a student site, and the easiest to fix. Almost every first portfolio has:

<!-- BEFORE: 4000 × 3000 px phone photo, 3.8 MB, no size, so the text below jumps when it loads -->
<img src="campus-photo.jpg">

4000 × 3000 is 12,000,000 pixels; a 400 × 300 spot needs 120,000. The file carries a hundred times more picture than anyone sees, and decoded at about 4 bytes per pixel it fills roughly 48 MB of the phone's memory. Done properly, as on the slide:

<!-- AFTER: hero, above the fold -->
<img src="campus-1200.webp"
     srcset="campus-600.webp 600w, campus-1200.webp 1200w"
     sizes="(max-width: 600px) 100vw, 1200px"
     width="1200" height="675"
     alt="Students on the main lawn">

<!-- AFTER: gallery, below the fold -->
<img src="lab-800.webp" width="800" height="533" loading="lazy" alt="CSE lab">
Version of the hero photo (illustrative)Download size
Original JPEG, 4000 px wide3.8 MB
Resized JPEG, 1200 px wide420 KB
WebP, 1200 px wide180 KB — about one twentieth of the original

Six habits produce that result:

1. Make it the right size

Resize the file to the largest size it is shown. Phones pack two or three screen pixels across every CSS pixel (the devicePixelRatio), so an image shown 400 CSS pixels wide is sharpest from a file about 800 pixels wide; beyond twice that, hardly anyone sees a difference. The free browser tool Squoosh resizes and compares side by side.

2. Compress it, in a modern format

A JPEG at quality 75–85% looks like one at 100% to most eyes and is far smaller. WebP is usually a quarter to a third smaller than JPEG at the same quality, AVIF often smaller again. Current browsers show both; <picture> can add a JPEG fallback (Chapter 8).

What the image isBest format
A photographWebP or AVIF (JPEG as a fallback)
A logo, icon or diagramSVG: tiny, sharp at every size
A screenshot with text, or transparencyPNG, or lossless WebP
Anything that movesA short MP4 or WebM video, not a much bigger GIF

3. Let the browser choose the file: srcset and sizes

srcset lists the files and their real widths (600w = 600 pixels wide). sizes gives the displayed width: "up to 600 px screens, the full screen width (100vw); otherwise 1200 px".

srcset lists the files you offer; sizes says how big the picture will be; the browser, knowing its own screen, downloads one, usually the smallest that still looks sharp.

4. Reserve the space: width and height

As in Chapter 8, width and height do not shrink the file. They give the browser the image's shape before a byte arrives, so it keeps a box of the right size. Nor do they lock the shown size, given this common rule:

img { max-width: 100%; height: auto; }   /* shrink to fit a phone, keep the shape */

So a width="1200" height="675" image shown 360 px wide on a phone gets a reserved 360 × 202.5 px box.

5. Lazy-load what is below the fold, and only that

"Above the fold" is newspaper language for what you see without scrolling. loading="lazy" makes the browser wait until the visitor scrolls near an image before downloading it, saving megabytes for every visitor who never scrolls that far.

Never lazy-load the hero. The big photo at the top is usually the LCP element. Marked lazy, its download waits until layout confirms it is on screen, so LCP gets worse. Load it normally, perhaps with fetchpriority="high" to fetch it before other images.

6. Check what you shipped

Hovering an <img>'s src in the Elements panel shows its intrinsic size (the file's pixels) against its rendered size; Lighthouse flags oversized images. The example does the same check with naturalWidth (the file's width) and width (the shown width), using the 600 px campus SVG as a stand-in photo.

<style>
  body { font-family: system-ui, sans-serif; padding: 12px; }
  img  { display: block; margin-bottom: 8px; border-radius: 8px; }
</style>
<img src="media/campus.svg" alt="Campus thumbnail" width="150" height="75">
<img src="media/campus.svg" alt="Campus banner" width="300" height="150">
<script>
// a tiny version of the "properly size images" check that Lighthouse runs
window.addEventListener("load", () => {
  console.log("This screen's devicePixelRatio:", window.devicePixelRatio);
  document.querySelectorAll("img").forEach((img) => {
    const ratio = img.naturalWidth / img.width;   // img.width: the width it is shown at
    console.log(`${img.alt}: file is ${img.naturalWidth}px wide, shown at ${img.width}px (${ratio}x)`);
    if (ratio > 2) {
      console.warn(`Too big: about ${ratio * ratio}x the pixels this spot needs. Resize the file.`);
    } else {
      console.log("Fine: up to 2x keeps it sharp on a high-density phone screen.");
    }
  });
});
</script>

The first line shows your screen's devicePixelRatio (often 1 on a lab monitor, 2 or 3 on a phone). The thumbnail reports a 600 px file shown at 150 px, 4x, and warns of about 16 times the pixels it needs (four times as wide and as tall). The banner reports 2x and passes.

Quick check: a page has a large banner photo at the top and twelve gallery photos further down. Which should get loading="lazy"?

Only the twelve gallery photos. The banner is probably the LCP element; lazy-loading it delays what LCP measures. All thirteen need width and height.

74.6 CSS and JavaScript: send less, block less, touch the page less

Block less

Your own scripts get defer; independent third-party scripts get async, or load after the visitor agrees to analytics. A big feature few visitors use (a chart, a map) can load when opened. CSS stays in the head, but small.

Send less: remove what you do not use

The slide's rule: don't add a 90 KB library for one helper. jQuery once papered over browser differences; today every browser has the tools built in:

// with jQuery: about 85 KB of library (minified) to download and run, for this
$("#list").html("Loading...");

// without: built into every browser, 0 KB extra
document.querySelector("#list").textContent = "Loading...";

The same goes for functions nobody calls and CSS rules for deleted elements. The Coverage panel (Section 74.7) shows the bytes of each file that never ran.

Make each file smaller: minify and compress

Spaces, line breaks and comments help people read code; the browser does not need them. Minification strips them out (and, for JavaScript, shortens local variable names):

/* Card styles for the course list */
.card {
  background: #ffffff;
  padding: 16px;
}

/* minified: 35 characters instead of 87 (comment included) */
.card{background:#fff;padding:16px}

Build tools (the slide's "minify & bundle" step) produce files such as app.min.js from the readable source you keep in Git (Chapter 75). Most servers, GitHub Pages among them, also compress text on the way out (gzip or Brotli): jQuery's 85 KB minified file travels as about 30 KB. Photos are already compressed, hence Section 74.5. The Network panel shows both transferred and resources (unpacked) sizes.

Fewer requests

Because of latency, forty tiny files cost more than four medium ones. Combine small CSS and JavaScript files (bundling), draw icons with SVG rather than thirty PNGs, and load only the font weights you use. HTTP/2 softens the cost, but every file still has one.

Download once: caching

The browser keeps a cache of downloaded files for reuse. The server says for how long with a header such as Cache-Control: max-age=31536000 (one year, in seconds); GitHub Pages says ten minutes, one reason a just-published change can take minutes to appear (Chapter 76). The professional trick is versioned file names: a changed styles.css is published as styles.v2.css (build tools add codes like styles.3f9a1c.css), and the new name forces a fresh download, so files can be cached for a year without anyone seeing an old version. In the Network panel a cached file shows (memory cache) or (disk cache) as its Size.

Touch the page less: one DOM update instead of hundreds

JavaScript can change the DOM and the CSSOM (Figure 74.2), and every change can make the browser redo work. The slide compares two ways of putting 500 students into a list:

// INEFFICIENT: render.js
for (const s of students) {                 // 500 students
  list.innerHTML += `<li>${s.name}</li>`;
}
// rebuilds the entire list 500 times; also unsafe with untrusted names

// IMPROVED: render.js
const fragment = document.createDocumentFragment();
for (const s of students) {
  const li = document.createElement("li");
  li.textContent = s.name;
  fragment.append(li);
}
list.append(fragment);                      // one DOM update

Why is the first so bad? a += b means a = a + b, so each pass turns the whole list back into HTML text, adds one <li>, throws the old elements away and parses the entire string again: the 500th pass rebuilds 500 items to add one. A DocumentFragment is an invisible holding box off the page: build every item inside it, append it once, and the page is updated once.

Try both with 800 items, the size of the challenge's list:

<style>
  body { font-family: system-ui, sans-serif; padding: 12px; }
  .cols { display: flex; gap: 14px; }
  ul { flex: 1; height: 120px; overflow: auto; margin: 0; padding-left: 34px;
       border: 1px solid #E3E9F0; border-radius: 8px; }
  #result { font-weight: 700; color: #0B2545; }
</style>
<button id="go">Build 800 items both ways</button>
<p id="result">Press the button.</p>
<div class="cols"><ul id="slow"></ul><ul id="fast"></ul></div>
<script>
const names = [];
for (let i = 1; i <= 800; i++) {
  names.push(`Student ${i}`);
}

function buildSlow(list) {
  list.innerHTML = "";
  for (const name of names) {
    list.innerHTML += `<li>${name}</li>`;   // turns the whole list into text and rebuilds it
  }
}

function buildFast(list) {
  list.textContent = "";
  const fragment = document.createDocumentFragment();
  for (const name of names) {
    const li = document.createElement("li");
    li.textContent = name;
    fragment.append(li);
  }
  list.append(fragment);                       // one update to the page
}

document.querySelector("#go").addEventListener("click", () => {
  const slowList = document.querySelector("#slow");
  const fastList = document.querySelector("#fast");

  let start = performance.now();
  buildSlow(slowList);
  const slowMs = performance.now() - start;

  start = performance.now();
  buildFast(fastList);
  const fastMs = performance.now() - start;

  console.log("innerHTML += in a loop:", slowMs.toFixed(1), "ms for", slowList.children.length, "items");
  console.log("DocumentFragment, one append:", fastMs.toFixed(1), "ms for", fastList.children.length, "items");
  document.querySelector("#result").textContent =
    `innerHTML loop: ${slowMs.toFixed(1)} ms | fragment: ${fastMs.toFixed(1)} ms`;
});
</script>

Both lists get 800 items. Times vary by machine, but the innerHTML loop is always one long task of tens or hundreds of milliseconds (exactly what ruins INP); the fragment takes a millisecond or two.

The slide's last point: instead of 500 click listeners, attach one to the list and ask which item was clicked: event delegation (Chapter 71).

// events.js: one listener for the whole list
list.addEventListener("click", (event) => {
  const li = event.target.closest("li");
  if (li) selectStudent(li);
});
Speed and safety point the same way. innerHTML with a student's name inside is also a security hole: a "name" containing HTML tags becomes real elements. textContent is faster and safe (Chapter 77).

74.7 Measure before and after

The slide calls this evidence over guesses: many "optimisations" change nothing, and some make things worse.

Key idea. Record the numbers. Change one thing. Measure again. Keep it only if the numbers improve. Change three at once and you never know which helped, or which hurt.

Lighthouse: the score and the to-do list

  1. Open the page in an incognito window, so extensions do not interfere.
  2. DevTools (F12) → Lighthouse tab.
  3. Mode Navigation, device Mobile, category Performance.
  4. Click Analyze page load.

The mobile test pretends to be a mid-range phone on slow 4G, whatever computer runs it. The report gives a score from 0 to 100 (0–49 red, 50–89 orange, 90–100 green), the lab metrics behind it, and prioritised suggestions:

Sorting numbers into the three bands takes one small function using the thresholds of Section 74.4. A boundary value counts as the better band (2.5 s is still "good").

<style>
  body { font-family: system-ui, sans-serif; padding: 12px; }
  li   { margin: 4px 0; }
</style>
<ul id="out"></ul>
<script>
// good if value <= good; poor if value > poor; otherwise needs improvement
const limits = {
  LCP: { good: 2.5, poor: 4.0 },   // seconds
  INP: { good: 200, poor: 500 },   // milliseconds
  CLS: { good: 0.1, poor: 0.25 }   // no unit
};

function rate(metric, value) {
  const { good, poor } = limits[metric];
  if (value <= good) return "good";
  if (value <= poor) return "needs improvement";
  return "poor";
}

console.log("Hero image at 3.1 s:", rate("LCP", 3.1));
console.log("LCP of exactly 2.5 s:", rate("LCP", 2.5));
console.log("A tap answered in 350 ms:", rate("INP", 350));
console.log("CLS of 0.31:", rate("CLS", 0.31));

// before and after a fix (pretend field data from real visitors)
const report = [
  { metric: "LCP", before: 4.8,  after: 1.9 },
  { metric: "INP", before: 380,  after: 140 },
  { metric: "CLS", before: 0.31, after: 0.02 }
];
report.forEach((row) => {
  row.ratedBefore = rate(row.metric, row.before);
  row.ratedAfter = rate(row.metric, row.after);
  const li = document.createElement("li");
  li.textContent = `${row.metric}: ${row.before} (${row.ratedBefore}) to ${row.after} (${row.ratedAfter})`;
  document.querySelector("#out").append(li);
});
console.table(report);
</script>

The console prints needs improvement for the 3.1 s hero, good for exactly 2.5 s, needs improvement for 350 ms and poor for a CLS of 0.31. The table shows all three vitals ending good.

74.8 The challenge: the nine-second page

The slide's 15-minute challenge: this page took nine seconds to become usable on a throttled phone connection. Find at least four improvements, each backed by a before-and-after measurement. Try it before reading the answer.

<!-- index.html -->
<head>
  <script src="analytics.js"></script>
  <script src="jquery-3.7.1.js"></script>
  <script src="app.js"></script>
</head>
<body>
  <img src="campus-4000px.jpg">
  <!-- ... several screens of text ... -->
  <img src="gallery-1.jpg">
  <img src="gallery-2.jpg">
  <ul id="list"></ul>
</body>
// app.js
data.forEach((item) => {
  $("#list").html($("#list").html() + "<li>" + item + "</li>");
});

Clues. campus-4000px.jpg is 4.2 MB, shown 400 px wide. jQuery is used for one line. data has 800 items. The text jumps when the images arrive. For each fix write problem → change → expected benefit → measured result.

The answer

ProblemFixExpected benefit
Render-blocking scripts in the head<script src="app.js" defer>HTML parses at once; faster first paint
jQuery for one lineRemove it; use document.querySelector85 KB or more less JavaScript
4.2 MB hero shown at 400 pxResize to 800 px, WebP, srcsetMegabytes saved; better LCP
No image dimensionswidth="800" height="450"Space reserved; CLS near 0
Gallery loads immediatelyloading="lazy"Waits until needed
800 HTML rebuildsA DocumentFragment, appended onceShorter long task; better INP

Notes. The unminified jquery-3.7.1.js here is roughly 280 KB, so the real saving beats 85 KB. Each .html() call reads the whole list out as text and writes it back: innerHTML += in jQuery clothing. Analytics is not needed for the page to work, so it can be async (the slide's bonus: should it load before the visitor agrees?). async was wrong for jQuery and app.js: app.js could run first and fail with $ is not defined.

The page with all six fixes:

<!-- index.html, fixed -->
<head>
  <style>
    img   { max-width: 100%; height: auto; }   /* shrink on phones, keep the shape */
    .hero { width: 400px; }                     /* shown 400 px wide, as before */
  </style>
  <script src="app.js" defer></script>
  <script src="analytics.js" async></script>   <!-- or load it only after consent -->
</head>
<body>
  <img class="hero" src="campus-800.webp"
       srcset="campus-400.webp 400w, campus-800.webp 800w"
       sizes="400px"
       width="800" height="450" alt="Students on the main lawn">
  <!-- ... several screens of text ... -->
  <img src="gallery-1.webp" width="600" height="400" loading="lazy" alt="CSE lab">
  <img src="gallery-2.webp" width="600" height="400" loading="lazy" alt="Library reading room">
  <ul id="list"></ul>
</body>
// app.js, fixed: no jQuery, one DOM update
const list = document.querySelector("#list");
const fragment = document.createDocumentFragment();

data.forEach((item) => {
  const li = document.createElement("li");
  li.textContent = item;          // safe even if an item contains < or &
  fragment.append(li);
});

list.append(fragment);            // one update instead of 800

With sizes="400px", a monitor with a devicePixelRatio of 1 takes the 400 px file; a phone with 2 or more gets the 800 px one. One fix in the four-part format (illustrative numbers): 4.2 MB hero shown at 400 px → 800 px WebP with srcset → smaller download, earlier LCP → Network panel: 4.2 MB down to 90 KB; Lighthouse LCP 8.7 s down to 2.4 s. Any four well-justified fixes answer the challenge.

You can estimate the bytes saved before opening DevTools. This example adds up what downloads before the visitor scrolls; sizes not in the clues are realistic guesses, and the lazy gallery, several screens down, is left out.

<style>
  body { font-family: system-ui, sans-serif; padding: 12px; }
  #out { font-weight: 700; color: #0B2545; }
</style>
<p id="out"></p>
<script>
const before = [
  { file: "index.html",        kb: 6 },
  { file: "analytics.js",      kb: 45 },
  { file: "jquery-3.7.1.js",   kb: 280 },
  { file: "app.js",            kb: 3 },
  { file: "campus-4000px.jpg", kb: 4200 },
  { file: "gallery-1.jpg",     kb: 900 },
  { file: "gallery-2.jpg",     kb: 850 }
];
const after = [
  { file: "index.html",        kb: 6 },
  { file: "analytics.js",      kb: 45 },
  { file: "app.js",            kb: 2 },
  { file: "campus-800.webp",   kb: 90 },
  { file: "gallery-1.webp",    kb: 70, lazy: true },
  { file: "gallery-2.webp",    kb: 65, lazy: true }
];

// what the browser downloads before the visitor scrolls
function firstLoad(files) {
  return files
    .filter((f) => !f.lazy)
    .reduce((sum, f) => sum + f.kb, 0);
}

const b = firstLoad(before);
const a = firstLoad(after);
const saved = ((b - a) / b * 100).toFixed(1);

console.table(after);
console.log("Before, first load:", b, "KB");
console.log("After, first load:", a, "KB");
console.log("Saved:", b - a, "KB, which is", saved + "% less");
console.log("Visits per 1 GB of data - before:", Math.floor(1000000 / b), "after:", Math.floor(1000000 / a));
document.querySelector("#out").textContent = `First load: ${b} KB before, ${a} KB after (${saved}% less)`;
</script>

The console shows the fixed file list as a table, then Before, first load: 6284 KB, After, first load: 143 KB, Saved: 6141 KB, which is 97.7% less, and that one gigabyte (1,000,000 KB) covers 159 visits to the old page but 6993 to the new. Most of the saving is the hero.

74.9 Common misunderstandings

✗ "It loads instantly on my laptop, so it is fast."
Your laptop has a fast processor, campus Wi-Fi and the files already cached. Visitors may have none of these.
✓ "Test the way a visitor arrives."
Incognito, Disable cache, Slow 4G, Lighthouse in Mobile mode, and a real mid-range phone when you can.
✗ "width and height make an image download faster."
They do not change the file at all.
✓ "width and height reserve space; resizing and compressing make it faster."
Dimensions are for stability (CLS); smaller files are for speed (LCP and page weight). Do both.
✗ "A Lighthouse score of 100 means every visitor gets a fast page."
It is one simulated lab test, with no real taps.
✓ "A page passes when 75% of real visits are good."
Lab data finds problems; field data is the verdict.

Exam-style checks

Answer each one before opening it.

What does Largest Contentful Paint (LCP) measure?L1
  • A. How long the server takes to send the first byte of the HTML
  • B. How much visible content moves while the page loads
  • C. When the largest image or text block in the first screen becomes visible
  • D. How quickly the page responds to a tap

Answer: C. LCP is the loading vital. B is CLS, D is INP; time to first byte is a server measurement, not a Core Web Vital.

Which of these is the "good" threshold for Interaction to Next Paint (INP)?L1
  • A. 2.5 seconds or less
  • B. 200 milliseconds or less
  • C. 0.1 or less
  • D. 50 milliseconds or less

Answer: B. 2.5 s is the LCP limit and 0.1 the CLS limit. 50 ms defines a long task, which makes INP worse; it is not the INP threshold.

Field data shows that a page's CLS is 0.18. How is it rated?L2
  • A. Poor
  • B. Good
  • C. Needs improvement
  • D. It cannot be rated, because CLS is only measured in the lab

Answer: C. Good is up to 0.1 and poor above 0.25, so 0.18 is between. CLS is measured from real visitors as well as in the lab.

Which change stops the text below an image from jumping when the image file arrives?L2
  • A. Adding width and height attributes to the <img>
  • B. Adding loading="lazy"
  • C. Converting the image to WebP
  • D. Moving the scripts to the end of the body

Answer: A. The two numbers let the browser reserve a box of the right shape before the file arrives. Lazy-loading and WebP change when and how much is downloaded, not whether space is kept.

Which image should NOT be given loading="lazy"?L2
  • A. The twelfth photo in a gallery far down the page
  • B. A logo in the footer
  • C. A product photo in the third screen of a long page
  • D. The large hero photo at the top of the page

Answer: D. The hero is in the first screen and usually the LCP element; lazy-loading it holds back its download and makes LCP worse. The other three are below the fold, where lazy-loading helps.

app.js calls a function defined in helpers.js, and both need the finished DOM. Which head markup is correct?L3
  • A. <script src="helpers.js" async></script><script src="app.js" async></script>
  • B. <script src="helpers.js" defer></script><script src="app.js" defer></script>
  • C. <script src="app.js"></script><script src="helpers.js"></script>
  • D. <script defer> with the code of both files pasted between the tags

Answer: B. Deferred scripts run after the HTML is parsed, in page order, so the helper exists when app.js runs. A does not keep order; C blocks the parser and runs app.js before its helper exists; in D, defer is ignored on an inline script, so it runs before the DOM is finished.

What does the console show when this page loads, and why?L3
<head>
  <script>
    console.log(document.querySelector("#title"));
  </script>
</head>
<body>
  <h1 id="title">Hi</h1>
</body>

Answer: null. A plain script runs the moment the parser reaches it; the body has not been read yet, so no element has id title. Fix: an external file loaded with defer, or a DOMContentLoaded listener.

Why is list.innerHTML += `<li>${name}</li>` inside a loop of 800 names so slow?L2
  • A. Modern browsers do not support innerHTML
  • B. Template literals are slower than +
  • C. Each += turns the whole list into text and rebuilds every item, so work grows each pass
  • D. The loop repaints the screen 800 times per second

Answer: C. a += b is a = a + b: the old list is turned into text, one item is added, and the whole string is parsed again. Build the items in a DocumentFragment and append once.

Which pair are modern image formats that are usually smaller than JPEG at the same quality?L1
  • A. BMP and TIFF
  • B. GIF and PNG
  • C. ICO and SVG
  • D. WebP and AVIF

Answer: D. WebP and AVIF compress photographs better than JPEG. BMP and TIFF are huge, GIF has only 256 colours, PNG is lossless and big for photos, ICO is for tiny icons, and SVG suits drawings, not photographs.

A Lighthouse test has no real person tapping the page. Which lab metric does it use in place of INP?L2
  • A. Total Blocking Time
  • B. First Contentful Paint
  • C. Speed Index
  • D. Cumulative Layout Shift

Answer: A. TBT adds up how long long tasks blocked the main thread during loading, which is what would have delayed a tap. FCP and Speed Index are about loading; CLS is about movement.

Using the rate function below, what do the three lines print?L3
const limits = { LCP: { good: 2.5, poor: 4.0 },
                 INP: { good: 200, poor: 500 },
                 CLS: { good: 0.1, poor: 0.25 } };
function rate(metric, value) {
  const { good, poor } = limits[metric];
  if (value <= good) return "good";
  if (value <= poor) return "needs improvement";
  return "poor";
}
console.log(rate("LCP", 2.5));
console.log(rate("INP", 500));
console.log(rate("CLS", 0.3));

Answer: good, needs improvement, poor. 2.5 <= 2.5 is true, so a boundary counts as good. 500 is not <= 200 but is <= 500. 0.3 is above 0.25.

In <img srcset="campus-600.webp 600w, campus-1200.webp 1200w" sizes="(max-width: 600px) 100vw, 1200px" ...>, what does sizes tell the browser?L2
  • A. The file size of each image, in kilobytes
  • B. How wide the image will be displayed, so it can pick a file from srcset
  • C. The largest number of images it may download
  • D. The aspect ratio to reserve while the image loads

Answer: B. srcset lists the files and their pixel widths; sizes gives the displayed width (full screen width on small screens, 1200 px otherwise), which the browser combines with its pixel density to choose. Reserving the shape is the job of width and height.

Quick revision

Key takeaways

  1. Performance = loading speed, responsiveness, visual stability. "Good": LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 (poor above 4 s, 500 ms, 0.25), for 75% of real visits.
  2. Usual causes: huge images, too much JavaScript, too many requests, render-blocking files, unused code, poor caching, slow APIs, images without a size.
  3. HTML → DOM, CSS → CSSOM, render tree, layout, paint. CSS blocks rendering; a plain script blocks parsing.
  4. defer: after the HTML, in order (your scripts). async: on arrival, any order (independent scripts).
  5. Images: at most about 2× the shown size, compressed, WebP or AVIF, srcset + sizes, always width + height, lazy only below the fold.
  6. CSS and JS: no unused code, minify, compress, fewer files, versioned names for caching; one DocumentFragment append.
  7. Measure, change one thing, measure again. Lab data finds problems; field data is the verdict.
