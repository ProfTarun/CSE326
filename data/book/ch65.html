Fetch API and JSON Processing

The weather in a weather app, the products in a shop and the marks in a student portal are not written inside the HTML file. They arrive from a server after the page has loaded. This chapter shows how your JavaScript asks a server for data with fetch, waits for the answer without freezing the page, reads the JSON text that comes back, and turns it into cards on the screen — and how to send data the other way.

About 36 minutes · Course outcome CO5

Before you start — one-line reminders

  • A browser (the client) sends a request to a server, and the server sends back a response with a status code such as 200 or 404 (Chapter 2).
  • An object groups named values, { name: "Rahul", marks: [88, 92] }, and you read one with student.name (Chapter 51).
  • An asynchronous callback runs later, when something happens, while the rest of the code carries on (Chapter 54).
  • A list or cards are built from an array with forEach, createElement and textContent (Chapter 58).

By the end of this chapter you can

  • Explain what an API, an endpoint, a request and a response are, and match GET, POST, PUT and DELETE to read, create, update and delete.
  • Write valid JSON, spot invalid JSON, and convert with JSON.stringify and JSON.parse.
  • Say what fetch(url) gives back, and predict the order in which asynchronous code prints.
  • Fetch JSON with a .then/.catch chain and with async/await and try...catch.
  • Check response.ok and response.status, knowing that fetch does not reject on a 404.
  • Show fetched data as cards with loading, success, empty and error states, and send data with a POST request.
  • Explain CORS in plain words, and practise fetch with no internet using a Blob URL.

65.1 Most pages do not hold their own data

Every page you have built so far carried its data inside the file: the list of courses was typed into the HTML, or into an array in the script. Real sites rarely work that way. Open a weather app and the temperature is not in its HTML; the page is an empty shell, and the numbers arrive from a weather server a moment after the shell appears. The same is true of product listings, news feeds, movie search and the LPU student portal. The page is the frame; the content is fetched.

The program on the other side has a published set of rules for how to ask it for things. That set of rules is called an API, short for Application Programming Interface: an agreed way for one program to talk to another. A web API is used over HTTP, the same request-and-response conversation the browser uses to load pages (Chapter 2). Each kind of data has its own address, called an endpoint, such as https://jsonplaceholder.typicode.com/users for a list of users.

Picture this. Dinner at a restaurant. You are the client. The kitchen is the server: it has the food, but you never walk in there. The waiter is the API — the agreed way to place an order. The menu is the API's documentation, listing what can be ordered. Your order ("one paneer tikka") is the request, and the plate that comes back is the response. If the dish is finished, the waiter returns with "Sorry, sold out" — that is still an answer, like a 404 status. And while the kitchen cooks, you do not freeze at the table: the waiter has taken the order, and you carry on talking until the food arrives. That last detail is the whole idea of section 65.4.

fetch is the browser's built-in function for sending such a request from JavaScript and receiving the response. Figure 65.1 shows one complete trip.

An API is a server's menu of things you may ask for. Each item has its own address (an endpoint). fetch sends your order to that address, and some time later the answer comes back — usually as JSON text.

65.2 HTTP in one page: methods and status codes

Chapter 2 showed the browser asking for pages. A request to an API is the same kind of HTTP message. It carries a method (the action), the address, some headers and, sometimes, a body (data you are sending). The response carries a status code, headers, and a body (usually the data you asked for).

MethodPurposeExample endpointSends a body?Real-life example
GETRead dataGET /usersNoLoad the product list
POSTCreate new dataPOST /postsYes (JSON)Submit a registration form
PUTReplace existing dataPUT /posts/1Yes (JSON)Save your edited profile
DELETEDelete dataDELETE /posts/1Usually noRemove an item from the cart

These four match the four basic jobs every data app does, often remembered as CRUD: Create, Read, Update, Delete. A fifth method, PATCH, updates only some fields, where PUT replaces the whole record. fetch(url) with nothing else sends a GET; for any other method you pass an options object, as section 65.8 shows.

The three-digit status code at the top of every response tells you how the request went. You only need a handful:

CodeMeaningWhen you see it
200 OKHere is what you asked forA successful GET
201 CreatedThe new record was madeA successful POST
400 Bad RequestThe server could not understand your requestYou sent broken data
404 Not FoundNothing lives at that addressA typo in the endpoint
500 Internal Server ErrorThe server itself brokeA bug on the server, not in your page

Codes from 200 to 299 mean success; 400 to 499 mean the request was wrong; 500 to 599 mean the server failed. Keep that grouping in mind: it is exactly what response.ok checks in section 65.6.

65.3 JSON: the text that travels

A server cannot send a JavaScript object down the wire. Only text and bytes travel. So the server writes its data out as text in an agreed format, and by far the most common format is JSON, JavaScript Object Notation. JSON looks almost exactly like a JavaScript object, which is why it is easy to read, but it is a string, and its rules are stricter.

{
  "id": 1,
  "name": "Rahul",
  "course": "CSE",
  "active": true,
  "marks": [88, 92, 79],
  "mentor": null
}

That is a complete JSON document, the kind a server might send for one student. Compare it with the JavaScript object a programmer might write:

const student = {
  id: 1,
  name: "Rahul",
  course: 'CSE',             // single quotes are fine in JavaScript
  active: true,
  greet() { return "Hi"; },  // so is a function
};                           // and so is the comma after the last item

The JavaScript version is legal JavaScript, but none of its three commented features is legal JSON. The rules:

  • Keys must be in double quotes: "name", never name or 'name'.
  • Strings use double quotes only. 'CSE' is an error.
  • No functions, no comments, no undefined. JSON holds data, not code.
  • No trailing comma after the last item in an object or array.

And a value can be one of only six types:

TypeJSON example
Object{ "a": 1 }
Array[1, 2, 3]
String"CSE"
Number19, 8.5, -3
Booleantrue, false
nullnull

Objects and arrays can be nested inside each other to any depth: a user can have an "address" object inside, holding a "city" string.

Quick check: is { 'name': 'Asha' } valid JSON?

No. JSON allows only double quotes, for keys and for strings. The valid version is { "name": "Asha" }.

JSON.stringify and JSON.parse

65.4 fetch gives you a promise, not the data

A request to a server can take ten milliseconds or ten seconds. If JavaScript stopped and waited, the whole page would freeze: no scrolling, no clicks, no typing. So fetch is asynchronous. It sends the request and immediately returns, and the next line of your script runs straight away. What it returns is not the data — the data has not arrived yet — but a Promise.

A Promise is an object that stands for a result that will exist later. It is always in one of three states:

  • pending — still waiting. Every promise starts here.
  • fulfilled — it worked, and the promise now holds a value. For fetch, the value is a Response object.
  • rejected — it failed, and the promise holds an error instead.

Once a promise is fulfilled or rejected, it is settled and never changes again. You do not check the state yourself; you hand the promise two callbacks (Chapter 54). .then(callback) registers what to do with the value when it is fulfilled; .catch(callback) registers what to do with the error if it is rejected.

Because fetch returns immediately, code written after it runs before its callback. The deck's A–B–C experiment shows this. Predict the order before you press Run.

The Console shows A, then Is it a Promise? true, then C, and only last B: the answer arrived, status 200. Even with a server inside the same page, the callback waits until the script has finished. With a real server far away, the gap is longer, but the order is the same.

Chapter 54 promised one more detail. Promise callbacks wait in a queue of their own, and the event loop empties that queue before it moves on to timers. So a callback of an already-settled promise beats a 0 ms timer:

setTimeout(() => console.log("timer"), 0);
Promise.resolve("done").then(() => console.log("promise"));
console.log("now");
// prints: now, promise, timer

fetch does not hand you the data. It hands you a promise: an object that means "the answer is coming". Your script keeps running. When the answer arrives, the function you gave to .then is called with it.

Quick check: what does const p = fetch(url); store in p, the moment that line runs?

A Promise in the pending state. The response has not arrived yet; p will be fulfilled with a Response later, or rejected with an error.

65.5 Your first fetch, with a pretend server

Here is the deck's first real example. It asks a free practice API for ten fake users and prints them:

fetch("https://jsonplaceholder.typicode.com/users")
  .then((response) => response.json())
  .then((users) => console.log(users))
  .catch((error) => console.error(error));

Read it as a sentence: fetch this address, then turn the response into data, then use the data, and catch anything that fails. There are two waits in it, not one:

  1. fetch(url) fulfils as soon as the response starts to arrive — the status code and headers come first. The value is a Response object.
  2. The body (the JSON text) may still be on its way. response.json() reads the whole body and parses it as JSON. That takes time too, so it also returns a promise, fulfilled with the finished array or object.

Each .then returns a new promise, which is why they can be chained. When the callback inside a .then returns a promise, the next .then waits for that promise and receives its result. That is why the first callback says response.json() (an arrow function with no braces returns its value), and the second callback receives the finished users array. If any step fails, the rest of the .thens are skipped and .catch runs.

The Response object has a few parts worth knowing:

PartWhat it isExample
response.statusThe status code, a number200, 404
response.oktrue if the status is 200–299true
response.headers.get("Content-Type")One response header"application/json; charset=utf-8"
response.json()A promise of the body, parsed as JSONan array of users
response.text()A promise of the body as plain text"[{\"id\":1,..."

The body can be read only once: after response.json(), a second response.json() or response.text() on the same response fails with a TypeError.

Practising with no internet: a Blob URL

The real example needs an internet connection, and the classroom network is often offline. So the runnable examples in this chapter bring their own server. A Blob is a lump of data held in the browser's memory. URL.createObjectURL(blob) gives that lump a temporary address that begins with blob:. The address lives only in this browser's memory: no other computer can open it, and it stops working when the page that made it closes or the address is switched off with URL.revokeObjectURL.

const data = [{ id: 1, name: "Leanne Graham" }];
const url = URL.createObjectURL(
  new Blob([JSON.stringify(data)], { type: "application/json" }));
// url is now something like "blob:null/4f1c..." - and fetch(url) answers 200 with that JSON

fetch treats a blob: address like any other: the promise fulfils with a Response whose status is 200 and whose body is the JSON text. So everything after the fetch line is exactly the code you would write for a real server. To go live, you change one thing — the address.

65.6 async and await: the same promises, read top to bottom

Chains of .then work, but most programmers today write the same thing with two keywords, async and await. Here is the deck's version:

async function getUsers() {
  try {
    const response = await fetch("https://jsonplaceholder.typicode.com/users");
    if (!response.ok) {
      throw new Error("Request failed");
    }
    const users = await response.json();
    console.log(users);
  } catch (error) {
    console.error(error);
  }
}

getUsers();
KeywordWhat it means
asyncMarks a function that may use await. An async function always returns a promise, even if you write return 5.
await promisePauses this function only until the promise settles. If it fulfils, await gives you the value; if it rejects, await throws the error.
try { } catch (error) { }Catches anything thrown inside try — including a rejected await.

Line by line, it reads like ordinary code: wait for the response, check it, wait for the data, use it. Underneath, nothing has changed. await is still promises and callbacks: while getUsers is paused, the rest of the page keeps running, clicks are handled, and the event loop is free. When the promise settles, the function carries on from where it paused.

Two rules that catch everyone. First, await works only inside an async function (or at the top level of a JavaScript module); in an ordinary <script>, writing it outside one is a SyntaxError. Second, forgetting await does not give an error — it gives you the promise instead of the value. const users = response.json(); stores a pending promise, and users.length is undefined.

fetch does not reject on a 404

Look again at the line if (!response.ok). It is there because of the most surprising fact about fetch: a 404 or a 500 does not make the promise reject. The promise rejects only when no response arrives at all — the network is down, the address cannot be reached, or the browser blocks the answer. A server saying "Not Found" is still a response, so fetch fulfils happily and .catch does not run.

That is the job of response.ok. It is true when the status code is from 200 to 299, and false for anything else. If it is false, you throw an error yourself, and the catch handles it along with the real network failures:

const response = await fetch(url);
if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);    // turn 404, 500... into a real error
}
const data = await response.json();               // only reached on 200-299

fetch only complains when it hears nothing back. "Not found" and "server broke" both count as hearing back. Checking response.ok is your job, and if (!response.ok) throw ... is how you do it.

Quick check: the server answers 500 and your code has no response.ok check. Does catch run because of the 500?

No. The promise from fetch fulfils, because an answer arrived. Your code goes on to treat the error page as if it were data — and if that page is not JSON, response.json() then throws a confusing SyntaxError. Chapter 70 looks at every way a fetch can fail.

65.7 Loading, success, empty and error: the user directory

Real networks are slow and unreliable, so a page that fetches data must be ready for four outcomes, not one. The deck calls them the four states, and a good page shows a clear message for each.

The deck's mini project puts all of this together: a User Directory with a search box (slides 31–33). It is built in two parts.

  • Part 1, showUsers(users), draws one card per user from any array — the full list or a filtered one. It clears the old cards with innerHTML = "", builds each card with createElement and textContent, and writes "N user(s) shown".
  • Part 2, loadUsers(), fetches once, checks response.ok, saves the array in allUsers and shows it. The search box's input event then filters the saved array on every keystroke with filter and includes: instant, and no new request to the server.

With no internet there is no response at all: the await itself throws a TypeError, the "Response:" line never runs, and the same catch takes over. One catch, every failure, one friendly message.

Notice also how little of the code is about the network. Only the two lines with await talk to the server; everything else is the DOM work you already know. To make the directory real, replace pretendFetch(API_URL) with fetch(API_URL) and delete the pretend-server block.

65.8 Sending data: POST, PUT and DELETE

So far the browser has only read. To create something on the server — a registration, a comment, a new post — you send a POST request with the data in its body. fetch takes a second argument, an options object, for this:

fetch("https://jsonplaceholder.typicode.com/posts", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ title: "JavaScript", body: "Learning Fetch API", userId: 1 })
})
  .then((response) => {
    if (!response.ok) {
      throw new Error("Request failed");
    }
    return response.json();
  })
  .then((data) => console.log(data))
  .catch((error) => console.error(error));
OptionWhat it says
method: "POST"We are creating data, not reading it
headers: { "Content-Type": "application/json" }A note to the server: the body is JSON
body: JSON.stringify(...)The data itself, which must be text — so it is stringified first

JSONPlaceholder answers with status 201 Created and the object it "saved", now with a new id: {"title":"JavaScript","body":"Learning Fetch API","userId":1,"id":101}. It is a practice server, so nothing is really stored; ask for post 101 afterwards and it is not there.

The body really must be text. If you pass the object itself, fetch does not complain: it converts the object to a string the default JavaScript way, which is the useless "[object Object]", and sends that. The server cannot parse it as JSON and refuses it, typically with 400 Bad Request. The example below lets you see both. A Blob address accepts only GET requests, so this pretend server is a small function instead: it builds a real Request from your options — exactly the message the browser would send — reads its body, and answers the way JSONPlaceholder does.

PUT and DELETE follow the same pattern, with the record's id in the address:

(Like every await, these lines belong inside an async function, with a response.ok check, as above.) One thing is not allowed: a GET request with a body. fetch(url, { body: "..." }) without a method is a GET, so the request is never sent: the promise rejects with a TypeError.

Quick check: why is the body wrapped in JSON.stringify, and why is the Content-Type header added?

The body must be text, and JSON.stringify turns the object into JSON text. The header tells the server that this text is JSON, so it knows to parse it as JSON.

65.9 CORS in one paragraph, and a practice task

Sooner or later a fetch that looks perfect fails, and the Console shows a red message containing the words blocked by CORS policy. Here is what it means. Every page has an origin — its protocol, host and port (Chapter 64). When a page asks a server on a different origin for data, the browser lets your JavaScript read the answer only if the server's response carries a permission header, Access-Control-Allow-Origin, naming your origin (or *, meaning "any site"). This rule is called CORS. Without that header, fetch rejects with a TypeError and your code never sees the data. For some requests, such as a POST with a JSON body, the browser even sends a small automatic "may I?" request first, called a preflight. The rule protects users: your browser may be logged in to a bank or a college portal, and CORS stops any random page from reading those sites' answers on your behalf. That is also why a CORS error cannot be fixed in your front-end code — only the server can grant permission. Practice APIs such as JSONPlaceholder send an Access-Control-Allow-Origin header that allows every site, which is why the deck's examples work from any page.

A server decides which other websites may read its data. If it has not said "yes" to yours, the browser hides the answer from your JavaScript and fetch fails. You cannot switch this off from your page; the server owner has to allow it.

Student challenge: a product display page

The deck ends this module with a 30–40 minute challenge. Build products.html that:

  1. Fetches https://fakestoreapi.com/products (another free practice API — it can be slow, which is good for testing your loading state).
  2. Shows each product's image, name and price as a card: img.src = product.image, product.title, product.price.
  3. Adds a <select> that filters by product.category.
  4. Shows "Loading…" first, and a friendly message if the request fails.

Start from the User Directory: showUsers becomes showProducts, the search box becomes the select, and the "input" event becomes "change". To practise offline, put three products in a Blob URL first. Filtering the saved array is instant and costs no network trip — exactly what the directory's search did.

65.10 Common misunderstandings

✗ "fetch(url) gives me the data."
It gives a promise, and when that fulfils, a Response — not the data.
✓ "fetch gives a promise of a Response; response.json() gives a promise of the data."
Two waits: await fetch(url), then await response.json().
✗ "If the server says 404, fetch rejects and catch runs."
A 404 is an answer, so the promise fulfils.
✓ "fetch rejects only when no answer arrives."
Check response.ok and throw yourself to send HTTP errors to catch.
✗ "JSON is a JavaScript object."
It looks like one, but JSON is text, with stricter rules.
✓ "JSON is a string; parse it to get an object, stringify an object to get JSON."
Double quotes everywhere, no functions, no comments, no trailing commas.
✗ "await freezes the page until the data comes."
Only the async function it is in is paused.
✓ "await pauses one function; the page keeps running."
Clicks, typing and other code carry on while the request is out.
✗ "I can send an object as the body."
It is turned into the text "[object Object]".
✓ "body: JSON.stringify(data), with Content-Type: application/json."
The body must be text, and the header says which kind.
✗ "A CORS error is a bug in my JavaScript."
Your request may be perfect; the server has not given your origin permission.
✓ "CORS is decided by the server's Access-Control-Allow-Origin header."
Only the server side can fix it.

Exam-style checks

Answer each one before opening it. Most have four options and exactly one correct answer; three are short answers that ask you to predict what the code prints.

What does fetch(url) return the moment it is called?L1
  • A. The data from the server
  • B. A Response object
  • C. A Promise
  • D. The JSON text of the body

Answer: C. The answer has not arrived yet, so fetch returns a pending promise. B is what that promise is later fulfilled with; the data itself (A, D) needs response.json() on top.

Which of these is valid JSON?L2
  • A. { name: "Rahul" }
  • B. { 'name': 'Rahul' }
  • C. { "name": "Rahul", }
  • D. { "name": "Rahul", "marks": [88, 92] }

Answer: D. A has an unquoted key, B uses single quotes, and C has a trailing comma — all legal in a JavaScript object, all errors in JSON.

What does this print, and in what order? console.log("A"); fetch(url).then(() => console.log("B")); console.log("C");L3

Answer: A, C, B. fetch starts the request and returns at once, so "C" prints straight after "A". The .then callback runs only after the response arrives and the script has finished. (If the request failed, B would never print.)

A page calls fetch("/api/marks").then(...).catch(...) and the server answers 404 Not Found. What happens?L2
  • A. The promise rejects and .catch runs with the 404
  • B. The promise fulfils; .then runs with a Response whose ok is false and status is 404
  • C. fetch throws an error before returning
  • D. The browser reloads the page

Answer: B. A 404 is still a response, so the promise fulfils. A is the most common wrong belief: fetch rejects only when no response arrives. Check response.ok yourself.

What does this print? console.log(JSON.stringify({ id: 1, greet() { return "hi"; } }));L3
  • A. {"id":1}
  • B. {"id":1,"greet":"hi"}
  • C. {id: 1, greet: ƒ}
  • D. A SyntaxError

Answer: A. JSON cannot hold functions, so stringify silently leaves the greet property out. It does not call the function (B), and the result is a string with quoted keys, not an object (C).

Which statement about await is true?L2
  • A. It pauses only the async function it is in; the rest of the page keeps running
  • B. It freezes the whole page until the promise settles
  • C. It makes fetch synchronous
  • D. It can be used anywhere in an ordinary script

Answer: A. While the function is paused, events and other code carry on. B and C describe a synchronous wait that blocks everything, which is exactly what await avoids; D is wrong because in an ordinary script await works only inside an async function.

Which call correctly sends { title: "Hi" } to the server as JSON?L3
  • A. fetch(url, { method: "POST", body: { title: "Hi" } })
  • B. fetch(url, { method: "GET", body: JSON.stringify({ title: "Hi" }) })
  • C. fetch(url, { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ title: "Hi" }) })
  • D. fetch(url, { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.parse({ title: "Hi" }) })

Answer: C. A sends the text "[object Object]"; B is refused, because a GET request cannot have a body; D uses parse, which turns text into an object — the wrong direction.

fetch(url) with no second argument sends which HTTP method?L1
  • A. POST
  • B. GET
  • C. PUT
  • D. It sends no request until a method is given

Answer: B. GET is the default. Any other method must be named in the options object, such as { method: "POST" }.

For which status code is response.ok true?L1
  • A. 404 Not Found
  • B. 500 Internal Server Error
  • C. 400 Bad Request
  • D. 201 Created

Answer: D. ok is true for every status from 200 to 299, and 201 is in that range. The other three are error codes, so ok is false for them.

What does this print? async function getCount() { return 5; } console.log(getCount() instanceof Promise);L3

Answer: true. An async function always returns a promise. The return 5 becomes the value the promise is fulfilled with; to get the 5 you would write await getCount() inside another async function, or getCount().then(...).

A page at http://127.0.0.1:5500 fetches https://api.example.com/data, and the Console says the request was "blocked by CORS policy". Who has to fix it?L2
  • A. Nobody: wrapping the fetch in try...catch makes it work
  • B. The API server, by sending an Access-Control-Allow-Origin header that allows the page's origin
  • C. The page, by switching from GET to POST
  • D. The user, by reloading the page

Answer: B. CORS permission is granted by the server's response headers. try...catch (A) only lets you handle the failure gracefully; it cannot make the browser hand over the data.

What does this print, and why? async function load() { const response = await fetch(url); const users = response.json(); console.log(users.length); } (the server returns an array of 10 users)L3

Answer: undefined. response.json() returns a promise, and without await, users is that promise, which has no length. Fix: const users = await response.json(); — then it prints 10.

Quick revision

Key takeaways

  1. An API is a server's agreed set of addresses (endpoints) and rules. GET reads, POST creates, PUT replaces, DELETE deletes; fetch(url) alone is a GET.
  2. JSON is text: double-quoted keys and strings, six value types, no functions, comments or trailing commas. JSON.stringify packs an object into JSON; JSON.parse unpacks it, and throws a SyntaxError on broken text.
  3. fetch is asynchronous: it returns a pending Promise at once, the next lines run, and the callback runs when the answer arrives.
  4. Two waits: fetch gives a Response; response.json() gives the data. Chain them with .then, or write await twice inside an async function with try...catch.
  5. fetch does not reject on 404 or 500 — only when no answer arrives. Check response.ok (status 200–299) and throw yourself.
  6. A data page has four states: loading, success, empty and error. Show a friendly message on the page, put details in console.error, and insert outside data with textContent.
  7. To send data: method, a Content-Type: application/json header and body: JSON.stringify(data). A server answers a good POST with 201 Created.
  8. CORS: a server on another origin must allow your page with Access-Control-Allow-Origin; only the server can fix a CORS error. Offline, practise with a Blob URL.
