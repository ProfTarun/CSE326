Geolocation API

Every “near me” button you have ever pressed — the nearest ATM, a cab pickup point, today's weather — starts with one question: where is this device right now? The Geolocation API is how a web page asks the browser that question. The browser asks the person first, and only if they agree does your JavaScript receive two numbers. This chapter teaches you to ask politely, read the answer, cope when the answer is no, and put the result on a map.

66.1 What the Geolocation API does

A food-delivery site offers to fill in your address. A map puts the blue dot on your street. Weather sites show the forecast for where you stand; ride apps set your pickup point. Each needs the device's position, and on the web there is one way to get it: the Geolocation API.

An API is a set of ready-made commands that one program offers another. The browser's location service lives in one object, navigator.geolocation. (navigator is a built-in object that describes the browser, the way document describes the page.)

What you get back is numbers only: a latitude, a longitude and an accuracy in metres. The API never tells you the city, the street or the PIN code. And it comes with two conditions that no code can get round, both explained in 66.4:

  • The user must agree. The browser shows its own prompt, and nothing happens until they click Allow.
  • The page must be secure: loaded over HTTPS, or from localhost while you are developing.

All modern browsers have the API, but a careful page still checks before using it:

// Always check support first
if ("geolocation" in navigator) {
  console.log("Geolocation is available");
} else {
  console.log("Not supported in this browser");
}

The in operator asks “does this object have a property with this name?” and gives true or false. Checking first, and showing a message when the answer is no, is called feature detection. Without it, an old browser would find undefined where navigator.geolocation should be, and stop your script with a TypeError.

66.2 How a device knows where it is

When your page asks for the location, six things happen in order. Read Figure 66.1 from the top left.

Step 4 is where the device works out its position, and it can use four kinds of signal:

Wi-Fi networksThe device lists the Wi-Fi networks it can hear; a location service knows roughly where those networks areTens of metresGood indoors and in cities

The key fact: JavaScript never chooses the source. The browser and device combine whatever is available and report a best guess with an honest estimate of how good it is. The same page might place a phone outdoors within 5 metres and a lab desktop only somewhere in the right city. Your code must accept both.

66.3 Latitude, longitude and accuracy

A position on Earth is written as two angles, in degrees.

  • Latitude says how far north or south of the Equator. It is 0° on the Equator, +90° at the North Pole and −90° at the South Pole.
  • Longitude says how far east or west of the Prime Meridian, an imaginary line from pole to pole through Greenwich in London. It is 0° there, up to +180° going east and −180° going west.

The pair is always written (latitude, longitude), in that order. India Gate in Delhi is (28.6129, 77.2295); the LPU campus at Phagwara is about (31.2560, 75.7051). Every place in India has both numbers positive, because India is north of the Equator and east of Greenwich.

Latitude is up–down on the globe (north or south). Longitude is left–right (east or west). Latitude comes first. A minus sign means south, for a latitude, or west, for a longitude.

The API gives decimal degrees such as 28.6129, not the 28°36′46″N style printed on some maps. One degree of latitude is about 111 km on the ground, so each extra decimal place is ten times finer:

Decimal placesExampleRoughly this sizeEnough to find
128.611 kmThe city
228.611.1 kmThe part of the city
328.613110 mThe street or campus block
428.612911 mThe building
528.612901.1 mThe door

Accuracy is the third number: the radius, in metres, of a circle around the reported point. “Accuracy 25” means the true position is very probably (about 95 times in 100) within 25 metres of the dot. Smaller is better. A position with accuracy 3000 is a guess at the neighbourhood, and an honest page says “within about 3 km”.

Quick check: Sydney is at (−33.87, 151.21) and New York at (40.71, −74.01). Which is south of the Equator, and which is west of Greenwich?

Sydney is south: its latitude (the first number) is negative. New York is west: its longitude (the second number) is negative. So Sydney is south and east; New York is north and west.

66.4 Permission and secure contexts

A location is personal — it can reveal where you live or which clinic you visit — so the browser never hands it over silently. The first time a site asks, the browser shows its own prompt, something like “127.0.0.1:5500 wants to know your location — Block / Allow”. Your page cannot draw that box, change its words, or click it for the user.

  • Allow: the device finds its position and your success function runs. The browser usually remembers the choice for this site.
  • Block: your error function runs with code 1. The browser usually remembers this too, so next time there is no prompt — just code 1 at once. Only the user can undo it, with the lock or site-information icon at the left of the address bar.
  • No answer yet: neither function runs. The page simply waits.
Picture this. A stranger phones your hostel warden and asks which room Asha is in. A good warden never just answers. He tells Asha who is asking, and only if she says yes does he phone back with the room number; otherwise he phones back to say “she said no”. The caller cannot skip the warden or force the answer, and must wait for the call. The website is the caller, the browser is the warden, the user is Asha, and the two phone-backs are your success and error functions. “Ring me every time she changes rooms” is watchPosition (66.8).

The second condition is about the page itself. Location, the camera and the microphone work only in a secure context: a page loaded over HTTPS, or from your own computer. On plain http, anyone on the network between the server and the user could change the page's code on the way and collect people's locations, so browsers refuse.

Page addressSecure?Geolocation
https://lpu.in/map.htmlYesWorks, after Allow
http://localhost:5500/map.htmlYes — localhost counts as secureWorks: this is why you test with Live Server
http://127.0.0.1:5500/map.htmlYes — the same as localhostWorks
http://lpu.in/map.htmlNoError code 1, no prompt
http://192.168.1.20/map.html (a classmate's laptop over Wi-Fi)NoError code 1, no prompt
file:///C:/web/map.html (double-clicked)Depends on the browserOften blocked — use Live Server

Two locks must both open. The page must be secure (https:// or localhost), and the person must click Allow. If either stays shut, your error function runs with code 1 and you get no position.

About the Run button in this book. The practice frames are sealed boxes that are not allowed to ask for a location, so a real request here is normally refused with code 1. That is why every example below also has a sample location button: the same code runs with pretend numbers. Copy an example into a file and open it with Live Server, or put it on an HTTPS site, and the real thing works.

66.5 Asking once: getCurrentPosition

navigator.geolocation.getCurrentPosition(
  successCallback,   // runs when the location is found
  errorCallback,     // runs if it fails (optional - but always write it)
  options            // settings object (optional) - see 66.7
);

You hand the browser two functions, and it calls exactly one of them back later, just like the callbacks of Chapter 54. Unlike Chapter 65's fetch, it does not return a Promise, so there is no .then() or await here: Geolocation is older and uses plain callbacks. The success function receives a position object; the error function receives an error object. Pass the functions themselves, showPosition with no brackets: showPosition() would call it yourself, at once, with no position.

The call is asynchronous. getCurrentPosition starts the request, returns nothing (undefined), and your code moves straight on to the next line. Finding a position takes time: the user has to decide, and GPS has to listen to satellites. Only when the answer is ready, and your current code has finished, does the browser call one of your functions. Even an instant “no” arrives this way.

Asking for the location starts a job that finishes later. The answer is delivered to your success or error function, never handed back to the line that asked. So const pos = navigator.geolocation.getCurrentPosition(...) does not put the position in pos; pos is undefined. Everything you want to do with the position goes inside the success function.

Here is what the success function receives:

PropertyMeaningExample
position.coords.latitudeNorth–south, in decimal degrees28.6129
position.coords.longitudeEast–west, in decimal degrees77.2295
position.coords.accuracyRadius of the “probably here” circle, in metres25
position.coords.altitude, heading, speedHeight above sea level, direction of travel, speedOften null: only some devices supply them
position.timestampWhen it was measured, in milliseconds since 1 January 1970new Date(position.timestamp) makes it a date (Chapter 62)

Line 2 is written after the call yet prints before the answer: that is asynchronous code in action. Inside this book the answer is usually Error code 1 followed by the browser's own message, which typically says geolocation is disabled in this document (the wording varies by browser). On your own Live Server page, after Allow, you would see Success: with your real numbers.

Now press Use a sample location. Quick check: what does this print? const result = navigator.geolocation.getCurrentPosition(showPosition, showError); console.log(result);

undefined. getCurrentPosition returns nothing; it only starts the request. The position is delivered later, as the argument of showPosition.

66.6 When it fails: the three error codes

The error object has two properties: error.code, a number from 1 to 3 saying which problem, and error.message, some text describing it.

CodeNameUsually meansTell the user
1PERMISSION_DENIEDThe user clicked Block (now or earlier), or the page is not secure“You blocked location access. Click the lock icon in the address bar to allow it.”
2POSITION_UNAVAILABLEThe device tried but could not find itself: location off, no signal“Location is unavailable. Check GPS / Wi-Fi.”
3TIMEOUTNo position within the time set by the timeout option“Took too long. Try again.”

A real error object also carries the numbers as named constants: error.PERMISSION_DENIED is 1, error.POSITION_UNAVAILABLE is 2 and error.TIMEOUT is 3. A switch that compares against the names reads almost like English (slide 42):

function showError(error) {
  switch (error.code) {
    case error.PERMISSION_DENIED:      // code 1
      msg.textContent = "You blocked location access.";
      break;
    case error.POSITION_UNAVAILABLE:   // code 2
      msg.textContent = "Location is unavailable.";
      break;
    case error.TIMEOUT:                // code 3
      msg.textContent = "Took too long. Try again.";
      break;
    default:
      msg.textContent = "An unknown error occurred.";
  }
}
navigator.geolocation.getCurrentPosition(showPosition, showError);

A shorter way is to look the message up in an object, with Chapter 44's || supplying a default for any code that is not in it (slide 46). That is the version below.

Why not just show error.message? It is written for developers, not users. The wording differs between browsers, is often technical (Chrome says Only secure origins are allowed on an http page) and is not translated for your users. Choose your own words from error.code, and log error.message to the Console for yourself.

66.7 Options: precision, patience and freshness

The optional third argument is an object with up to three settings:

OptionMeaningDefaultExample
enableHighAccuracytrue asks for the most precise position the device can give, often from GPS. Slower, and uses more batteryfalsetrue for walking directions; false is fine for “weather near me”
timeoutThe longest wait, in milliseconds. After it, the error function runs with code 3No limit: wait as long as it takes10000 = give up after 10 seconds
maximumAgeAccept a cached position up to this many milliseconds old0: it must be fresh60000 = a position from the last minute will do
 
const options = {
  enableHighAccuracy: true,   // prefer GPS (more battery)
  timeout: 10000,             // give up after 10 seconds
  maximumAge: 0               // never reuse a cached position
};
navigator.geolocation.getCurrentPosition(showPosition, showError, options);

enableHighAccuracy asks how precise? timeout says how long will I wait? maximumAge says how old an answer will I accept? All three are requests; the browser does its best.

Two details are worth knowing. The timeout clock starts only after the user has allowed, so time spent reading the prompt does not count against it. And enableHighAccuracy is a request, not a switch: a laptop with no GPS cannot produce GPS precision however politely you ask, and JavaScript cannot pick GPS directly. For a “find me” button, { enableHighAccuracy: true, timeout: 10000 } is a sensible choice.

66.8 Following a moving user: watchPosition and clearWatch

getCurrentPosition answers once. Navigation, run tracking and a delivery rider's live dot need a new answer every time the device moves. watchPosition takes the same three arguments, but its success function runs again and again, whenever the position changes, until you tell it to stop.

getCurrentPosition()watchPosition()
UpdatesOne answerEvery time the position changes
ReturnsNothing (undefined)A watch ID, a number
Stop withNot neededclearWatch(watchId)
Use forShow my location, nearby searchLive navigation, fitness tracking, delivery tracking
 
const watchId = navigator.geolocation.watchPosition(
  (pos) => console.log(pos.coords.latitude),
  (err) => console.error(err.message),
  { enableHighAccuracy: true, timeout: 10000, maximumAge: 0 }
);

// later - when the user presses Stop, or leaves the screen:
navigator.geolocation.clearWatch(watchId);

The watch ID is the only way to name this watch later. Keep it in a variable the Stop button can reach — a let declared outside both click handlers — because clearWatch needs it. Forget clearWatch and the watch runs for as long as the page is open: GPS stays busy, the battery drains, and someone who pressed Stop is still being tracked.

  body { font-family: system-ui, sans-serif; padding: 16px; }
  button { padding: 7px 12px; margin-right: 6px; cursor: pointer; }
  #status { color: #6B7A90; }
  ol { font-family: monospace; }
</style>
<h3>Run tracker</h3>
<button id="start">Start tracking</button>
<button id="stop">Stop</button>
<p id="status">Not tracking.</p>
<ol id="log"></ol>

<script>
  const statusText = document.getElementById("status");
  const log = document.getElementById("log");
  let watchId = null;      // the number watchPosition gives back
  let sampleTimer = null;  // the timer for the pretend walk
  let updates = 0;

  // Runs EVERY time a new position arrives
  function onUpdate(position) {
    updates = updates + 1;
    const { latitude, longitude } = position.coords;
    const li = document.createElement("li");
    li.textContent = `${latitude.toFixed(5)}, ${longitude.toFixed(5)}`;
    log.append(li);
    console.log(`Update ${updates}:`, li.textContent);
  }

  function onError(error) {
    navigator.geolocation.clearWatch(watchId);   // stop the real watch
    watchId = null;
    console.log(`No real location (code ${error.code}). Walking a sample route instead.`);
    statusText.textContent = "Sample walk: about 11 m north every second.";
    startSampleWalk();
  }

  // A pretend walk north from the LPU campus, one step per second
  function startSampleWalk() {
    if (sampleTimer !== null) return;
    let lat = 31.2560;
    sampleTimer = setInterval(() => {
      lat = lat + 0.0001;                       // about 11 metres north
      onUpdate({ coords: { latitude: lat, longitude: 75.7051 } });
    }, 1000);
  }

  document.getElementById("start").addEventListener("click", () => {
    if (watchId !== null || sampleTimer !== null) return;   // already tracking
    updates = 0;
    log.innerHTML = "";
    statusText.textContent = "Tracking...";
    watchId = navigator.geolocation.watchPosition(onUpdate, onError, {
      enableHighAccuracy: true,
      timeout: 10000,
      maximumAge: 0
    });
    console.log("watchPosition gave back the watch ID", watchId);
  });

  document.getElementById("stop").addEventListener("click", () => {
    if (watchId !== null) {
      navigator.geolocation.clearWatch(watchId);
      watchId = null;
    }
    if (sampleTimer !== null) {
      clearInterval(sampleTimer);
      sampleTimer = null;
    }
    statusText.textContent = "Stopped.";
    console.log("Stopped after", updates, "updates");
  });
</script>

Press Start tracking. watchPosition hands back its ID at once, and the Console prints it. In this book the request is then refused, so onError clears the real watch and starts a pretend walk: one position a second, each 0.0001° (about 11 m) further north — Update 1: 31.25610, 75.70510, Update 2: 31.25620, 75.70510, and so on. Press Stop: the watch and the timer are both cleared and the Console says how many updates arrived. On a real phone the updates would come from the device; a laptop sitting on a desk may give only one, because it is not moving.

Quick check: a page saves the watch ID, but its Stop button only hides the map. What keeps happening after Stop is pressed?

The watch keeps running. The success function goes on firing at every move, GPS stays on and drains the battery, and the user's location is still being collected although they think it stopped. The Stop button must call navigator.geolocation.clearWatch(watchId).

66.9 Showing the place on a map — and the privacy rules

Two numbers mean little to a user; a map means a lot. You do not need a map library for that, because both big map sites accept coordinates in an ordinary link:

  • Google Maps: https://www.google.com/maps/search/?api=1&query=28.6129,77.2295
  • OpenStreetMap, the free and open map: https://www.openstreetmap.org/?mlat=28.6129&mlon=77.2295#map=17/28.6129/77.2295 — mlat and mlon place the marker, and map=17/... means zoom level 17, about street level.

Build these with the URL object instead of gluing strings together. searchParams.set() encodes each value correctly (the comma becomes %2C), so a stray character can never break the address:

const url = new URL("https://www.google.com/maps/search/");
url.searchParams.set("api", "1");
url.searchParams.set("query", `${latitude},${longitude}`);
mapLink.href = url.toString();
// https://www.google.com/maps/search/?api=1&query=28.6129%2C77.2295

In the HTML, target="_blank" opens the map in a new tab, and rel="noopener" stops that new tab from being able to control your page.

What about a city name? The Geolocation API cannot give one. Turning coordinates into an address is called reverse geocoding, and it needs a separate online service (Google and OpenStreetMap both run one). Your page sends the numbers and gets an address back — so the user's location goes to that company, one more reason for the rules below.

Key idea: location is personal data. Six rules, every time:
  1. Ask only when needed, on a click. A button that says what it is for (“Show restaurants near me”), never a surprise prompt on page load. People block surprise prompts, and a block is remembered.
  2. Explain why, next to the button: “We use your location once to find the nearest exam centre. It is not stored.”
  3. Never track silently. Watch only while the user can see that tracking is on, and clearWatch the moment they stop.
  4. Take only what you need. A weather page needs the city, not the door: round to two decimals, and let maximumAge reuse a recent position.
  5. Do not keep or send it quietly. A location saved in localStorage (Chapter 64) or sent to a server is stored personal data. Tell the user, or do not do it.
  6. Offer a way forward without it, such as typing a city or PIN code. A blocked location should never break the page.

66.11 Common misunderstandings

✗ "getCurrentPosition returns the position."
It returns undefined; it only starts the request.
✓ "The position arrives later, as the argument of my success function."
So everything that uses the position goes inside that function.
✗ "The Geolocation API tells me the user's city or address."
It gives only latitude, longitude and accuracy.
✓ "Numbers only; an address needs a separate reverse-geocoding service."
Which means sending the location to that service, so tell the user.
✗ "enableHighAccuracy: true switches on GPS."
JavaScript cannot choose the source.
✓ "It asks for the best precision the device can manage."
A laptop with no GPS still answers from Wi-Fi or its IP address.
✗ "If my code is right, it works on any page."
On plain http (other than localhost) it always fails with code 1, before any prompt.
✓ "It needs a secure context and the user's Allow."
Test with Live Server (localhost); publish on HTTPS.
✗ "error.message is good enough to show users."
It is technical, varies between browsers and is not translated for users.
✓ "Choose a friendly message from error.code."
Log error.message to the Console for yourself.

Exam-style checks

Answer each one before opening it. Most have four options and exactly one correct answer; three ask you to predict or explain.

Which line correctly checks that the browser supports geolocation?L1
  • A. if (navigator.location)
  • B. if ("geolocation" in navigator)
  • C. if (window.gps)
  • D. if (navigator.geolocation.supported())

Answer: B. The API lives in navigator.geolocation, and in asks whether that property exists. A and C name objects that do not exist. D calls a supported() method that no browser has, so it throws a TypeError everywhere — and on an old browser it would already fail at navigator.geolocation being undefined.

The error callback receives an error with code equal to 1. What happened?L1
  • A. The device had no signal
  • B. The request took longer than the timeout
  • C. The user blocked the request, or the page is not a secure context
  • D. The browser does not support geolocation

Answer: C. Code 1 is PERMISSION_DENIED. A is code 2 and B is code 3. D is caught by feature detection; an unsupported browser never calls your callback at all.

On which page can getCurrentPosition get a real position, once the user clicks Allow?L2
  • A. http://lpu.in/map.html
  • B. http://192.168.1.20/map.html
  • C. https://lpu.in/map.html
  • D. Any page, as long as the user clicks Allow

Answer: C. Geolocation needs a secure context: HTTPS, or localhost while developing. A and B are plain http on other machines, so they fail with code 1 without a prompt. D forgets the second lock.

What does watchPosition() return?L2
  • A. A position object
  • B. The latitude, as a number
  • C. Nothing
  • D. A watch ID, to pass to clearWatch later

Answer: D. Positions go to the success function. What comes back at once is the ID that clearWatch(id) needs. C describes getCurrentPosition.

The user has already blocked location for this site. What does this print? console.log("A"); navigator.geolocation.getCurrentPosition(p => console.log("B"), e => console.log("C")); console.log("D");L3
  • A. A B D
  • B. A D C
  • C. A C D
  • D. A D B C

Answer: B. The request is asynchronous, so "D" prints before any callback, even though the refusal is instant. Only the error callback runs, so there is no B. C is the tempting wrong answer: it assumes the refusal interrupts the code.

Which options object waits at most 5 seconds and accepts a position up to one minute old?L2
  • A. { timeout: 5000, maximumAge: 60000 }
  • B. { timeout: 5, maximumAge: 1 }
  • C. { wait: 5000, cache: 60000 }
  • D. { timeout: 5000, maximumAge: 0 }

Answer: A. Both options are in milliseconds, so 5 seconds is 5000 and one minute is 60000. B uses seconds and minutes, C uses names that do not exist, and D's maximumAge: 0 insists on a fresh position.

A position is reported as (−33.8688, 151.2093). Where is it?L2
  • A. North of the Equator and east of Greenwich
  • B. North of the Equator and west of Greenwich
  • C. South of the Equator and east of Greenwich
  • D. South of the Equator and west of Greenwich

Answer: C. The first number is the latitude, and negative means south; the second is the longitude, and positive means east. (It is Sydney.) Reading the pair the wrong way round is the usual mistake.

Which is the best way for a "restaurants near me" page to ask for the location?L2
  • A. Call getCurrentPosition as soon as the page loads, so the answer is ready early
  • B. Start watchPosition on load, so the location is always fresh
  • C. Ask on load, but hide the request inside the first click anywhere on the page
  • D. Ask only when the user clicks a button that says why the location is needed

Answer: D. A surprise prompt on load is usually blocked, and the block is remembered. B tracks the user silently; C tricks them.

Which expression gives the radius, in metres, within which the true position probably lies?L1
  • A. position.accuracy
  • B. position.coords.accuracy
  • C. position.coords.radius
  • D. position.timestamp

Answer: B. Accuracy sits inside coords, next to latitude and longitude. A misses the coords step, C does not exist, and timestamp is when the position was measured.

What does this print? const messages = { 1: "Denied", 2: "Unavailable", 3: "Timed out" }; const friendly = (code) => messages[code] || "Unknown error"; console.log(friendly(3)); console.log(friendly(4));L3

Answer: Timed out, then Unknown error. messages[3] is found. messages[4] is undefined, which is falsy, so || supplies the fallback text.

A client wants your page to say "You are in Phagwara". Can getCurrentPosition give you that? Explain.L2

Answer: no. The Geolocation API gives only numbers: latitude, longitude, accuracy and a timestamp. For a place name you send the coordinates to a separate reverse-geocoding service, which replies with an address — sharing the user's location with another company, so the page should say so.

A run-tracking page calls watchPosition when Start is pressed, but its Stop button only hides the route. What is wrong, and how do you fix it?L3

Answer: the watch is never cleared. The success function keeps firing, GPS drains the battery and the user is still tracked after pressing Stop. Keep the ID in a let declared outside both handlers, and call navigator.geolocation.clearWatch(watchId) in the Stop handler.

Quick revision

Key takeaways

  1. navigator.geolocation gives the device's position as numbers only. Check support with "geolocation" in navigator. The device picks the source (GPS, Wi-Fi, towers, IP), so accuracy ranges from metres to a whole city.
  2. Latitude is north–south (−90 to +90), longitude east–west (−180 to +180), always in that order. Positive means north and east. Accuracy is a radius in metres.
  3. Two locks: the user must click Allow, and the page must be a secure context (HTTPS, or localhost while developing). Otherwise the error callback runs with code 1.
  4. getCurrentPosition(success, error, options) is asynchronous and returns nothing; the position arrives later in success(position).
  5. Error codes: 1 PERMISSION_DENIED, 2 POSITION_UNAVAILABLE, 3 TIMEOUT. Show friendly text chosen from the code.
  6. Options: enableHighAccuracy (precision), timeout (patience, in ms), maximumAge (freshness, in ms). watchPosition repeats the answer and returns an ID; clearWatch(id) stops it.
  7. Location is personal: ask on a click, explain why, never track silently, take only what you need, and offer a way forward without it.
