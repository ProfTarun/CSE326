Unit 4 · Chapter 41 · Introduction to JavaScript

Introduction to JavaScript

With HTML you built pages, and with CSS you made them look good. But put a "Show my marks" button on one of those pages, press it, and nothing happens: HTML and CSS cannot calculate, check what was typed, or change what the page says. JavaScript is the language that adds the reacting part. This chapter explains what it is, who runs it, what it is not allowed to do, how it gets into a page, and then you write your first program.

About 30 minutes · Course outcome CO4

Before you start — one-line reminders

  • The browser downloads a page's files and draws the page from them: HTML for structure, CSS for presentation, JavaScript for behaviour (Chapter 1).
  • An element is a start tag, its content and an end tag, and attributes such as id="title" sit inside the start tag (Chapter 3).
  • A page has a <head> with invisible information and a <body> with everything visible (Chapter 4).
  • CSS can be written inline, internally or in an external file, and real projects use the external file (Chapter 22).

By the end of this chapter you can

  • Say what job each of HTML, CSS and JavaScript does on a page.
  • Explain what JavaScript is, where it runs (the browser and Node.js), and how an engine such as V8 turns it into instructions the processor can carry out.
  • List what JavaScript in a browser is not allowed to do, and explain why.
  • Add JavaScript to a page inline, internally and as an external file, and explain why the external file is the professional choice.
  • Put the <script> tag in the right place, at the end of the body or in the head with defer, and say what goes wrong otherwise.
  • Write and run a first program with console.log, and find its output in the DevTools Console.
  • Write statements, semicolons and comments correctly, and spot an error caused by a wrong capital letter.

41.1 Three languages, three jobs

Every web page you have made so far uses two languages. HTML says what is on the page: a heading, a paragraph, a form, a button. CSS says how it looks: colours, fonts, spacing, layout, and how it changes on a phone. Both of them only describe. Neither one can add up numbers, check what somebody typed, or change what the page says when a button is pressed.

That third job is called behaviour, and it belongs to JavaScript. JavaScript is what lets a page:

  • respond to the user: open a menu when it is clicked, show a password when an eye icon is tapped;
  • check input: say "Please enter a 10-digit mobile number" before the form is sent;
  • calculate: add up the cart total, or work out a CGPA from marks;
  • change the page while you look at it: a new message appears in a chat without the whole page reloading.
Picture this. A new house. HTML is the building itself: the walls, the rooms, the doors and windows, the place where the fan will hang. CSS is the decoration: the paint, the tiles, the curtains. JavaScript is the electrical wiring: press a switch and the fan turns, press the bell and it rings. A house with no wiring still stands and can look beautiful, but nothing in it does anything. And wiring does not replace walls; it is fitted into them.

That last sentence matters. JavaScript does not replace HTML or CSS. It works with them. Most interactive pages use all three, each doing only its own job.

Here is a page that uses all three. Do not try to understand every word of the script yet; Chapters 55 to 57 explain each one. For now, just see the three layers working together.

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  .card { background: #FFF7ED; border-left: 5px solid #FF9933;
          border-radius: 8px; padding: 10px 16px; max-width: 360px; }
  button { background: #FF9933; color: white; border: 0;
           border-radius: 6px; padding: 8px 14px; cursor: pointer; }
</style>

<div class="card">
  <h3>Asha's CSE326 result</h3>
  <p id="marks">Marks: hidden</p>
  <button id="show">Show my marks</button>
</div>

<script>
  // The behaviour. Chapters 55-57 explain every word of this.
  const button = document.getElementById("show");
  const marks = document.getElementById("marks");

  button.addEventListener("click", () => {
    marks.textContent = "Marks: 87 / 100";
    console.log("Button pressed. The text is now:", marks.textContent);
  });

  console.log("JavaScript is running on this page.");
</script>

Press Run. The Console panel under the preview shows JavaScript is running on this page. Press Show my marks: the paragraph changes to Marks: 87 / 100 and the Console adds Button pressed. The text is now: Marks: 87 / 100. Now delete the <style> block and Run: the button still works but looks plain. Put it back and delete the script: the card looks perfect, but the button does nothing.

41.2 What JavaScript is

Start with a word you will use every day from now on: a program is a list of instructions that a computer carries out, one after another. "Show this message. Add these two numbers. If the box is empty, complain." A programming language is a way of writing those instructions down that both people and computers can read. HTML and CSS are not programming languages: they describe what a page contains and how it looks, but they cannot carry out a list of steps, keep a running total, or decide what to do next from what the user did. JavaScript can.

The slides describe JavaScript in four phrases:

  • A high-level programming language. You write console.log("Hello"), which a person can read, not the long strings of numbers the processor really works with. Something else does that translation for you (41.3).
  • A scripting language. A JavaScript program is usually called a script: plain text handed to another program, the browser, to carry out.
  • It runs mainly in web browsers; every browser understands it, with nothing extra to install. It also runs outside the browser, in Node.js (41.4).
  • It supports several styles of programming: event-driven (code that waits for something, such as a click, and then runs), functional (building programs from small reusable functions) and object-oriented (grouping related data and actions). Units 4 and 5 show all three.

Typical jobs: responding to user actions, updating the page, calling APIs (asking a server for data; Chapter 65) and processing data (sorting marks, totalling a bill).

JavaScript is a language for writing instructions. You write them as readable text, the browser carries them out, and the page reacts. No installing, no separate app: save, reload, and it runs.

JavaScript is not Java

The names cause endless confusion, so settle it now. Java and JavaScript are two different languages, made by different people for different purposes, with different rules. JavaScript was written in about ten days in 1995 by Brendan Eich at Netscape, maker of the most popular browser of the time. First called Mocha, then LiveScript, it was renamed JavaScript mainly for marketing, because Java was that year's fashionable language. Programmers say the two are as related as car and carpet.

The official standard for the language is called ECMAScript. "ES6" or "ES2015" means its 2015 edition, which added much of the modern JavaScript this book uses.

41.3 Who runs your code: the JavaScript engine

Here is a fact that surprises most beginners: the processor inside your laptop does not understand JavaScript. It does not understand English words like console or log either. A processor understands only machine code, very simple instructions stored as numbers, such as "copy this value" or "add these two". So between your readable script and the processor, something must translate.

That something is the JavaScript engine: a program built into the browser whose only job is to read JavaScript and carry it out. Every browser has one:

EngineMade byUsed in
V8GoogleChrome, Microsoft Edge, Opera, Brave — and Node.js
SpiderMonkeyMozillaFirefox (it was the very first JavaScript engine)
JavaScriptCoreAppleSafari, and almost every browser on an iPhone

Because all of them follow the same ECMAScript standard, the same script almost always gives the same result in all of them. Follow V8, the engine your slides name, through its three steps.

  1. Parse. The engine reads your text and checks the grammar: every bracket and quote closed, no word in an impossible place. If something is broken, nothing in that script runs, and the Console shows a SyntaxError.
  2. Interpret. To start quickly, the engine carries out your instructions straight away, one by one. A program that does this is an interpreter.
  3. Compile what is busy. The engine watches which parts run again and again (a calculation done for each of 500 students, say). Those parts are converted into fast machine code by a just-in-time (JIT) compiler, so the next 500 runs go much faster.

You may read that JavaScript is an "interpreted language". That was true of early engines; modern ones mix interpreting and compiling, which is why JavaScript is fast enough for games and Google Maps. You never start the engine yourself: the browser does it.

The processor speaks only machine code. The engine is the translator living inside the browser: it reads your JavaScript, checks it, runs it, and turns the parts used most into fast machine code. V8 is Chrome's translator; SpiderMonkey is Firefox's.

Quick check: your script has a missing closing bracket on its last line. Do the lines above it still run?

No. The engine parses (checks) the whole script before running any of it. A grammar mistake anywhere stops the entire script, and the Console shows a SyntaxError.

41.4 What browser JavaScript is not allowed to do

Each time you open a website, you run a stranger's program on your own laptop, without being asked. If it could do anything it liked, any website could read your photos or delete your files. So browsers run every page's JavaScript inside a sandbox: a fenced-off area where it can work on its own page and very little else.

The slides list what browser JavaScript cannot do:

It cannot…What that means in practice
Read or write your filesIt cannot look around your disk. It sees a file only when you pick one (<input type="file">) or drag one onto the page, and saves one only as a download or into a place you choose in a save box.
Access the operating systemIt cannot start other programs, change Windows settings or read your contacts. Camera, microphone and location are possible only after the browser asks you and you say yes (Chapter 66).
Run a serverIt cannot sit waiting for other computers to connect to it. A page is a client; it asks servers for things (Chapter 2).
Access databases directlyIt cannot log in to the university's database server. It asks a web server, and the server talks to the database (Chapter 65). It does get a small storage area of its own inside the browser (Chapter 64).
Run foreverA script that never finishes freezes its tab, and the browser soon offers to stop it ("Page Unresponsive"). Background tabs are slowed down, and closing the tab ends every script in it.
See into other tabsA page from one site cannot read what is in another site's tab, such as your email or your UMS account.

These limits are not weaknesses: they are why you can safely open a stranger's link.

Node.js: JavaScript outside the browser

In 2009 a developer named Ryan Dahl took Chrome's V8 engine out of the browser and wrapped it in a program of its own, called Node.js. The slides call Node.js a runtime environment: the engine plus a set of extra tools around it. Node.js runs on a computer, not inside a page, so it has no browser sandbox and can do exactly what a browser forbids: read and write files, run a web server, talk to a database.

JavaScript in the browserJavaScript in Node.js
EngineV8, SpiderMonkey or JavaScriptCoreV8
Can change a web pageYes: that is its main jobNo: there is no page
Can read your files, run a serverNo: sandboxedYes
Typical useMenus, forms, games, live updatesWeb servers, tools, scripts

The language is the same in both places; only the surroundings differ. This course uses JavaScript in the browser.

41.5 Three ways to add JavaScript to a page

Chapter 22 gave CSS three possible places and one right answer for real projects. JavaScript has the same three, and the same answer.

1. Inline: inside an event attribute

An HTML attribute whose name starts with on, such as onclick, can hold a little JavaScript that runs when that thing happens:

<button onclick="console.log('Clicked!');">Click me</button>

It works, and old tutorials use it. But the behaviour is buried in the HTML, scattered over many tags and impossible to reuse, and many sites block inline code for security. Avoid it.

2. Internal: inside a <script> element

A <script> element with JavaScript written between its tags:

<script>
  console.log("Hello from an internal script");
</script>

Fine for a small experiment, which is why most examples in this book use it. But the code belongs to this one page: if five pages need it, you paste it five times and fix every mistake five times.

<style> body { font-family: system-ui, sans-serif; padding: 16px; } </style>
<h3>Two ways that fit inside one file</h3>

<!-- 1. Inline: the code sits in the onclick attribute -->
<button onclick="console.log('Inline: you pressed the button');">Press me</button>

<!-- 2. Internal: the code sits in a script element -->
<script>
  console.log("Internal: this ran while the page was loading");
</script>

Run it: the Console shows Internal: this ran while the page was loading at once, because the browser runs a script element as soon as it reaches it. The inline code waits; press the button and Inline: you pressed the button appears. Notice the quotes: the attribute's value is wrapped in double quotes, so the text inside it uses single quotes. Two double quotes would end the attribute early.

3. External: a separate .js file

The code goes into its own file whose name ends in .js, and the page points to it with the src (source) attribute:

<!-- index.html -->
<script src="script.js"></script>

// script.js  (a separate file in the same folder)
console.log("Hello from an external file");

This is the professional choice, for four reasons:

  • One file, many pages. Every page of a site loads the same script.js; fix a mistake once and every page is fixed.
  • Faster later pages. The browser keeps a copy of the file in its cache, so the next page does not download it again.
  • Clean HTML. The HTML stays about structure, the separation you met in Chapter 22.
  • Easier teamwork. One student works on the page while another works on the script.
Two traps with src. First, a <script> that has a src must be empty: any code written between its tags is ignored, because the browser uses the file instead. Second, you must write the closing </script>. The short form <script src="script.js" /> does not work in HTML: the slash is ignored, so the browser treats everything after it, up to the next </script>, as the script's content, and that part of your page vanishes.
Exam tip. The attribute is src, not href. CSS is joined with <link rel="stylesheet" href="...">; JavaScript with <script src="..."></script>. And in HTML5 you do not need type="text/javascript": JavaScript is the default.

41.6 Where the script tag goes

The browser reads your HTML file the way you read a page of a book: from the top, line by line. As it reads each tag it parses it and builds the element, so a heading exists only after the browser has read the heading's tag. When it meets a <script>, it stops building, runs the script (downloading the file first, if it has a src), and only then carries on reading.

Two things follow from that one rule:

  • A script in the head runs before the body has been read, so the elements it wants do not exist yet.
  • While a big script downloads in the head, the page stays blank.

The next example proves it. Both scripts ask the page for the element whose id is title, using document.getElementById("title"). You will learn this tool properly in Chapter 55; for now, read it as "page, give me the element called title". If there is no such element, it answers null, which means "nothing".

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>Script position</title>
  <script>
    // Script A: in the head. The body has not been read yet.
    console.log("A (in the head) finds:", document.getElementById("title"));
  </script>
</head>
<body>
  <h1 id="title">CSE326 Notice Board</h1>
  <p>Classes resume on Monday.</p>

  <script>
    // Script B: just before the end of the body. Everything above exists.
    console.log("B (end of body) finds:", document.getElementById("title"));
  </script>
</body>
</html>

The Console shows A (in the head) finds: null and then B (end of body) finds: <h1 id="title">. Same line, same page, different answer, decided only by where the script sits. Had script A tried to change the heading's text, you would get the most famous beginner error, TypeError: Cannot set properties of null. When you see it, check the script's position first.

The two correct positions

  1. Just before </body>, as Chapter 4 recommended. Everything above is built, and the visitor sees the content while the script loads. It works for internal and external scripts alike.
  2. In the head, with defer: <script src="script.js" defer></script>. defer means "start downloading this file now, but run it only after the whole HTML has been read": an early download and a complete page. It works only on scripts with src; on an internal script it is ignored. Chapters 73 and 74 make it the standard for real projects.
Quick check: a script in the head, without defer, changes the text of a paragraph in the body. Why does it fail?

The browser runs the script as soon as it reaches it, while it is still in the head. The paragraph has not been read and built yet, so the script finds null instead of the paragraph. Move the script to just before </body>, or make it an external file loaded with defer.

Time to write a real program, the way the slides set it up: two files, side by side in one folder.

The <script> element is the bridge: it tells the page to fetch script.js from the same folder and run it. Open index.html in your browser (double-click it, or use VS Code's Live Server). Only the heading shows. Where did Hello go?

Opening the Console

console.log() does not write on the page. It writes to the Console, a panel inside the browser's Developer Tools (DevTools) that only the developer looks at. To open it:

There it is: Hello, CSE326!. The Console is also where the browser reports mistakes, in red, with the file name and line number, so programmers keep it open (Chapter 69 covers the rest of DevTools). In this book, the Console panel under every Run shows what the real Console would.

What console.log prints

<h3>My first program</h3>
<p>Nothing that console.log prints appears here on the page.
   Look in the Console panel underneath.</p>

<script>
  console.log("Hello, CSE326!");
  console.log("I am learning JavaScript at LPU.");
  console.log(2 + 3);
  console.log("2 + 3");
  console.log("Asha scored", 87, "out of", 100);
</script>

The Console shows five lines, in order:

Hello, CSE326!
I am learning JavaScript at LPU.
5
2 + 3
Asha scored 87 out of 100
  • Text in quotes is printed exactly as written, without the quotes. Text in quotes is called a string (Chapter 43).
  • 2 + 3 without quotes is worked out first, so the Console shows 5. The same characters inside quotes, "2 + 3", are just text, and are printed as text. That one pair of quote marks is the difference between a calculation and a message.
  • You can give console.log several values separated by commas. It prints them all on one line, with a space between each. That is why the last line reads Asha scored 87 out of 100 although no quoted piece begins or ends with a space.

console.log(...) means "write this in the Console". Put text in quotes and it is copied out letter for letter; leave a calculation without quotes and its answer is printed. Separate several things with commas, and they come out on one line with spaces between them.

Typing straight into the Console

The Console also accepts JavaScript. Click in it, type 2 + 3 and press Enter: it answers 5 at once, a perfect scratch pad for trying a line. Type console.log("Hi") there and you see Hi followed by a grey undefined. That is not an error: the Console reports what each line gave back, and console.log gives back nothing, which JavaScript writes as undefined (Chapter 43).

Quick check: what does console.log("Marks:", 40 + 45) print?

Marks: 85. The text in quotes is printed as it is, the calculation without quotes is worked out to 85, and the two values are joined with one space.

41.8 Statements, semicolons, comments and capital letters

Statements and semicolons

Each instruction in a program is called a statement: one complete thing to do, like one sentence in a paragraph. console.log("Hello"); is a statement. JavaScript carries out statements in order, from top to bottom, unless you tell it otherwise (Chapter 47 shows how).

A simple statement like this one ends with a semicolon ;, the way an English sentence ends with a full stop. Because the semicolon marks the end, two statements can share one line, and spaces and blank lines between statements are only for the human reader.

A missing semicolon at a line's end often still works, because rules called automatic semicolon insertion guess where you meant one. The rules have surprising exceptions, so always write it.

Comments

A comment is a note for people. JavaScript skips it completely. There are two kinds:

  • // ... a one-line comment: everything from the two slashes to the end of that line is ignored. It can fill a line, or sit at the end of a statement.
  • /* ... */ a block comment: everything between /* and */ is ignored, however many lines it spreads over.

Use comments to explain why something is done. Programmers also comment out a line: a // in front switches it off without deleting it. Inside a script, use // and /* */, never HTML's <!-- -->.

Capital letters matter

HTML did not mind whether you wrote <P> or <p>. JavaScript is case-sensitive: a capital and a small letter are different characters, so console and Console are two different words, and only one of them exists. The same goes for every name: log is not Log, and a variable called total is not one called Total. JavaScript's own keywords, such as let and if, are always in small letters.

<p>Nothing appears here. Read the Console panel below.</p>
<script>
  // A one-line comment: JavaScript skips everything after the two slashes.
  console.log("Statement 1 runs");   // a comment can also end a line

  /* A block comment can spread
     over several lines.
     JavaScript skips all of it. */

  // console.log("Statement 2 is switched off, so it never runs");

  console.log("Statement 3 runs"); console.log("Statement 4 shares its line");

  console.log("Capital letters matter");
  // To see an error, delete the two slashes at the start of the next line and Run:
  // Console.log("Capital C");

  console.log("Last statement runs");
</script>

Run it and the Console shows five lines: Statement 1 runs, Statement 3 runs, Statement 4 shares its line, Capital letters matter and Last statement runs. Statement 2 is missing because it is commented out, and nothing from either comment appears.

Now do what line 15 says: delete the // at the start of line 16 and Run again. The Console shows the first four lines, then, in red, Uncaught ReferenceError: Console is not defined (line 16), and Last statement runs never appears. Read it like a sentence: JavaScript looked for something called Console with a capital C, found nothing, and stopped on line 16, so the statements after it never ran. A wrong capital later in the name, console.Log("Hi"), gives a different error, TypeError: console.Log is not a function: console exists, but has no tool called Log.

A statement is one instruction ending in a semicolon, and statements run from top to bottom. Comments (// for one line, /* */ for several) are notes JavaScript ignores. Capital and small letters are different to JavaScript, so copy every name exactly, and read the red error message: it names the word it could not find and the line it was on.

41.9 alert, prompt and document.write: tools from the past

Old tutorials start with three tools this book will not use in real work. Learn to recognise them: they appear in older code and in exam questions.

  • alert("message") shows a pop-up box with the message and an OK button. Until the user presses OK, the whole page is frozen: nothing can be clicked and no other code runs.
  • prompt("question", "default") shows a pop-up with a text box and gives back whatever the user typed, as text. If the user presses Cancel, it gives back null. Its cousin confirm("question") gives back true for OK and false for Cancel.
  • document.write("...") writes HTML into the page while the page is still loading, at the place where the script sits. Call it after the page has finished loading, and it wipes out the entire page and starts a new, empty one.
<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  button { margin: 4px 6px 4px 0; padding: 7px 12px; cursor: pointer; }
</style>
<h3>Three tools from 1990s JavaScript</h3>
<button id="a">alert</button>
<button id="p">prompt</button>
<button id="w">document.write after loading</button>

<script>
  // While the page is loading, document.write adds HTML right here
  document.write("<p>This paragraph was added by document.write while the page loaded.</p>");
  console.log("Page loaded. Now press the buttons.");

  document.getElementById("a").addEventListener("click", () => {
    alert("Hello from alert! The page is frozen until you press OK.");
    console.log("alert finished - the page can move again");
  });

  document.getElementById("p").addEventListener("click", () => {
    const answer = prompt("What is your name?", "Rahul");
    console.log("prompt gave back:", answer);
  });

  document.getElementById("w").addEventListener("click", () => {
    document.write("The whole page has been replaced by this one line.");
  });
</script>

On Run, a paragraph appears under the buttons (written by document.write during loading) and the Console says Page loaded. Now press the buttons. Press alert: only after you press OK does the Console add alert finished - the page can move again. Press prompt and OK without typing: prompt gave back: Rahul, the default; type Meera and you get prompt gave back: Meera; press Cancel and you get prompt gave back: null. Last, the third button: everything vanishes, replaced by one line of text. Press Run to get the page back.

Why avoid them? alert and prompt freeze the page, cannot be styled and annoy users; document.write slows loading and can destroy a finished page. The modern replacements: console.log for checking values, the DOM (Chapters 55 and 56) for showing results, and forms with events (Chapter 57) for asking questions.

Quick check: a user types 19 into a prompt box. Is the result the number 19?

No. prompt always gives back text, so the result is the string "19" (or null if the user pressed Cancel). Turning text into a number is covered in Chapter 46.

Only the names are alike; the name was a 1995 marketing choice.
✓ "Java and JavaScript are separate languages."
Different creators, different rules, different uses.
✗ "console.log shows the message on my page."
The page stays exactly as it was.
✓ "console.log writes to the DevTools Console."
Open it with F12. To put something on the page, use the DOM (Chapter 55).
✗ "A script works the same wherever I put the tag."
A script in the head runs before the body exists and finds null.
✓ "Put scripts just before </body>, or in the head with defer."
Then everything the script needs has already been built.
✗ "<script src="app.js" /> is a neat short form."
HTML ignores the slash, so the page after it, up to the next </script>, is swallowed as script.
✓ "Always write <script src="app.js"></script>, with nothing between the tags."
Code written between them would be ignored anyway.

Exam-style checks

Answer each one before opening it. Most have four options and exactly one correct answer; four ask you to predict what code prints.

On a web page, which language is responsible for behaviour, such as responding to a click?L1
  • A. HTML
  • B. CSS
  • C. JavaScript
  • D. HTTP

Answer: C. HTML gives structure and CSS presentation; neither can react. HTTP carries pages; it is not a language for writing them.

Which JavaScript engine does Google Chrome use?L1
  • A. SpiderMonkey
  • B. V8
  • C. JavaScriptCore
  • D. Node.js

Answer: B. SpiderMonkey is Firefox's and JavaScriptCore is Safari's. D tempts because Node.js uses V8, but Node.js is a runtime environment built around the engine.

Which statement about Java and JavaScript is true?L1
  • A. JavaScript is the browser edition of Java
  • B. JavaScript programs must be compiled by Java first
  • C. They are the same language with different file extensions
  • D. They are different languages; the similar name was a marketing choice

Answer: D. JavaScript was created at Netscape in 1995 and renamed to ride on Java's popularity; it shares no engine or rules with Java.

Which of these can JavaScript running in a browser NOT do?L2
  • A. Change the text of a paragraph on its own page
  • B. Read any file on the user's hard disk without the user choosing it
  • C. Respond when a button is clicked
  • D. Write a message to the Console

Answer: B. The sandbox stops a page from looking through your files; it sees a file only when you pick one. A, C and D are exactly what browser JavaScript is for.

Which line correctly loads an external JavaScript file?L2
  • A. <script src="app.js"></script>
  • B. <script href="app.js"></script>
  • C. <link rel="script" href="app.js">
  • D. <script src="app.js" />

Answer: A. Scripts use src; href belongs to links and stylesheets. D looks tidy, but HTML ignores the slash, so the page after it, up to the next </script>, is treated as script.

What does this print? console.log("5 + 5"); console.log(5 + 5);L3

Answer: two lines, 5 + 5 and then 10. Text in quotes is printed as written; without quotes, the sum is worked out first.

What does this print? console.log("Total:", 40, "marks");L3

Answer: Total: 40 marks. console.log prints every value it is given on one line and puts one space between neighbouring values.

A student writes Console.log("Hi");. What happens?L2
  • A. Hi is printed in the Console
  • B. Hi is printed on the page
  • C. Nothing happens and no message appears
  • D. The Console shows ReferenceError: Console is not defined

Answer: D. JavaScript is case-sensitive, and nothing called Console exists. A needs console in small letters; B never happens with console.log, even spelt correctly.

What does the defer attribute do on <script src="app.js" defer> in the head?L2
  • A. Runs the script before anything else on the page
  • B. Runs the script only when the user clicks
  • C. Downloads the file straight away but runs it after the whole HTML has been read
  • D. Stops the file from being cached

Answer: C. The download starts early and the script runs once every element exists. A describes a plain head script, the very problem defer solves.

What does this print? console.log("A"); // console.log("B"); then, on the next lines, /* console.log("C"); */ and console.log("D");L3

Answer: A and then D. Everything after // on the first line is a comment, so B never runs, and C sits inside a block comment.

This script sits in the <head>, without defer, and the page's body contains <h1 id="title">. What does it print? console.log(document.getElementById("title"));L3

Answer: null. The script runs as soon as the browser reaches it, before the body has been read, so the heading does not exist yet. Just before </body>, the same line would find it.

Why do real projects keep JavaScript in an external .js file?L2
  • A. It is the only way that lets the code run
  • B. One file can serve many pages, and the browser can cache it
  • C. It lets the script read files on the visitor's computer
  • D. It turns JavaScript into machine code before upload

Answer: B. Reuse, caching and clean HTML are the reasons. A is false, because inline and internal scripts run too; C and D are false, because the sandbox still applies and the engine still does the translating.

Quick revision

Key takeaways

  1. HTML is structure, CSS is presentation, JavaScript is behaviour. JavaScript works with the other two; it does not replace them.
  2. JavaScript is a high-level programming language that runs in every browser and, through Node.js, outside it. It is not Java. Its standard is ECMAScript.
  3. A JavaScript engine (V8 in Chrome and Edge, SpiderMonkey in Firefox) parses your code, starts running it, and JIT-compiles busy parts into machine code for the processor.
  4. Browser JavaScript is sandboxed: no free access to your files, the operating system, databases or other tabs, no running a server, no running forever.
  5. Three ways to add it: inline (onclick), internal (<script>), external (<script src="script.js"></script>). Projects use external: reusable, cached, clean.
  6. The browser reads HTML top to bottom and runs a script where it meets it. Put scripts just before </body>, or in the head with defer.
  7. console.log writes to the DevTools Console (F12), not the page; several values are printed with spaces between them.
  8. Statements run in order and end with ;. Comments are // and /* */. JavaScript is case-sensitive. alert, prompt and document.write are old tools to recognise, not to use.
