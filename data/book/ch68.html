Debugging Techniques

Every programmer writes code that does not work the first time — beginners and experts alike. What separates them is not luck but a method: notice exactly what is wrong, collect the evidence, find the one line responsible, fix it, and prove the fix. This chapter teaches that method, and the simple tools that make it fast.

About 35 minutes · Course outcome CO6

Before you start — one-line reminders

  • console.log(value) prints a value in the browser's Console, which you open with F12 (Chapter 41).
  • if (condition) { ... } else { ... } runs one block or the other (Chapter 47).
  • A function's code runs only when the function is called; () => { ... } is the short arrow way to write one (Chapter 48).
  • document.querySelector("#id") returns null when nothing on the page matches (Chapter 56).

  • Read an error message: its type, its description and its file and line.

68.2 Bugs, and what debugging is

A bug is a mistake in a program that makes it behave differently from what was intended. Engineers were using the word long before computers. In 1947 the team running the Harvard Mark II computer found a real moth trapped in one of its relays (electrically worked switches), and taped it into their logbook as the "first actual case of bug being found". The joke stuck.

Debugging is the systematic process of identifying, understanding and fixing those bugs. Notice the word systematic: debugging is a method you follow, not a guess you hope for.

The Unit 6 slides sort bugs into five families:

FamilyWhat happensExample

This chapter concentrates on the first three, which live in your own JavaScript. Network failures belong to error handling (Chapter 70), and the panels that expose layout and network trouble belong to Chapter 69. The next example, from the slides, is a UI bug — and it is worth running because it shows something important: a program can be wrong without a single red error.

<style>
  body { font-family: system-ui, sans-serif; padding: 10px; }
  .row { margin: 10px 0; }
</style>
<div class="row">Broken — Tasks added: <b id="countBroken">0</b> <button id="addBroken">Add task</button></div>
<div class="row">Fixed — Tasks added: <b id="countFixed">0</b> <button id="addFixed">Add task</button></div>
<script>
  // Broken: the variable changes, but nobody tells the page
  let brokenCount = 0;
  document.querySelector("#addBroken").addEventListener("click", () => {
    brokenCount++;
    console.log("broken count is now", brokenCount);
    // forgot to update the page!
  });

  // Fixed: one extra line copies the new value onto the page
  const countEl = document.querySelector("#countFixed");
  let fixedCount = 0;
  document.querySelector("#addFixed").addEventListener("click", () => {
    fixedCount++;
    countEl.textContent = fixedCount;
  });
</script>

Click the broken button five times. The page still says 0, and the console shows no error at all — only broken count is now 1, 2… up to 5. That one console.log line is the evidence: the variable is changing, so the bug must be in the step that should copy it onto the page. That step is missing. The fixed version adds it: countEl.textContent = fixedCount;.

Why debugging matters

A bug that slips through costs more than a wrong number. Debugging protects five qualities of a program:

  • Correctness — the right result for every input.
  • Reliability — it works every time, not just on your laptop.
  • User experience — no silent failures or confusing screens.
  • Maintainability — a bug you understood stays fixed.
  • Security — unhandled crashes and unchecked input can expose data.

The slides' case study shows how small the cause can be. A college registration form did nothing when students clicked Register: no message, no account. The console held one red line — Uncaught TypeError: Cannot read properties of null (reading 'value'), at register.js:12. The script looked for #email, but the HTML said id="userEmail", so querySelector returned null. One mismatched name, and every sign-up was lost. The fix was to match the id — and, to prevent a repeat, to show a visible message whenever submission fails.

A bug is the program doing something you did not mean. Debugging is finding out why, with evidence, and then changing the one thing that caused it. Experienced programmers are not people who never make bugs; they are people who find them quickly.

68.3 The debugging workflow

Faced with a broken page, most beginners start changing things: add a semicolon, swap let for var, delete a line, refresh, repeat. Sometimes the symptom vanishes. But the real cause is often still there, hidden, and the random edits have added new bugs of their own. Professionals follow a fixed sequence instead. The Unit 6 slides give it seven steps:

  1. Observe the problem. Say exactly what is wrong as expected versus actual: "For quantity 2 I expect Total: ₹525.00; I get nothing."
  2. Reproduce it. Find the exact steps that make it happen every time. A bug you can trigger on demand is half solved; one you cannot trigger cannot be tested.
  3. Inspect the evidence. Read the console, print the values of variables, pause the code (section 68.6).
  4. Identify the root cause. The one wrong line, or the one wrong assumption.
  5. Fix the code with the smallest change that removes that cause.
  6. Retest with the same steps — and with unusual inputs: 0, an empty box, a huge number.
  7. Verify the fix. Check that nothing else broke, then commit with a clear message (Chapter 75).

Steps 3 and 4 are really a small loop. Looking at the evidence, you form a hypothesis — "I think qty is text, not a number" — and then you test it, usually with one console.log. If the test says no, you form a better guess. You change real code only when a guess has been confirmed.

Picture this. You tell a good doctor, "I feel unwell." She does not hand you five medicines at once to see which one helps. She asks what exactly is wrong and since when (observe), checks whether it happens every morning or only after meals (reproduce), takes your temperature and orders a blood test (inspect the evidence), names the cause (diagnosis), prescribes one medicine for it (the smallest fix), and asks you to come back in a week (retest and verify). Random medicines might hide the symptom and leave the illness. Random code changes do exactly the same to a bug.

Compare root-cause thinking, in the slides' words: "The error says null at line 12. querySelector returned null because the id is different." One piece of evidence, one fix.

Quick check: why does the workflow put "reproduce it" before "fix the code"?

Because if you cannot make the bug happen on demand, you cannot check that your fix worked. Exact steps that always trigger the bug are also the test you rerun in step 6.

68.4 Three kinds of error, demonstrated

The three families you will meet most in your own code differ in when they show themselves. A browser handles a script in two stages. First its parser reads the whole script and checks the grammar. Only if the grammar is correct does it start running the lines, one after another. That gives three moments at which something can go wrong.

Demo 1: a syntax error

let message = "Hello World;      // the closing quote is missing
console.log(message);

The string opens with " and never closes. The parser reads to the end of the line hunting for the closing quote, fails, and rejects the whole script. Not one line of it runs — not even lines above the mistake. Chrome reports Uncaught SyntaxError: Invalid or unexpected token. The fix is to close the quote: "Hello World". Your editor gives you an early warning, too: an unclosed string turns the rest of the line the colour of a string.

Run this example. The page holds two separate scripts. As written, both are correct:

<p id="s1">Script 1: did not run</p>
<p id="s2">Script 2: did not run</p>
<script>
  console.log("Script 1 starts");
  let message = "Hello World";     // line 5: try deleting the closing quote
  console.log(message);
  document.querySelector("#s1").textContent = "Script 1: ran";
</script>
<script>
  // A separate script
  console.log("Script 2 runs");
  document.querySelector("#s2").textContent = "Script 2: ran";
</script>

The first Run prints Script 1 starts, Hello World and Script 2 runs, and the page says both scripts ran. Now break line 5: delete the " just before the semicolon, so the string never closes, and Run again. The console shows Uncaught SyntaxError: Invalid or unexpected token pointing at line 5, then Script 2 runs, and the page says Script 1: did not run. Script 1 starts never appears, although it is the line above the mistake: the parser rejected script 1 before running any of it. The browser simply moved on to the next script. (Firefox words the message differently — it mentions an unescaped line break in a string literal — but the type, SyntaxError, is the same.)

Demo 2: a runtime error

Now the grammar is perfect, so the script starts running — and crashes at the one line it cannot carry out:

<p id="out"></p>
<script>
  console.log("1. The script starts");
  const student = null;            // e.g. the search found no student
  console.log("2. student is", student);
  // console.log(student.name);    // line 6: delete the first // and Run again
  console.log("3. The script reached its last line");
</script>
<script>
  // The safe version, in its own script
  const found = null;
  const label = found?.name ?? "No student available";
  console.log("4. Safe version:", label);
  document.querySelector("#out").textContent = label;
</script>

As written, line 6 is switched off by its //, so all four labelled lines print. Delete that first // and Run again. Now the console shows 1. The script starts and 2. student is null, then Uncaught TypeError: Cannot read properties of null (reading 'name') at line 6. Line 3 no longer prints: an uncaught runtime error stops the rest of that script. The second script still runs normally and prints 4. Safe version: No student available.

The safe version uses two operators from the slides. ?. (optional chaining) means "if the thing on the left is null or undefined, stop and give undefined instead of crashing". ?? (nullish coalescing) means "use the right-hand value only when the left is null or undefined" — not for 0 or "", which is where it differs from ||.

A guard is not a diagnosis. ?. stops the crash, but it does not answer the real question: why is student null? Perhaps the server sent nothing, or querySelector was given the wrong id. Find that cause first; add the guard only where "nothing there" is a normal, expected situation.

Demo 3: a logical error

The third kind is the most dangerous, because nothing complains at all. A shop wants 10% off a ₹500 item:

<p id="out"></p>
<script>
  const price = 500;
  const discount = 10;                         // means 10%
  const expected = 450;                        // worked out by hand first

  const broken = price - discount;             // takes off 10 rupees
  const fixed = price * (1 - discount / 100);  // takes off 10 per cent

  console.log("Broken:", broken, broken === expected ? "correct" : "WRONG, expected " + expected);
  console.log("Fixed:", fixed, fixed === expected ? "correct" : "WRONG, expected " + expected);
  document.querySelector("#out").textContent = `Broken gives ₹${broken}, fixed gives ₹${fixed}.`;
</script>

The console shows Broken: 490 WRONG, expected 450 and Fixed: 450 correct. The broken line is perfectly good JavaScript; it just says the wrong thing — subtract 10 rupees, not 10 per cent. The fix turns the percentage into a fraction: price * (1 - discount / 100) is 500 × 0.9.

Notice the line const expected = 450;. The only way to catch a logical error is to know the right answer before you run the code and compare. Try the slides' prediction: with price = 800 and discount = 25, the broken version prints 775 (800 − 25) and the corrected one prints 600 (800 × 0.75).

Syntax errorRuntime errorLogical error
When it showsAs the script is read, before any of it runsAt the moment the bad line runsOnly when someone checks the answer
How much runsNone of that scriptEverything before the bad lineEverything
Red message?Yes: SyntaxErrorYes: TypeError, ReferenceError…No

A syntax error is bad grammar: the browser refuses to start. A runtime error is an impossible instruction: the browser starts, then stops at that line. A logical error is a wrong instruction: the browser does exactly what you said, and what you said was not what you meant.

Quick check: a script prints three lines correctly, then a red TypeError appears. Which kind of error is it, and did the three lines run?

A runtime error. The three lines before the bad one did run — that is how you know it was not a syntax error, which would have stopped the whole script from running at all.

68.5 Reading an error message

Never panic at a red line, and never ignore it. A JavaScript error message is a precise report with up to three useful parts: what type of problem, what exactly went wrong, and where.

The type sorts problems into a few big groups. Chapter 70 meets all of them properly; for debugging, three cover most of what you will see:

Message (Chrome / Edge)TypeUsual cause
Invalid or unexpected token; Unexpected token ')'SyntaxErrorAn unclosed quote, a stray or missing bracket
Unexpected end of inputSyntaxErrorA { or ( that is never closed — reported at the very end of the script
totl is not definedReferenceErrorA typo in a name, or a variable never declared
Cannot read properties of null (reading 'value')TypeErrorquerySelector found nothing, usually because the id or class is spelled differently
btn.addEventListner is not a functionTypeErrorA misspelled method name
Assignment to constant variable.TypeErrorGiving a const a new value

The location is a link. In the DevTools Console the file name and line number appear on the right of the message (register.js:12); clicking it opens the file at that line. Below the message there may be a short list of at ... lines, showing which function was running and which function had called it. That list is a stack trace, and Chapter 69 shows how to explore it.

Two habits make error messages far more useful:

  • Fix the first error first. One mistake often causes others further down. Start at the topmost red line, fix it, reload, and look again — several "errors" may disappear together.
  • The line is where JavaScript noticed, not always where you went wrong. In the registration case the crash was on line 12, where .value was read; the real mistake was the selector a few lines earlier. A missing } is reported at the end of the file, far from where it belonged.

Read the whole red line, slowly, every time. The type says what kind of problem; the message says what exactly; the file and line say where to start looking. Then work backwards from that line to find where the bad value came from.

68.6 The debugging toolkit

When the error message alone does not explain the bug — or there is no error at all — you collect more evidence. These tools need nothing but the browser.

console.log, with labels

The most used debugging tool in the world is printing a value at a key point in the code. Always add a label, so that when ten lines appear you know which is which:

console.log(total);                    // 500.05       which variable was that?
console.log("total:", total);          // total: 500.05
console.log({ qty, subtotal, total }); // {qty: 2, subtotal: 500, total: 500.05}

The last line is a handy trick. Wrapping the variables in { } builds a small object whose property names are the variable names, so the console prints every name beside its value in one line.

console.table, console.error and console.warn

  • console.table(array) prints an array of objects as a grid, one row per item and one column per property. Ten students' marks are far easier to check in a table than in ten lines.
  • console.error(...) prints in red, like a real error. Use it for "this should never happen" checks, so they stand out.
  • console.warn(...) prints in yellow: for something suspicious but not fatal.

Check your assumptions with typeof

Many bugs come from a value being a different type from the one you assumed. The classic is "5" versus 5: text read from a form box is always a string, even when it looks like a number. typeof settles the question in one line:

Valuetypeof givesTrap
5"number"—
"5""string""5" + 1 is "51", not 6

undefined"undefined"Usually a misspelled property or a missing return
null"object"A famous old quirk; test it with x === null

The next example puts all of this together. Three students' marks arrive as text, exactly as they would from form boxes, and the average comes out impossible. Run it and read the console from top to bottom, like a detective:

<p id="out"></p>
<script>
  // Marks typed into a form arrive as text, even when they look like numbers
  const students = [
    { name: "Asha",  marks: "78" },
    { name: "Rahul", marks: "85" },
    { name: "Meera", marks: "92" },
  ];
  console.table(students);                  // look at the quotes round the marks

  // --- buggy version ---
  let total = 0;
  for (const s of students) {
    total += s.marks;
    console.log("after", s.name, { total });
  }
  console.log("typeof total:", typeof total);
  const average = total / students.length;
  if (average > 100) {
    console.error("Average is", average, "- impossible for marks out of 100!");
  }

  // --- fixed version: turn the text into a number first ---
  let fixedTotal = 0;
  for (const s of students) {
    fixedTotal += Number(s.marks);
  }
  const fixedAverage = fixedTotal / students.length;
  console.log("Fixed average:", fixedAverage, typeof fixedAverage);
  document.querySelector("#out").textContent = `Buggy average: ${average}. Fixed average: ${fixedAverage}.`;
</script>

Follow the clues. The table shows the marks as '78', '85', '92' — the quotes mean strings. The labelled lines show total growing as '078', then '07885', then '0788592': + is gluing text together instead of adding. typeof total: string confirms it. Dividing the text "0788592" by 3 makes JavaScript convert it to the number 788592, so the red line reports Average is 262864 - impossible for marks out of 100!. The fixed version converts each mark with Number() first and prints Fixed average: 85 number.

Quick check: in the buggy loop, why is the first value '078' and not 78?

Because total starts as the number 0 and s.marks is the string "78". When + meets a string it joins text, so 0 + "78" is "078". From then on total is a string, and every += glues on more text.

Isolate the failing section

When you have no idea where a long script goes wrong, cut the search in half. Put a console.log("reached A") half-way down. If it prints and the values look right, the bug is in the second half; if not, it is in the first. Halve that half, and so on. Forty lines take about six rounds (40, 20, 10, 5, 3, 2, 1) to narrow down to one. The same idea works by commenting out: put // in front of a suspect block (or wrap it in /* ... */), reload, and see whether the problem goes with it. Testing one function at a time, with inputs whose answers you know, is the same idea again.

Explain it to a rubber duck

A famous programmers' technique, with a silly name: explain your code, line by line and out loud, to a rubber duck on your desk — or to a patient friend. Saying "this line adds the tax to the subtotal" forces you to look at what the line really does, and very often you hear your own mistake half-way through the sentence.

Pause the code: the debugger statement

Printing shows a value at one moment. Sometimes you want to freeze the program and look at everything at once. Write the statement debugger; on the line where you want to stop:

button.addEventListener("click", () => {
  const qty = Number(qtyInput.value);
  debugger;                       // with DevTools open, the program pauses here
  const subtotal = qty * PRICE;
});

With DevTools open, the program stops on that line, and you can see every variable's current value and move forward one line at a time. With DevTools closed, debugger; does nothing at all. A breakpoint does the same job without editing your code: you click a line number in the Sources panel. Breakpoints, stepping and the call stack are the heart of Chapter 69.

Clean up before you commit. Debugging lines are scaffolding. Remove stray console.log calls and every debugger; before you save your work to Git: a forgotten debugger; pauses the page for anyone who opens DevTools on your live site.

Test the correction

A fix is not finished until it has passed the original failing case and its neighbours: edge cases such as 0, an empty box, one item, two hundred items, a huge number. The slides' eight-item checklist sums up the chapter so far: read the error message; use console.log(); check variable values and types; isolate the failing section; reproduce the error; use breakpoints; inspect the call stack; test the correction.

68.7 The debugging challenge, step by step

Here is the slides' hands-on challenge. An order-total calculator: a notebook costs ₹250 and tax is 5%. For quantity 2 the page should show Total: ₹525.00 (500 plus 5% of 500, which is 25). The code contains exactly three bugs — one selector, one typo, one formula. Run it, click Calculate, and before reading on, try to fix them yourself using the workflow.

<label>Quantity <input id="qty" type="number" value="2"></label>
<button id="calcBtn">Calculate</button>
<p id="total"></p>
<script>
  const qtyInput = document.querySelector("#quantity");
  const button = document.querySelector("#calcBtn");
  const totalEl = document.querySelector("#total");
  const PRICE = 250;          // price per notebook
  const TAX_RATE = 0.05;      // 5% tax

  button.addEventListener("click", () => {
    const qty = Number(qtyInput.value);
    const subtotal = qty * PRICE;
    const total = subtotal + TAX_RATE;
    totalEl.textContent = `Total: ₹${totl.toFixed(2)}`;
  });
</script>

Round 1. Observe: nothing appears on the page. Inspect: the console says Uncaught TypeError: Cannot read properties of null (reading 'value') at line 12. So qtyInput is null. Root cause: work backwards to where qtyInput got its value, line 5, querySelector("#quantity"). The HTML says id="qty". Nothing matched, so the result was null. Fix 1: "#quantity" becomes "#qty".

Round 2. Click again. A new message: Uncaught ReferenceError: totl is not defined at line 15. This bug was there all along; it was hidden because the click handler crashed on line 12 and never reached line 15. A ReferenceError names something that does not exist; the variable is called total. Fix 2: totl becomes total.

Round 3. Click again. The console is clean, and the page shows Total: ₹500.05. Many students stop here. But step 6 says retest against the expected value, and 500.05 is not 525.00. This is a logical error: subtotal + TAX_RATE adds the rate (0.05 rupees) instead of the tax. The tax is subtotal * TAX_RATE, so the total is subtotal + subtotal * TAX_RATE, written more neatly as subtotal * (1 + TAX_RATE). Fix 3 gives 500 × 1.05 = 525.

Here is the corrected program. It adds two things to the slides' solution: a labelled console.log for the evidence, and a check for a blank or impossible quantity, found by retesting with edge cases (step 6). Try 2, then 3, then 0, then clear the box:

<label>Quantity <input id="qty" type="number" value="2"></label>
<button id="calcBtn">Calculate</button>
<p id="total"></p>
<script>
  const qtyInput = document.querySelector("#qty");              // fix 1: the real id
  const button = document.querySelector("#calcBtn");
  const totalEl = document.querySelector("#total");
  const PRICE = 250;          // price per notebook
  const TAX_RATE = 0.05;      // 5% tax

  button.addEventListener("click", () => {
    const qty = Number(qtyInput.value);
    if (!Number.isInteger(qty) || qty < 1) {                     // edge cases found by retesting
      console.warn("Bad quantity:", JSON.stringify(qtyInput.value));
      totalEl.textContent = "Please enter a quantity of 1 or more.";
      return;
    }
    const subtotal = qty * PRICE;
    const total = subtotal * (1 + TAX_RATE);                       // fix 3: add 5% of the subtotal
    console.log({ qty, subtotal, total });
    totalEl.textContent = `Total: ₹${total.toFixed(2)}`;    // fix 2: total, not totl
  });
</script>

Quantity 2 logs {qty: 2, subtotal: 500, total: 525} and shows Total: ₹525.00; quantity 3 shows Total: ₹787.50. Quantity 0 shows the friendly message and a yellow warning, Bad quantity: "0". An empty box gives Bad quantity: "" — without the check, Number("") would have quietly become 0 and shown Total: ₹0.00, a logical bug nobody asked for.

Key idea. The slides' lesson: runtime errors can hide logical errors. A clean console means the program ran; it does not mean the program is right. Keep testing against a known expected answer after the last red line has gone.
Quick check: why did the page load without any error, even though querySelector("#quantity") found nothing?

Because finding nothing is not an error: querySelector simply returned null and stored it. The crash came only later, when the click handler asked null for its .value. The line that failed (12) was not the line that was wrong (5).

68.8 Common misunderstandings

✗ "No red error means my code works."
It only means nothing crashed. Logical and UI errors produce no message at all: 490 instead of 450, 500.05 instead of 525, a counter stuck at 0.
✓ "Code works when it gives the answer I worked out in advance."
Decide the expected result first, then compare — for the normal case and for the edge cases.
✗ "The line in the error message is the line I got wrong."
It is the line where JavaScript noticed. A wrong selector on line 5 crashes on line 12; a missing } is reported at the end of the file.
✓ "The line in the error message is where I start looking."
Go there, then work backwards: where did this bad value come from?
✗ "Debugging means trying things until the error goes away."
Random edits can hide a symptom, leave the cause, and add new bugs.
✓ "Debugging means following the evidence to the root cause."
Observe, reproduce, inspect, find the cause, make the smallest fix, retest, verify.
✗ "A syntax error only breaks the line it is on."
The parser rejects the whole script before running any of it — lines above the mistake do not run either.
✓ "A syntax error stops that entire script."
Other, separate scripts on the page still run, which is why a page can half-work.

Exam-style checks

Which kind of error stops a whole script before any of its lines run?L1
  • A. A runtime error
  • B. A logical error
  • C. A syntax error
  • D. A UI error

Answer: C. The parser checks the grammar of the whole script first; if it is broken, nothing in that script runs. A runtime error lets every line before the bad one run; a logical error lets everything run and simply gives a wrong answer.

A program meant to give 10% off ₹500 prints 490. The console shows no error. What kind of bug is this?L2
  • A. A logical error
  • B. A syntax error
  • C. A runtime error
  • D. A network failure

Answer: A. The code ran perfectly and did what it was told — subtract 10 rupees — which was not what was meant. With no red message, only a comparison with the expected answer (450) exposes it. B and C would both have shown a red error.

What does this print? const s = null; console.log("A"); console.log(s.name); console.log("B");L3

Answer: A, then Uncaught TypeError: Cannot read properties of null (reading 'name'). B is never printed. The grammar is fine, so the script starts and prints A. Reading a property of null is impossible, so it crashes there, and an uncaught runtime error abandons the rest of the script.

The console shows Uncaught ReferenceError: totl is not defined. What is the most likely cause?L2
  • A. The file totl.js could not be downloaded
  • B. The variable totl holds null
  • C. A string is missing its closing quote
  • D. A name has been misspelled, or was never declared

Answer: D. A ReferenceError means the code used a name that does not exist — here almost certainly a typo for total. A missing file is a network problem, a null value gives a TypeError, and an unclosed quote is a SyntaxError.

The JavaScript says document.querySelector("#email") but the HTML input has id="userEmail". When does the error appear?L3
  • A. As a SyntaxError, before the page loads
  • B. As a TypeError, when code later reads .value from the result
  • C. As a ReferenceError, on the querySelector line
  • D. Never: querySelector fixes the id automatically

Answer: B. Finding nothing is not an error: querySelector quietly returns null. The crash comes later, when something asks null for .value. That is why the reported line is not the line that is wrong.

In the debugging workflow, what should you be able to do before you change any code?L2
  • A. Rewrite the whole function from scratch
  • B. Switch every let to var
  • C. Reproduce the bug with exact steps and know its root cause
  • D. Delete the lines the error message mentions

Answer: C. Observe, reproduce, inspect the evidence and identify the root cause come first; only then the smallest fix. The other options are random changes, which can hide the symptom while leaving the cause.

What does console.log(typeof NaN); print?L3
  • A. NaN
  • B. number
  • C. undefined
  • D. string

Answer: B. Oddly, "Not a Number" is a value of type number — it is what failed number calculations produce. To test for it, use Number.isNaN(x), not typeof.

What does this print? let total = 0; for (const m of ["4", "5"]) { total += m; } console.log(total, typeof total);L3

Answer: 045 string. Step by step: 0 + "4" joins text to make "04", then "04" + "5" is "045". Once a string is involved, + glues instead of adding. The fix is total += Number(m);, which prints 9 number.

What does the statement debugger; do when DevTools is closed?L2
  • A. Nothing at all
  • B. Pauses the program until the user presses a key
  • C. Throws a SyntaxError
  • D. Prints every variable to the console

Answer: A. debugger; pauses only when debugging tools are open; otherwise it has no effect. That is also why it must be removed before publishing: anyone opening DevTools on the live site would hit the pause.

In the challenge, subtotal is 500 and TAX_RATE is 0.05. What does subtotal + TAX_RATE give, and what is the correct formula?L3

Answer: 500.05; the correct formula is subtotal * (1 + TAX_RATE), giving 525. Adding the rate adds 0.05 rupees. The tax itself is subtotal * TAX_RATE (25), and subtotal * (1 + TAX_RATE) is the subtotal plus that tax in one step.

Which console method shows an array of student objects as a grid of rows and columns?L1
  • A. console.error
  • B. console.warn
  • C. console.grid
  • D. console.table

Answer: D. console.table gives one row per item and one column per property. console.error and console.warn print red and yellow messages, and there is no console.grid.

Quick revision

Key takeaways

  1. A web application's life is a loop — plan, build, debug, deploy, maintain — and bugs found in testing send you back to coding.
  2. A bug is behaviour you did not intend; debugging is the systematic process of identifying, understanding and fixing it.
  3. The workflow: observe, reproduce, inspect the evidence, identify the root cause, make the smallest fix, retest with edge cases, verify. Never change lines at random.
  4. Syntax errors stop the whole script before it runs; runtime errors stop it at the bad line; logical errors stop nothing and show no message.
  5. Read every error message for its type, its message and its file:line — and remember the line is where JavaScript noticed, not always where you went wrong. Fix the first error first.
  6. Collect evidence with labelled console.log, console.table, console.error, typeof, halving the code, explaining it aloud, and debugger; or breakpoints.
  7. Runtime errors can hide logical errors. A clean console means the code ran, not that it is right: always compare with an answer worked out in advance.
