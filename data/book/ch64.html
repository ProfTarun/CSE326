Browser Storage: localStorage and sessionStorage

Type your name into a page, tick dark mode, add three things to a cart — then press F5, and an ordinary page has forgotten all of it. Web Storage gives every website a small notebook inside the visitor's own browser, where your JavaScript can write things down and read them back on the next visit.

About 32 minutes · Course outcome CO5

Before you start — one-line reminders

  • An object groups named values, { name: "Rahul", age: 19 }, and you read one with student.name (Chapter 51).
  • addEventListener("click", fn) runs a function when something happens; "change" and "input" are events too (Chapter 57).
  • getElementById finds an element; textContent and classList change it (Chapter 56).
  • "5" (text) and 5 (a number) are different types, and typeof tells you which (Chapter 43).

By the end of this chapter you can

  • Explain why a reload wipes every variable, and where Web Storage keeps data instead.
  • Choose between localStorage and sessionStorage by how long the data must live and which tabs need it.
  • Use setItem, getItem, removeItem, clear, key and length, and say what getItem returns for a missing key.
  • Turn stored text back into numbers, and store objects and arrays with JSON.stringify and JSON.parse.
  • Build pages that remember a name, a theme, a draft and a set of preferences.
  • Find, edit and clear stored data in DevTools.
  • State the limits and safety rules: about 5 MB, synchronous, never secrets, can vanish, wrap risky calls in try...catch.

64.1 Why a page forgets everything

Open any page you have built so far, type into a box, tick a checkbox, and press F5. The box is empty and the tick has gone. Nothing is broken: every time the browser loads a page it builds it fresh from the HTML, runs your JavaScript from the first line, and keeps every variable in the page's working memory. A reload throws that memory away. As far as your code is concerned, every visit is the first visit.

Real websites remember:

  • Dark mode — YouTube keeps your theme even when you are not logged in.
  • Your name — "Welcome back, Rahul!" on every visit.
  • A shopping cart — the items are still there after a refresh.
  • Form drafts — a half-written feedback form is not lost when the page reloads.

None of these needs a server, a database or a login. The page asks the browser to persist a small note on the visitor's own device, and reads it back the next time the page starts. This browser feature is Web Storage, and it gives your JavaScript two ready-made objects, localStorage and sessionStorage. There is nothing to create or import: like document and console, they are simply there.

Key idea. Variables live in the page and die with it. Web Storage lives in the browser and survives the reload. Your page writes to it when something changes and reads from it when the page starts.

64.2 Key–value pairs, kept per origin

Web Storage keeps data as key–value pairs. The key is a label you choose, such as "theme". The value is the data filed under that label, such as "dark". You save a value under a key; later you ask for the key and get the value back. No tables, no queries.

KeyValue (always text)What a site might use it for
theme"dark"The colour scheme the visitor chose
studentName"Rahul"A friendly greeting
semester"1"Which semester's timetable to open first
cart'["pen","book"]'A list, written out as text (64.6 shows how)

Two rules matter from the very first minute:

  1. Keys and values are both strings. Even semester above holds the text "1", not the number 1. This explains most beginner bugs (64.5).
  2. One key holds one value. Saving under an existing key replaces the old value.
Picture this. A wall of lockers in a hostel corridor. Each locker has a label on its door (the key) and holds one folded paper note (the value). Put a new note into the locker labelled theme and the old note is thrown away first. The lockers take only paper: your cricket kit will not fit, but a written description of it will — that writing-down step is JSON, in 64.6. And each hostel block has its own wall: a student from another block cannot open your lockers.

That last point is the safety rule of Web Storage. Storage is kept separately for every origin. An origin is three things taken together: the protocol (http or https), the host (such as lpu.in) and the port (443 is the hidden default for https, 80 for http). Pages whose addresses share all three parts share one storage area; change even one and you get a separate area that cannot read the first. The path after the host — /courses, /exam/results.html — does not count.

PageSame origin as https://lpu.in?Why
https://lpu.in/courses/cse326.htmlYesOnly the path differs
http://lpu.inNoDifferent protocol
https://ums.lpu.inNoA sub-domain is a different host
https://lpu.in:8443NoDifferent port (the plain address means 443)
http://127.0.0.1:5500 vs http://127.0.0.1:5501NoTwo Live Server ports are two different origins

Only pages from your own address can read your site's storage. Change https to http, add a sub-domain such as ums., or change the port, and you are at a different address with different — and empty — storage. The page name at the end makes no difference — so a value saved on Live Server's port 5500 is not lost when Live Server opens on 5501 tomorrow; you are just looking at another origin's storage.

Quick check: a page at https://lpu.in saved a key. Can https://lpu.in/courses/cse326.html read it? Can http://lpu.in?

The first one can: only the path differs, and the path is not part of the origin. The second one cannot: http and https are different protocols, so it is a different origin with its own, separate storage.

64.3 localStorage and sessionStorage: long-term and short-term memory

Both objects have exactly the same methods. They differ in only two ways: how long the data lives, and which tabs can see it.

FeaturelocalStoragesessionStorage
Data lifetimeUntil your code or the user deletes it (or the browser clears it to free space)Until the tab is closed
Page reload (F5)✓ Survives✓ Survives
Close and reopen the browser✓ Survives✗ Lost (unless the browser restores your old tabs)
Tabs and windowsOne copy, shared by every tab of the originA separate copy for each tab
Typical useTheme, language, saved preferencesMulti-step form, quiz progress, a one-visit filter

sessionStorage, step by step

sessionStorage is the one people misjudge. In one tab, a page runs the lecture's example:

// Save for this tab only
sessionStorage.setItem("username", "Aman");
console.log(sessionStorage.getItem("username"));   // Aman
What happens nextsessionStorage.getItem("username") givesWhy
Reload the tab (F5)"Aman"Same tab, same session: a reload keeps it
Close the tab, then open the site againnullClosing the tab ended the session and threw the data away
Open the site in a second tabnullA new tab starts a new, empty session

localStorage: one copy for the whole site, kept until somebody deletes it. sessionStorage: one copy per tab, kept through reloads, thrown away when that tab closes. Two tabs never share a sessionStorage, even on the same site.

One footnote: reopening a closed tab, restoring tabs after a crash or using Duplicate tab may bring a copy of the old sessionStorage along. Never build a page that depends on it.

Which one should you use? Ask: should this still be here tomorrow? If yes — a theme, a language, preferences — use localStorage. If it only matters for this visit in this tab — a multi-step registration form, quiz progress — use sessionStorage, so a half-filled form on a shared lab computer does not greet tomorrow's student.

Quick check: Meera's quiz saves quizStep = "3" in sessionStorage. She opens the same quiz in a new tab. What does getItem("quizStep") give in the new tab?

null. Each tab has its own sessionStorage, and a brand-new tab starts empty. In the original tab it would still be "3", even after a reload. Had the quiz used localStorage, both tabs would see "3".

64.4 The six tools

Everything you do with Web Storage uses five methods and one property, and they work identically on both objects: localStorage.setItem(...) or sessionStorage.setItem(...), and so on.

CodeWhat it doesGives back
localStorage.setItem("theme", "dark")Saves the value under the key — or replaces it, if the key existsNothing (undefined)
localStorage.getItem("theme")Reads the value saved under the keyThe text, e.g. "dark" — or null if there is no such key
localStorage.removeItem("theme")Deletes that one key and its value; the others are untouchedNothing, and no error if the key was not there
localStorage.clear()Deletes every key this origin saved in this storageNothing
localStorage.key(0)The name of the key at position 0, 1, 2 …A key name, or null past the end
localStorage.lengthHow many keys are stored. A property, so no bracketsA number

clear() does not touch other websites' storage, or the other storage object: localStorage.clear() leaves sessionStorage alone, and vice versa.

Every one of these calls is synchronous. When the setItem line finishes, the value is already saved and the next line can read it back. (Fetching data from a server is the opposite — it takes time, and Chapter 65 shows how to wait for it.)

The preview frames have no web address of their own, so their storage is a temporary stand-in: it behaves like the real thing while you click, but Run again starts it empty. On a real site — such as your own file opened with VS Code Live Server — the data stays through reloads and browser restarts.

Press Run and read the Console from the top: length is now 3, course: CSE, then hostel: null — never saved, so nothing to find. Then semester: 2: the second setItem replaced the "1", so the count is still 3. Now press removeItem("course") (two keys left), then clear() (none): one locker emptied, then the whole wall.

The loop in show() is the standard way to list everything: count from 0 to length - 1, ask key(i) for each name, then getItem for its value. The order of the keys is up to the browser, so never depend on it.

Exam tip. getItem on a key that does not exist returns null — not undefined, not an empty string "", not false. Your restore-on-load code depends on it: "if I got null, nothing was saved yet, so use the default."
Use the methods, not dots. Browsers also accept localStorage.theme = "dark", and you will meet it in old code. Avoid it: a key named length or key clashes with the built-in names, and the methods make it obvious you are talking to storage.

64.5 Everything comes back as text

Whatever value you hand to setItem, it is first turned into a string, and that string is what gets stored. getItem then gives you the string — never the original number, true/false, array or object.

You saveWhat is stored, and what getItem gives back
setItem("count", 5)"5" — text, not a number
setItem("price", 19.5)"19.5"
setItem("seen", true)"true"
setItem("seen", false)"false" — a non-empty string, which counts as true in an if
setItem("x", null)"null" — four letters, not the value null
setItem("cart", ["pen", "book"])"pen,book" — the list structure is lost
setItem("student", { name: "Rahul" })"[object Object]" — the data is lost completely

Two kinds of bug follow. Maths: when one side of + is a string, JavaScript joins, so "5" + 1 gives "51". Yes/no values: if (localStorage.getItem("seen")) runs even after you saved false, because the stored value is the text "false" and every non-empty string counts as true.

Storage only understands words. Hand it the number 5 and it writes down the character "5" — so convert it with Number() before you add. Hand it false and it writes the word "false", which counts as true because it is not empty — so compare words with words: localStorage.getItem("seen") === "true".

Press it three times: the ordinary variable says 1 every time, because it is born again at 0; the stored count climbs 2, 3, 4, because it lives outside the page.

On the first visit there is no key, so getItem gives null — and Number(null) is 0, so the first visit counts as 1 with no special case. If the text could ever be non-numeric, Number("abc") gives NaN; Number(...) || 0 turns that into 0 too.

Quick check: after localStorage.setItem("n", 7), what is typeof localStorage.getItem("n")?

"string". The 7 was stored as the text "7". To get the number back, write Number(localStorage.getItem("n")).

64.6 Objects and arrays: JSON.stringify and JSON.parse

A student's record is naturally an object: { name: "Rahul", age: 19, course: "CSE" }. Hand that straight to setItem and you get the useless string "[object Object]" — every name and value gone for good. Arrays fare little better: ["pen", "book"] becomes "pen,book", a plain string, no longer a list.

The answer is JSON, JavaScript Object Notation: a way of writing an object or array out as text that keeps all of its structure. You need both of its functions:

  • JSON.stringify(value) — object or array → text. Use it on the way in, just before setItem.
  • JSON.parse(text) — text → object or array. Use it on the way out, just after getItem.
const student = { name: "Rahul", age: 19, course: "CSE" };

localStorage.setItem("student", JSON.stringify(student));
// stored text: {"name":"Rahul","age":19,"course":"CSE"}

const savedStudent = JSON.parse(localStorage.getItem("student"));
console.log(savedStudent.name);   // Rahul

Storage cannot hold an object, only text. So before saving, JSON.stringify writes the object out as text, keeping every name and value. After reading, JSON.parse builds a real object from that text again, so .name works. Parse what you stringified — that is the whole rule.

What survives the trip? Text, numbers, true/false, null, arrays and plain objects, nested as deeply as you like. Functions and undefined values inside an object silently disappear (inside an array they become null), and a date comes back as text (Chapter 62). JSON is also how browsers and servers exchange data; Chapter 65 gives its full rules.

A safe default when nothing is saved yet

On a first visit there is no cart key, so getItem gives null. Conveniently, JSON.parse(null) also gives null (it reads the text "null"), so a default fits in one line:

const cart = JSON.parse(localStorage.getItem("cart")) || [];   // [] on a first visit

When the saved text is broken

If the stored text is not valid JSON — an older version of your page saved "[object Object]", someone edited it in DevTools, or a plain word like "Rahul" was saved without stringify — then JSON.parse throws an error, and an uncaught error stops the rest of your script. One bad note in one locker kills the page.

The protection is try...catch. Put the risky line inside try { }. If it works, the catch part is skipped; if it throws, JavaScript jumps into catch (err) { } instead of crashing, and your code carries on with a default.

try means "attempt this". catch means "if that blew up, do this instead of crashing". For storage, "this instead" is almost always use the default value. Chapter 70 covers try...catch fully; here you only need this one pattern.

Changing an array that is in storage

You cannot push into storage, because storage holds text. Changing a stored list takes three steps: read it (parse), change the real array, write it back (stringify). Forget the third and the change lives only in a variable, which dies on reload.

<script>
  // 1. The bug: an object saved directly
  const student = { name: "Rahul", age: 19, course: "CSE" };
  localStorage.setItem("student", student);
  console.log("Without JSON:", localStorage.getItem("student"));

  // 2. The fix: stringify on the way in, parse on the way out
  localStorage.setItem("student", JSON.stringify(student));
  const text = localStorage.getItem("student");
  console.log("Stored text:", text);
  const saved = JSON.parse(text);
  console.log("Name:", saved.name, "| age next year:", saved.age + 1);

  // 3. A safe reader: missing or broken data gives a default, not a crash
  function loadJSON(key, fallback) {
    try {
      const value = JSON.parse(localStorage.getItem(key));   // null if missing
      if (value === null) return fallback;
      return value;
    } catch (err) {
      console.warn(`"${key}" holds broken JSON (${err.name}) - using the default`);
      return fallback;
    }
  }
  localStorage.setItem("broken", "[object Object]");
  console.log("missing key:", loadJSON("wishlist", []));
  console.log("broken key:", loadJSON("broken", []));

  // 4. An array: read it, change it, write it back
  const list = document.getElementById("list");
  localStorage.setItem("cart", JSON.stringify(["pen", "book"]));

  function showCart() {
    const cart = loadJSON("cart", []);
    list.innerHTML = "";
    for (const item of cart) {
      const li = document.createElement("li");
      li.textContent = item;
      list.append(li);
    }
    if (cart.length === 0) list.innerHTML = "<li>(empty)</li>";
    console.log("cart in storage:", localStorage.getItem("cart"));
  }

  document.getElementById("add").addEventListener("click", () => {
    const cart = loadJSON("cart", []);                     // 1 read
    cart.push("notebook");                                 // 2 change
    localStorage.setItem("cart", JSON.stringify(cart));    // 3 write back
    showCart();
  });
  document.getElementById("empty").addEventListener("click", () => {
    localStorage.removeItem("cart");
    showCart();
  });

  showCart();
</script>

Read the Console in order. Without JSON: [object Object] is the bug. Stored text: {"name":"Rahul","age":19,"course":"CSE"} is real JSON: double quotes round every name, no spaces. Name: Rahul | age next year: 20 proves age came back as the number 19, not the text "19". JSON keeps types; plain setItem does not.

Then the safe reader: missing key: [], a warning that "broken" holds broken JSON (SyntaxError is what JSON.parse throws), and broken key: [] — the script survived. Finally cart in storage: ["pen","book"]. Press Add a notebook twice and watch the stored text grow; Empty the cart makes it null, which the reader turns back into an empty list.

64.7 Mini projects: a name, a theme and a draft

Every storage project follows the same five steps:

  1. The user does something — types a name, clicks a toggle.
  2. Your event handler runs.
  3. setItem() saves the new value in the browser.
  4. Later, on the next page load, getItem() reads it back.
  5. The page updates its interface to match.

Steps 1–3 happen when the user acts. Steps 4–5 happen every time the page starts, and beginners forget them. To try these projects for real, Copy the code into a file, open it with VS Code Live Server, and reload. (A double-clicked file gets a file: address, and browsers treat storage for those inconsistently; Live Server gives a proper origin such as http://127.0.0.1:5500.)

Mini project 1: remember my name

This is the lecture's project, with the script inside the page so it runs in one box (the slides keep it in app.js).

Quick check: Asha deletes the last line, showName();, and saves her file. Saving a name still works. What breaks?

The greeting no longer appears after a reload. The name is still in storage, but nothing reads it when the page starts, so the page shows "No name saved yet." until she presses Save again. Saving is only half of persistence; restoring on load is the other half.

Mini project 2: dark mode that survives a reload

The CSS defines two looks, and a class dark on the <body> switches between them. JavaScript only adds or removes that class — and remembers the choice.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>Theme Saver</title>
  <style>
    body { font-family: sans-serif; padding: 20px; background: #ffffff; color: #222222; }
    body.dark { background: #1e1e2e; color: #f1f1f1; }
  </style>
</head>
<body>
  <h2>My Study Notes</h2>
  <label><input type="checkbox" id="themeToggle"> Dark mode</label>

  <script>
    // Pretend a dark theme was saved on an earlier visit:
    // in the Playground, delete the two slashes on the next line and Run.
    // localStorage.setItem("theme", "dark");

    const toggle = document.getElementById("themeToggle");

    // 1. On page load: restore the saved theme
    const savedTheme = localStorage.getItem("theme");
    if (savedTheme === "dark") {
      document.body.classList.add("dark");
      toggle.checked = true;
    }
    console.log("Theme found on load:", savedTheme);

    // 2. When the user flips the toggle: apply + save
    toggle.addEventListener("change", () => {
      if (toggle.checked) {
        document.body.classList.add("dark");
        localStorage.setItem("theme", "dark");
      } else {
        document.body.classList.remove("dark");
        localStorage.setItem("theme", "light");
      }
      console.log("Saved theme:", localStorage.getItem("theme"));
    });
  </script>
</body>
</html>

Part 1 runs once, on load; part 2 runs every time the checkbox changes. The Console starts with Theme found on load: null; tick the box for Saved theme: dark, untick it for Saved theme: light. On a real site: Rahul ticks Dark mode → setItem("theme", "dark") → he closes the browser → tomorrow getItem gives "dark" and the class is added before he touches anything.

Two details are worth copying. toggle.checked = true on load keeps the checkbox honest — without it the page would be dark with the box unticked. And the test is === "dark", text compared with text. (Polish for later: a script at the end of the body runs after the page may already have been drawn in light colours, so a slow page can flash white first; large sites put a tiny theme script in the <head>.)

<h3>Feedback for CSE326</h3>
<textarea id="draft" placeholder="Start typing your feedback..."></textarea>
<p id="note">Nothing saved yet.</p>
<button id="send">Submit</button>

<script>
  const draft = document.getElementById("draft");
  const note  = document.getElementById("note");

  // On load: bring back this tab's unsent draft, if there is one
  const kept = sessionStorage.getItem("feedbackDraft");
  if (kept !== null) {
    draft.value = kept;
    note.textContent = "Draft restored from this tab.";
  }
  console.log("Draft found on load:", kept);

  // Every keystroke: save the draft for THIS TAB only
  draft.addEventListener("input", () => {
    sessionStorage.setItem("feedbackDraft", draft.value);
    note.textContent = `Draft saved (${draft.value.length} characters).`;
  });

  // Submitted: the draft is no longer needed
  document.getElementById("send").addEventListener("click", () => {
    console.log("Sending:", draft.value);
    sessionStorage.removeItem("feedbackDraft");
    draft.value = "";
    note.textContent = "Sent. The draft has been removed.";
    console.log("Draft left in this tab:", sessionStorage.getItem("feedbackDraft"));
  });
</script>

The Console starts with Draft found on load: null. Type a sentence and the note counts characters as each is saved. Press Submit: Sending: shows your text and Draft left in this tab: null confirms the clean-up. The load test is kept !== null, not if (kept): an empty draft "" is a real saved value, and only null means "nothing saved". A localStorage version would swap only the object's name in its four places; the methods stay, the lifetime changes.

64.8 Seeing storage in DevTools

The browser will show you what is stored, and let you change it by hand. In Chrome or Edge:

  1. Open DevTools with F12 (or Ctrl+Shift+I; on a Mac Cmd+Option+I).
  2. Choose the Application tab. If you cannot see it, it is hiding behind the » at the end of the tab row.
  3. In the left sidebar, under Storage, open Local storage and click your origin, such as http://127.0.0.1:5500. Session storage is just below it.
  4. A Key / Value table appears. Double-click a value to edit it, select a row and press Delete to remove it, or use the toolbar above to refresh or clear everything.

In Firefox the same table is in the Storage tab (Shift+F9). Two more tricks work in any browser's Console: type localStorage and press Enter to see every key at once, or type a single call such as localStorage.getItem("theme") to see one value — the Console prints it in quotes, a reminder that it is text.

Try the five-minute exercise from the lecture. On any page opened from Live Server, type localStorage.setItem("studentName", "Rahul") in the Console and check the Application tab: the row is there. Reload, then type only localStorage.getItem("studentName"). The answer is still 'Rahul' — persistence, seen with your own eyes. Editing by hand also tests odd data: type banana into a key your page expects to be JSON and see whether your try...catch earns its keep.

The Application tab also shows cookies and has a Clear site data button that empties everything an origin has stored. Chapter 69 tours the whole of DevTools.

64.9 Limits, safety rules, and cookies

Web Storage is small and simple, and that sets six limits to remember.

RuleWhat it meansWhat you do
Values become stringssetItem("age", 19) stores "19"Number(); JSON for objects
JSON.parse can throwBroken text crashes the scripttry...catch with a default
Limited spaceAbout 5 MB per origin for localStorage, and about the same for sessionStorageSmall settings and lists — never photos or files
SynchronousEach call makes the page wait until it is doneKeep values small
Not secretAny script on the page can read every keyNever passwords, tokens or sensitive personal data
Not a real databaseOne browser on one device; the user can clear itAlways a default; real records on a server

The 5 MB quota is plenty for settings and lists, nowhere near enough for images. Go over it and setItem throws a QuotaExceededError instead of saving; and since every call is synchronous, storing a huge string freezes the page while it happens.

Storage is not a safe place for secrets

Never store passwords, login tokens, bank or card details, Aadhaar or phone numbers in Web Storage. It feels private because it is "on my own computer", but every script running on the page can read every key: your own code, the analytics and advertising scripts the page includes, and — if the site has a cross-site scripting (XSS) bug — an attacker's script too. Anyone at the same computer can also read it in DevTools. Secrets belong on the server.

Good uses are harmless ones: a theme, a language, a draft, a high score. If losing it, or a stranger reading it, would do no harm, it can go in storage.

Storage can vanish, or refuse to work

Data in localStorage lives in one browser on one device: Chrome on your laptop cannot see what your phone saved, or what Edge on the same laptop saved. The user can wipe it with Clear browsing data, and a browser short of disk space may clear it for sites not visited lately. In a private (incognito) window it usually works, but everything is thrown away when the last private window closes. And when the user has blocked site data, some browsers throw an error the moment your code touches localStorage.

So treat storage as a nice extra, not a guarantee, and wrap the risky calls so that if storage fails the page still works — it just forgets:

// Save if we can; if storage is blocked or full, carry on without it
function saveSetting(key, value) {
  try {
    localStorage.setItem(key, value);
    return true;
  } catch (err) {
    console.warn("Could not save", key, "-", err.name);   // e.g. QuotaExceededError
    return false;
  }
}

// Read if we can; otherwise use the default
function readSetting(key, fallback) {
  try {
    const value = localStorage.getItem(key);
    return value === null ? fallback : value;
  } catch (err) {
    return fallback;
  }
}

const theme = readSetting("theme", "light");

Storage usually remembers, sometimes has been wiped, and occasionally refuses to work. Your page must work in all three cases: a default for "nothing saved", and try...catch round anything that could throw.

How storage differs from cookies

Before Web Storage, sites remembered things with cookies ("This site uses cookies"). A cookie is also a small named piece of text kept by the browser, but the browser sends it to the server automatically with every request to that site. That makes cookies right for things the server must see on every visit, such as "this browser is logged in as Asha", and wrong for things only the page needs.

CookieslocalStoragesessionStorage
SizeAbout 4 KB eachAbout 5 MB per originAbout 5 MB per origin
Sent to the server?Yes, with every request to that siteNever, unless your code sends itNever, unless your code sends it
ExpiresOn a date the site chooses (or, without one, usually when the browser closes)Never, until deletedWhen the tab closes

That HttpOnly row is why real login systems use cookies, not localStorage: a cookie that JavaScript cannot read is a cookie an XSS attack cannot steal. (For large amounts of data, browsers also offer a much bigger store, IndexedDB, beyond this course.)

64.10 Build it: the preference saver

The lecture's practice task pulls the chapter together. Try it for 15–20 minutes before reading the solution. The page must:

  • let a student enter a name;
  • let them choose a favourite programming language from a <select>;
  • save both in localStorage — as one object, with JSON.stringify({ name, lang });
  • show the saved information again when the page loads;
  • offer a Clear Data button.
<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  label { display: block; margin: 8px 0; }
  button { margin: 6px 6px 0 0; padding: 7px 12px; cursor: pointer; }
  #saved { background: #F0FDF4; border-left: 4px solid #138808; padding: 8px 12px; }
</style>
<h3>My Preferences</h3>
<label>Name <input id="who" type="text" placeholder="Your name"></label>
<label>Favourite language
  <select id="langBox">
    <option>JavaScript</option>
    <option>Python</option>
    <option>C++</option>
    <option>Java</option>
  </select>
</label>
<button id="save">Save</button>
<button id="clear">Clear Data</button>
<p id="saved">Nothing saved yet.</p>

<script>
  const KEY = "prefs";                    // one key holds the whole object
  const who = document.getElementById("who");
  const langBox = document.getElementById("langBox");
  const out = document.getElementById("saved");

  // Read the object back; null if nothing saved or the text is broken
  function loadPrefs() {
    try {
      return JSON.parse(localStorage.getItem(KEY));
    } catch (err) {
      return null;
    }
  }

  // Steps 4-5: show what is saved, and put it back into the form
  function showPrefs() {
    const prefs = loadPrefs();
    if (prefs) {
      out.textContent = `Saved: ${prefs.name} likes ${prefs.lang}`;
      who.value = prefs.name;
      langBox.value = prefs.lang;
    } else {
      out.textContent = "Nothing saved yet.";
    }
    console.log("In storage:", localStorage.getItem(KEY));
  }

  // Steps 1-3: the user saves
  document.getElementById("save").addEventListener("click", () => {
    const name = who.value.trim();
    const lang = langBox.value;
    if (name === "") {
      out.textContent = "Please type your name first.";
      return;
    }
    const prefs = { name, lang };         // short for { name: name, lang: lang }
    localStorage.setItem(KEY, JSON.stringify(prefs));
    showPrefs();
  });

  document.getElementById("clear").addEventListener("click", () => {
    localStorage.removeItem(KEY);
    who.value = "";
    showPrefs();
  });

  showPrefs();                            // on every page load
</script>

Run it: In storage: null. Type Riya, choose JavaScript, press Save, and the page says Saved: Riya likes JavaScript while the Console shows In storage: {"name":"Riya","lang":"JavaScript"} — one key, one JSON string, two values inside. Clear Data takes it back to null.

loadPrefs() is the safe reader from 64.6: JSON.parse(null) gives null on a first visit, and the catch gives null for broken text, so showPrefs() has only one "nothing saved" case. Putting the saved values back into the form (who.value, langBox.value) means a returning student sees their own choices. And the last line restores everything on load — steps 4 and 5.

The task's discussion question: would sessionStorage work here? Technically, yes — swap the object's name in its four places and the page behaves identically while the tab is open. But Riya would have to enter her preferences again in every new tab and after every browser restart. Preferences are meant to last, so localStorage is right: ask the "tomorrow" question from 64.3.

64.11 Common misunderstandings

✗ "getItem gives undefined for a key that was never saved."
That is what a missing object property gives.
✓ "getItem gives null for a missing key."
Test for it with === null.
✗ "setItem("age", 19) saves the number 19."
It saves the two characters "19".
✓ "Everything is stored as a string."
Number() before maths, === "true" for yes/no, JSON for objects and arrays.
✗ "I can put an object straight into storage."
It becomes the text "[object Object]" and the data is gone.
✓ "JSON.stringify on the way in, JSON.parse on the way out."
And wrap the parse in try...catch in case the text is broken.
✗ "sessionStorage is wiped when I reload the page."
A reload keeps it.
✓ "sessionStorage survives reloads and is lost when the tab closes; every tab has its own."
✗ "It is on my own computer, so a password in localStorage is safe."
Every script on the page can read it, including an attacker's injected one.
✓ "Storage is for harmless preferences only."
Secrets stay on the server; login sessions use HttpOnly cookies.
✗ "localStorage.clear() wipes the whole browser."
It cannot reach other websites at all.
✓ "clear() removes only this origin's keys, in this one storage object."
Other sites, sessionStorage and cookies are untouched.

Exam-style checks

Answer each one before opening it.

Which storage keeps its data after the browser is closed and opened again?L1
  • A. sessionStorage
  • B. localStorage
  • C. Both
  • D. Neither

Answer: B. localStorage lasts until it is deleted. sessionStorage survives a reload but ends when the tab closes, so C is the tempting wrong answer.

localStorage.getItem("missing"), for a key that was never saved, returns:L1
  • A. undefined
  • B. "" (an empty string)
  • C. false
  • D. null

Answer: D. Storage reports "no such key" with null. A is what a missing object property gives, which is why it tempts people.

JSON.stringify({ x: 1 }) gives:L2
  • A. The string '{"x":1}'
  • B. An object with a property x
  • C. The array [x, 1]
  • D. An error

Answer: A. stringify always produces text, with the property name in double quotes. Turning that text back into an object (B) is the job of JSON.parse.

What does this print? localStorage.setItem("count", 5); const c = localStorage.getItem("count"); console.log(c + 1);L3

Answer: 51. getItem returns the string "5", and "5" + 1 joins the two as text. To get 6, write Number(c) + 1.

What happens when this line runs? localStorage.saveItem("theme", "dark");L3
  • A. The theme is saved normally
  • B. A key called "saveItem" is created
  • C. TypeError: localStorage.saveItem is not a function
  • D. It returns null and nothing else happens

Answer: C. There is no saveItem method, so the name gives undefined, and calling undefined throws a TypeError. The method is setItem: set, not save.

What does this print, and how do you fix it? localStorage.setItem("user", JSON.stringify({ name: "Riya" })); const u = localStorage.getItem("user"); console.log(u.name);L3

Answer: undefined. u is the text {"name":"Riya"}, and a string has no name property. Fix: const u = JSON.parse(localStorage.getItem("user")); — then u.name prints Riya.

Which statement about sessionStorage is true?L2
  • A. It is shared by all tabs of the same origin
  • B. It is cleared every time the page reloads
  • C. It survives a reload but is cleared when the tab is closed
  • D. It is sent to the server with every request

Answer: C. A describes localStorage, D describes cookies, and B is the most common misbelief — a reload keeps the session.

A page at https://lpu.in saved a key in localStorage. Which of these pages can read it?L3
  • A. http://lpu.in
  • B. https://ums.lpu.in
  • C. https://lpu.in:8443
  • D. https://lpu.in/exam/results.html

Answer: D. Only the path differs, and the path is not part of the origin. A changes the protocol, B the host and C the port, so each is a different origin with separate storage.

After localStorage.setItem("student", { name: "Rahul" }), what does localStorage.getItem("student") return?L2
  • A. "[object Object]"
  • B. { name: "Rahul" }
  • C. "Rahul"
  • D. null

Answer: A. The object is turned into text the default way, which loses everything; it needed JSON.stringify first. D is wrong because a value was saved — just a useless one.

Why must a password or login token never be kept in localStorage?L2
  • A. Storage is too small to hold one
  • B. Any script running on the page can read it
  • C. It is deleted on every reload
  • D. It is shared with every other website

Answer: B. Your own scripts, third-party scripts and any script injected through an XSS bug can all read every key. A and C are false; D is false because storage is per origin — the danger is scripts on your own page.

What does this print? localStorage.setItem("seen", false); if (localStorage.getItem("seen")) { console.log("yes"); } else { console.log("no"); }L3

Answer: yes. The stored value is the five-letter text "false", and any non-empty string counts as true. The correct test is localStorage.getItem("seen") === "true", which would make it print no.

What does localStorage.clear() delete?L2
  • A. Every website's saved data in the browser
  • B. Only the key that was saved last
  • C. This site's localStorage and its cookies
  • D. Every localStorage key of this origin, and nothing else

Answer: D. It cannot reach other origins (A), it removes all keys rather than one (B), and it does not touch cookies or sessionStorage (C). To delete one key, use removeItem.

Quick revision

Key takeaways

  1. A reload wipes every variable. Web Storage keeps small pieces of text in the user's browser, separately for each origin (protocol + host + port; not the path).
  2. localStorage: shared by all tabs of the origin, survives a browser restart. sessionStorage: one tab, survives reloads, gone when the tab closes.
  3. getItem gives null for a missing key; setItem on an existing key replaces it; clear() deletes only this origin's keys.
  4. Everything is stored as a string: "5" + 1 is "51", and "false" counts as true. Use Number() and === "true".
  5. Objects and arrays: JSON.stringify in, JSON.parse out; || [] for a default, try...catch for broken text.
  6. Persistence has two halves: save when the user acts, and restore when the page loads.
  7. About 5 MB, synchronous, readable by every script on the page, liable to vanish: never secrets, always a default.
  8. Cookies are tiny, travel to the server with every request and can be hidden from JavaScript (HttpOnly); Web Storage stays in the browser.
