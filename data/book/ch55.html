DOM Fundamentals

So far your JavaScript has talked only to the Console. This chapter connects it to the page. When the browser reads your HTML it builds a living model of the page in memory, the Document Object Model, and every change a script makes to a page — a new heading, a red error message, a score that updates — is a change to that model. Learn its shape once and the next five chapters fall into place.

About 35 minutes · Course outcome CO5

Before you start — one-line reminders

  • Elements nest: the outer one is the parent, the inner one the child, and the browser turns the whole page into a tree (Chapter 4).
  • An id names exactly one element on a page; it must be unique (Chapter 5).
  • A <script> element holds JavaScript, and console.log() prints values to the Console (Chapter 41).
  • An object is a bundle of named properties read with a dot, such as student.name; a method is a property that holds a function (Chapter 51).

By the end of this chapter you can

  • Explain what the DOM is, how the browser builds it from HTML, and why it is a tree.
  • Start from document, read document.title, tagName, id and className, and make a first change with textContent.
  • Name the four main kinds of node and identify each with nodeType and nodeName.
  • Walk the tree with parentElement, children, firstElementChild and the sibling properties, and explain why childNodes holds extra text nodes.
  • Say what window is and how it differs from document.
  • Explain why the live DOM can differ from the source code, and see the difference in DevTools.
  • Diagnose the null error from a script that runs too early, and fix it three ways.

55.1 From text to a tree

When you open a page, the server sends your browser text: a long string of characters with angle brackets in it (Chapter 1). Text is a good way to store and send a page, and a poor way to work on one. To find "the second paragraph" inside a string, a program would have to count angle brackets. So the browser does something cleverer. It reads the text once, top to bottom, and parses it into a model of the page in memory: one object for every element and every piece of text, each linked to the objects around it. That model is the Document Object Model, the DOM.

Your slides define it in one sentence: the DOM represents an HTML document as a tree of objects that JavaScript can access and modify. Take the name one word at a time:

  • Document — the web page itself, as written in its HTML.
  • Object — every part of the page becomes a JavaScript object, with properties you read with a dot, exactly like the objects of Chapter 51.
  • Model — a working copy that stands for the page. The screen is drawn from the model, so when the model changes, the screen changes to match.

Here is the slides' example. This HTML:

<html>
<head></head>
<body>
  <h1>Hello Students</h1>
  <p>Welcome to JavaScript.</p>
</body>
</html>

becomes the tree in Figure 55.1.

Each box in the tree is a node. At the top sits document, which stands for the whole page. Below it is the html element; below that its two children, head and body; below body come the h1 and the p; and below each of those hangs the text it holds. The tree is drawn upside down, root at the top, like the family tree of Chapter 4.

Why a tree, and not a list? Because HTML nests. Every element sits inside exactly one other element (the html element sits directly under document), and "every item has exactly one parent" is what makes a tree. You have walked this tree before without knowing it: the CSS selector ul li (Chapter 23) means "an li somewhere below a ul". Now JavaScript walks it too, and once it is in, it can change the text, the style, the attributes and the structure of any element.

The browser reads your HTML once and builds a tree of objects from it. JavaScript never edits your HTML file. It edits that tree, and the browser redraws the screen from the tree.

Picture this. An architect draws the plan of a house on paper; a building crew reads it and puts up a real house of bricks. The plan is your HTML file; the house is the DOM. Three things follow. Once the house stands, renovation is done on the house, not on the plan: JavaScript changes the DOM, and the file on the server is untouched. If the plan has a small mistake, say a doorway with no frame drawn, an experienced crew fits the frame anyway, so the house does not always match the plan line for line. And a painter who arrives while the crew is still on the foundations cannot paint the bedroom, because its walls do not exist yet. Section 55.8 is about that painter.

55.2 document: your way into the tree

JavaScript reaches the tree through one ready-made object called document. You never create it. The browser makes it for each page and leaves it where every script on the page can use it by name. Every journey into the tree starts there:

CodeGives you
documentThe whole page: the root of the tree
document.documentElementThe <html> element
document.headThe <head> element
document.bodyThe <body> element
document.titleThe text of the <title>, which the browser shows on the tab
document.getElementById("greeting")The one element with id="greeting", or null if there is none

getElementById is the only finder this chapter needs. Give it an id as a string, without the # that CSS puts in front, and it hands back that element's object. An id must be unique on the page, so it returns one element, never a list, and null when no element has that id. Chapter 56 adds querySelector and its relatives, which find elements by any CSS selector.

Once you hold an element's object, its properties describe it. Four are enough for now:

  • tagName — the element's tag in capital letters: "H1", "P", "LI". For HTML elements the DOM reports tag names in upper case, however you typed them.
  • id — the value of its id attribute.
  • className — the value of its class attribute as one string, such as "title big" for two classes. The property was named className, not class, because class is a reserved word in JavaScript.
  • textContent — all the text inside the element.

And here is the moment that makes this chapter worth reading. These properties are not only for reading. Assign to one and the page on the screen changes at once.

<title>My first DOM page</title>
<style>
  body { font-family: system-ui, sans-serif; padding: 10px 16px; color: #3C4A60; }
  h1 { color: #0B2545; margin: 0 0 6px; }
</style>
<h1 id="greeting" class="title big">Hello Students</h1>
<p id="msg">Welcome to JavaScript.</p>
<script>
  // document is the root; three shortcuts lead to the three big elements
  console.log("1.", document, document.documentElement, document.head, document.body);

  // reading
  console.log("2. Title:", document.title);
  const heading = document.getElementById("greeting");   // find ONE element by its id
  console.log("3. Found:", heading);
  console.log("4. tagName:", heading.tagName, "| id:", heading.id, "| className:", heading.className);
  console.log("5. Text:", heading.textContent);

  // writing: the page changes at once
  heading.textContent = "Hello, CSE326!";
  document.getElementById("msg").textContent = "This sentence was written by JavaScript.";
  document.title = "DOM Lab";
  console.log("6. Title now:", document.title);
  console.log("7. Text now:", heading.textContent);

  // asking for an id nobody has
  console.log("8. No such id:", document.getElementById("marks"));
</script>

Line 1 shows the four objects the shortcuts lead to; document prints as #document, the name of its kind of node (next section). Lines 2 to 5 only read. Then three assignments change the heading and the paragraph on the screen, with no reload and nothing sent to any server: the browser changed objects in its tree and redrew. The title changed too (line 6), but a preview frame has no tab to show it on; on a real site the tab would now say DOM Lab. Line 8 is the polite failure: no element has the id marks, so the answer is null, not an error.

Quick check: the page has <p id="msg">. What does document.getElementById("#msg") return?

null. The # belongs to CSS selectors. getElementById wants the bare id, "msg", so it looks for an element whose id is literally #msg and finds none.

55.3 Four kinds of node

Every box in the tree is a node, but not every node is an element. Four kinds matter, and every node object reports its kind through two properties: nodeType, a number, and nodeName, a string.

KindMade fromnodeTypenodeName
DocumentThe whole page (one per page)9"#document"
ElementEach tag, such as <p id="intro">1The tag in capitals: "P"
TextEach run of text between tags3"#text"
AttributeEach attribute on a tag, such as id="intro"2The attribute's name: "id"

Element nodes are the branches of the tree. Text nodes are the leaves: a piece of text cannot contain anything, so a text node never has children. Text inside a <b> belongs to the b element, not to the paragraph around it.

Attribute nodes are the odd ones out. They belong to an element but are not its children; they are stored with the element, not inside it. You will rarely touch them directly, because properties such as id and className read them for you, and Chapter 56 adds getAttribute and setAttribute. HTML comments become nodes too (type 8, "#comment").

Tags become element nodes. The words between tags become text nodes. Attributes become extra information stored on their element. The document node sits above everything.

<style>
  body { font-family: system-ui, sans-serif; padding: 10px 16px; color: #3C4A60; }
</style>
<p id="intro" class="lead">Marks are out of <b>100</b>.</p>
<script>
  const p = document.getElementById("intro");

  console.log("1. document:", document.nodeType, document.nodeName);
  console.log("2. the p element:", p.nodeType, p.nodeName);
  console.log("3. p's child nodes:", p.childNodes);

  const words = p.firstChild;                     // the text before <b>
  console.log("4. first child:", words.nodeType, words.nodeName);
  console.log("5. it holds:", words.textContent + "|");   // the | shows where the text ends
  console.log("6. the b element:", p.children[0].nodeName, "- its text:", p.children[0].textContent);
  console.log("7. all text inside p:", p.textContent);

  const idAttr = p.attributes[0];                 // attributes are stored on the element
  console.log("8. attributes:", p.attributes.length, "| first:", idAttr.name, "=", idAttr.value, "| nodeType", idAttr.nodeType);
</script>

2. the p element: 1 P
3. p's child nodes: NodeList(3) [#text, <b>, #text]
4. first child: 3 #text
5. it holds: Marks are out of |
6. the b element: B - its text: 100
7. all text inside p: Marks are out of 100.
8. attributes: 2 | first: id = intro | nodeType 2

Read line 3 slowly: the paragraph has three child nodes, not one. The text before <b> is one text node, the b element is the second, and the full stop after it is a third. The "100" is not among them; it is a child of the b. Line 5 adds a | to show where the first text node ends, and you can see that it includes the space before 100. Line 7 shows that textContent collects the text of every node below an element, at every depth. Line 8 finds two attributes on the element, and line 3 confirms that neither appeared among its children.

55.4 Parents, children and siblings

Nodes are linked like the members of a family, and the DOM uses family words for the links. An element's parent is the node directly above it. Its children are the nodes directly below it. Its siblings are the other children of the same parent, the nodes beside it. Six properties let you step from any element to its relatives:

PropertyGivesWhen there is nobody there
parentElementThe element directly abovenull (in a page, only for <html>, whose parent is the document, not an element)
childrenAll the child elements, as a listAn empty list, length 0
firstElementChildThe first child elementnull
lastElementChildThe last child elementnull
previousElementSiblingThe element just before it, with the same parentnull
nextElementSiblingThe element just after it, with the same parentnull

children gives an HTMLCollection: not an array, but close enough for now. It has a length, its items are read with [0], [1] and so on, and a for...of loop (Chapter 52) visits each one. Figure 55.2 shows all six steps, starting from Rahul's list item.

<style>

  h2 { margin: 0; color: #0B2545; }

<ul>
  <li>Asha</li>
  <li id="rahul">Rahul</li>
  <li>Meera</li>
</ul>
<script>

  console.log("1. Start at:", rahul.textContent);

  // up and sideways
  console.log("2. parentElement:", rahul.parentElement);
  console.log("3. previousElementSibling:", rahul.previousElementSibling.textContent);
  console.log("4. nextElementSibling:", rahul.nextElementSibling.textContent);
  console.log("5. after Meera:", rahul.nextElementSibling.nextElementSibling);

  // down from the list
  const list = rahul.parentElement;
  console.log("6. children:", list.children);
  console.log("7. how many:", list.children.length, "| children[0]:", list.children[0].textContent);
  console.log("8. first:", list.firstElementChild.textContent, "| last:", list.lastElementChild.textContent);

  // steps chain, read left to right
  console.log("9. the list's sibling above:", list.previousElementSibling);
  console.log("10. two levels up:", rahul.parentElement.parentElement);

  // visit every child, then change one

Every step returns another element object, so steps chain, read from left to right as in Chapter 51: rahul.parentElement.parentElement is "Rahul's parent's parent", the body. When a relative does not exist the property gives null (line 5), never an error. The error comes one step later, if you ask null for something: rahul.nextElementSibling.nextElementSibling.textContent stops the script with a TypeError, because the second step already gave null. The script's last line shows that a step can lead to a change: the first item on the page now reads Asha (rank 1).

Up is parentElement. Down is children, or firstElementChild and lastElementChild for the two ends. Sideways is previousElementSibling and nextElementSibling. Each one gives null when there is nobody there.

Quick check: in the same list, what is list.lastElementChild.previousElementSibling.textContent?

"Rahul". Read it left to right: the list's last element child is Meera's item; the element just before Meera is Rahul's item; its text is "Rahul".

55.5 The invisible text nodes

Every property in that table has Element in its name, and the word is doing real work. Each one has an older twin without it: parentNode, childNodes, firstChild, lastChild, previousSibling and nextSibling. The twins count every node, text nodes included. And a page has more text nodes than you would guess.

Look at how you normally write a list: each <li> on its own line, indented. Between one </li> and the next <li> there is a line break and a few spaces. Those characters are whitespace, and the parser keeps them. They make no difference to what you see, because the browser squeezes runs of whitespace together when it draws text, but each run becomes a text node in the tree. So a list of three items written on separate lines has seven child nodes: four runs of whitespace with the three items between them.

<style>
  body { font-family: system-ui, sans-serif; padding: 10px 16px; color: #3C4A60; }
</style>
<ul id="list">
  <li>Asha</li>
  <li>Rahul</li>
  <li>Meera</li>
</ul>
<ul id="tight"><li>Asha</li><li>Rahul</li><li>Meera</li></ul>
<script>
  const list = document.getElementById("list");
  console.log("1. childNodes:", list.childNodes);
  console.log("2. children:", list.children);
  console.log("3. firstChild:", list.firstChild, "| firstElementChild:", list.firstElementChild);

  const gap = list.firstChild;                     // the whitespace before Asha
  console.log("4. That text node holds", gap.textContent.length, "characters:", JSON.stringify(gap.textContent));

  const asha = list.firstElementChild;
  console.log("5. nextSibling:", asha.nextSibling, "| nextElementSibling:", asha.nextElementSibling.textContent);

  const tight = document.getElementById("tight");
  console.log("6. Tight list:", tight.childNodes.length, "childNodes,", tight.children.length, "children");
</script>
1. childNodes: NodeList(7) [#text, <li>, #text, <li>, #text, <li>, #text]
2. children: HTMLCollection(3) [<li>, <li>, <li>]
3. firstChild: #text | firstElementChild: <li>
4. That text node holds 3 characters: "\n  "
5. nextSibling: #text | nextElementSibling: Rahul
6. Tight list: 3 childNodes, 3 children

Line 1 is the list with its gaps: text, item, text, item, text, item, text. (childNodes gives a NodeList, a list-like object much like the HTMLCollection; Chapter 56 explains how the two differ.) children, on line 2, skips the gaps. Line 4 opens the first gap: three characters, which JSON.stringify (Chapter 51) spells out as \n, the line break, followed by the two spaces of indentation. Line 5 is the trap that catches everyone: the nextSibling of Asha's item is not Rahul's item but the whitespace between them. The tight list on line 6 has no gaps between its tags, so both counts agree — but squashing your HTML is not the fix. Use the right property.

Any kind of node (text and comments too)Counts elements only — use these
parentNodeparentElement
childNodeschildren
firstChild / lastChildfirstElementChild / lastElementChild
previousSibling / nextSiblingpreviousElementSibling / nextElementSibling

When you want elements, and you almost always do, use the names with Element in them, plus children. The shorter twins include the whitespace between your tags, so they land on the gaps instead of the elements.

Exam tip. To count childNodes, count the gaps as well as the elements. When n elements sit on their own lines inside a parent, there are n + 1 runs of whitespace, so childNodes.length is 2n + 1 while children.length is n. A comment is a node too: it shows up in childNodes but never in children.
Quick check: <div><p>A</p> <p>B</p></div> is written on one line, with a single space between the two paragraphs. How long are the div's childNodes and children?

3 and 2. The childNodes are the first p, a text node holding the single space, and the second p. The children are just the two paragraphs.

55.6 window and document

document has a bigger neighbour. window is the object for the browser tab, or the frame, that the page is showing in, and document is one of its properties: window.document is the very same object as document.

window is also the global object. The things you have used without ever declaring them, such as alert, console and setTimeout (Chapter 54), are properties of window. That is why alert("Hi") works: when JavaScript cannot find a name among your variables, it looks on window, so it runs window.alert("Hi"). Plain document is found the same way.

console.log(typeof window);                  // object
console.log(window.document === document);   // true  - one object, two ways to reach it
console.log(window.alert === alert);         // true  - alert lives on window
console.log(window.innerWidth);              // e.g. 1280 - the tab's visible width in pixels
console.log(document.body.tagName);          // BODY  - the page itself belongs to document

window is the tab. document is the page inside the tab. The DOM tree hangs from document.

55.7 The DOM is not your source code

Go back to the house and its plan. Two things make the house differ from the plan, and you should expect both.

The browser repairs your HTML. HTML parsers are forgiving. When the text breaks a rule, the browser does not refuse the page; it follows repair rules in the HTML standard and builds the tree the author most probably meant. Three repairs you will meet:

  • A table written without <tbody> gets one, because the HTML parser puts every table row it reads inside a table section (Chapter 19).
  • A paragraph left open is closed when the next <p> begins, because a paragraph cannot contain another paragraph.
  • A page with no <html>, <head> or <body> tags still gets all three. Most runnable examples in this book rely on that.

JavaScript changes the tree. After Example 1 ran, the heading in the DOM said "Hello, CSE326!" while the source still said "Hello Students".

The example below shows both. It uses one new property, outerHTML, only for reading: it writes an element and everything inside it back out as HTML text, built from the tree as it is right now. It is the quickest way to see what the browser actually built.

<style>
  body { font-family: system-ui, sans-serif; padding: 10px 16px; color: #3C4A60; }
  td { border: 1px solid #94A3B8; padding: 4px 10px; }
</style>
<table id="marks"><tr><td>Asha</td><td>82</td></tr></table>
<p id="one">First paragraph, never closed
<p id="two">Second paragraph</p>
<script>
  // the source has no tbody; the tree does
  const table = document.getElementById("marks");
  console.log("1. Table's first child:", table.firstElementChild.tagName);
  console.log("2. As the browser built it:", table.outerHTML);

  // the open p was closed for you, so #two is NOT inside #one
  const two = document.getElementById("two");
  console.log("3. Parent of #two:", two.parentElement.tagName);

  // no html, head or body tags were written, yet all three exist
  console.log("4.", document.documentElement.tagName, document.head.tagName, document.body.tagName);

  // JavaScript changes the tree, never the source text above
  const one = document.getElementById("one");
  one.textContent = "This text was changed by JavaScript.";
  console.log("5. #one now:", one.outerHTML);
</script>
1. Table's first child: TBODY
2. As the browser built it: <table id="marks"><tbody><tr><td>Asha</td><td>82</td></tr></tbody></table>
3. Parent of #two: BODY
4. HTML HEAD BODY
5. #one now: <p id="one">This text was changed by JavaScript.</p>

Compare line 2 with the source: a <tbody> has appeared that nobody typed. Line 3 shows the second paragraph is a child of the body, a sibling of the first, not nested inside it. Line 4 names three elements the example never wrote. Line 5 shows the tree after JavaScript's change, while the source in the box above still says First paragraph, never closed.

Seeing the live DOM

Your browser lets you look at both versions. View Source (Ctrl+U) shows the text exactly as the server sent it. The Elements panel of the DevTools (press F12, or right-click any part of a page and choose Inspect) shows the live tree: the repairs, and every change JavaScript makes, the moment it makes it. Chapter 69 tours DevTools properly.

Try this on any real website. Open DevTools, click the Console tab, type document.title = "Hello from me" and press Enter. The text on the tab changes. Now reload: it is back to normal. You changed the tree in your own browser's memory. The website's file was never touched, and the reload simply built a fresh tree from it.

Quick check: a script changes a heading's text, and then you press Ctrl+U. Which text does View Source show?

The original text. View Source shows the file as the server sent it. The change exists only in the DOM, so you would see it in the Elements panel, and it disappears on reload.

55.8 When the script runs before the elements exist

Now the painter. The browser builds the tree as it reads, from top to bottom, and it runs each ordinary <script> the moment it reaches it, pausing the reading until the script has finished (Chapter 74 shows the pause). So a script can see only the part of the tree built above it. A script in the <head> runs before a single element of the body exists.

In that situation getElementById finds nothing and returns null, the value that means "nothing here" (Chapter 43). Asking null for a property is an error, so the very next line stops the script with TypeError: Cannot set properties of null (setting 'textContent'), or Cannot read properties of null if the line was reading. It is the most common error in beginner JavaScript, and often the id is spelled perfectly. The script simply looked too early.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>Too early</title>
  <style>
    body { font-family: system-ui, sans-serif; padding: 10px 16px; color: #3C4A60; }
  </style>
  <script>
    // A: runs in the head - the body has not been read yet
    const early = document.getElementById("status");
    console.log("A. Head script found:", early);

    // C: the same search, but only once the whole page has been read
    document.addEventListener("DOMContentLoaded", () => {
      const later = document.getElementById("status");
      console.log("C. DOMContentLoaded code found:", later);
      later.textContent = "Found by the DOMContentLoaded code (C), which ran last.";
    });

    // the real-life crash: delete the two slashes on the next line, then Run again
    // early.textContent = "Hello";
  </script>
</head>
<body>
  <h1>Results</h1>
  <p id="status">Waiting for JavaScript...</p>
  <script>
    // B: at the end of the body - everything above already exists
    const found = document.getElementById("status");
    console.log("B. End-of-body script found:", found);
    found.textContent = "Found by the end-of-body script (B).";
  </script>
</body>
</html>
A. Head script found: null
B. End-of-body script found: <p id="status">
C. DOMContentLoaded code found: <p id="status">

The lines arrive in the order the browser reached the code. A runs while the head is being read, and finds nothing. B runs when the parser reaches the end of the body, and finds the paragraph above it. C is written before B but runs last, because it was handed to the browser to call once the whole page had been read; that is why the page ends up showing C's sentence. Now delete the two slashes in front of early.textContent = "Hello"; and Run again. A red line joins the Console: Uncaught TypeError: Cannot set properties of null (setting 'textContent') (line 22). B and C still work: the listener was set up before the crash, and B is a separate script.

Three fixes

1. Put the script at the end of the body, just before </body>. Everything above it has been built when it runs. It is simple, and it works both for code written between the tags and for a file loaded with src.

2. Load an external file with defer, in the head:

<!-- index.html -->
<head>
  <script src="js/app.js" defer></script>
</head>

// js/app.js - when this runs, the whole tree already exists
document.getElementById("status").textContent = "Found by a deferred script.";

defer means "start downloading this file now, but run it only after the whole HTML has been read". Chapters 73 and 74 make it the standard for real projects.

defer needs src. On a script written between its tags, <script defer> ... </script>, the browser ignores defer completely and runs the code at once, too early. Adding the word to an inline head script fixes nothing.

3. Wait for DOMContentLoaded, as part C did. An event is something that happens which code can respond to, and DOMContentLoaded happens once, when the browser has finished reading the HTML and building the tree. document.addEventListener("DOMContentLoaded", () => { ... }) hands the browser a function, a callback (Chapter 54), to call when that happens. It works anywhere, even inline in the head. The window's load event is different: it also waits for every image and stylesheet to download, which finding elements does not need. Chapter 57 covers addEventListener fully.

A script can only find what the browser has already built. Put the script after the elements, defer the file, or wait for DOMContentLoaded, and the elements exist when the script looks for them.

Exam tip. A null from getElementById has two usual causes: the script ran too early, or the id is wrong — a typo, a # inside the string, or different capital letters, since ids are case-sensitive. A question that shows a head script and an element in the body is testing the first.

55.9 Common misunderstandings

✗ "The DOM is my HTML file."
Changes made through the DOM never reach the file, and View Source never shows them.
✓ "The DOM is a tree of objects in memory, built from the file."
A reload throws the tree away and builds a fresh one from the file.
✗ "childNodes and children are the same list."
A list of three items on separate lines has seven childNodes.
✓ "children holds child elements only; childNodes holds every child node."
The extra ones are text nodes of whitespace, plus any comments.
✗ "firstChild gives the first element."
It often gives the whitespace before it.
✓ "firstElementChild gives the first element."
The same goes for every twin: use the names with Element in them.
✗ "getElementById gave null, so the id must be misspelt."
It may be spelled perfectly.
✓ "First ask whether the script ran before the element was built."
Then check the spelling, the capitals and any stray #.
✗ "Adding defer to any script tag makes it wait."
An inline script ignores it.
✓ "defer works only with src."
For inline code, use the end of the body or DOMContentLoaded.
✗ "window and document are the same thing."
One holds the other.
✓ "window is the tab and the global object; document is the page inside it."
window.document === document is true.

Exam-style checks

Answer each one before opening it. For the "what does this print?" questions, draw the tree first, and remember the whitespace.

What does DOM stand for?L1
  • A. Data Object Map
  • B. Document Object Model
  • C. Dynamic Output Method
  • D. Document Order Markup

Answer: B. Document Object Model: the page (document) turned into objects, arranged as a working model of the page that JavaScript can read and change.

Which statement best describes the DOM?L2
  • A. The HTML file as it is stored on the server
  • B. A stylesheet language that controls layout
  • C. A tree of objects the browser builds in memory from the HTML, which JavaScript can read and change
  • D. A list of the scripts on a page, in the order they run

Answer: C. The browser parses the HTML into a tree of node objects. A is the tempting wrong answer: the file is only the plan the tree is built from, and changing the DOM never changes the file.

What does this print?
<ul id="u">
  <li>A</li>
  <li>B</li>
</ul>
<script>
  const u = document.getElementById("u");
  console.log(u.childNodes.length, u.children.length);
</script>L3

Answer: 5 2. Each item sits on its own line, so there are three runs of whitespace: before A, between A and B, and after B. Those three text nodes plus the two li elements make 5 childNodes; children counts only the 2 elements.

Which property gives the first child that is an element, skipping any whitespace text node?L1
  • A. firstElementChild
  • B. firstChild
  • C. childNodes[0]
  • D. parentNode

Answer: A. firstChild and childNodes[0] count every node, so on an indented list both give the whitespace text node before the first element. parentNode goes up, not down.

What happens when this page loads?
<head>
  <script>
    document.getElementById("msg").textContent = "Hi";
  </script>
</head>
<body>
  <p id="msg">Hello</p>
</body>L3
  • A. The paragraph shows Hi
  • B. The paragraph shows Hello, and the Console shows TypeError: Cannot set properties of null (setting 'textContent')
  • C. The browser waits until the paragraph exists, then shows Hi
  • D. Nothing at all: no text and no error

Answer: B. The head script runs before the body has been read, so getElementById returns null, and setting a property on null is a TypeError. An ordinary script never waits for later elements, so C is wrong; the paragraph is built afterwards with its original text.

Which change does NOT fix the page in the previous question?L3
  • A. Moving the script to just before </body>
  • B. Moving the code into js/app.js and loading it in the head with <script src="js/app.js" defer></script>
  • C. Wrapping the line in document.addEventListener("DOMContentLoaded", () => { ... });
  • D. Writing <script defer> on the same inline script

Answer: D. defer works only on a script with src; on an inline script it is ignored and the code still runs too early. A, B and C each make the code run after the paragraph has been built.

What is the nodeType of a text node?L1
  • A. 1
  • B. 2
  • C. 9
  • D. 3

Answer: D. Elements are 1, attributes 2, text nodes 3 and the document 9. A text node's nodeName is "#text".

The source is <table id="t"><tr><td>1</td></tr></table>. What does console.log(document.getElementById("t").firstElementChild.tagName); print?L3
  • A. TBODY
  • B. TR
  • C. TD
  • D. undefined

Answer: A. The parser puts every table row inside a table section, so it adds a tbody nobody typed. The live DOM is not the source. B is what you would answer from reading the source alone.

Which statement about window and document is true?L2
  • A. They are two names for the same object
  • B. alert and setTimeout are properties of document
  • C. document is a property of window, so window.document === document is true
  • D. Every element on the page has a window of its own

Answer: C. window stands for the tab and is the global object; the page, document, is one of its properties. alert and setTimeout belong to window, not to document.

What does this print?
<h1 id="t" class="big red">Hi</h1>
<script>
  const h = document.getElementById("t");
  console.log(h.tagName, h.id, h.className);
</script>L2

Answer: H1 t big red. tagName is the tag in capitals, id is the id's value, and className is the whole class attribute as one string, both classes included.

A script has just changed a heading's text. Where can you see the new text?L2
  • A. In the DevTools Elements panel
  • B. In View Source (Ctrl+U)
  • C. In the HTML file on the server
  • D. Nowhere until the page is reloaded

Answer: A. The Elements panel shows the live DOM. View Source and the server's file both show the original text, and a reload throws the change away rather than revealing it.

What does this print?
<ol>
  <li>Asha</li>
  <li id="m">Meera</li>
</ol>
<script>
  const m = document.getElementById("m");
  console.log(m.previousElementSibling.textContent, m.nextElementSibling, m.parentElement.tagName);
</script>L3

Answer: Asha null OL. The element before Meera's item is Asha's. Meera's item is the last child, so there is no next element sibling: null, not an error. Its parent is the ol, reported in capitals.

Quick revision

Key takeaways

  1. The browser parses your HTML into the DOM, a tree of node objects in memory. JavaScript changes the tree, the screen follows, and the file never changes.
  2. document is the way in: documentElement, head, body, title, and getElementById("id"), which gives null when nothing matches.
  3. Node types: element 1, attribute 2 (stored on an element, never among its children), text 3, document 9. Tag names are reported in capitals.
  4. Walk with parentElement, children, firstElementChild, lastElementChild, previousElementSibling and nextElementSibling. Each gives null where there is nobody.
  5. The twins without Element in their names count text nodes too, including the whitespace between tags: three items on separate lines make seven childNodes.
  6. window is the tab and the global object; document is window.document, the page inside it.
  7. The live DOM can differ from the source: the browser's repairs (such as tbody) and JavaScript's changes. View Source shows the text; the DevTools Elements panel shows the tree.
  8. A script finds only what has been built above it. Fix early scripts with the end of the body, an external file with defer, or DOMContentLoaded.
