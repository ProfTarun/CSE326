Error Handling

Every program meets a bad day: the Wi-Fi drops, the server is down, a user types "eighty" into a marks box. A program without error handling freezes on a spinner. A program with it tells the user calmly what happened and what to do next, and keeps working. This chapter teaches you to write the second kind.

About 38 minutes · Course outcome CO6

Before you start — one-line reminders

  • Bugs come in three kinds — syntax, runtime and logical — and an error message names the type, describes the problem and points to a file and line (Chapter 68).
  • fetch(url) returns a promise of a Response; inside an async function, await waits for it (Chapter 65).
  • JSON.parse(text) turns JSON text into an object, and JSON insists on double-quoted keys (Chapter 65).
  • A form's submit listener calls event.preventDefault() to stop the page reloading (Chapter 57).

By the end of this chapter you can

  • Name SyntaxError, ReferenceError, TypeError and RangeError, and write a line that causes each.
  • Trace exactly which lines run in a try...catch...finally, with and without an error.
  • Read an error's name, message and stack, and reject bad input with throw new Error(...).
  • Say what try...catch cannot catch, and where the try must go instead.
  • Handle all three ways a fetch can fail: no answer, an HTTP error status, a broken JSON body.
  • Show the user a plain message while logging full detail for the developer, and never swallow an error.

70.1 Things will go wrong

Up to now almost every program in this book has assumed a good day. Real programs get no such promise, and some failures cannot be prevented at all:

  • The network drops. A student on hostel Wi-Fi steps into a lift halfway through loading a page.
  • The server fails. It is overloaded on result day, or down for maintenance.
  • The user types something unexpected. Letters in a number box, a blank email, 50 seats when the limit is 5.
  • Data arrives damaged. A saved setting, or a server's answer, that is not the JSON you expected.

What you can decide, in advance, is what your program does when they happen. Error handling lets an application detect unexpected situations and respond in a controlled way — instead of crashing or failing silently. A program that does it well fails gracefully: something went wrong, and the user still knows where they stand.

On the left the user cannot tell whether to wait, refresh or give up; the only clue is a red line in a console they will never open. On the right the same failure produces one calm sentence and a Retry button. Nothing about the network was fixed: the second page simply expected that the request might fail.

Picture this. A train is cancelled. At a badly run station the departure board quietly goes blank, and passengers wait on the platform for an hour, wondering. At a well-run station an announcement comes at once: "The 09:40 to Jalandhar is cancelled. Passengers may take the 10:15 from platform 3." Meanwhile the station master writes the technical reason — signal failure near Ludhiana, 09:12 — in the log book for the engineers. The cancellation could not be prevented; the response was planned. That is error handling: a plain announcement for the passengers (your users), a detailed log entry for the engineers (you), and never a blank board.

What "unhandled" really means

When JavaScript reaches a line it cannot carry out — reading the name of a student who is null, say — it creates an error and throws it. A thrown error is called an exception. If no code catches it, it is an uncaught exception: JavaScript abandons the piece of code it was running — the rest of that script, or the rest of that click handler — and prints a red Uncaught ... line in the console.

An unhandled error does not break the computer, or even the whole page: other buttons may still work. It stops the one piece of code that was running, halfway through. If its next line was "hide the spinner", the spinner spins forever — the left-hand screen in Figure 70.1.

70.2 The kinds of error you will meet

Chapter 68 sorted bugs into syntax, runtime and logical. Error handling adds a fourth kind that comes from outside — the network and the server. Each is dealt with by a different tool:

The built-in error types

Every error JavaScript throws carries a name saying what kind of problem it was. Four names cover nearly everything; here is a line that causes each, with Chrome's message beside it:

// SyntaxError: the text breaks the grammar rules
let x = "hi;                     // in your own code: the whole script refuses to run
JSON.parse("{invalid}");         // in data: thrown while the program runs

// ReferenceError: a name that does not exist
let total = 90;
console.log(totl);               // totl is not defined        (you meant total)

// TypeError: the right name, but the wrong kind of value
const student = null;
console.log(student.name);       // Cannot read properties of null (reading 'name')
const pi = 3.14;
pi = 3;                          // Assignment to constant variable.
"Asha".toUpperCas();             // "Asha".toUpperCas is not a function

// RangeError: a number outside the allowed range
(5).toFixed(200);                // toFixed() digits argument must be between 0 and 100
new Array(-1);                   // Invalid array length

Rarer types exist too (URIError, EvalError, AggregateError), and every one is a particular kind of the general Error.

70.3 try, catch and finally

JavaScript's tool for planning a response is the try...catch statement: risky code in try, plan B in catch, and an optional finally for anything that must happen either way:

try {
  // code that might throw an exception
} catch (error) {
  // runs ONLY if something in try threw; error describes what went wrong
} finally {
  // optional: ALWAYS runs, error or no error
}
  • try — the risky code: parsing text, talking to a server.
  • catch (error) — runs only if try throws. The variable (you choose the name; error, err, e) receives the error; error.name and error.message describe it.
  • finally — optional clean-up that always runs: hide the spinner, re-enable the button.

The two paths in Figure 70.2 give four rules that answer every "what does this print?" question:

  1. If nothing in try throws, catch is skipped completely.
  2. If any line in try throws, JavaScript jumps straight to catch. The remaining lines of try do not run — not later, not ever.
  3. finally runs in both cases.
  4. After that, the program continues normally with the next statement, instead of crashing.

try means "attempt this". catch means "if it went wrong, do this instead". finally means "whatever happened, finish with this". The moment something goes wrong inside try, the rest of try is abandoned.

Here is the example from the Unit IV slides. Its try block throws an error on purpose, so you can watch control move:

try {
  // Code that may throw an error
  throw new Error("An error");
} catch (error) {
  // Code to handle the error
  console.error(error.message);    // prints: An error
} finally {
  // Code that will run regardless of whether there was an error
  console.log("Cleanup code");     // prints: Cleanup code
}

The try block creates an Error object with the message "An error" and throws it; control jumps to catch, whose error parameter now holds that object; finally runs last. Real danger usually comes from something like JSON.parse, given text that arrived while the program was running — from a server, or from localStorage:

try {
  const result = JSON.parse("{invalid}");
  console.log(result);                   // never runs
} catch (error) {
  console.error("Invalid JSON data");    // this runs instead
}

JSON.parse('{"name": "Ravi"}');          // valid JSON, for comparison: { name: "Ravi" }

Why it fails: JSON insists that keys and strings wear double quotes, {"key": "value"}; here the parser meets the letter i where it expected ". Why catch runs: JSON.parse throws a SyntaxError object, and catch receives it. This is a runtime exception even though its name says "syntax": your code is fine, the data broke JSON's grammar. console.log(result) never runs. Run the version below and read the numbered console lines:

<p id="out"></p>
<script>
  function readStudent(text) {
    console.log("1. about to parse:", text);
    try {
      const student = JSON.parse(text);
      console.log("2. parsed! The name is", student.name);
      return student.name;
    } catch (error) {
      console.error("3. Invalid JSON data -", error.name);
      return "(unknown)";
    } finally {
      console.log("4. finally runs for", text);
    }

  const second = readStudent("{invalid}");         // keys need double quotes

For Ravi you see lines 1, 2 and 4; for {invalid} you see 1, 3 and 4. And line 4 ran even though try or catch had already said return: JavaScript holds on to the returned value, runs finally, and only then hands the value back. Line 5 proves the program carried on.

Exam tip. For "what does this print?": run try until the first throw; skip the rest; run catch, then finally, then carry on below. If nothing throws, skip catch.
Quick check: if nothing inside try throws, does catch run? Does finally?

catch does not run at all — it is skipped completely. finally does run: it runs whether or not anything was thrown.

Two grammar notes: a try needs a catch, a finally, or both (a lone try is a syntax error); and if you do not need the error object you may write just catch { ... }.

70.4 The error object: name, message and stack

catch (error) receives whatever was thrown — almost always an Error object, a small bundle of facts about what went wrong. Three properties matter:

PropertyHoldsExample
error.nameThe kind of error"TypeError"
error.messageA human-readable description"Cannot read properties of null (reading 'name')"
error.stackWhere it happened, and the chain of calls that led thereSeveral lines, shown below

The stack is a snapshot of the call stack at the moment of the error. Printed, it looks something like this (the file names and numbers depend on your page):

TypeError: Cannot read properties of null (reading 'name')
    at showName (app.js:12:23)
    at loadPage (app.js:20:3)
    at app.js:24:1

Read it from the top: the error happened inside showName (line 12, column 23 of app.js), which was called by loadPage at line 20, which was called by the top-level code at line 24. It is the same trail the Sources panel shows as the Call Stack (Chapter 69). Strictly, stack is not yet part of the ECMAScript standard, but every major browser provides it.

Two habits follow. When you log an error, pass the whole object — console.error("Load failed:", error) — so DevTools shows the name, the message and the stack. And to react differently to different kinds of error, test the kind with instanceof:

catch (error) {
  if (error instanceof SyntaxError) {
    console.warn("The saved data was damaged:", error.message);
  } else {
    console.error("Something unexpected:", error);
  }
}

70.5 throw: raising an error on purpose

So far every error was thrown by JavaScript itself. You can throw your own with the throw statement whenever a function is handed input it cannot sensibly work with. The example from the Unit 6 slides:

function calculateArea(width, height) {
  if (width <= 0 || height <= 0) {
    throw new Error("Dimensions must be positive");
  }
  return width * height;
}

try {
  console.log(calculateArea(5, 4));      // 20
} catch (error) {
  console.error(error.message);
} finally {
  console.log("Calculation finished");   // Calculation finished
}
  • throw stops the function on the spot and hands the error to the nearest catch; the return never runs.
  • new Error(message) creates the error object carrying your readable message.
  • finally runs after success and after failure.

Why throw, instead of quietly returning 0 or -1? A meaningless number lets the mistake travel: an "area" of −20 would be printed, stored, perhaps used to price floor tiles. throw refuses loudly, at the exact place the rule was broken.

Quick check: in the code above, what would print for calculateArea(-5, 4)?

Dimensions must be positive, then Calculation finished. The if is true because −5 ≤ 0, so throw runs before any area is returned; catch prints the message and finally still runs. No number is printed at all. Check yourself with the example below.

The error climbs to the nearest catch

The catch need not be in the same function as the throw. When an error is thrown with no try around it, JavaScript abandons the current function and climbs back up the call stack, one caller at a time, until it reaches one that made its call inside a try; if it reaches the top, the error is uncaught. This climbing is called propagation. It lets you validate deep inside a small helper and decide what to tell the user in one place, higher up:

function readSeats(text) {
  const seats = Number(text);
  if (!Number.isInteger(seats)) throw new TypeError("Seats must be a whole number");
  if (seats < 1 || seats > 5) throw new RangeError("Choose 1 to 5 seats");
  return seats;
}

function book(text) {
  const seats = readSeats(text);         // no try here, so an error passes straight through
  return `Booked ${seats} seat(s)`;
}

try {
  console.log(book("3"));                // Booked 3 seat(s)
  console.log(book("9"));                // readSeats throws; book is abandoned too
  console.log("never printed");
} catch (error) {
  console.log(error.name, "-", error.message);   // RangeError - Choose 1 to 5 seats
}

You may also throw the built-in types when they fit, as readSeats does.

throw is your function saying "I refuse". It stops at once, and the refusal travels back up through every function that was waiting for an answer, until one of them is inside a try. That one's catch deals with it.

Throw Error objects, not strings. throw "Seats must be 1 to 5"; is legal, but the catch then receives a bare string: no name, no stack, and error.message is undefined. Always write throw new Error("..."), or one of its kinds.

Your own kinds of error

An error kind of your own lets a catch tell "the user typed something wrong" apart from "the program has a bug". You make one by extending Error:

class ValidationError extends Error {
  constructor(message) {
    super(message);                  // let Error store the message (and the stack)
    this.name = "ValidationError";   // our own name tag
  }
}

Read it as: "A ValidationError is an Error, plus its own name." Classes in general are beyond this course — you only need to recognise this six-line pattern. Its pay-off is in the catch:

function readMarks(text) {
  const marks = Number(text);
  if (text.trim() === "") throw new ValidationError("Please enter the marks.");
  if (Number.isNaN(marks)) throw new ValidationError("Marks must be a number, like 78.");
  if (marks < 0 || marks > 100) throw new ValidationError("Marks must be from 0 to 100.");
  return marks;
}

try {
  const marks = readMarks(marksInput.value);
  showStatus(`Saved: ${marks} out of 100.`, "success");
} catch (error) {
  if (error instanceof ValidationError) {
    showStatus(error.message, "error");            // written for the user: safe to show
  } else {
    console.error("Unexpected problem:", error);   // a bug: full detail for the developer
    showStatus("Something went wrong. Please try again.", "error");
  }
}

Messages you wrote for the user can be shown; messages JavaScript wrote for programmers should not be (section 70.8).

70.6 What try...catch cannot catch

try...catch can only catch an error thrown while its own lines are running. Three kinds escape it:

1. Syntax errors in your own script

Before a browser runs a script, it parses the whole of it. If the grammar is broken anywhere, nothing in that script runs — including the try:

try {
  let x = "hi;                  // the closing quote is missing
} catch (error) {
  console.log("never runs");
}
// Console: Uncaught SyntaxError: Invalid or unexpected token
// ...and not one line of this script ran.

The cure is a correction, not a catch (Chapter 68). Compare JSON.parse("{invalid}"): that SyntaxError can be caught, because the broken grammar was in the data, discovered while your valid code was running.

2. Errors in code that runs later

A callback you hand to setTimeout, addEventListener or a promise's then runs later — after the timer, after the click — and by then the try around the line that scheduled it has long finished:

<p>Read the console panel: one line at once, two more a moment later.</p>
<script>
  // 1. try around code that runs LATER
  try {
    setTimeout(() => {
      const student = null;
      console.log(student.name);        // throws - but 0.3 seconds from now
    }, 300);
    console.log("1. try finished. Nothing has gone wrong... yet");
  } catch (error) {
    console.log("This line never prints:", error.name);
  }

  // 2. the fix: put try...catch INSIDE the code that runs later
  setTimeout(() => {
    try {
      const student = null;
      console.log(student.name);
    } catch (error) {
      console.log("2. caught inside the callback:", error.name);
    }
  }, 600);
</script>

The console shows line 1 at once. A third of a second later the first timer's error arrives as an Uncaught TypeError — the catch beside it never saw it. Then the second timer, which carries its own try...catch, reports line 2 calmly. Event handlers are the same: wrapping addEventListener(...) in try protects nothing.

A try only watches while its own lines are running. Code you have scheduled for later — a timer, a click handler — runs after that try has finished. So the try...catch has to go inside the later code.

3. A promise that is not awaited

fetch hands back a promise at once and fails later, so it has exactly the same problem:

// WRONG: try finishes long before the failure arrives
try {
  fetch("https://example.invalid/data");          // no await
} catch (error) {
  console.log("never runs");
}
// Console: Uncaught (in promise) TypeError: Failed to fetch

// RIGHT: await makes the failure arrive INSIDE the try
async function load() {
  try {
    const response = await fetch("https://example.invalid/data");
  } catch (error) {
    console.log("caught:", error.name);           // caught: TypeError
  }
}
load();

await pauses the function until the promise settles. If it rejects, await throws the failure right there, inside the try, where catch can see it. (Names ending in .invalid are reserved and never exist, so that fetch always fails.) The other way, from Chapter 65, is to attach .catch(...) to the promise itself. And, as you know, a logical error throws nothing, so there is nothing to catch.

Quick check: you wrapped button.addEventListener("click", handler) in try...catch. When the button is clicked, the handler crashes. Does your catch run?

No. The try finished the moment the listener was attached, long before any click. The handler runs later, outside it, so the error is uncaught. Put the try...catch inside the handler.

70.7 Error handling with fetch

Loading data from a server is where failure is normal. Here is the pattern from the Unit 6 slides, written against a real test API:

async function loadData() {
  try {
    const response = await fetch("https://jsonplaceholder.typicode.com/users");
    if (!response.ok) {
      throw new Error(`HTTP error: ${response.status}`);
    }
    const users = await response.json();
    console.log(users);                     // (10) [{...}, {...}, {...}, ...]
  } catch (error) {
    console.error("Unable to load users:", error.message);
  }
}

loadData();

Three different things can go wrong on the way, and this one catch handles all three:

What went wrongWhat fetch doesHow it reaches catch
HTTP error — 404, 500Resolves normally! A server answered, so you get a Response with ok falseYour if (!response.ok) throws
Network failure — offline, DNS, CORSRejects: no answer arrivedawait fetch(...) throws TypeError: Failed to fetch
Bad JSON body — an HTML page or broken textResolves; the problem shows when you read the bodyawait response.json() throws a SyntaxError
The most common beginner bug. Assuming that fetch rejects on a 404 or a 500. It does not. fetch rejects only when no HTTP response arrives at all. A 404 is a response — the server answered "I don't have that" — so if you do not check response.ok yourself, the error page is treated as data. (Exam favourite.)

response.ok is true when the status code is from 200 to 299, and false otherwise; response.status holds the number itself (200 OK, 201 Created, 404 Not Found, 500 Internal Server Error).

fetch only complains when it hears nothing back. A server saying "not found" or "I crashed" still counts as hearing back. So reading the status is your job: if (!response.ok) throw ....

The example below visits a pretend server four times — a good day, a wrong address, no internet, a broken JSON body — so it runs offline: Blob URLs for the good and broken JSON (as in Chapter 65), a hand-made new Response(...) with status 404, and a Blob address that has been switched off, which fails just as an unplugged cable would.

  body { font-family: system-ui, sans-serif; padding: 12px; color: #0B2545; font-size: 14px; }

<script>
  // ---- a pretend server, so this runs with no internet ----
  const users = [{ name: "Asha" }, { name: "Rahul" }, { name: "Meera" }];
  const goodUrl = URL.createObjectURL(
    new Blob([JSON.stringify(users)], { type: "application/json" }));
  const brokenUrl = URL.createObjectURL(
    new Blob(["{ name: Asha "], { type: "application/json" }));    // not valid JSON
  const deadUrl = URL.createObjectURL(new Blob(["gone"]));
  URL.revokeObjectURL(deadUrl);         // nobody answers here any more: like being offline

  const visits = [
    { label: "Good day",      go: () => fetch(goodUrl) },
    { label: "Wrong address", go: async () => new Response("Not found", { status: 404 }) },
    { label: "Offline",       go: () => fetch(deadUrl) },
    { label: "Broken JSON",   go: () => fetch(brokenUrl) },
  ];

  // ---- the pattern you will really write ----
  const log = document.querySelector("#log");
  function note(text, cls) {
    const li = document.createElement("li");
    li.textContent = text;
    li.className = cls;
    log.append(li);
  }

    try {
      const response = await go();                    // 1. did any answer arrive?
      console.log(label, "- fetch resolved. status:", response.status, "ok:", response.ok);
      if (!response.ok) {                             // 2. was it a happy answer?
        throw new Error(`HTTP error: ${response.status}`);
      }
      const data = await response.json();             // 3. is the body real JSON?
      console.log(label, "- success:", data.length, "users");
      note(`${label}: loaded ${data.length} users`, "good");
    } catch (error) {
      console.error(label, "- caught", error.name + ":", error.message);
      note(`${label}: caught ${error.name}`, "bad");
    }
  }

  async function main() {
    for (const v of visits) {
      await visit(v.label, v.go);
    }
  }
  main();
</script>

The wrong-address visit prints fetch resolved. status: 404 ok: false before it is caught — the 404 itself was no error. Only the offline visit has no "fetch resolved" line, because only there did no answer arrive. Three failures, three error names (Error, TypeError, SyntaxError), one catch. The message wording depends on your browser; the names do not.

Quick check: the server answers 500 and your code has no if (!response.ok) line. Does catch run because of the 500?

No — fetch resolves, because an answer arrived. If the 500 page is HTML, response.json() then throws a misleading SyntaxError; if it is JSON, your code treats an error report as data.

The same thing with then and catch

With promise chains (Chapter 65) the shape is the same: a throw inside any then skips the remaining thens and lands in .catch.

fetch("https://jsonplaceholder.typicode.com/users")
  .then((response) => {
    if (!response.ok) throw new Error(`HTTP error: ${response.status}`);
    return response.json();
  })
  .then((users) => console.log(users))
  .catch((error) => console.error("Unable to load users:", error.message));

When the server never answers

One more way to fail: just silence, while the user watches "Loading…". fetch has no time-limit option of its own, but you can give it one with a signal. When the time is up the promise rejects with an error named "TimeoutError", and your catch handles it like any other:

const response = await fetch(url, { signal: AbortSignal.timeout(8000) });   // give up after 8 s

The developer's side: logging well

  • Log the whole error object, with a label: console.error("Registration failed:", error), not console.log("error").
  • Use the right level: console.error for failures, console.warn for problems you recovered from.
  • Never log secrets such as passwords or tokens.
  • Find out about the errors nobody caught. The console exists only on the user's machine, so real sites add last-resort listeners that report uncaught errors back:
window.addEventListener("error", (event) => {
  console.error("Uncaught error:", event.error);
  // a real site would also send this to its own server, so the developers find out
});

window.addEventListener("unhandledrejection", (event) => {
  console.error("Unhandled promise rejection:", event.reason);
});

These listeners do not handle anything — the failed code has already stopped — but a failure on a student's phone no longer goes unnoticed. They are also how the console panel under every example in this book learns about uncaught errors.

70.9 Never swallow an error

One kind of error handling is worse than none: catching an error and doing nothing with it, called swallowing the error.

// BAD: the error is caught and thrown away
function readSettings(text) {
  try {
    return JSON.parse(text);
  } catch (error) {
    // nothing here - the problem silently vanishes
  }
}

const settings = readSettings("{theme: dark}");   // damaged: keys need double quotes
console.log(settings);          // undefined - no warning, no clue
console.log(settings.theme);    // TypeError: Cannot read properties of undefined (reading 'theme')

The developer finally sees a TypeError on the last line, blaming undefined. The real cause — damaged JSON inside readSettings — has been erased. With no try at all, the console would at least have pointed at the right line. The cure is to say what went wrong, then recover:

// GOOD: report it, then carry on with a safe default
function readSettings(text) {
  try {
    return JSON.parse(text);
  } catch (error) {
    console.warn("Saved settings were damaged; using defaults.", error);
    return { theme: "light", fontSize: 16 };
  }
}

Five habits keep your error handling honest:

  1. Catch only where you can do something useful — show a message, use a safe default, offer a retry.
  2. If you cannot handle it here, let it travel. Do not catch it, or pass it on with throw error; (re-throwing) so a catch higher up can deal with it.
  3. Keep try blocks small. A giant try hides which line failed and catches the bugs you needed to see.
  4. Do not use try...catch to hide bugs. When a value is expected to be missing sometimes, check for it: if (user) ..., or user?.name, which gives undefined instead of throwing (Chapter 51).
  5. Always leave the user in a clear state — success or a helpful error, never stuck on "Loading…" (finally helps).

Re-throwing: the function handles the one problem it understands and passes every other one up:

function loadSettings() {
  try {
    return JSON.parse(localStorage.getItem("settings"));
  } catch (error) {
    if (error instanceof SyntaxError) {
      console.warn("Settings damaged, using defaults:", error.message);
      return { theme: "light" };       // we know how to handle this one
    }
    throw error;                        // anything else is not ours: pass it on
  }
}

70.10 The error-handling challenge

The slides end with a fifteen-minute challenge: this loader works on a good day — make it survive a bad one:

// students.js (broken)
const list = document.querySelector("#studentList");

async function loadStudents() {
  const response = await fetch("https://jsonplaceholder.typicode.com/users");
  const users = await response.json();
  list.innerHTML = users.map((u) => `<li>${u.name}</li>`).join("");
}

loadStudents();

On a good day it shows ten names. Offline, fetch rejects, nothing catches it, and the page shows an empty list with no explanation. With a mistyped URL the 404 is never noticed, so the code stumbles later — in response.json() or users.map — with an error that points away from the real cause.

#Your task
1Add try...catch
2Check the HTTP status (response.ok)
3Show "Loading students…" first
4Show a friendly error message on failure
5Render the names on success

Expected outcomes: success → ten names (Leanne Graham, Ervin Howell, …) and 10 students loaded.; the URL changed to /userz → Couldn't load students (HTTP 404).; offline → Check your connection and try again. Bonus: API data in innerHTML is risky — a name containing HTML would be treated as HTML. Build each <li> with createElement and textContent (Chapter 56).

Walk through it. The loading message is set before the request (task 3). One catch handles HTTP errors, network failures and bad JSON alike (tasks 1, 2 and 4). Two touches go beyond the slides: the button is disabled while loading and given back in finally, and catch clears any old list so a failure never sits beside stale names. 70.11 Common misunderstandings

✗ "fetch rejects when the server returns 404 or 500."
It resolves: a 404 is an answer.
✓ "I check response.ok and throw for a bad status myself."
Then one catch handles all three failures.
✗ "After an error, the rest of the try block still runs."
The first throw abandons it for good.
✓ "First throw → catch → finally → carry on below."
finally is never skipped.
✗ "A try around setTimeout or addEventListener protects the callback."
The callback runs after that try has finished.
✓ "The try...catch goes inside the callback."
And a promise must be awaited inside the try, or given a .catch.
✗ "Wrap the whole program in try...catch and the bugs go away."
They go quiet, not away.
✓ "try...catch is for failures I expect at runtime; bugs get fixed."
Keep try blocks small.
✗ "Showing error.message to the user is the honest thing to do."
Built-in messages are for programmers and vary by browser.
✓ "Users get plain words and a next step; developers get the error object."
Two audiences, two messages.
✗ "An empty catch block is harmless."
It swallows the error and erases the real cause.
✓ "Every catch handles, logs, or re-throws."
If you cannot handle it, throw error;.

Exam-style checks

Answer each one before opening it.

Which block runs whether or not an error was thrown?L1
  • A. try
  • B. catch
  • C. throw
  • D. finally

Answer: D. finally always runs, after success and after failure, which makes it the place for clean-up. catch runs only when something was thrown; throw is a statement, not a block.

What does this code print, in order? try { console.log("A"); JSON.parse("{bad}"); console.log("B"); } catch (e) { console.log("C"); } finally { console.log("D"); } console.log("E");L3

Answer: A, C, D, E. JSON.parse("{bad}") throws a SyntaxError, so the "B" line is skipped for good; catch prints "C", finally prints "D", and the program carries on to "E".

You type consle.log("hi"); by mistake. Which error is thrown?L2
  • A. SyntaxError
  • B. TypeError
  • C. ReferenceError
  • D. RangeError

Answer: C. consle is not defined: the name does not exist. The grammar is fine, so not a SyntaxError; a TypeError would need consle to exist with the wrong kind of value.

Which error does const student = null; console.log(student.name); throw?L2
  • A. TypeError
  • B. ReferenceError
  • C. SyntaxError
  • D. RangeError

Answer: A. Cannot read properties of null (reading 'name'). The name student exists (so not a ReferenceError), but its value, null, is the wrong kind of value to read a property from.

A fetch request reaches the server, which answers 404 Not Found. What happens?L2
  • A. fetch rejects with TypeError: Failed to fetch
  • B. response.json() throws immediately, before you can check anything
  • C. fetch resolves with a Response whose ok is false and status is 404
  • D. The browser shows an alert box to the user

Answer: C. A 404 is an answer, so fetch resolves. It rejects (option A) only when no answer arrives — offline, DNS failure, CORS. Turning the 404 into an error is your if (!response.ok)'s job.

Why can't try { let x = "hi; } catch (e) { } catch its own error?L3
  • A. A catch only works when a finally block follows it
  • B. The browser parses the whole script first; with a syntax error nothing in it runs, including the try
  • C. SyntaxErrors can never be caught by any code, anywhere
  • D. let is not allowed inside a try block

Answer: B. The script is rejected before a single line runs. Option C is the tempting one, and it is wrong: JSON.parse("{invalid}") throws a SyntaxError at runtime, and that one can be caught.

What appears in the console? try { setTimeout(() => { null.name; }, 0); console.log("scheduled"); } catch (e) { console.log("caught", e.name); }L3

Answer: "scheduled", then an Uncaught TypeError. The try only schedules the callback, so nothing fails inside it and catch is skipped. The callback runs after the try has finished, so its TypeError is uncaught and "caught" never prints. The fix is a try...catch inside the callback.

Loading a student's courses fails because the network dropped. Which message should the page show?L2
  • A. TypeError: Failed to fetch
  • B. Error 0x1F: request aborted by user agent
  • C. Nothing on the page; console.error is enough
  • D. We couldn't load your courses. Check your connection and try again.

Answer: D. It says what happened and what to do next, in plain words. A and B are developer messages; C leaves the user staring at a spinner.

What does this print? function check(age) { if (age < 0) throw new RangeError("Age cannot be negative"); return age; } try { console.log(check(20)); console.log(check(-1)); console.log(check(30)); } catch (e) { console.log(e.name + ": " + e.message); }L3

Answer: 20, then RangeError: Age cannot be negative. check(-1) throws, so the rest of try is abandoned and check(30) is never called. The error climbed out of check to the nearest catch.

What is wrong with try { saveMarks(data); } catch (e) { }?L2
  • A. Nothing: it is the safest way to stop crashes
  • B. It swallows the error: the save can fail silently, the user believes it worked, and the developer never finds out
  • C. A catch block must always be followed by finally
  • D. It turns every error into a SyntaxError

Answer: B. An empty catch erases the evidence. Log the error and tell the user the save failed, or re-throw it with throw e;.

Which property of an error object holds its human-readable description?L1
  • A. message
  • B. name
  • C. stack
  • D. type

Answer: A. name is the kind (such as "TypeError"), stack is where it happened and the chain of calls that led there, and there is no standard type property.

Which version catches a fetch that fails because the user is offline?L3
  • A. try { fetch(url); } catch (e) { show(e); }
  • B. async function load() { try { await fetch(url); } catch (e) { show(e); } }
  • C. fetch(url); try { } catch (e) { show(e); }
  • D. try { setTimeout(() => fetch(url), 0); } catch (e) { show(e); }

Answer: B. await makes the rejection arrive inside the try. In A and D the try has finished before the failure arrives (Uncaught (in promise)); in C the try is empty.

Quick revision

Key takeaways

  1. Error handling means detecting failures and responding in a controlled way — never a stuck spinner, never silent failure.
  2. Four common types: SyntaxError (broken grammar), ReferenceError (no such name), TypeError (wrong kind of value, e.g. null.name), RangeError (number out of range).
  3. The first throw in try jumps to catch (error), skipping the rest of try; finally always runs; then the program carries on.
  4. An error has name, message and stack. throw new Error("...") refuses bad input; the error climbs to the nearest catch. A custom class extends Error and sets name.
  5. try...catch cannot catch syntax errors in its own script, errors in callbacks that run later, or un-awaited promises.
  6. fetch rejects only when no answer arrives. Check response.ok; response.json() may throw a SyntaxError. One try...catch around the awaits handles all three.
  7. Two audiences: console.error("Label:", error) for the developer; a plain message with a next step, in a role="status" region, for the user.
  8. Never swallow an error: handle, log, or re-throw, and always leave the user in a success or error state.
