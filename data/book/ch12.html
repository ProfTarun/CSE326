HTML Best Practices

Everything in Unit 1 works even when it is written badly, because browsers forgive. Best practices are the habits that make HTML work everywhere: on other browsers, on phones, in screen readers, in search engines, and for the next person who has to edit it. This chapter collects them, explains the reason behind each, and walks through a code review of a typical first-year page.

About 13 minutes · Course outcome CO1 · Closes Unit 1

By the end of this chapter you can

  • Write HTML in the standard style: lowercase, quoted, closed, indented, commented.
  • Keep structure, presentation and behaviour in separate files.
  • Choose semantic elements over generic ones and the right element for the job.
  • Recognise and replace obsolete tags and layout hacks.
  • Validate, test on a phone and avoid the deployment traps.

12.1 Write it in the standard style

HTML is case-insensitive and tolerant, so a great deal of sloppy markup renders. Every professional style guide, and this course, asks for the same conventions, because they make mistakes visible and code readable.

RuleDoNot
Lowercase tag and attribute names<p class="intro"><P CLASS="intro">
Quote every attribute value<div class="my box"><div class=my box> (splits into two attributes)
Close every paired element<p>text</p><p>text and hoping
Never close void elements<br>, <img ...></br>, </img>
Nest properly<p><b>x</b></p><p><b>x</p></b>
Indent children consistently (2 spaces)structure visible at a glanceeverything at the margin
Comment the sections<!-- registration form -->no comments, or secrets in comments
Start every document the same waydoctype, html lang, charset, viewport, titlea bare <html><body>

A student who writes <P CLASS=Intro>Text</P> has broken two of these at once: names should be lowercase and values quoted. Nothing about capital letters in class names, ids on paragraphs, or wrapping paragraphs in divs is a rule.

12.2 Separate structure, presentation and behaviour

Chapter 1 introduced separation of concerns; here is how it looks in files. HTML holds the content, one external stylesheet holds all the CSS, and one or more script files hold the JavaScript.

  • Use an external stylesheet, linked with <link rel="stylesheet" href="style.css"> in the head. One file styles every page and the browser caches it. Inline style attributes and internal <style> blocks are for quick experiments, not projects, and obsolete presentational tags such as <font> are never the answer.
  • Put scripts just before </body> so the content is parsed and displayed before they run (Chapter 4).
  • Keep presentation out of the markup. No <br><br> for spacing, no <table> for layout, no <h4> chosen for its size, no <center>. If the reason for a tag is "it looks right", it belongs in CSS.

12.3 Use the correct element

The single most valuable habit: choose an element for what the content is, not for how you want it to look.

  • Going somewhere? <a href>. Performing an action? <button>.
  • A navigation menu is <nav> around a <ul> of links; a copyright line is <footer>; a blog post is <article>; a section with a heading is <section>. <div> is for grouping with no meaning (Chapters 5 and 13).
  • A heading is <h2>, never <div class="h2">. Style the heading as small as you like in CSS; the fake one loses the document outline, so assistive technology's heading navigation no longer finds it, while the real one can still be styled any way at all.
  • Importance is <strong>; a term is <i>; deleted text is <del>; a data grid is <table>; a set of steps is <ol>.

Semantic HTML is not an extra layer for accessibility experts. It is the cheapest SEO, the cheapest accessibility and the most maintainable code you can write, and it costs nothing at render time: <header> and <div class="header"> look identical.

12.4 Accessibility and performance basics you owe every page

  • alt on every image (empty for decorative ones); a <label> for every form control; a title on every iframe; lang on <html>; a logical heading outline; link text that describes the destination. Chapter 15 takes these further.
  • Images compressed and in modern formats, with width and height to stop layout jumps and loading="lazy" below the fold; scripts deferred; as few separate files as sensible; HTTPS.
  • The viewport meta tag, and a real test on a phone: not a shrunk browser window, a phone.

12.6 Before you publish

  1. Validate at validator.w3.org. HTML fails silently; the validator is the only thing that tells you about unclosed tags, duplicate ids and bad nesting (Chapter 3).
  2. Test on a phone and in DevTools. Press F12: the Elements panel shows the tree the browser actually built (compare it with what you wrote), the Console shows errors, and the Network tab shows every request and which ones failed.
  3. Check every path and file name. The server is case-sensitive; use lowercase names with no spaces, and relative paths that match the folder layout exactly. The file the server shows by default must be called index.html.
  4. Keep it in version control. A GitHub repository is your backup, your history and, with GitHub Pages, your free host (Unit 6).

12.7 Worked example: a code review

Here is a page as a student might first write it. Every line has something to fix. Find them before reading the corrected version.

<HTML>
<BODY>
<CENTER><FONT SIZE=6>My Profile</FONT></CENTER>
<TABLE WIDTH=800><TR><TD>
<IMG SRC=Me.JPG>
<BR><BR>
<B>About me</B><BR>
I study at LPU.<BR><BR>
<A>My portfolio</A> - <A HREF=page2.html>click here</A>
</TD></TR></TABLE>
</BODY>
</HTML>

Problems: no doctype (quirks mode), no lang, no head, no charset, no viewport, no title; uppercase tags and unquoted values; obsolete center and font used for a heading; a table used for layout with a fixed width; an image with no alt and a capitalised file name that will break on the server; br br for spacing; a fake heading made from b; a link with no href; and "click here" link text. The corrected page:

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Asha Kumar | Profile</title>
  <link rel="stylesheet" href="style.css">
</head>
<body>
  <header>
    <h1>My Profile</h1>
  </header>
  <main>
    <img src="images/me.jpg" alt="Asha Kumar at the campus library" width="200" height="200">
    <section>
      <h2>About me</h2>
      <p>I study at LPU.</p>
      <p>See <a href="portfolio.html">my portfolio</a> and <a href="page2.html">my second project</a>.</p>
    </section>
  </main>
</body>
</html>

Exam-style checks

How should tags and attributes be written?L1
  • A. UPPERCASE
  • B. lowercase
  • C. Mixed case
  • D. It does not matter

Answer: B. HTML tolerates uppercase, but every style guide requires lowercase.

Which is the recommended way to attach CSS to a real project?L2
  • A. Inline style attributes
  • B. An internal <style> block
  • C. An external stylesheet linked with <link>
  • D. Using <font>

Answer: C. One file styles every page and is cached.

Which is BAD practice in modern HTML?L2
  • A. Using semantic elements
  • B. Quoting attribute values
  • C. Using <table> for page layout
  • D. Adding alt to images

Answer: C. Tables are for data; layout is CSS's job.

Why should tables not be used to lay out an entire web page today?L3

Answer: it breaks accessibility (screen readers announce a data table) and responsiveness (fixed grids do not reflow on phones); tables are for tabular data. Tables can contain images, are still supported and are not inherently slower.

A developer styles a section heading as <div class="h2">Results</div>. What is lost?L3
  • A. The document outline, so heading navigation by assistive technology no longer finds it
  • B. The ability to apply any CSS to the text
  • C. The ability to place the text inside a <section>
  • D. The text is no longer rendered by the browser

Answer: A. A real h2 can be styled identically and keeps the outline.

A student writes <P CLASS=Intro>Text</P>. Which best practices does this violate?L3

Answer: tag and attribute names should be lowercase and attribute values should be quoted.

Which tool checks your HTML for structural errors, and why does it matter that HTML fails silently?L2

Answer: the W3C Validator at validator.w3.org. Because browsers give no error message, unclosed tags, duplicate ids and bad nesting survive unnoticed until they break on another device; the validator is what reveals them.

A developer places <script> just before </body>. Why?L3

Answer: so the page content is parsed and displayed before the script runs, and the elements the script needs already exist.

Which habit best prepares HTML for a responsive layout before any CSS is written?L3
  • A. Hardcoding width="800" on every container
  • B. Nesting layout tables three levels deep
  • C. Using a logical source order and flexible, scalable media
  • D. Setting fixed pixel heights on all sections

Answer: C. Structure first; fixed widths and layout tables fight every screen size.

Quick revision

Key takeaways

  1. Style: lowercase names, quoted values, closed elements, correct nesting, indentation, comments, the standard head.
  2. Separation: content in HTML, all CSS in an external stylesheet via link, all JS in external files loaded before </body>.
  3. Semantics: the element for what the content is; a is for going somewhere, button for doing something; a heading is a real h-element, never a styled div.
  4. Owed to every page: alt, labels, iframe titles, lang, viewport, compressed images with width/height, lazy loading.
  5. Obsolete: font, center, big, tt, strike, marquee, frames; layout tables; br br spacing. Replace with CSS and semantic elements.
  6. Before publishing: validate, test on a phone with DevTools, check lowercase relative paths and index.html, keep it in GitHub.
