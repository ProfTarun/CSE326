78.1 What GitHub Copilot is — and what it is not

Every chapter so far taught you to write code yourself. GitHub Copilot is an AI-assisted coding tool, made by GitHub, that writes some of it with you. It runs inside your editor (VS Code, Visual Studio, JetBrains editors and others) and on GitHub.com. It suggests code as you type, explains unfamiliar code, helps refactor functions and helps investigate errors. GitHub calls it an AI pair programmer.

Copilot is built on large language models trained on natural-language text and on source code from publicly available sources, including public repositories on GitHub. When you pause while typing, Copilot sends the context it can see as a prompt to the model, which predicts the code most likely to come next; the editor shows it as grey "ghost text". In chat, your question joins the prompt.

Copilot does not understand your project the way you do. It makes a very good guess at what usually comes next. A good guess is often right, but not always, and Copilot cannot tell you which guesses are wrong. Finding out is your job.

FeatureWhat you see
Inline suggestionsGrey text completing the line or function. Tab accepts, Esc dismisses.
ChatA panel for plain-English requests: explain this, why does it fail, write tests.
Inline chatCtrl+I in VS Code: a chat box inside the file, about the selected lines.
Multi-file editsProposed changes across several files, for you to review, keep or undo.
On GitHub.comHelp with pull requests and repository questions, depending on your plan.

Features vary with your editor, plan and organisation's settings. At the time of writing there is a free plan with a monthly limit, and verified students get a paid plan free through GitHub Education. In VS Code, set it up from the Copilot icon and sign in to GitHub; check GitHub's current documentation before a lab.

Your comments and names are instructions

// Format a rupee amount with two decimals, e.g. 525 -> "₹525.00"
function formatRupees(amount) {
  return `₹${amount.toFixed(2)}`;     // <- this line appears as grey ghost text
}

You typed the comment and the first line; the grey line is the suggestion. It is probably right because the comment states the goal and gives an example. Call the function doStuff(x) with no comment and you get a guess. Chapter 73's naming habits steer an AI too.

Quick check: Copilot shows you a suggestion. Has it checked that the code works?

No. It predicted the code from patterns. It has not run it, cannot see your browser, and knows only the requirements in the prompt.

78.2 Why use it, and the review-first workflow

AI help is at its best on the boring and the unfamiliar. The deck lists seven uses:

UseAn example request
Repetitive coding"Write handlers for these five buttons, like the first one." (boilerplate)
Understanding code"Explain this function line by line."
Generating test cases"List the edge cases I should test."
Refactoring"Suggest smaller functions and clearer names; keep the behaviour."
Explaining errors"Explain TypeError: Cannot read properties of undefined in plain words."
Documentation"Draft a README for this project."
Exploring alternatives"Show two other ways to write this loop and compare them."
The non-negotiable part. AI-generated code can contain mistakes, insecure patterns and outdated APIs, and wrong code arrives as confidently formatted as right code. Review and test everything.
Picture this. A wedding caterer hires a kitchen helper who has read ten thousand recipe books. Ask for gravy for two hundred guests and the pot is on in a minute. But nobody told the helper that the bride's grandmother cannot eat garlic, so in it goes — most gravy has garlic. The head cook keeps the fast helper, but states the rules first, tastes every dish before it leaves, and answers for any guest who falls ill. Copilot is the helper. You are the head cook.
Key idea. Copilot is a fast junior teammate who has read a lot of code but has never seen your requirements. Use its speed; keep your judgement.

For a beginner the valuable requests explain ("why is this a TypeError?"); the risky ones write. Code you accept but cannot explain teaches you nothing, you cannot debug it, and the exams have no Copilot in them.

Ask Copilot to explain far more often than to write. When it writes something, make sure you could have written it yourself, just more slowly.

The review-first workflow

The deck's six-step loop gives the AI exactly one step: (1) you write a clear prompt; (2) Copilot suggests a draft; (3) you review every line for logic, security and style; (4) you test normal, empty and invalid input in a browser; (5) you fix — edit, re-prompt or reject; (6) you commit the verified change, as its author.

A suggestion that fails review goes round again; you own every line that ships. If you can't explain a line, don't commit it.

Exam tip. After a suggestion "passes your one test", the answer is never "commit it" or "ask Copilot if it is right". It is: review the code and test the edge cases.
Quick check: which of the six steps does Copilot actually do?

Only step 2, the suggestion. Everything else — and the responsibility for the live site — is yours.

78.3 Writing effective prompts

A prompt is Copilot's only window onto your requirements. Whatever you leave out, it guesses — usually whatever is most common in the code it has read.

✗ Weak prompt
"Make a website better."

Which file? Better how? What must not change? Copilot has to invent every answer.
✓ Improved prompt
"Review this vanilla JavaScript task manager. Identify duplicated logic, improve input validation and add accessible error messages, preserve the existing interface, and suggest small, testable changes. Explain each modification and list the cases I should test."

The improved prompt fills in the parts of the seven-part template:

PartThe question it answersIn the task-manager prompt
1 ContextWhat code, what project?"this vanilla JavaScript task manager"
2 ObjectiveWhat change do you want?"identify duplicated logic, improve input validation"
3 RequirementsWhat must the result have?"add accessible error messages"
4 ConstraintsWhat must not change?"preserve the existing interface"
5 Expected outputWhat form should the answer take?"small, testable changes; explain each"
6 Error handlingWhich failures must be covered?(missing — e.g. "an empty title")
7 TestingHow will you check it?"list the cases I should test"

"Explain this line" needs only context; the more you ask it to change, the more parts you need. Two more repairs:

WeakStrong
"Fix my code.""averageMarks(students) (below) throws TypeError: Cannot read properties of undefined (reading 'marks') with two students. Explain the root cause, suggest the smallest safe fix, and list tests for normal, empty and invalid input."
"Make a navbar.""Create a responsive navigation bar in semantic HTML (nav, ul), CSS and vanilla JavaScript. Below 600px, a menu button toggles the links and updates aria-expanded. No libraries. Explain each part."

Good habits: one job per prompt, so the answer is small enough to review; ask for a plan before code; give an example ("formatRupees(525) returns "₹525.00""); paste the exact error, never a secret; and follow up — "that uses innerHTML; use textContent".

78.5 Using Copilot for debugging

The deck's debugging challenge: a function should return the average mark of a group.

// marks.js
function averageMarks(students) {
  let total = 0;
  for (let i = 0; i <= students.length; i++) {
    total += students[i].marks;
  }
  return total / students.length;
}

Called with two students, it stops with:

✖ Uncaught TypeError: Cannot read properties of undefined (reading 'marks')

Spend two minutes on it yourself first (Chapter 68); you can only judge Copilot's answer if you have thought about the question. Only students[i].marks reads .marks, so for some i, students[i] is undefined…

"Analyze this JavaScript function. Identify the likely root cause of the error, explain why it occurs, suggest the smallest safe correction, and provide test cases for normal, empty, and invalid inputs."

Paste the failing function, the exact error, what you expected ("85 for 80 and 90") and a made-up sample input. Never paste passwords, keys, tokens, real students' data or exam questions.

Illustrative answer. i <= students.length runs one step too far. With two students the loop runs for i = 0, 1 and 2, but students[2] is undefined, and reading .marks from undefined throws. Also, an empty array would return 0 / 0, which is NaN.

This is the classic off-by-one error: arrays start at 0, so the last index is length - 1 and the condition must be i < students.length. Treat the explanation as a hypothesis — Copilot recognised a pattern; it did not run your code. One labelled log confirms it:

for (let i = 0; i <= students.length; i++) {
  console.log("i =", i, "student:", students[i]);

}
// i = 0 student: {marks: 80}
// i = 1 student: {marks: 90}
// i = 2 student: undefined       <- the loop went one step too far
function averageMarks(students) {
  if (students.length === 0) return null;     // nothing to average
  let total = 0;
  for (let i = 0; i < students.length; i++) { // < not <=
    total += students[i].marks;
  }
  return total / students.length;
}

The smallest safe fix changes as little as possible: one character in the loop, one line for the empty case. A big rewrite that "also fixes it" brings new unreviewed code, and new code is where new bugs live.

78.6 Using Copilot for refactoring

This grade function works, but every branch repeats the same two lines:

function showGrade(marks) {
  if (marks >= 90) {
    gradeEl.textContent = "Grade: A"; gradeEl.style.color = "green";
  } else if (marks >= 75) {
    gradeEl.textContent = "Grade: B"; gradeEl.style.color = "green";
  } else if (marks >= 60) {
    gradeEl.textContent = "Grade: C"; gradeEl.style.color = "orange";
  } else {
    gradeEl.textContent = "Grade: F"; gradeEl.style.color = "red";
  }
}

Asked to make it modular, Copilot might propose a table and two tiny functions:

const GRADES = [
  { min: 90, grade: "A", level: "good" },
  { min: 75, grade: "B", level: "good" },
  { min: 60, grade: "C", level: "warn" },
  { min: 0,  grade: "F", level: "bad" },
];

function getGrade(marks) {
  return GRADES.find((g) => marks >= g.min);
}

function showGrade(marks) {
  const { grade, level } = getGrade(marks);
  gradeEl.textContent = `Grade: ${grade}`;
  gradeEl.className = `grade grade--${level}`;
}

It looks better: the bands live in one table, and the colours have moved into CSS classes (Chapter 73). Now the refactoring checklist: ☐ behaviour unchanged? ☐ edge cases — 90, 75, 60, 0, −5, not-a-number? ☐ clear names? ☐ less duplication? ☐ tests still pass?

Quick check: predict it before you read on. What does the new showGrade(-5) do?

It throws a TypeError. No row has min at or below −5, so find() returns undefined, and undefined cannot be destructured. The old code fell through to else and showed "Grade: F".

The AI introduced a regression: the old final else caught everything, and the table version quietly removed that safety net. The example runs the old version, the AI's refactor and a fixed refactor on the same nine inputs.

    { min: 0, grade: "F", level: "bad" },
  ];
  function getGrade(marks) {
    return GRADES.find((g) => marks >= g.min);
  }
  function showGradeNew(marks, gradeEl) {
    const { grade, level } = getGrade(marks);
    gradeEl.textContent = `Grade: ${grade}`;
    gradeEl.className = `grade grade--${level}`;
  }

  // FIXED: same table, but nothing can fall off the end of it
  function getGradeFixed(marks) {
    return GRADES.find((g) => marks >= g.min) ?? GRADES[GRADES.length - 1];
  }
  function showGradeFixed(marks, gradeEl) {
    const { grade, level } = getGradeFixed(marks);
    gradeEl.textContent = `Grade: ${grade}`;
    gradeEl.className = `grade grade--${level}`;
  }

  // what does each version show for one input? (errors are reported, not thrown)
  function shown(showFn, marks) {
    const el = document.createElement("b");     // a scratch element, never on the page
    try {
      showFn(marks, el);
      return el.textContent;
    } catch (err) {
      return err.name;
    }
  }

  const inputs = [95, 90, 80, 75, 65, 30, 0, -5, NaN];
  const rows = inputs.map((marks) => ({
    marks,
    before: shown(showGradeOld, marks),
    refactor: shown(showGradeNew, marks),
    fixed: shown(showGradeFixed, marks),
  }));
  console.table(rows);

  const broken = rows.filter((r) => r.refactor !== r.before).map((r) => r.marks);
  const stillBroken = rows.filter((r) => r.fixed !== r.before).map((r) => r.marks);
  console.log("Refactor changed the result for:", broken);
  console.log("Fixed version changed the result for:", stillBroken);

  try {
    showGradeNew(-5, document.createElement("b"));
  } catch (err) {
    console.error("showGradeNew(-5):", err.message);
  }

  document.querySelector("#out").textContent =
    `Inputs tried: ${inputs.length}. The AI refactor broke ${broken.length}; the fixed version broke ${stillBroken.length}.`;
</script>

For the seven ordinary marks all three columns agree. For -5 and NaN, before and fixed say 'Grade: F' but refactor says 'TypeError'; the summary lines read [-5, NaN] and [], and Chrome's red line says Cannot destructure property 'grade' of 'getGrade(...)' as it is undefined.

The fix is Chapter 44's ??: "if the left side is null or undefined, use the right side". When find() comes back empty-handed, getGradeFixed falls back to the last row, F — the old safety net.

A refactor may change the shape of the code and nothing else. Feed old and new the same inputs, strange ones included: the outputs must match. If not, it is a bug with nicer formatting.

Should −5 really be an F? Probably not. But changing that is a behaviour change — a deliberate decision in its own commit, which the next section makes.

78.7 Using Copilot to write tests and documentation

AI-suggested tests find cases you forgot, but a wrong test gives confidence you have not earned. Ask for the cases as a table first, quick to review before any test code exists:

"List test cases for getGrade(marks) as a table: input, expected grade, reason. Cover boundaries, invalid and empty input. Don't write code yet."
InputExpectedReason (illustrative output)
90ALower boundary of A
89.9BJust below A
60CLower boundary of C
0FMinimum valid
-5F ?Policy decision — and the refactored code crashes!
"abc"errorNot a number

Each edge case listed is good, but 75 (B's lower boundary) and 100 (the maximum) are missing, and the −5 row asks what should happen? The team decides: marks outside 0–100, or not numbers, are refused — getGrade returns null. Copilot turns the reviewed table, plus your two rows, into test code. Run it:

<style>
  body { font-family: system-ui, sans-serif; padding: 8px 14px; }
  .pass { color: #166534; font-weight: 700; }
  .fail { color: #B91C1C; font-weight: 700; }
</style>
<p id="summary"></p>
<script>
  const GRADES = [
    { min: 90, grade: "A", level: "good" },
    { min: 75, grade: "B", level: "good" },
    { min: 60, grade: "C", level: "warn" },
    { min: 0, grade: "F", level: "bad" },
  ];

  /**
   * Returns the grade band for a mark.
   * @param {number} marks - a number from 0 to 100
   * @returns {{grade: string, level: string} | null} the band, or null
   *   when marks is not a number from 0 to 100
   */
  function getGrade(marks) {
    if (!Number.isFinite(marks) || marks < 0 || marks > 100) return null;   // policy: refuse
    return GRADES.find((g) => marks >= g.min);
  }

  // test cases: the reviewed table, turned into code by the assistant
  const tests = [
    { input: 90, expected: "A", reason: "lower boundary of A" },
    { input: 89.9, expected: "B", reason: "just below A" },
    { input: 75, expected: "C", reason: "lower boundary of B" },
    { input: 60, expected: "C", reason: "lower boundary of C" },
    { input: 0, expected: "F", reason: "minimum valid" },
    { input: 100, expected: "A", reason: "maximum valid" },
    { input: -5, expected: null, reason: "below the range: refused" },
    { input: "abc", expected: null, reason: "not a number: refused" },
  ];

  const results = tests.map((t) => {
    const band = getGrade(t.input);
    const actual = band ? band.grade : null;
    return { input: t.input, expected: t.expected, actual,
             result: actual === t.expected ? "PASS" : "FAIL" };
  });
  console.table(results);

  const failed = results.filter((r) => r.result === "FAIL");
  console.log(`${results.length - failed.length} passed, ${failed.length} failed`);
  failed.forEach((r) => {
    console.warn(`FAIL: getGrade(${r.input}) gave ${r.actual}, but the test expected ${r.expected}`);
  });

  const summary = document.querySelector("#summary");
  summary.textContent = `${results.length - failed.length} of ${results.length} tests pass.`;
  summary.className = failed.length === 0 ? "pass" : "fail";
</script>

Seven pass, one fails: FAIL: getGrade(75) gave B, but the test expected C. Don't rush to "fix" the code: 75 is B's lower boundary, as the test's own reason says. The code is right; the test is wrong. Change that "C" to "B" and run again: 8 of 8 tests pass, in green. Then add a row: 74.9 should be "C".

Generated tests need review too. A wrong expected value either sends you "fixing" correct code or, worse, matches a bug and locks it in. A test file nobody runs protects nothing while feeling safe.

Documentation must describe the real behaviour

The deck's illustrative doc comment:

/**
 * Returns the grade band for a mark.
 * @param {number} marks - 0 to 100
 * @returns {{grade: string, level: string}}
 * @throws if marks is not a number 0-100
 */

The shipped getGrade never throws; for bad input it returns null. So @throws is untrue and @returns omits null — the comment in the example says {...} | null instead. Check generated comments against what the code does.

Copilot can also draft a README (then delete inventions such as features you never built) and a GitHub Pages deployment checklist (then compare it line by line with Chapter 76).

Every limitation below has already appeared in this chapter:

Confident is not the same as correct. Wrong answers arrive in the same fluent grammar as right ones. An AI may even invent a function that does not exist and explain it smoothly. Only reading and testing reveal the truth.

Licences. A suggestion can occasionally match public code, which belongs to its author under a licence. Your Copilot settings on GitHub can block such matches; if you allow them, code referencing shows where a match came from and its licence. Follow it, or write your own.

Sensitive data. A prompt leaves your computer for someone else's servers. Use placeholders such as "YOUR_API_KEY" and "Student A". If a real key ever leaks, into a prompt or a commit, revoke it and make a new one (Chapter 75).

Academic integrity. Follow LPU's and your course's policy on AI, and ask your teacher if unsure. Where AI is allowed, disclose which tool you used and for what, be able to explain and modify everything you submit, and never paste exam questions into an AI tool. A README note is the usual disclosure:

## AI use
I used GitHub Copilot Chat to explain a TypeError in js/form.js and to
list test cases for the email check. I wrote and tested the final code
myself. Suggestions I rejected, and why, are in docs/ai-log.md.
Key idea. AI is an assistant, not a replacement for engineering judgement. It can draft; only you can decide.
Quick check: your fetch() fails, and the file contains const API_KEY = "a8f3...". Is it fine to paste the whole file into chat and ask why?

No. Replace the key with a placeholder and paste only the failing function and the exact error. If the real key was already sent, revoke it.

  // js/form.js - checks the form and explains every problem.
  // GitHub Pages has no server, so this page cannot deliver the message itself.
  const form = document.querySelector("#contact");
  const statusEl = document.querySelector("#status");
  const EMAIL_PATTERN = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

  // one rule per field: return "" when it is fine, or the message to show
  const RULES = {
    name: (value) => (value === "" ? "Please enter your name." : ""),
    email: (value) => (EMAIL_PATTERN.test(value) ? "" : "Please enter an email such as asha@example.com."),
    message: (value) => (value.length < 10 ? "Please write at least 10 characters." : ""),

    document.querySelector(`#${field.id}-error`).textContent = message;
    field.setAttribute("aria-invalid", message === "" ? "false" : "true");
  }

  form.addEventListener("submit", (event) => {
    event.preventDefault();                        // no server to send it to
    statusEl.textContent = "";

    for (const fieldName of Object.keys(RULES)) {
      const field = document.querySelector(`#${fieldName}`);
      const message = RULES[fieldName](field.value.trim());
      showError(field, message);
      if (message !== "" && firstProblem === null) firstProblem = field;
    }
    if (firstProblem !== null) {
      firstProblem.focus();                        // take the visitor straight to it
      console.warn("Not sent. First problem:", firstProblem.id);
      return;
    }
    const sender = document.querySelector("#name").value.trim();
    statusEl.textContent = `Thank you, ${sender}! (Demo: nothing was sent - this page has no server.)`;
    console.log("Valid message from", sender);
    form.reset();
  });
</script>

78.11 Common misunderstandings

✗ "Copilot has read millions of programs, so its code must be right."
It predicts likely code; likely is not correct for your requirements.
✓ "Copilot drafts; I verify."
Every suggestion is reviewed and tested before it is committed.
✗ "To check a suggestion, I ask Copilot whether it is correct."
Its "yes" is another prediction, not a test.
✓ "I read it and run it."
Normal, empty and invalid input, the keyboard, a phone, the Console.
✗ "A refactor that looks cleaner is an improvement."
The table-based showGrade looked cleaner and crashed on −5.
✓ "A refactor behaves exactly like the old code."
Behaviour changes are separate, deliberate decisions.
✗ "When a test fails, the code is wrong."
Generated tests can be wrong, like getGrade(75) expecting "C".
✓ "I find out which side is wrong."
Tests are code, and get reviewed like code.
✗ "Using Copilot is always cheating" — or — "always allowed."
The rules belong to the course, not the tool.
✓ "I follow the policy for this piece of work."
Where allowed, I disclose my AI use and can explain every line.

Exam-style checks

GitHub Copilot is best described as:L1
  • A. A compiler that reports every bug before you run the code
  • B. An AI coding assistant that suggests, explains and edits code, built on models trained on public code and text
  • C. A free hosting service for static websites
  • D. A version-control system that records commits

Answer: B. Copilot predicts code from context and guarantees nothing, so A is wrong. C is GitHub Pages; D is Git.

A Copilot suggestion passes your one test. What is the next step?L2
  • A. Commit it immediately
  • B. Ask Copilot whether it is right, then commit
  • C. Review it line by line and test the edge cases
  • D. Delete the test, since the code now works

Answer: C. You own the code. One passing test proves little, and asking the model to grade itself (B) is another prediction, not a check.

Which prompt is most likely to get a useful, reviewable answer?L2
  • A. "Make my website better."
  • B. "Fix the form."
  • C. "Write JavaScript for a contact page."
  • D. "In form.js (below), validate name, email and message in vanilla JavaScript; show each error next to its field; do not change the HTML; explain each change and list the cases to test."

Answer: D. It has context, objective, requirements, a constraint, an output format and testing. A, B and C leave Copilot to guess.

With the fixed averageMarks from section 78.5, what does this print?
console.log(averageMarks([{ marks: 70 }, { marks: 80 }, { marks: 90 }]), averageMarks([]));L3

Answer: 80 null. The loop stops before i reaches 3, adds 70 + 80 + 90 = 240 and divides by 3. The empty list returns null before any 0 / 0 can produce NaN.

The original averageMarks, with i <= students.length, is called with two students. What happens?L3
  • A. A TypeError, because the last pass reads .marks from students[2], which is undefined
  • B. It returns 85
  • C. A SyntaxError, because <= is not allowed in a for loop
  • D. It returns NaN without any error

Answer: A. Indexes 0 and 1 exist; the condition also tries 2, and reading .marks from undefined throws before anything is returned. <= is legal syntax, so C is wrong.

getGrade(marks) returns GRADES.find((g) => marks >= g.min), and showGrade does const { grade, level } = getGrade(marks);. The lowest row has min: 0. What does showGrade(-5) do?L3
  • A. Shows "Grade: F", like the old code
  • B. Shows "Grade: undefined"
  • C. Shows nothing and logs nothing
  • D. Throws a TypeError, because find() returns undefined and undefined cannot be destructured

Answer: D. No row matches −5, so find() returns undefined, and destructuring it throws. A is what the old code did — that is the regression. B would need an object without a grade.

A suggestion adds cards with list.innerHTML += `<div class="card">${title}</div>`; where title is typed by the user. What is the most serious problem?L2
  • A. Cross-site scripting: the title is parsed as HTML, so code inside it can run; use createElement and textContent
  • B. Template literals cannot be used with innerHTML
  • C. innerHTML works only in Chrome
  • D. card is a reserved class name

Answer: A. A title such as <img src="x" onerror="..."> runs its code in the page. B, C and D are simply false.

Which of these must never be pasted into a prompt?L1
  • A. The exact error message from the Console
  • B. Your GitHub personal access token
  • C. The function you are debugging
  • D. The expected output for one example input

Answer: B. Tokens, passwords, keys and personal data never go into a prompt, which leaves your computer. A, C and D belong in a good debugging prompt.

Your course allows AI tools for the project. Which use is responsible?L2
  • A. Generate the whole site and submit it without mentioning AI
  • B. Paste the CA question into Copilot Chat during the test
  • C. Use Copilot to explain an error, write and test the fix yourself, and note the AI use in the README
  • D. Submit code you cannot explain, as long as it passes

Answer: C. Follow the policy, disclose, and be able to explain everything. A hides the use, B breaks exam rules, D fails "explain every line".

Ananya's portfolio on GitHub Pages validates its contact form and shows "Thank you", but no email ever arrives. Why?L2
  • A. The email pattern is wrong
  • B. HTTPS blocks forms
  • C. Forms only work with jQuery
  • D. GitHub Pages serves static files only; without a backend or a form service, nothing delivers the message

Answer: D. Browser code can validate, but delivering email needs a server. Validation passed, so A is not the cause; B and C are false.

An AI-generated test expects getGrade(75) to return "C", and it fails because the function returns "B". What do you conclude, and what do you do?L2

Answer: the test is wrong, not the code. 75 is B's lower boundary (75 >= 75 is true), so "B" is correct. Fix the expected value and rerun. A failing test means "find out which side is wrong".

You ask Copilot to refactor a working function. Which review question matters most?L2
  • A. Does it behave exactly as before for every input, including edge cases such as −5 and NaN?
  • B. Is the new version shorter?
  • C. Does it use newer syntax, such as arrow functions?
  • D. Did the AI write it, or did I?

Answer: A. A refactor may change only the shape, never the behaviour. B and C are worthless if the result is wrong; D does not change whether it works.

Quick revision

Key takeaways

  1. Copilot is an AI pair programmer: it predicts code from the context it can see, never runs your code, and knows only the requirements you wrote down.
  2. Use it for boilerplate, explanations, test ideas, refactors, docs and alternatives — and, as a beginner, to explain more than to write.
  3. Review-first loop: prompt, suggestion, review, test, fix, commit. If you can't explain a line, don't commit it.
  4. A strong prompt has context, objective, requirements, constraints, expected output, error handling and testing.
  5. Review AI UI code for semantics, keyboard access, XSS and responsiveness.
  6. Debug: think first, treat the AI's explanation as a hypothesis, apply the smallest safe fix, test normal, empty and invalid input.
  7. A refactor behaves identically; generated tests and docs must match the real behaviour.
  8. Responsible use: protect secrets and personal data, respect licences, follow your institution's policy and disclose AI use.
