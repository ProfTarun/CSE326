Accessibility Fundamentals

Web accessibility is the practice of building pages that people with visual, auditory, motor or cognitive disabilities can perceive, understand and use. It is mostly a matter of writing correct, meaningful HTML, which is why it belongs in this unit rather than at the end of the course. This chapter covers the fundamentals every page owes its users, the small ARIA vocabulary that fills the gaps, and the mistakes that lock people out.

15.1 What accessibility is, and who it is for

Web accessibility means building sites that people with visual, auditory, motor or cognitive disabilities can perceive, understand and use. It is not about loading in under a second, ranking first in search results or working only in the newest browser; it is about not locking people out. Users reach pages through assistive technology: a screen reader (NVDA, JAWS, VoiceOver, TalkBack) that speaks the page aloud, a screen magnifier, voice control, a switch device, or simply the keyboard alone because a mouse is unusable.

Accessibility also helps everyone else. Captions help a student watching a lecture on a noisy bus. Good contrast helps anyone in bright sunlight. Keyboard operability helps a power user. Clear structure helps a tired reader. And, as Chapter 11 showed, almost every accessibility improvement is a search-engine improvement too.

Labels: the rule in detail

For <label for="email">Email</label> to be associated with its field, the input must carry id="email": the for attribute matches the id, not the name, class or type. Alternatively wrap the control inside the label: <label><input type="checkbox"> Remember me</label>. Loose text next to a control is not associated with it at all.

Placeholder is not a label. Placeholder text disappears as soon as the user starts typing, so halfway through a long form the user cannot remember what the field wanted; and screen readers may skip it entirely. Use it only as a hint alongside a visible label. It can be styled, it does not block submission and it is not deprecated; those are not the problems.

Live: click the word "Email" and the field receives focus, because label and id are linked

 

15.3 Keyboard operability and the skip link

Many users never touch a mouse. Everything on a page must be reachable and usable with Tab (move to the next control), Shift+Tab (previous), Enter (activate a link or button), Space (toggle a checkbox, press a button) and the arrow keys (move within radio groups and menus). A user who completes a checkout using only Tab and Enter is testing the Operable principle of WCAG (Chapter 20).

Native elements are keyboard-operable for free: links, buttons and form controls all sit in the tab order and respond to Enter and Space. A <div onclick> does none of that. This is the main practical reason to prefer native HTML controls before inventing custom ones. The focused element must also be visible: never remove the focus outline without providing another.

The skip link

Because keyboard users move through every link in order, a page with a forty-link menu makes them press Tab forty times before reaching the content, on every page. A "skip to main content" link at the very top of the page, pointing at #main-content, lets keyboard users bypass repeated navigation blocks. It is usually hidden by CSS until it receives focus. It is not for hiding navigation from mobile users, not for search ranking and not about HTTP requests.

<style>
  .skip { position: absolute; left: -999px; }
  .skip:focus { left: 8px; top: 8px; background: #FFF1E0; padding: 8px; }
</style>
<a class="skip" href="#main-content">Skip to main content</a>
<header>
  <nav><a href="#">Home</a> <a href="#">Courses</a> <a href="#">Results</a> <a href="#">Contact</a></nav>
</header>
<main id="main-content">
  <h1>Results</h1>
  <p>Click inside this preview, then press Tab: the skip link appears first.</p>
</main>

15.4 ARIA: filling the gaps

ARIA (Accessible Rich Internet Applications) is a set of attributes that tell assistive technology what an element is and how to name or describe it, when HTML alone cannot. Two facts frame everything:

  1. The first rule of ARIA: if a native HTML element with the semantics and behaviour you need already exists, use it rather than recreating it with ARIA. A <button> beats <div role="button"> every time. Adding role="button" to a native <button> is redundant and counts as a mistake.
  2. ARIA changes how assistive technology reports an element; it does not change the element's actual behaviour. role="button" on a div makes a screen reader say "button", but the div still does not respond to Enter or Space, still is not focusable, and still needs JavaScript to do anything. ARIA does not make elements keyboard-operable, does not replace semantic HTML, and is applied through HTML attributes, not CSS.
AttributeWhat it doesTypical use
roleClarifies the purpose of a non-semantic element for assistive technology<svg role="img">, <div role="alert">; never on an element that already has that role natively
aria-labelGives an element an accessible name when it has no visible textAn icon-only button: <button aria-label="Close">×</button>; a nav: <nav aria-label="Main">
aria-labelledbyNames an element by pointing to the id of other visible text<section aria-labelledby="h-results"><h2 id="h-results">Results</h2>
aria-describedbyLinks an element to additional descriptive text elsewhere on the page, read after the nameA hint under an input: <input aria-describedby="hint"> <span id="hint">Use your college address</span>
aria-hidden="true"Hides the element from assistive technology (it stays visible on screen)A purely decorative icon beside an already-labelled button; never the main heading, a required field or a button's text
tabindex="0"Makes a custom element keyboard-focusable in the normal tab orderA custom widget built from a div (and then it still needs key handling)
tabindex="-1"Removes an element from the tab order while still allowing it to be focused by scriptThe target of a skip link or a dialog that a script focuses

Avoid positive tabindex values (tabindex="5"): they rearrange the tab order unpredictably. tabindex="0" does not place an element first and does not hide it; tabindex="-1" does not hide it from screen readers either, it only takes it out of the Tab sequence.

15.5 Worked example: an accessible email field

Compare four ways of marking up a required email field with a format hint. Only one gives the field an accessible name and attaches the hint.

MarkupVerdict
<label>Email</label><input id="em" type="text" required>The label has no for, so it is not associated; and type="text" throws away email validation and the @ keyboard.
<input type="email" required placeholder="Email">No label at all; the placeholder vanishes on typing.
<div>Email</div><input type="email" required title="Email">A div is not a label; title is only a tooltip.
<label for="em">Email</label><input id="em" type="email" required aria-describedby="h1"><span id="h1">Use your college address</span>Correct. The label names the field via for/id; the type gives validation; aria-describedby attaches the hint so a screen reader reads "Email, edit text, required, use your college address".
 
<form>
  <label for="em">Email</label>
  <input id="em" name="email" type="email" required aria-describedby="em-hint">
  <span id="em-hint">Use your college address</span>
  <button type="submit">Register</button>
</form>

15.6 The mistakes that lock people out

  • Images without alt; icon buttons without a name; a logo with alt="".
  • Forms with placeholders instead of labels; radio groups without a fieldset/legend (Chapter 16).
  • Headings faked with styled divs; levels skipped; several h1s.
  • Custom controls made from divs with click handlers and no keyboard support.
  • role="button" on a native button, aria-hidden on content people need, positive tabindex.
  • Pages built only from divs, so there are no landmarks and no skip link target.
  • Colour as the only way to show an error; text that fails the contrast ratio (Chapter 20).

Exam-style checks

Web accessibility is the practice of building sites that:L2
  • A. Load in under one second on every device
  • B. Rank first in search engine results
  • C. People with visual, auditory, motor or cognitive disabilities can perceive, understand and use
  • D. Work only in the most recent browser version

Answer: C.

For <label for="email">Email</label> to be correctly associated, the input must carry:L3
  • A. name="email"
  • B. class="email"
  • C. id="email"
  • D. type="email"

Answer: C. for matches id.

Why should placeholder text never fully replace a visible <label>?L2
  • A. Placeholder text cannot be styled with CSS
  • B. Placeholder text blocks form submission
  • C. The placeholder attribute is deprecated in HTML5
  • D. It disappears once typing starts and may be skipped by screen readers

Answer: D.

A "skip to main content" link at the top of a page exists mainly to:L2
  • A. Hide the navigation from mobile users
  • B. Improve the page's position in search results
  • C. Reduce the number of HTTP requests
  • D. Let keyboard users bypass repeated navigation blocks

Answer: D.

When a native semantic HTML element already exists for a purpose, best practice is to:L3
  • A. Always use a <div> with a role attribute
  • B. Use the native element rather than recreating it with ARIA
  • C. Use the native element together with a conflicting role
  • D. Avoid semantic elements because ARIA is newer

Answer: B. The first rule of ARIA.

Which of the following is a mistake in the use of ARIA?L3
  • A. Adding aria-describedby to link a hint to an input
  • B. Adding aria-label to an icon-only button
  • C. Adding aria-hidden="true" to a decorative icon
  • D. Adding role="button" to a native <button> element

Answer: D. The native button already has that role; A, B and C are correct uses.

Which statement about ARIA is correct?L3
  • A. It changes how assistive technology reports an element but does not change the element's actual behaviour
  • B. It automatically makes any element keyboard-operable
  • C. It replaces the need for semantic HTML elements
  • D. It is applied through CSS rather than HTML attributes

Answer: A.

What does the aria-label attribute provide?L2
  • A. A validation rule for form input
  • B. A visible caption below the element
  • C. A CSS class used for styling
  • D. An accessible name for an element that has no visible text

Answer: D.

Which ARIA attribute names an element by pointing to the id of other visible text?L3
  • A. aria-labelledby
  • B. aria-label
  • C. aria-describedby
  • D. aria-hidden

Answer: A. aria-label supplies the text directly; aria-describedby adds a description, not the name.

What does aria-describedby do?L2
  • A. Hides the element from assistive technology
  • B. Replaces the element's visible label
  • C. Links an element to additional descriptive text elsewhere on the page
  • D. Sets the element's position in the tab order

Answer: C.

The attribute aria-hidden="true" is appropriate for:L2
  • A. The page's main heading
  • B. A purely decorative icon beside an already-labelled button
  • C. A required form field
  • D. The submit button's text

Answer: B.

The role attribute is used to:L2
  • A. Define the element's position in the tab order
  • B. Assign a CSS class to an element
  • C. Restrict which users may view an element
  • D. Clarify the purpose of a non-semantic element for assistive technology

Answer: D.

What does tabindex="0" do to a custom element, and what does tabindex="-1" do?L3

Answer: tabindex="0" makes it keyboard-focusable in the normal tab order (it does not place it first or hide it). tabindex="-1" removes it from the tab order while still allowing a script to focus it (it does not hide it from keyboard and screen-reader users entirely).

Which markup correctly gives a required email field an accessible name and a format hint?L3

Answer: <label for="em">Email</label><input id="em" type="email" required aria-describedby="h1"><span id="h1">Use your college address</span>. A label without for, a placeholder alone, or a div with a title attribute all fail to name the field properly.

Why should every <iframe> carry a title attribute, and which is the most accessible way to label a radio button?L2

Answer: the title gives screen-reader users an accessible name for the frame. A radio button is labelled with a <label> using for/id, or by wrapping the input in the label; loose text next to it is not associated.

Quick revision

Key takeaways

  1. Accessibility: people with visual, auditory, motor or cognitive disabilities can perceive, understand and use the page. It helps everyone and overlaps with SEO.
  2. Fundamentals: lang, logical headings, alt text, label for/id, landmarks, native controls, descriptive links, captions, iframe titles, colour plus another cue.
  3. Placeholder is not a label: it disappears on typing and may be skipped.
  4. Everything must work with Tab, Enter and Space; native elements do this for free; a skip link lets keyboard users bypass the menu.
  5. ARIA: role clarifies a non-semantic element; aria-label names an element with no visible text; aria-labelledby names it via another element's id; aria-describedby attaches extra description; aria-hidden hides decoration; tabindex 0 adds to the tab order, -1 removes it but allows script focus.
  6. First rule of ARIA: prefer the native element. ARIA changes what is announced, never how the element behaves.
