Form Validation with JavaScript

A form is a conversation: the page asks, the user answers, and somebody has to check the answers before they are used. HTML can already refuse an empty box, but it speaks in the browser's words, one bubble at a time, and only when Submit is pressed. JavaScript lets you check any rule you like, say exactly what is wrong right next to the box that is wrong, and help while the user is still typing.

About 35 minutes · Course outcome CO5

Before you start — one-line reminders

  • type="email", type="number", min/max and minlength describe what a box should hold (Chapter 17); with required and pattern the browser checks them before sending, and the server must check again (Chapter 18).
  • Every box needs a <label for="..."> that names it, and a form is sent by a type="submit" button (Chapter 16).
  • addEventListener("submit", fn) runs a function when a form is sent, and event.preventDefault() stops the browser's usual action (Chapter 57).
  • text.trim() gives back a copy of the text without the spaces at its two ends (Chapter 45).

By the end of this chapter you can

  • Say what HTML's built-in validation cannot do, and when JavaScript is needed.
  • Write a submit handler that stops the send, reads and trims each value, decides, and shows a message.
  • Show each error next to its box, mark it with aria-invalid and aria-describedby, and move focus to the first problem.
  • Check boxes while the user types without complaining too early.
  • Use checkValidity(), reportValidity(), the validity flags, setCustomValidity() and novalidate.
  • Explain why the server checks everything again, and build the lecture's Product Order Form.

60.1 What validation is, and what HTML already does

Form validation means checking that the information a user entered obeys your rules before the application accepts it. The lecture's examples are the everyday ones: an email must be in an acceptable format, a password must be long enough, an age must fall within an allowed range, and required boxes must not be empty. Each rule is a constraint.

You met the HTML way in Chapter 18: write the rule as an attribute, and the browser enforces it when Submit is pressed.

AttributeRule it describes
requiredThe box must not be empty
type="email", "url", "number"The value must fit that kind of data
min, maxA number or date must be inside the range
minlength, maxlengthThe number of characters must be inside the range
patternThe whole value must match a pattern

That is a good start, but it has real limits:

  • The words are not yours. The browser writes its own sentence ("Please fill in this field.") in a bubble that fades away, worded differently in every browser.
  • One problem at a time, only on Submit. The bubble appears for the first bad box only. The user fixes it, presses Submit again, and only then discovers the second problem.
  • No rule can compare two boxes. "Confirm password must match password" or "return date must be after departure date" has no attribute.
  • Looser than you expect. A box containing three spaces satisfies required, and type="email" happily accepts asha@lpu with no dot, because the HTML standard allows addresses on private networks.

JavaScript fills every one of these gaps. It does not replace the attributes: they still describe your rules, they still work if your script fails to load, and in 60.5 your script will read them.

Quick check: a box has the required attribute, and the user types three spaces. Does the browser accept it?

Yes. Spaces are characters, so the box is not empty as far as required is concerned. That is why every script in this chapter calls .trim() before testing for "".

Picture this. The clerk at a speed-post counter. She does not snatch your form while you are still writing. When you hand it over, she reads every box, puts a pencil mark and a short note beside each one that is wrong — not a vague "form incorrect" — and points to the first. The moment you correct a box she stops complaining about it. And whatever she accepts, the head post office checks again before anything is dispatched, because forms can reach it without passing her counter. This chapter teaches you to be that clerk.

60.2 Taking over the submit: four steps

Every JavaScript validator, from a one-box OTP form to a forty-box admission form, does the same four things:

  1. Stop. Listen for the form's submit event and call event.preventDefault() as the very first line.
  2. Read. Take each box's .value — always a string, even in a number box — and .trim() it, so stray whitespace at the ends does not count.
  3. Decide. Test the value with if / else.
  4. Tell. Write a message on the page. If everything passed, let the data go on.

For "exactly 10 digits" the lecture uses a regular expression: /^\d{10}$/. Read it as "from the start, ten digits, then the end". Its .test(text) method answers true or false. Chapter 61 teaches you to write these; in this chapter every pattern is explained in words.

<script>
  const form = document.getElementById("signup");
  const mobile = document.getElementById("mobile");
  const msg = document.getElementById("msg");

  form.addEventListener("submit", (event) => {
    event.preventDefault();                       // 1. stop: do not send the form yet
    const value = mobile.value.trim();            // 2. read the box, cut stray spaces
    console.log("Checking:", JSON.stringify(value));

    let message;
    if (value === "") {                           // 3. decide
      message = "Please enter your mobile number.";
    } else if (!/^\d{10}$/.test(value)) {
      message = "A mobile number is exactly 10 digits.";
    } else {
      message = "OTP sent to " + value + ".";
    }
    msg.textContent = message;                    // 4. tell the user
    console.log("Message:", message);
  });
</script>

Press Send OTP with the box empty: the Console shows Checking: "" and Message: Please enter your mobile number. Now type   98765  with spaces around it: Checking: "98765" proves the spaces were trimmed, and the ten-digit message appears. Finally type 9876543210 and press Enter instead of clicking: OTP sent to 9876543210. The same handler ran: Enter in a box submits the form too. (JSON.stringify adds the quotes, so you can see where the value starts and ends.)

Pressing Submit normally means "send this form now and load the reply page". preventDefault() says "not yet — let my code look first". If the answers are fine, your code sends them on; on a real site that is usually done with fetch (Chapter 65). If not, the user stays on the page, sees the message, and loses nothing they typed.

Listen to the form, not the button. The submit event fires however the form is sent — the button, Enter in a box, or a second submit button — and its default action is exactly the send you want to stop. Make preventDefault() the first line: if any line above it crashes, it never runs, and the browser goes ahead and sends the unchecked form.
Quick check: what does the browser do if your handler has a typing mistake on its second line and preventDefault() is on its last line?

It sends the form anyway. The error stops your function before it reaches preventDefault(), so nothing cancelled the submission. Put preventDefault() first and a crash leaves the user safely on the page.

60.3 Error messages people can find

"Invalid input" printed at the bottom of a long form helps nobody. Good error messages follow three rules:

  1. Next to the box, saying what to do. "Enter an email like asha@lpu.in", not "Email invalid".
  2. All at once. Check every box on each submit and show every message, so the user fixes everything in one pass.
  3. Go to the first one. Move focus there with input.focus(), so the cursor is already in the box that needs fixing.

A sighted user sees the red text under the box. A blind user, listening through a screen reader, needs the message joined to its box in code. Two attributes do it; you used both on a single roll-number box in Chapter 59, and now every box gets them:

  • aria-invalid="true" on the input marks it as wrong; screen readers announce "invalid entry". Remove it when the box is fixed.
  • aria-describedby="email-error" on the input names the id of the message element. Whenever the box gets focus, the reader speaks its label and then that message.

Here is the registration form from the lecture, built on those rules. Each box has an empty <p class="error"> waiting under it; the script fills it or empties it.

<script>
  const form = document.getElementById("reg");
  const fullname = document.getElementById("fullname");
  const email = document.getElementById("email");
  const pw = document.getElementById("pw");
  const pw2 = document.getElementById("pw2");
  const done = document.getElementById("done");
  const emailPattern = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;   // text@text.text, no spaces

  // One rule per box: give back "" if the value is fine, otherwise the message
  function checkName(value) {
    if (value.trim() === "") return "Enter your full name.";
    return "";
  }
  function checkEmail(value) {
    const v = value.trim();
    if (v === "") return "Enter your email address.";
    if (!emailPattern.test(v)) return "That email looks incomplete - try asha@lpu.in.";
    return "";
  }
  function checkPassword(value) {
    if (value.length < 8) return `Use at least 8 characters (you have ${value.length}).`;
    return "";
  }
  function checkConfirm(value) {
    if (value !== pw.value) return "The two passwords do not match.";
    return "";
  }

  // Put a message under a box (or clear it) and mark the box for screen readers
  function showMessage(input, message) {
    document.getElementById(input.id + "-error").textContent = message;
    if (message === "") {
      input.removeAttribute("aria-invalid");
    } else {
      input.setAttribute("aria-invalid", "true");
    }
  }

  const fields = [
    { box: fullname, check: checkName },
    { box: email, check: checkEmail },
    { box: pw, check: checkPassword },
    { box: pw2, check: checkConfirm },
  ];

  form.addEventListener("submit", (event) => {
    event.preventDefault();
    let firstBad = null;

    for (const f of fields) {                      // check EVERY box, top to bottom
      const message = f.check(f.box.value);
      showMessage(f.box, message);
      if (message !== "" && firstBad === null) {
        firstBad = f.box;                          // remember the first failure
      }
    }

    if (firstBad !== null) {
      done.textContent = "";
      firstBad.focus();                            // take the user straight to it
      console.log("Not sent. First problem:", firstBad.id);
    } else {
      done.textContent = `Registered! Welcome, ${fullname.value.trim()}.`;
      console.log("All four boxes passed - now the data would go to the server.");
    }
  });
</script>

Press Register with every box empty. Three messages appear at once, the password one saying (you have 0), and the cursor jumps into Full name; the Console says Not sent. First problem: fullname. Confirm password shows nothing, because two empty passwords do match — the password message already explains the real problem.

Now type Asha Kumar, asha@lpu, secret12 and secret21, and press Register again. The name's message vanishes, because every submit rewrites every box's message. Email (no dot) and Confirm (21, not 12) are marked, and the Console names email. Fix both and you get Registered! Welcome, Asha Kumar.

Each check function answers one question: "what is wrong with this value?" An empty answer, "", means "nothing". The loop asks every check, writes each answer under its own box, and remembers the first box that complained so the cursor can be sent there.

Two small decisions are worth noticing. The passwords are not trimmed, because a space can be a deliberate part of a password. And the form carries novalidate, so the browser's own email bubble does not jump in ahead of the script; 60.6 explains why that matters.

60.4 Checking while the user types, without nagging

Two events from Chapter 57 let you check before Submit. input fires on every change to a box: each key, each paste, each delete. blur fires when the box loses focus, because the user pressed Tab or clicked somewhere else.

Checking on every key from the very first one is nagging: type one letter of your email and you are told "That is not an email address". Of course not — you have typed one letter. The friendly rule is late to complain, quick to forgive:

MomentWhat the script does
Typing in a box that shows no errorStay quiet
Leaving a box the user has typed in (blur)Check it; show a message if it is wrong
Typing in a box that is showing an error (input)Re-check on every key, so the message disappears the moment it is fixed
Pressing SubmitCheck every box, whatever happened before

  .error { color: #C42B2B; font-size: 14px; margin: 3px 0 0; min-height: 18px; }

<script>
  function nameMessage(value) {
    return value.trim().length >= 3 ? "" : "At least 3 characters, please.";
  }
  function phoneMessage(value) {
    return /^\d{10}$/.test(value.trim()) ? "" : "Exactly 10 digits, no spaces.";
  }

  // Late to complain, quick to forgive
  function liveCheck(input, getMessage) {
    const slot = document.getElementById(input.id + "-error");
    let touched = false;                          // has the user typed here yet?

    function judge(why) {
      const message = getMessage(input.value);
      slot.textContent = message;
      if (message === "") {
        input.removeAttribute("aria-invalid");
      } else {
        input.setAttribute("aria-invalid", "true");
      }
      console.log(`${why} on ${input.id}:`, message || "OK");
    }

    input.addEventListener("input", () => {
      touched = true;
      if (input.hasAttribute("aria-invalid")) {   // an error is showing, so
        judge("input");                           // re-check on every key
      }
    });
    input.addEventListener("blur", () => {
      if (touched) {                              // they have finished with the box:
        judge("blur");                            // now it is fair to judge
      }
    });
  }

  liveCheck(document.getElementById("who"), nameMessage);
  liveCheck(document.getElementById("phone"), phoneMessage);
</script>

Click into Name and press Tab without typing: the Console stays empty, because a box nobody has touched is not an error yet. Click back, type As and press Tab: blur on who: At least 3 characters, please. Click back and type h: input on who: OK, and the message disappears on that very key. In Mobile, type 98765 and leave: the message appears. Go back and type the remaining digits one at a time; each key re-checks, and the tenth digit brings input on phone: OK.

Do not judge a box while someone is still writing in it. Judge it when they leave. Once you have pointed out a mistake, watch every key, so you can take the complaint back the instant it is fixed.

Live hints are a kindness, never a replacement. A user can skip a box completely, and then no blur ever fires on it, so the full check on Submit from 60.3 must still run.

60.5 The Constraint Validation API: the browser's checker, from JavaScript

Writing every rule by hand repeats work the browser already knows how to do. Every input carries a ready-made checker that reads its HTML attributes and reports, to your script, exactly what is wrong. Its official name is the Constraint Validation API, and these are its tools:

CodeWhat it doesGives back
input.checkValidity()Checks one box against its attributes, quietlytrue / false
form.checkValidity()Checks every box in the form, quietlytrue / false
form.reportValidity()Checks, and if something fails shows the browser's bubble on the first bad box and focuses ittrue / false
input.validityAn object of true/false flags saying which rule failedA ValidityState object
input.validationMessageThe browser's own sentence for the current problemText, or "" if the box is valid
input.setCustomValidity("...")Marks the box invalid with your message; "" clears itNothing

input.validity is the most useful of them. Each of its properties is a flag for one kind of failure:

FlagIs true whenSwitched on by
valueMissingThe box is emptyrequired
typeMismatchThe value does not fit the typetype="email", type="url"
patternMismatchThe value does not match the patternpattern
tooShort / tooLongFewer / more characters than allowedminlength / maxlength
rangeUnderflow / rangeOverflowA number or date below min / above maxmin / max
stepMismatchThe number is not on the stepstep
customErrorYour script set a non-empty custom messagesetCustomValidity()
validEvery flag is false (the above, plus the rarer badInput: text a number box cannot read)(all of them together)

Two facts surprise almost everyone. First, an empty box breaks only required: pattern, type and minlength all ignore an empty box, so an optional box may be left blank. If a value is compulsory and must match a pattern, write both attributes. Second, tooShort only switches on after the user has typed in the box; a value placed there by your script or by the value attribute is not length-checked. That is why the explorer below has no minlength box.

Some rules no attribute can express, such as "the two passwords must match". For those, setCustomValidity(message) switches the box to invalid with your message, and setCustomValidity("") switches it back to valid. The explorer runs its matchPasswords on every key in either password box.

<script>
  const form = document.getElementById("f");
  const pw = document.getElementById("pw");
  const pw2 = document.getElementById("pw2");
  const FLAGS = ["valueMissing", "typeMismatch", "patternMismatch", "tooShort",
                 "rangeUnderflow", "rangeOverflow", "customError"];

  // A rule no attribute can express: the two passwords must match
  function matchPasswords() {
    if (pw2.value === pw.value) {
      pw2.setCustomValidity("");                       // "" means: no complaint
    } else {
      pw2.setCustomValidity("Passwords do not match.");
    }
  }
  matchPasswords();
  pw.addEventListener("input", matchPasswords);
  pw2.addEventListener("input", matchPasswords);

  // Print the flags that are switched on, box by box
  function showFlags() {
    for (const box of form.querySelectorAll("input")) {
      const on = FLAGS.filter((name) => box.validity[name]);
      console.log(`${box.id}:`, on.length > 0 ? on.join(", ") : "valid");
    }
    console.log("pw2 says:", pw2.validationMessage);
  }
  showFlags();

  document.getElementById("check").addEventListener("click", () => {
    showFlags();
    console.log("form.checkValidity() =", form.checkValidity());
  });
  document.getElementById("report").addEventListener("click", () => {
    console.log("form.reportValidity() =", form.reportValidity());
  });
</script>

Run it and read the Console from the top: mail: typeMismatch, code: patternMismatch, age: rangeUnderflow, city: valueMissing, pw: valid (it has no rules at all), pw2: customError, and pw2 says: Passwords do not match. The red and green borders come from the CSS :invalid and :valid pseudo-classes (Chapter 32), which read the same flags.

Press reportValidity(): a bubble appears beside the email box, the cursor goes there, and the Console prints form.reportValidity() = false. Now fix every box — asha@lpu.in, PRD1234, 19, any city, and secret12 in Confirm — and press checkValidity(). Every line says valid, pw2 says: is empty, and the last line is form.checkValidity() = true, with no bubble, because checkValidity() never shows anything.

The browser keeps a little row of lights for every box, one light per kind of mistake. validity lets your script look at the lights. checkValidity() asks "are all the lights off?" quietly; reportValidity() asks the same question out loud, with a bubble. setCustomValidity() is a light your own script switches on, and only your script can switch it off again.

The empty string is the off switch. Call setCustomValidity("Passwords do not match.") without ever calling setCustomValidity(""), and the box stays invalid for ever, even after the user types the right password. It is the most common setCustomValidity bug. And run the check whenever either box changes, because changing the first password can break or mend the match.
Quick check: in matchPasswords, someone deletes the line pw2.setCustomValidity(""). The user then types matching passwords. What is pw2.validity.valid?

false. customError was switched on when the passwords differed, and now nothing ever switches it off, so the box can never become valid.

60.6 novalidate: keep the rules, write the messages yourself

Here is a trap that catches every class. You build a form with required and type="email", add a submit listener that writes lovely messages under each box, and press Submit with a bad value. Your listener never runs. The browser checks the attributes first, shows its own bubble, and cancels the send before the submit event even fires.

The fix is novalidate on the form (Chapter 18). It tells the browser to stop blocking and stop showing bubbles — but the browser still understands every attribute, so validity and checkValidity() keep working. Now submit always fires, your script asks the browser what is wrong, and you choose the words.

Better still, switch it on from the script with form.noValidate = true;. If the script ever fails to load — a slow network, a typing mistake — the line never runs, and the browser's own checks still protect the form.

<script>
  const form = document.getElementById("join");
  const done = document.getElementById("done");
  form.noValidate = true;     // the script is running, so the script shows the messages

  // The browser has already worked out WHAT is wrong; we only choose the words
  function messageFor(input) {
    const v = input.validity;
    if (v.valueMissing) return "Please fill in this box.";
    if (v.typeMismatch) return "That does not look like an email address.";
    if (v.rangeUnderflow) return `Members must be at least ${input.min}.`;
    if (v.rangeOverflow) return `The upper age limit is ${input.max}.`;
    return input.validationMessage;            // anything else: the browser's own words
  }

  form.addEventListener("submit", (event) => {
    event.preventDefault();
    let firstBad = null;

    for (const input of form.querySelectorAll("input")) {
      const ok = input.checkValidity();        // the browser checks the attributes
      const message = ok ? "" : messageFor(input);
      document.getElementById(input.id + "-error").textContent = message;
      input.setAttribute("aria-invalid", ok ? "false" : "true");
      console.log(input.id, ok ? "OK" : "-> " + message);
      if (!ok && firstBad === null) {
        firstBad = input;
      }
    }

    if (firstBad !== null) {
      done.textContent = "";
      firstBad.focus();
    } else {
      done.textContent = "Welcome to the coding club!";
      console.log("All rules passed.");
    }
  });
</script>

Press Join with both boxes empty: email -> Please fill in this box. and the same for age. Type asha and 15: That does not look like an email address. and Members must be at least 17. Change the age to 75: The upper age limit is 60. Then asha@lpu.in and 19 give All rules passed. Notice that the script contains no email pattern and no number checks: the rules live only in the HTML.

The experiment. Put // in front of the form.noValidate line, press Run again, and press Join with the boxes empty. The browser's bubble appears, and the Console stays at Nothing logged yet: the submit event never fired, which is exactly the trap described above.

novalidate does not delete a single rule. It only tells the browser: "do not interrupt — my script will show the messages." The attributes stay in the HTML as the description of the rules, and both the browser and your script read them.

Quick check: a form has required boxes and a submit listener, but no novalidate. The user presses Submit with one box empty. Does the listener run?

No. The browser's own check fails first, so it shows its bubble and cancels the send before any submit event is fired. Add novalidate (or form.noValidate = true) if your script is to show the messages.

60.7 Why the server must check again

Everything in this chapter runs inside the user's browser, on a machine the user controls. Anyone who wants to send bad data can bypass it in a minute:

  • Switch JavaScript off. Your submit handler simply never runs.
  • Use DevTools. Delete an attribute, edit your script, or type document.querySelector("form").submit() into the Console. The form's submit() method sends the form without firing the submit event and without any validation at all.
  • Skip the page entirely. Tools such as curl or Postman send data straight to the server's address, with no form involved.

So browser validation is for convenience: quick, friendly feedback that saves a round trip. Server validation is for security: the server repeats every rule, usually in another language such as Python, Java, PHP or Node.js, before anything is saved. The lecture puts it in one line: client-side validation improves usability, but the server must independently validate untrusted input.

Exam tip. Any option claiming that JavaScript validation makes server-side validation unnecessary, or "more secure", is wrong. The correct pairing is always: client for user experience, server for security.

60.8 Worked task: the Product Order Form

The lecture's task asks for an order form with six fields, each validated with a regular expression and .test(), a Submit Order button handled through the submit event and event.preventDefault(), a specific message for each invalid field, and "Order Placed Successfully!" only when everything passes.

<script>
  // The six rules from the task: which box, its pattern, and how to describe it
  const rules = [
    { id: "cname",  label: "Customer name", pattern: /^[A-Za-z ]+$/,  hint: "English letters and spaces only" },
    { id: "cemail", label: "Email",         pattern: /^[^\s@]+@[^\s@]+\.[^\s@]+$/, hint: "an address like asha@lpu.in" },
    { id: "cphone", label: "Phone number",  pattern: /^\d{10}$/,      hint: "exactly 10 digits" },
    { id: "pcode",  label: "Product code",  pattern: /^PRD\d{4}$/,    hint: "PRD followed by 4 digits, e.g. PRD1234" },
    { id: "qty",    label: "Quantity",      pattern: /^\d{1,3}$/,     hint: "a whole number from 1 to 999" },
    { id: "coupon", label: "Coupon code",   pattern: /^SAVE\d{2}$/,   hint: "SAVE followed by 2 digits, e.g. SAVE25" },
  ];

  const form = document.getElementById("order");
  const result = document.getElementById("result");

  form.addEventListener("submit", (event) => {
    event.preventDefault();                  // nothing leaves until every rule passes
    let firstBad = null;

    for (const rule of rules) {
      const input = document.getElementById(rule.id);
      const value = input.value.trim();
      let message = "";

      if (value === "") {
        message = `${rule.label} is required.`;
      } else if (!rule.pattern.test(value)) {
        message = `${rule.label} must be ${rule.hint}.`;
      } else if (rule.id === "qty" && Number(value) < 1) {
        message = `${rule.label} must be ${rule.hint}.`;    // "0" has the right shape but is not positive
      }

      document.getElementById(rule.id + "-error").textContent = message;
      input.setAttribute("aria-invalid", message === "" ? "false" : "true");
      console.log(rule.id, JSON.stringify(value), message || "OK");
      if (message !== "" && firstBad === null) {
        firstBad = input;
      }
    }

    if (firstBad !== null) {
      result.textContent = "Order not placed: please fix the messages under the boxes.";
      result.style.color = "#C42B2B";
      firstBad.focus();
    } else {
      result.textContent = "Order Placed Successfully!";
      result.style.color = "#138808";
    }
    console.log("Result:", result.textContent);
  });
</script>

The cursor lands in Email, the first failure. Notice "98765 43210": trim() removes spaces only at the ends, so the space in the middle still breaks the ten-digit rule. Now fix the four boxes — asha@lpu.in, 9876543210, PRD1234, 2 — and press again: six OK lines and Result: Order Placed Successfully! Then try to break it: save25 fails (capitals matter), 000 fails (right shape, but not positive), 1000 fails (four digits) and Asha K. fails (a dot is not a letter).

Two design notes. The quantity rule shows that a pattern checks shape, not meaning: /^\d{1,3}$/ happily accepts 0, so a second, numeric test is needed. And the task makes the coupon compulsory, but a real shop would make it optional. Give that rule optional: true and change the first test:

if (value === "") {
  message = rule.optional ? "" : `${rule.label} is required.`;

An empty optional box is accepted; anything typed in it must still match. Finally, role="status" on the result line makes screen readers announce it when it changes, so a blind user hears whether the order went through (Chapter 59).

60.9 Common misunderstandings

✗ "With JavaScript validation, the server can trust the data."
One line in the Console, form.submit(), sends the form with no checks at all.
✓ "The browser checks for the user's sake; the server checks for safety."
Every rule is repeated on the server before anything is saved.
✗ "required stops a box full of spaces."
Spaces are characters, so the box is not empty.
✓ "Trim first, then test for ""."
value.trim() === "" catches empty and spaces-only alike.
✗ "My submit listener will show my messages even though the boxes have required."
The browser blocks first, and the event never fires.
✓ "Add novalidate, or form.noValidate = true, and let the script speak."
The attributes and the validity flags keep working.
✗ "I only call setCustomValidity when something is wrong."
Then the box stays invalid for ever.
✓ "Call it with the message when wrong, and with "" when right."
And re-run it when either related box changes.
✗ "pattern makes a box compulsory."
An empty box passes pattern, type and minlength.
✓ "Use required as well when a value must be given."
Each attribute checks one thing only.

Exam-style checks

Which method checks a form AND shows the browser's message bubble on the first invalid box?L1
  • A. checkValidity()
  • B. reportValidity()
  • C. setCustomValidity()
  • D. validationMessage

Answer: B. Both A and B return true or false, but checkValidity() is silent. setCustomValidity() sets a message, and validationMessage is a property holding the text, not a check.

In a form's submit handler, what does event.preventDefault() do?L2
  • A. Clears every box in the form
  • B. Runs the browser's built-in validation
  • C. Stops the browser sending the form and loading a new page
  • D. Shows an error message under each box

Answer: C. It cancels the submit event's default action, which is sending the form. It does not validate or show anything by itself.

A form has <input required>, no novalidate, and a submit listener that logs "submit ran". The user presses Submit with the box empty. What happens?L3
  • A. The browser shows its own message and the listener does not run
  • B. The listener runs and logs "submit ran"
  • C. The form is sent with an empty value
  • D. The browser removes the required attribute

Answer: A. Built-in validation runs before the submit event. When it fails, the browser shows its bubble and cancels the send, so no event fires. B is the trap: it is what happens with novalidate.

An <input type="email" required> contains asha@ . Which validity flag is true?L2
  • A. valueMissing
  • B. patternMismatch
  • C. tooShort
  • D. typeMismatch

Answer: D. The box is not empty, so not A; it has no pattern or minlength, so not B or C. The value does not fit type="email", which is a type mismatch.

A confirm-password box calls setCustomValidity("Passwords do not match.") when the passwords differ. After the user fixes them, the box still refuses to be valid. Why, and what is the fix?L3

Answer: the custom error was never switched off. A custom message stays until the script calls setCustomValidity(""). Check on every change of either box and set "" when they match.

Which timing gives live validation without nagging?L2
  • A. Show an error from the very first keystroke
  • B. Check on blur once the user has typed; then re-check on every input while an error is showing
  • C. Check only when the page loads
  • D. Use alert() after every key

Answer: B. Late to complain, quick to forgive. A judges an unfinished value, C runs before the user has typed anything, and D is the worst kind of nagging.

Which pair of attributes connects an invalid input to its error message for screen-reader users?L2
  • A. tabindex and role
  • B. title and placeholder
  • C. aria-hidden and aria-label
  • D. aria-invalid="true" and aria-describedby

Answer: D. aria-invalid announces "invalid entry"; aria-describedby holds the id of the message, which is read after the label whenever the box gets focus.

Why must the server validate data that JavaScript has already validated?L3
  • A. Browser checks can be bypassed: JavaScript can be switched off, edited in DevTools, or skipped by sending data straight to the server
  • B. The server runs JavaScript faster than the browser
  • C. Browsers cannot run regular expressions
  • D. HTML validation attributes are out of date

Answer: A. The browser is on the user's machine, under the user's control. Client-side checks are for convenience; the server's checks are for security.

What does this print?
const v = " 98765 43210 ".trim();
console.log(JSON.stringify(v), /^\d{10}$/.test(v));L3

Answer: "98765 43210" false. trim() removes spaces only at the two ends; the space in the middle stays, so the value is not ten digits from start to end.

What is the effect of form.noValidate = true; in a script?L2
  • A. It deletes every required and pattern attribute
  • B. It makes the form impossible to submit
  • C. The browser stops blocking and showing bubbles, so submit always fires, but validity and checkValidity() still work
  • D. It moves validation to the server

Answer: C. It is the script version of the novalidate attribute. The rules stay in the HTML; the script takes over the messages.

Predict both lines. The box is <input id="code" pattern="PRD\d{4}"> and starts empty.
const code = document.getElementById("code");
console.log(code.validity.valid);
code.value = "PRD12";
console.log(code.validity.patternMismatch);L3

Answer: true, then true. An empty box is not checked against pattern (only required complains about empty), so it starts valid. PRD12 has only two digits, so it does not match and patternMismatch switches on.

Which value passes the Product Code rule /^PRD\d{4}$/ ?L2
  • A. PRD1234
  • B. prd1234
  • C. PRD123
  • D. PRD12345

Answer: A. B has small letters (patterns are case-sensitive), C has only three digits, and D has five, which $ forbids: after exactly four digits the value must end.

Quick revision

Key takeaways

  1. HTML attributes are the foundation, but their messages are the browser's, one at a time, only on Submit, and no attribute can compare two boxes.
  2. Four steps: listen for the form's submit, call preventDefault() first, read and trim() each value, decide, then tell the user.
  3. Check every box, put each message beside its box, mark it with aria-invalid and aria-describedby, and focus() the first problem.
  4. Live checks: late to complain (on blur), quick to forgive (on input while an error shows). Submit still checks everything.
  5. validity flags say which rule failed; checkValidity() is silent, reportValidity() shows bubbles; setCustomValidity("") clears a custom error.
  6. Without novalidate, a failing form never fires submit. Set form.noValidate = true from the script to take over the messages.
  7. A pattern checks shape, not meaning, and an empty box passes every rule except required. The server checks everything again.
