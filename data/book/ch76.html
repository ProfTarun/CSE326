Website Hosting using GitHub Pages

Until now every page you built lived on your own laptop, and nobody else in the world could open it. This chapter puts it on the Internet. GitHub Pages turns the repository you pushed in Chapter 75 into a real website with an address you can send to anyone. It is free, it takes about ten clicks, and the few things that go wrong go wrong in predictable ways.

Before you start — one-line reminders

  • A server is a computer that waits for requests and answers them, and a 404 status means "no such file here" (Chapter 2).
  • A relative path is read from the folder of the current page; ../ goes up one folder; a leading / starts from the top of the site (Chapter 8).
  • A tidy project keeps index.html at the top, with css/, js/ and assets/ beside it, every name in lower case with hyphens (Chapter 73).
  • git add, git commit -m and git push origin main send your latest work to your GitHub repository (Chapter 75).

  • Prepare a project for deployment: index.html at the root, relative paths, lower-case file names, a clean console.
  • Publish a repository through Settings → Pages, and update the live site by pushing again.

76.1 From your laptop to everyone: what hosting means

While you build a site you view it through Live Server, at an address like http://127.0.0.1:5500/index.html. The number 127.0.0.1 always means this very computer; its nickname is localhost. That is why nobody else can see your page.

To let anyone open your pages, the files must sit on a computer that is switched on day and night, connected to the Internet with a public address, and running web server software that answers requests — the server role from Chapter 2. Keeping your files on such a computer is called web hosting; whoever runs that computer is the hosting service. Copying your finished files onto it is called deploying (or publishing) the site.

Hosting means: put a copy of your site on a computer that never sleeps, so that anybody's browser, anywhere, at any hour, can ask it for your pages.

Five words get mixed up all the time in this topic:

WordWhat it isExample
Local siteYour files, opened on your own machinehttp://127.0.0.1:5500/ — only you can see it
RepositoryWhere the code and its history are storedhttps://github.com/ananya-k/portfolio — shows the code
Hosting serviceThe always-on computer that sends your files to visitorsGitHub Pages, Netlify, a college server
Live URLThe public address people type to see the sitehttps://ananya-k.github.io/portfolio/
DeploymentPutting the finished files on the host and switching them onPushing to main with Pages turned on
Key idea. A repository stores code; it is not automatically a website. Hosting is what turns a folder of files into a site people can visit. GitHub offers both in the same place, which is why students confuse them.
Quick check: Rahul opens the link http://127.0.0.1:5500/index.html that Asha sent him. What does he see?

Not Asha's site. 127.0.0.1 always means "this computer", so his browser asks his own laptop. If he is not running Live Server he gets "This site can't be reached"; if he is, he sees his own project. A localhost address can never be shared.

76.2 Static hosting and backend servers

Hosts come in two kinds, and the difference decides whether GitHub Pages can host your project at all.

A static host does the simplest job possible. A request arrives for about.html; the host finds that file and sends it exactly as it is stored, the same bytes to every visitor. It can serve any kind of file — HTML, CSS, JavaScript, images, fonts, PDFs, JSON — but it never runs any of your code itself.

A backend server (a dynamic host) does more. A request arrives for /my-marks; the server runs code — Node.js with Express, Python with Django, PHP, Java… — which checks who is asking, reads a database and builds a fresh page for that one person. Logins, saved comments, payments and anything with a database need a server like this.

Picture this. The notice board outside your department office is a static host. Anyone walking past reads exactly what is pinned — the same sheet for everybody, at any hour, with nobody on duty. You cannot hand the board a form, because there is no one behind it. The help desk inside is a backend server: you ask "what are my marks?", and the clerk looks you up in the register and writes an answer just for you. GitHub Pages is a notice board. Updating it means pinning up a new sheet (pushing a new commit), and because the board stands in a public corridor, you never pin up anything secret.

Static does not mean boring

A common mistake is "a static site cannot have JavaScript". It can. The host sends main.js exactly as it sends logo.png, and then the visitor's browser runs it. So quizzes, calculators, games, a to-do list saved with localStorage (Chapter 64) and a weather page that fetches a public API (Chapter 65) all work on a static host.

A static host only sends files. Any thinking happens afterwards, inside the visitor's own browser. If your project needs thinking on the host — checking a password, saving a message for everyone — a static host cannot do it.

Everything on Pages is public. Every file of a published site can be downloaded by anyone, including the API key you "hid" in js/config.js. Nothing sent to a browser is secret (Chapter 1), and on a static host every file is sent to the browser. Secrets belong on a backend server.
Quick check: can a to-do list that saves its tasks with localStorage be hosted on GitHub Pages?

Yes. Its files are ordinary static files, and the saving happens in the visitor's own browser, not on the host. The catch: each visitor sees only their own list. A list shared between Asha and Rahul would need a backend.

76.3 What GitHub Pages is

GitHub Pages is a hosting service for static websites — HTML, CSS, JavaScript and other static files — published directly from a GitHub repository. Pages reads the files from your repository and serves them at a github.io address. Three facts worth knowing:

  • It is free for public repositories on the GitHub Free plan. Publishing from a private repository needs a paid plan (GitHub Pro, Team or Enterprise), and even then the published site is normally public: a private repository hides the code, not the website.
  • It uses HTTPS automatically: every github.io address starts with https://.
  • It updates itself: once switched on, every push to the publishing branch publishes the new version.

User site and project site

Pages makes two kinds of site, and the only thing that decides which one you get is the name of the repository:

Site typeRepository namePublished URLHow many
User siteUSERNAME.github.io, e.g. ananya-k.github.iohttps://ananya-k.github.io/One per account
Project siteAny other name, e.g. portfoliohttps://ananya-k.github.io/portfolio/One per repository

Look at the project site's address: the repository name has become the first folder of the path. A project site does not own the whole ananya-k.github.io address; it lives in a sub-folder of it, the project subpath. Section 76.7 is about the trouble this causes.

https://ananya-k.github.io/portfolio/about.html

        username GitHub    repo name the file

Two URLs, two audiences

Every published project has two addresses, and students regularly hand in the wrong one. The repository URL, https://github.com/ananya-k/portfolio, shows the code: file list, README, commits — for developers. The published URL, https://ananya-k.github.io/portfolio/, shows the website itself — for users, teachers and recruiters.

Exam tip. A user-site URL has no repository name in its path (https://USERNAME.github.io/); a project-site URL ends with it (https://USERNAME.github.io/REPOSITORY/). An option starting https://github.com/ is the repository, not the website; https://REPOSITORY.github.io/USERNAME/ has the two names swapped.

76.4 How a repository becomes a website

Deployment with Pages is a chain of six stages. You already know the first three from Chapter 75; the last three are new.

  1. Local site. It works with Live Server, and the Console is clean.
  2. Commit. git add . and git commit -m "..." snapshot the final files.
  3. Push. git push origin main copies the commits to GitHub. The files are now in the repository — but still not a website.
  4. Configure Pages (once). In Settings → Pages you choose a branch (usually main) and a folder in it (usually / (root), the top of the repository).
  5. Publish. GitHub runs an automatic workflow, shown in the Actions tab as pages build and deployment, which copies the files from that branch and folder onto GitHub's web servers.
  6. Live URL. The site is at https://ananya-k.github.io/portfolio/. Open it, test it, share it.

Pushing puts your files in the repository. Switching Pages on tells GitHub: "whenever main changes, copy its files onto your web servers". From that moment, push = publish.

Publishing usually finishes within a minute or two; GitHub's documentation allows up to ten minutes. So when a change "has not appeared", look at the Actions tab before changing any code.

One thing the publishing step may do to your files

When you publish from a branch, GitHub passes your files through Jekyll, a tool that can turn Markdown files into HTML pages. Ordinary HTML, CSS and JavaScript come out unchanged, with two side effects. First, Jekyll skips files and folders whose names begin with an underscore, so a folder called _images/ never reaches the live site; rename it, or add an empty file called .nojekyll at the top of the publishing folder to switch Jekyll off. Second, if there is no index.html, Pages uses index.md or README.md as the home page — which is why a mis-named index.html can show up as "my site shows my README".

Most deployment problems are created before anything is deployed, so a five-minute check on your laptop saves an hour later. Start with the folder shape from Chapter 73:

CheckWhy it matters
index.html at the top of the folderA folder address such as …/portfolio/ is answered with that folder's index.html. A home page called home.html or Index.html gives a 404 (or your README).
Relative paths onlyhref="css/style.css", src="assets/images/logo.png". Never C:\Users\… or file:///… (they exist only on your laptop), never a leading / (section 76.7).
Lower-case names, hyphens, no spacesLogo.PNG and logo.png are different files online. Spaces become %20 in addresses. Write team-photo.jpg.

External APIs use HTTPSPages is served over https://, so the browser blocks a fetch to an http:// address as mixed content. The API must also allow requests from other sites (CORS, Chapter 65).
Everything committed and pushedgit status should say nothing to commit, working tree clean. A file that was never added never reaches GitHub.
Key idea. If it does not work with Live Server and a clean console, it will not work on GitHub Pages either. The reverse is not guaranteed: two bugs hide on your laptop — capital letters in file names, and paths that start with /.

Why capital letters only hurt online

Windows treats Logo.PNG and logo.png as the same file, so <img src="assets/images/logo.png"> happily finds Logo.PNG on your laptop. GitHub Pages, like most web servers, treats file names as case-sensitive: Logo.PNG and logo.png are two different names, and only one of them exists. The image is broken online and perfect at home.

Your laptop forgives capital letters; the server does not. Name every file in small letters, and type every path exactly as the file is named.

One more trap on Windows: if you rename Logo.PNG to logo.png in File Explorer, Git usually does not notice a change that is only in capital letters, and the repository keeps the old name. Rename it through Git instead:

git mv assets/images/Logo.PNG assets/images/logo.png
git commit -m "Rename logo to lower case"
git push

# if git mv complains, go through a temporary name:
git mv assets/images/Logo.PNG assets/images/temp.png
git mv assets/images/temp.png assets/images/logo.png

Here is the checklist as a little program. It looks at the files in Rahul's project and the paths in his HTML, and reports what will break online.

<style>
  body { font-family: system-ui, sans-serif; padding: 14px; color: #14243B; font-size: 14px; }
  li { margin: 4px 0; }
  .ok  { color: #138808; font-weight: 700; }
  .bad { color: #C42B2B; font-weight: 700; }
</style>
<p id="verdict"></p>
<ol id="list"></ol>
<script>
  // Every file in Rahul's project folder, exactly as Git will upload it
  const files = [
    "Index.html",
    "css/style.css",
    "js/main.js",
    "assets/Logo.PNG",
    "assets/team photo.jpg"
  ];

  // Every href and src written inside his HTML
  const links = [
    "css/style.css",
    "/js/main.js",
    "assets/logo.png",
    "C:\\Users\\rahul\\Desktop\\site\\team.jpg",
    "http://api.example.com/marks.json"
  ];

  const problems = [];
  function report(what, detail) {
    problems.push({ what, detail });
  }

  // 1. The home page must be called exactly index.html, at the top
  if (!files.includes("index.html")) {
    report("home page", "no index.html at the top of the folder");
  }

  // 2. File names: small letters only, no spaces
  for (const f of files) {
    if (f !== f.toLowerCase()) report("file name", `${f} has capital letters`);
    if (f.includes(" ")) report("file name", `"${f}" has a space`);
  }

  // 3. Links: relative, and spelled exactly like a real file
  for (const link of links) {
    if (link.startsWith("https://")) continue;     // another site, over HTTPS: fine
    if (link.startsWith("http://")) {
      report("link", `${link} is http:// and will be blocked on an https:// site`);
    } else if (link.includes(":\\")) {
      report("link", `${link} points into your own computer`);
    } else if (link.startsWith("/")) {
      report("link", `${link} starts with / and will miss a project site`);
    } else if (!files.includes(link)) {
      const near = files.find(f => f.toLowerCase() === link.toLowerCase());
      report("link", near ? `${link} - but the file is called ${near}` : `${link} - no such file`);
    }
  }

  console.table(problems);
  const verdict = document.querySelector("#verdict");
  verdict.textContent = problems.length === 0
    ? "Ready to push."
    : `${problems.length} problems to fix before you push:`;
  verdict.className = problems.length === 0 ? "ok" : "bad";
  console.log(verdict.textContent);

  for (const p of problems) {
    const li = document.createElement("li");
    li.textContent = `${p.what}: ${p.detail}`;
    document.querySelector("#list").append(li);
  }
</script>

As written it finds 8 problems: no index.html, two names with capitals, one with a space, and four bad links (a root path, a capital-letter mismatch, a C:\ path, an http:// API). Now play Rahul: rename Index.html to index.html, assets/Logo.PNG to assets/logo.png and assets/team photo.jpg to assets/team-photo.jpg; change the links to js/main.js, assets/team-photo.jpg and https://api.example.com/marks.json; and Run again until it says Ready to push.

76.6 Deploy it, step by step

The first deployment takes about ten minutes; after that, publishing a change takes one command.

  1. Create or open a GitHub repository. Make it Public (on the free plan, Pages needs a public repository).
  2. Put the website files in it. Push from your computer (Chapter 75), or use Add file → Upload files on GitHub. index.html must be at the top of the repository, not inside another folder.
  3. Open the repository's Settings tab (the last tab along the top).
  4. Click Pages in the left sidebar.
  5. Source: under Build and deployment, choose Deploy from a branch.
  6. Branch: choose main, and folder / (root).
  7. Click Save.
  8. Wait for the deployment: the Actions tab's pages build and deployment run shows a yellow dot while it works, a green tick when done, a red cross if it failed.
  9. Open the published URL. Settings → Pages now says Your site is live at…, with a Visit site button.
  10. Verify; fix problems; push again. Click every link, check every image, open the Console on the live site, try it on a phone.
ananya-k / portfolio  ›  Settings  ›  Pages        (recreated; GitHub's layout may change)

GitHub Pages

Build and deployment
  Source    [ Deploy from a branch ▾ ]
  Branch    [ main ▾ ]   [ / (root) ▾ ]   [ Save ]

The folder menu offers only / (root) or /docs; pick /docs only if you keep the website inside a docs folder. The Source menu's other choice, GitHub Actions, is for sites that need a build tool first; a plain HTML, CSS and JavaScript site does not.

Redeploying: just push

You never go back to Settings to publish a change. Edit, commit, push:

# fixed a spelling mistake in index.html, then:
git add index.html
git commit -m "Fix typo in About section"
git push

# Actions tab: a new run appears; when it shows a green tick,
# reload the live site

Pages was switched on once, in step 7; from then on every push to main starts a new deployment by itself.

76.7 Paths on a project site: the subpath problem

This is the most common reason a site that is perfect on a laptop arrives broken on GitHub Pages: the text appears, but with no styling, no pictures and no JavaScript. Here are Chapter 8's path rules again, applied to a real project site.

When the browser meets href="css/style.css" on the page https://ananya-k.github.io/portfolio/about.html, it drops the file name to get the page's folder, https://ananya-k.github.io/portfolio/, adds the path to the end, and requests https://ananya-k.github.io/portfolio/css/style.css.

A path that starts with / means "start from the very top of the domain": the browser keeps only https://ananya-k.github.io and adds the path to that. /css/style.css becomes https://ananya-k.github.io/css/style.css — portfolio has gone, and there is no such file.

Written in about.htmlBrowser requestsResult
css/style.csshttps://ananya-k.github.io/portfolio/css/style.css200 ✓
./css/style.csshttps://ananya-k.github.io/portfolio/css/style.css200 ✓ (./ means "this folder")
/css/style.csshttps://ananya-k.github.io/css/style.css404 ✗ outside the project
../css/style.csshttps://ananya-k.github.io/css/style.css404 ✗ climbed out of the project
assets/Logo.pnghttps://ananya-k.github.io/portfolio/assets/Logo.png404 ✗ the file is logo.png

Why did it work on my laptop?

Because Live Server serves your project folder as the top of the site: http://127.0.0.1:5500/ is your portfolio folder, so /css/style.css really was your file. Online, the top of ananya-k.github.io belongs to Ananya's user site, not to her portfolio. For the same reason a root path works on a user site and breaks when the same files are published as a project site. Relative paths work in all three places — laptop, user site, project site.

A path without a slash at the front says "start from the folder this page is in". A path with a slash at the front says "start from the very top of the domain". On a project site the very top is not your project — so leave the slash off.

Pages inside sub-folders need one more step. From blog/first-post.html the stylesheet is up one folder, so that page writes ../css/style.css, while index.html writes css/style.css.

JavaScript's new URL(path, page) resolves a path exactly the way the browser does, which makes it a perfect checking tool:

    return new URL(path, page).href;

  const pageBox = document.querySelector("#page");

    } catch (err) {

https://ananya-k.github.io/portfolio/css/style.css. A relative path is added to the folder of the current page, which is /portfolio/.

76.8 When it goes wrong: reading the symptoms

Almost every deployment error is the same thing underneath: the browser asked for one particular file and the server said 404. So the method is always the same:

  1. Open the live site, not your local copy.
  2. Press F12, open the Network panel, and reload.
  3. Click a red row with status 404: Request URL shows exactly which address was asked for.
  4. Compare it with your repository's file list, letter by letter, capitals included.
SymptomLikely causeFix
404 for the whole sitePages not switched on, wrong branch or folder, or still deployingCheck Settings → Pages and the Actions tab; wait, then reload
The site shows your README, or 404 at the main addressNo index.html at the top of the publishing folder (Index.html, home.html, or in a sub-folder)Rename or move it to index.html at the root
Page loads with no stylesWrong CSS path, or a path starting with /Use relative href="css/style.css"; check Network
Buttons do nothingThe JS file is a 404, or there is a console errorFix the script path; read the Console on the live site
Broken imagesCapitals do not match, or the image was never pushedMatch the case (git mv); git status; push it

"I pushed, but nothing changed"

Two things can show you an old version. The deployment may not have finished, so look at the Actions tab. Or your browser's cache may be showing yesterday's style.css (Chapter 74). A hard refresh — Ctrl+Shift+R on Windows and Linux, Cmd+Shift+R on a Mac — fetches every file again; a private (incognito) window, which starts with an empty cache, is another quick test.

Do not "fix" a site that is still deploying. A student pushes, reloads ten seconds later, sees the old page, changes three more things and pushes again — and now has three new bugs. Check the Actions tab first. Green tick and still old? Hard refresh. Only then debug.

A finishing touch: a file named 404.html at the top of the publishing folder is shown whenever someone asks for an address that does not exist, instead of GitHub's plain error page.

  // How a static host answers one request: find the file, or say 404
  function serve(address) {
    const url = new URL(address);
    if (url.hostname !== "ananya-k.github.io") return "(this pretend server only knows ananya-k.github.io)";
    const path = url.pathname;                         // e.g. "/portfolio/css/style.css"
    if (path === "/portfolio") return "301 Moved: adds the missing / at the end";
    if (!path.startsWith(site)) return "404 Not Found: outside the /portfolio/ site";
    let file = decodeURIComponent(path.slice(site.length));        // "css/style.css"
    if (file === "" || file.endsWith("/")) file += "index.html";   // a folder means its index.html
    return repo.includes(file) ? "200 OK: sends " + file : "404 Not Found: no file called " + file;
  }

  // Show one answer on the page: green for 200 or 301, red for anything else
  function line(where, answer, label = "") {
    const div = document.createElement("div");
    div.className = "r " + (/^(200|301)/.test(answer) ? "ok" : "bad");
    div.textContent = label + answer;
    where.append(div);
  }

  // 1. The home page, then every file it asks for
  const page = "https://ananya-k.github.io/portfolio/";
  const log = document.querySelector("#log");
  line(log, serve(page), "the page itself → ");
  console.log(page, "→", serve(page));

  const wanted = ["css/style.css", "/css/style.css", "js/main.js",
                  "assets/Logo.png", "about.html"];
  for (const path of wanted) {
    const address = new URL(path, page).href;
    const answer = serve(address);
    line(log, answer, path + " → ");
    console.log(path, "→", address, "→", answer);
  }

  // 2. Your own experiments
  const box = document.querySelector("#url");
  const one = document.querySelector("#one");
  function ask() {
    one.textContent = "";
    try {
      line(one, serve(box.value));
    } catch (err) {
      line(one, "Type a full address starting with https://");
    }
  }
  box.addEventListener("input", ask);
  ask();
</script>

The page itself and three of its files come back 200; /css/style.css and assets/Logo.png come back 404. In the box, change Logo to logo and watch it turn green. Then try https://ananya-k.github.io/portfolio without the final slash (GitHub really does redirect it), https://ananya-k.github.io/portfolio/ (the folder gives you index.html) and https://ananya-k.github.io/css/style.css (outside the project).

Quick check: on Rahul's live quiz, the Network panel shows GET https://rahul-dev.github.io/js/app.js — 404. His repository is called quiz. What is the bug?

The address has lost /quiz/, so his home page almost certainly says src="/js/app.js" with a leading slash. Changing it to src="js/app.js" makes the browser request https://rahul-dev.github.io/quiz/js/app.js, where the file really is.

76.9 Your own domain name (briefly)

A github.io address is free and perfectly respectable. If you would rather have www.ananyak.in, you can buy that name yearly from a domain registrar and point it at GitHub Pages. Names are turned into the numbers of real computers by the DNS, so connecting a domain means adding two or three records to that phone book:

  1. In Settings → Pages → Custom domain, type www.ananyak.in and click Save. When you publish from a branch, GitHub commits a small file called CNAME to your repository to record it.
  2. In the registrar's DNS settings, add the records below: www points at your github.io address (without the repository name); the bare name (written @) points at GitHub Pages' four IP addresses.
  3. Wait: DNS changes can take up to 24 hours to spread.
  4. Tick Enforce HTTPS in Settings → Pages once it becomes available.

76.11 Common misunderstandings

✗ "I pushed my code, so my website is live."
A push only stores the code in the repository. Until Pages is switched on, github.com/you/project shows a file list, not a website.
✓ "Pages is switched on once; after that, every push publishes."
Settings → Pages → Deploy from a branch, main, / (root), Save. Then share the github.io address.
✗ "A static site cannot have JavaScript."
The host does not run the JavaScript, but it sends the file, and the visitor's browser runs it.
✓ "Static means the host sends files unchanged."
Quizzes, games and pages that fetch public APIs all work. Only server code, databases and secrets are ruled out.
✗ "It works on my laptop, so the paths must be right."
Windows ignores capital letters, and Live Server makes / mean your project folder.
✓ "Test the live site too, with the Network panel open."
Lower-case names and relative paths remove both bugs.
✗ "The live site didn't change, so my push failed."
Publishing takes a minute or two (up to ten), and your browser may show a cached copy.
✓ "Check the Actions tab, then hard-refresh."
Green tick plus Ctrl+Shift+R settles it.

Answer each one before opening it.

Which of these projects can be hosted on GitHub Pages as it is?L1
  • A. A Node.js and Express API that stores orders
  • B. A PHP login page that checks passwords in MySQL
  • C. A portfolio built from HTML, CSS, JavaScript and images
  • D. A Django shop that takes payments

Answer: C. GitHub Pages is a static host: it sends files unchanged and runs no code of yours. A, B and D all need server code and a database.

The GitHub user rahul-dev publishes the repository quiz-app with GitHub Pages from main / (root). What is the published URL?L3
  • A. https://github.com/rahul-dev/quiz-app
  • B. https://rahul-dev.github.io/
  • C. https://quiz-app.github.io/rahul-dev/
  • D. https://rahul-dev.github.io/quiz-app/

Answer: D. Any repository not named rahul-dev.github.io is a project site, published at https://USERNAME.github.io/REPOSITORY/. A is the repository (the code), B is the user site, and C swaps the two names.

Predict the URL: the page https://ananya-k.github.io/portfolio/about.html contains <link rel="stylesheet" href="css/style.css">. Which address does the browser request?L3

Answer: https://ananya-k.github.io/portfolio/css/style.css. A relative path is added to the folder of the current page, and that folder is /portfolio/.

A project site at https://ananya-k.github.io/portfolio/ shows its text but no styling. Its index.html contains <link rel="stylesheet" href="/css/style.css">. What is the most likely cause?L3
  • A. GitHub Pages does not support external CSS files
  • B. The leading / makes the browser request https://ananya-k.github.io/css/style.css, outside the project
  • C. CSS files must sit next to index.html, never in a folder
  • D. The stylesheet must be linked at the end of the body

Answer: B. A leading slash means "start from the top of the domain", which skips /portfolio/, so the request is a 404. href="css/style.css" fixes it.

Rahul's image shows on his Windows laptop but is broken on GitHub Pages. The file is assets/Logo.PNG and the tag is <img src="assets/logo.png" alt="Logo">. What is wrong?L2

  • B. GitHub Pages cannot serve PNG images
  • C. Images must be stored in the root folder
  • D. The alt text must match the file name

Answer: A. Windows ignores capital letters; GitHub Pages does not. Rename the file to logo.png with git mv, commit and push.

GitHub Pages shows a site's home page from a file with which exact name, at the top of the publishing folder?L1

Meera pushed a fix twenty seconds ago, but the live site still shows the old version. What is the best first step?L3

Which sequence publishes a site with GitHub Pages for the first time?L2

  • B. Settings → Pages, then run git init, then share the repository URL

Answer: A. The files must be in the repository, Pages must be switched on once, and the result is the github.io address. A repository URL shows code, not a site, and a private repository on the free plan cannot use Pages.

Meera adds a "Contact me" form to her portfolio on GitHub Pages. Visitors press Send, but the messages are never stored anywhere. Why?L2

Answer: No. The page loads config.js, so the file is sent to every visitor's browser, where anyone can read it in DevTools (Sources or Network) or by typing its address. A secret key belongs on a backend server; since this one is already public, he should revoke it and create a new one.

Quick revision

Key takeaways

  1. Hosting means keeping your files on an always-on, connected computer that answers requests. A repository stores code; it is not automatically a website.
  2. A static host sends files exactly as stored; JavaScript runs in the visitor's browser. GitHub Pages is static: no server code, no database, no secrets.
  3. User site: repository USERNAME.github.io → https://USERNAME.github.io/. Project site: any other repository → https://USERNAME.github.io/REPOSITORY/. Share the github.io address, not the github.com one.
  4. Deploy: push, then Settings → Pages → Deploy from a branch → main, / (root) → Save; wait for the Actions run; open the URL. After that, every push redeploys.
  5. Before pushing: index.html at the root, relative paths, lower-case names without spaces, a clean console, HTTPS APIs, everything committed.
  6. A leading / means the top of the domain, outside a project site. Write css/style.css, never /css/style.css.
  7. Diagnose on the live site with the Network panel: most failures are one 404 for one file. An old version means a deployment still running or the cache (Ctrl+Shift+R).
