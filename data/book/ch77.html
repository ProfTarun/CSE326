Web Development Best Practices

A website can work perfectly on your laptop and still fail the blind student who cannot find its button, the teammate who cannot read its code, the phone it does not fit, and the stranger who uses it to steal your users' data. Best practices are the habits that prevent all four. This chapter gathers them in one place and ends with the checklist to tick before you hand anything in.

About 35 minutes · Course outcome CO6

Before you start — one-line reminders

  • HTML should be lowercase, quoted, semantic and validated before it is published (Chapter 12).
  • A responsive page has the viewport meta tag and flexible media, and is tested on a real phone (Chapter 21).
  • Native <button>, <a> and <input> come with keyboard and screen-reader support; custom controls do not (Chapter 59).
  • Lighthouse and the Network panel measure how fast a page loads (Chapter 74).

By the end of this chapter you can

  • Connect each best practice to the quality it protects.
  • Find and fix the six semantic and accessibility problems in a typical first page.
  • Refactor repeated CSS and cryptic JavaScript without changing the result.
  • Show user data safely with textContent, and explain why browser-side validation and "hidden" API keys are not security.
  • Plan a test across widths, browsers, the keyboard and a slow network with a testing matrix.
  • Use the W3C validator, Lighthouse and axe or WAVE, and say what each cannot see.
  • Run the final checklist on your own project.

77.1 Why best practices matter

Chapter 76 put your site on the Internet, so now strangers will use it. Working is the minimum. A best practice is a habit experienced developers follow because it keeps code working, and understandable, long after the day it was written: when the data is strange, when the reader cannot see, when somebody is trying to break it.

Who meets your website? Not only you, with Chrome and fast Wi-Fi. Also a student on a cheap phone; a blind student whose screen reader speaks the page aloud; Google's search robot; the teammate adding a feature next month; and somebody looking for a way to misuse it. The slide groups the habits by the quality each one protects:

Reliability means the page survives edge cases such as an empty box (Chapter 70). Maintainability means the next change is cheap (Chapter 73). Accessibility means keyboard and screen-reader users can use the page (Chapter 59). Security means it cannot easily be turned against its users. Teamwork means someone else can pick it up (Chapter 75). Search engines gain too: semantic headings, alt text, speed and HTTPS all help a page rank (Chapter 11).

Picture this. A city's building code demands a ramp beside the steps, fire exits and wiring in standard colours. None of it makes the building look better on opening day, and a builder in a hurry can skip it all and still hand over a building that stands. The code exists for the days after: the visitor in a wheelchair, the electrician repairing a wall he did not build, the night of a fire. Best practices are a website's building code: the ramp is accessibility, the fire exit is error handling, the wiring colours are clear names.
Key idea. Every practice here costs a little time once and saves time, money or a user every time the code is read, run or attacked afterwards.

77.2 Semantic and accessible HTML

Units 1 and 2 taught semantic, accessible HTML one element at a time. The slide turns it into one exercise: before.html looks fine with a little CSS, but it has six problems. Find them before you read on.

<!-- before.html -->
<div class="header">
  <div class="title">My Blog</div>
  <div onclick="go('home')">Home</div>
</div>
<div class="big">Latest posts</div>
<div class="small">Post one</div>
<img src="cat.jpg">
<input placeholder="Email">
<div class="btn" onclick="send()">Send</div>
Quick check: why is placeholder="Email" not enough to name the box?

The placeholder vanishes as soon as the user types, and it is not a reliable name for screen readers. A <label> stays visible, is read out, and clicking it puts the cursor in the box.

The corrected after.html, and the six problems it fixes:

<!-- after.html -->
<header>
  <h1>My Blog</h1>
  <nav><a href="index.html">Home</a></nav>
</header>
<main>
  <h2>Latest posts</h2>
  <h3>Post one</h3>
  <img src="cat.jpg" alt="Ginger cat asleep">
  <form>
    <label for="email">Email</label>
    <input id="email" type="email">
    <button type="submit">Send</button>
  </form>
</main>

after.html can be styled to look exactly like before.html. The difference is what the browser knows. Use the element that matches what the thing is, and keyboard support, screen-reader announcements and search-engine understanding come free. A div gives you none of them.

77.3 Maintainable CSS and JavaScript

The next slide is a refactor: change how code is written without changing what it does. First the CSS, three buttons and three rules:

/* styles.css - BEFORE */
#saveBtn   { background: #4338ca; color: white; padding: 8px 16px; border-radius: 6px; }
#sendBtn   { background: #4338ca; color: white; padding: 8px 16px; border-radius: 6px; }
#deleteBtn { background: red;     color: white; padding: 8px 16px; border-radius: 6px; }

It works. Now the college changes its brand colour: you must find the same hex code twice here, and in every file where somebody copied it. Miss one and the site has two blues. The habit that avoids this is called DRY.

/* styles.css - AFTER */
:root { --primary: #4338ca; --danger: #dc2626; }

.btn         { background: var(--primary); color: white;
               padding: 8px 16px; border-radius: 6px; }
.btn--danger { background: var(--danger); }

<!-- index.html -->
<button class="btn">Save</button>
<button class="btn">Send</button>
<button class="btn btn--danger">Delete</button>

Three ID rules became one reusable class plus a modifier class that changes only what differs (the double dash, a habit called BEM, means "a variation of .btn"). The colours moved into custom properties (Chapter 36), so a new brand colour is one edit; the slide also swaps the keyword red for a chosen shade. Now the JavaScript:

// cart.js - BEFORE
function f(a) { var t = 0; for (var i = 0; i < a.length; i++) t = t + a[i].p * a[i].q; return t * 1.18; }

// cart.js - AFTER
const GST_RATE = 0.18;   // 18% GST on all items

function cartTotal(items) {
  let subtotal = 0;
  for (const item of items) {
    subtotal += item.price * item.qty;
  }
  return subtotal * (1 + GST_RATE);
}

What do f, a, t, p and q mean? You can only guess. 1.18 is a magic number: a tax? a discount? In the second version every name answers its own question, the rate has a name and a comment, and var is gone (Chapter 42). Prove that only readability changed:

<p>Both functions get the same cart. Read the Console panel.</p>
<p id="out"></p>
<script>
  // BEFORE: works, but tells the reader nothing
  function f(a) { var t = 0; for (var i = 0; i < a.length; i++) t = t + a[i].p * a[i].q; return t * 1.18; }

  // AFTER: the same logic, readable
  const GST_RATE = 0.18;   // 18% GST on all items

  function cartTotal(items) {
    let subtotal = 0;
    for (const item of items) {
      subtotal += item.price * item.qty;
    }
    return subtotal * (1 + GST_RATE);
  }

  // the old code needed the short property names p and q
  const oldCart = [{ p: 250, q: 2 }, { p: 100, q: 1 }];
  const cart = [
    { name: "Notebook", price: 250, qty: 2 },
    { name: "Pen set", price: 100, qty: 1 }
  ];

  console.log("Before:", f(oldCart));
  console.log("After:", cartTotal(cart));
  console.log("Same answer?", f(oldCart) === cartTotal(cart));
  document.querySelector("#out").textContent =
    "Total with GST: ₹" + cartTotal(cart).toFixed(2);
</script>

Both print 708 (₹600 plus 18%), the third line prints true, and the page shows Total with GST: ₹708.00. Identical output, very different cost the next time the rate changes.

Refactoring is tidying, not changing. You rename, split and remove repetition, then check the result is exactly the same. If the output changes, it was not a refactor — it was a new bug.

A comment that explains why stays true; one that explains what goes stale when the line changes:

// WEAK: says what the code already says

Let tools enforce the boring parts. A formatter such as Prettier re-indents a whole file in one keystroke. A linter such as ESLint underlines likely mistakes, such as an unused variable, before you press Run. Both have VS Code extensions.

77.4 Frontend security fundamentals

The slide's big idea: everything sent to the browser is visible to, and changeable by, the person using it. Any visitor can read and edit your HTML and JavaScript in DevTools, watch every request, and call your server without your page at all (Chapter 69). So front-end security rests on two habits: never trust what comes in, and never hide in the page what must stay secret. The slide's six practices follow, plus one it leaves out: safe new-tab links.

1. Never trust input: textContent, not innerHTML

Untrusted data is anything you did not write yourself: form input, the query string, API data, values from localStorage. Any of it can contain HTML. On Asha's class-notes site, Rahul leaves this comment:

Nice notes! <img src="x" onerror="...any JavaScript Rahul likes...">

If the site displays comments with innerHTML, the browser reads those characters as HTML code. It builds a real <img>, fails to load the image x, and runs the onerror attribute as JavaScript. Every visitor now runs Rahul's code inside Asha's site. This is XSS, cross-site scripting, one of the Web's most common security holes. The script can read what users type, steal a login token from localStorage, or redraw the page as a fake login form.

// UNSAFE: the browser parses the comment as HTML and may run code inside it
wall.innerHTML = comment;

// SAFE: the browser shows the comment as plain characters, nothing runs
wall.textContent = comment;

The example does it for real. Here the attacker's comment only turns the page pink and prints a warning; on a real site it could do anything.

<style>
  body { font-family: system-ui, sans-serif; padding: 14px; color: #0B2545; }
  textarea { width: 100%; height: 58px; font: 13px monospace; box-sizing: border-box; }
  button { margin: 8px 8px 8px 0; padding: 8px 14px; font-weight: 700; border: 0;
           border-radius: 8px; color: #fff; cursor: pointer; }
  #unsafe { background: #C42B2B; }
  #safe { background: #138808; }
  .wall { border: 1px solid #CBD5E1; border-radius: 8px; padding: 8px 10px; min-height: 22px; }
</style>
<label for="msg">A comment (an attacker typed this):</label>
<textarea id="msg">Nice notes! <img src="x" onerror="document.body.style.background='#FCE4E4'; console.error('ATTACK: code from a comment just ran inside your page')"></textarea>
<button id="unsafe" type="button">Post with innerHTML</button>
<button id="safe" type="button">Post with textContent</button>
<p><b>Comment wall</b></p>
<div class="wall" id="wall"></div>
<script>
  const msg = document.querySelector("#msg");
  const wall = document.querySelector("#wall");

  document.querySelector("#unsafe").addEventListener("click", () => {
    wall.innerHTML = msg.value;            // parsed as HTML: an <img> is created
    console.log("innerHTML: elements inside the wall =", wall.children.length);
  });

  document.querySelector("#safe").addEventListener("click", () => {
    document.body.style.background = "";
    wall.textContent = msg.value;          // shown as characters: nothing is created
    console.log("textContent: elements inside the wall =", wall.children.length);
  });
</script>

Press the red button: the Console prints innerHTML: elements inside the wall = 1 (the image the browser built), then the red ATTACK line as the failed load fires onerror. Press the green button: the page turns white, the comment appears as ordinary text, angle brackets and all, and the Console prints ... = 0. Nothing was built, so nothing could run.

innerHTML means "read this as HTML code". textContent means "show these letters". Anything a user typed, or an API sent, must go in as letters.

A trap. Students test XSS with <script>alert(1)</script>, see nothing happen, and decide innerHTML is safe. It is not. A <script> inserted through innerHTML never runs (the HTML standard says so), but event-handler attributes such as onerror on the elements it creates do.

When you build content from data (Chapter 58), create the element yourself and put the user's words in as text. innerHTML is fine for fixed markup you wrote:

// SAFE: create the element, then add the user's words as text
const li = document.createElement("li");
li.textContent = comment.text;            // any < > & stay harmless characters
commentList.append(li);

// RISKY: user text pasted into a template, then parsed as HTML
commentList.innerHTML += `<li>${comment.text}</li>`;

// FINE: fixed markup you wrote yourself, no outside data
emptyState.innerHTML = "<b>No comments yet.</b> Be the first!";

A site that must accept formatted HTML from users passes it through a tested sanitiser library such as DOMPurify. Never write your own filter; attackers know the ways round them.

2. Validate in the browser for convenience, on the server for safety

Validating data means checking its type, length, format and range (marks from 0 to 100) before you use it, as Chapters 18 and 60 did in the browser. Now the slide's prediction question. A registration page contains this check:

if (age.value < 18) {
  return showError("Must be 18+");
}

Can a 15-year-old still register? Yes: turn JavaScript off; edit the if in DevTools; or skip the page and send the request straight to the server with fetch in the Console or a tool such as curl. The check lives on the user's computer, so the user decides whether it runs. Client-side validation is not a security boundary. The server must check again.

The browser's check helps honest users fix mistakes quickly. It cannot stop a dishonest one, because the browser belongs to the user. Only the server, which you control, can refuse a bad request.

The example has two pretend servers inside it. The form's check stops the honest 15-year-old; an attacker skips the form and calls the servers directly.

<style>
  body { font-family: system-ui, sans-serif; padding: 14px; color: #0B2545; }
  input { width: 70px; padding: 6px 8px; }
  button { margin-left: 6px; padding: 7px 14px; font-weight: 700; }
  #msg { font-weight: 700; }
</style>
<form id="signup">
  <label for="age">Your age</label>
  <input id="age" type="number" value="15">
  <button>Register</button>
</form>
<p id="msg">Press Register, then read the Console.</p>
<script>
  // ---- two pretend SERVERS (in real life these run on another computer) ----
  function trustingServer(data) {                 // assumes the browser checked
    return "Trusting server: registered, age " + data.age;
  }
  function carefulServer(data) {                  // checks everything again
    const age = Number(data.age);
    if (!Number.isInteger(age) || age < 18 || age > 120) {
      return "Careful server: refused, must be 18 or older";
    }
    return "Careful server: registered, age " + age;
  }

  // ---- BROWSER code: a quick check, for the honest user's convenience ----
  const ageBox = document.querySelector("#age");
  const msg = document.querySelector("#msg");
  document.querySelector("#signup").addEventListener("submit", (event) => {
    event.preventDefault();
    if (ageBox.value < 18) {                       // "15" < 18 is true
      msg.textContent = "Must be 18+ (checked in the browser)";
      return;
    }
    msg.textContent = carefulServer({ age: ageBox.value });
  });

  // ---- an ATTACKER skips the form and calls the servers directly ----
  console.log("The box holds a", typeof ageBox.value, "-", ageBox.value);
  console.log("Attacker, age 15 ->", trustingServer({ age: 15 }));
  console.log("Attacker, age 15 ->", carefulServer({ age: 15 }));
  console.log("Attacker, age 'abc' ->", carefulServer({ age: "abc" }));
  console.log("Honest adult, age 19 ->", carefulServer({ age: 19 }));
</script>

The Console shows five lines. The box holds a string - 15: an input's value is always text, and "15" < 18 works only because JavaScript converts it to a number (Chapter 44). Then the disaster: Trusting server: registered, age 15. The careful server refuses 15 and "abc" (which becomes NaN) and accepts 19. Press Register and the browser check stops you; change the box to 19 and you are registered. So validate twice: in the browser for friendliness, on the server for safety.

3. No secrets in frontend code

The slide's "never do this" example:

// app.js - visible to every visitor:
const API_KEY = "sk_live_51H8xK...";
fetch(`${API_URL}?key=${API_KEY}`);

An API key is a password that lets a program use a paid or limited service: a weather feed, a payment gateway, an AI model. In app.js it is readable in the Sources panel and in every request URL in the Network panel. On GitHub Pages it is public twice: in DevTools, and in your repository, where bots scan new commits for keys within minutes. Someone else then runs up your bill.

If the browser can read it, the visitor can read it. A secret used by browser code is not a secret.

Quick check: Rahul minifies app.js so the key is buried in one enormous unreadable line. Is it safe now?

No. Minifying, base64-encoding or splitting the key into pieces only makes it slower for a human to spot. The browser still has to rebuild the real key to send it, and the Network panel shows it in the request. Hiding is not securing.

What to do instead:

  • Keep the key on a server you control. The browser asks your server; it adds the key, calls the real API and returns only the result. GitHub Pages serves static files only (Chapter 76), so this needs a small back end or "serverless function" elsewhere.
  • Keep server secrets in a .env file listed in .gitignore (Chapter 75). This protects server code only: build tools that feed .env to front-end code paste the value into the JavaScript.
  • If a key leaks, rotate it at once: revoke it and create a new one. Deleting the line in a new commit does not help; the old commit still has it.

Some services also issue a publishable key (often pk_) designed for browser code; the secret one (sk_, like the slide's) never leaves the server.

4. HTTPS everywhere

HTTPS encrypts what travels between browser and server, so nobody on the café Wi-Fi can read or alter it (Chapter 1). "Everywhere" means the site itself (GitHub Pages gives it free), every API call and every asset. A page loaded over HTTPS that tries fetch("http://...") is blocked as mixed content, a common reason a project fails once it is live. Geolocation (Chapter 66), the camera and the clipboard API need HTTPS; http://localhost counts as secure for testing.

What HTTPS does not mean. The padlock says the connection is private, not that the site is honest: a fake bank site can have a perfectly valid padlock. HTTPS protects the journey, not the destination.

5. Links that open a new tab

<a href="https://github.com/asha-kumar" target="_blank" rel="noopener noreferrer">My GitHub</a>
  • noopener — the new tab gets no window.opener, so the linked page cannot quietly send your tab to a lookalike login page (reverse tabnabbing).
  • noreferrer — the browser sends no Referer header, so the new site is not told which page the user came from. It also implies noopener.

Current browsers apply noopener to target="_blank" links automatically, but write it anyway: older browsers still exist, and audit tools look for it. Every link in this chapter's Reference material is written this way.

6. A Content Security Policy

A Content Security Policy (CSP) tells the browser where your page may load things from. The slide's one-line version goes in the <head>:

<meta http-equiv="Content-Security-Policy" content="default-src 'self'">

default-src 'self' means: scripts, styles, images and fetch requests may come only from my own site. A second wall behind textContent: even if an attacker injects <img onerror="...">, the browser refuses to run inline JavaScript. The price: your own inline <script> and <style> elements and onclick and style attributes stop working too, — one more reason to keep JS and CSS in their own files (Chapter 73). Servers usually send the policy as an HTTP header; GitHub Pages sites use the meta tag.

77.5 Responsive design and cross-browser testing

"It works on my machine" is the most famous excuse in software. Your machine is one screen, one browser, one mouse and one fast connection; your users have hundreds of combinations. The slide's answer is a testing matrix: what must work down the side, where across the top, every cell filled in honestly. Its sample results:

  • Safari iPhone, layout — something is wider than 375 pixels (the example below finds it).
  • Keyboard, menu — the toggle is a clickable div; make it a <button> (Chapter 59).
  • Keyboard, focus — a stylesheet says outline: none; use :focus-visible (demo below).
  • Slow 4G, layout shift — images without width and height (Chapter 74).

Copy the matrix into your project's README and fill it in for your own site; it shows a reviewer that you tested properly.

Screen sizes: the device toolbar, then a real phone

In Chrome or Edge DevTools, Ctrl+Shift+M opens the device toolbar (Chapter 69). Try widths of 375 (a phone), 768 (a tablet) and 1280 (a laptop), and drag slowly between them: at every width, no horizontal scroll bar. The toolbar imitates a phone's screen size and its touch, but it is still your computer's browser on your computer's fast processor, not the phone's own. The slide's advice: DevTools emulation is good; a real phone is better.

Quick check: which three widths does the testing matrix check, and which kind of device does each stand for?

375 px (a phone), 768 px (a tablet) and 1280 px (a laptop or desktop). The final checklist stretches the range from 375 up to 1440 px.

The most common responsive bug is one element that is too wide. This function compares the width of the page with the width of the window, then lists every element that pokes out past the right edge.

<style>
  * { box-sizing: border-box; }
  body { font-family: system-ui, sans-serif; margin: 0; padding: 12px; color: #0B2545; }
  .card { background: #EEF2FF; border-radius: 8px; padding: 10px; margin-bottom: 8px; }
  .banner { width: 1200px; background: #FFE8D1; padding: 10px; margin-bottom: 8px; }
</style>
<div class="card">A normal card: it shrinks to fit any screen.</div>
<div class="banner">A banner someone gave a fixed width of 1200px</div>
<div class="card">Another normal card.</div>
<button id="fix" type="button">Apply the fix: max-width: 100%</button>
<script>
  function findOverflow() {
    const visible = document.documentElement.clientWidth;   // the window
    const page = document.documentElement.scrollWidth;      // the content
    console.log("Window:", visible + "px", "| page:", page + "px");

    const tooWide = [...document.body.querySelectorAll("*")]
      .filter((el) => el.getBoundingClientRect().right > visible)
      .map((el) => el.tagName.toLowerCase() + "." + el.className);

    if (tooWide.length > 0) {
      console.warn("Too wide:", tooWide.join(", "));
    } else {
      console.log("No horizontal scroll. Good.");
    }
  }

  window.addEventListener("load", findOverflow);    // check once the page is drawn
  document.querySelector("#fix").addEventListener("click", () => {
    document.querySelector(".banner").style.maxWidth = "100%";
    findOverflow();
  });
</script>

The first run reports a page about 1212 pixels wide in a narrower window (its width depends on your screen) and names the culprit: Too wide: div.banner. Press the button and the two widths match, then No horizontal scroll. Good. The fix is Chapter 21's: max-width: 100% means never wider than the container.

Browsers: four names, three engines

Browsers draw pages with a rendering engine, and three matter today. Testing one browser from each catches almost every difference.

BrowserEngineWhy test it
ChromeBlinkThe most used browser in India and the world

Prefer standard features, and look up anything new on caniuse.com, which shows which browsers support it. When a feature might be missing, check for it first and offer a fallback — feature detection:

// JavaScript: use a feature only where it exists
if ("geolocation" in navigator) {
  navigator.geolocation.getCurrentPosition(showMap, showError);
} else {
  showMessage("Location is not available - please type your city.");
}

/* CSS has its own version */
@supports (display: grid) {
  .gallery { display: grid; grid-template-columns: repeat(3, 1fr); }
}

How does a tool like axe work? It runs rules against the page, asking of every element questions such as "does this image have an alt?" Here is a tiny one, run against a page with seven mistakes left in on purpose:

<style>
  body { font-family: system-ui, sans-serif; padding: 12px; color: #0B2545; }
  .fake { display: inline-block; background: #0B2545; color: #fff;
          padding: 6px 12px; border-radius: 6px; cursor: pointer; }
  #report { font-weight: 700; }
</style>
<!-- a page with mistakes left in on purpose -->
<h1>Asha's Portfolio</h1>
<h3>Projects</h3>
<img src="media/campus.svg" width="120" height="60">
<img src="media/campus.svg" alt="LPU campus gate" width="120" height="60">
<p><input id="email" type="email" placeholder="Email">
   <label for="phone">Phone</label> <input id="phone" type="tel"></p>
<p><span class="fake" onclick="console.log('contact')">Contact me</span>
   <a href="https://github.com/" target="_blank">My GitHub</a>
   <a href="cv.pdf"></a></p>
<p id="report"></p>
<script>
  const problems = [];
  const report = (element, problem) => problems.push({ element, problem });

  // Rule 1: every image needs alt (alt="" is allowed for decoration)
  document.querySelectorAll("img").forEach((img, i) => {
    if (!img.hasAttribute("alt")) report("img #" + (i + 1), "no alt text");
  });

  // Rule 2: every form field needs a label
  document.querySelectorAll("input, select, textarea").forEach((field) => {
    if (field.labels.length === 0 && !field.hasAttribute("aria-label")) {
      report("input#" + field.id, "no label (a placeholder is not a label)");
    }
  });

  // Rule 3: clickable things must be real links or buttons
  document.querySelectorAll("div[onclick], span[onclick]").forEach((el) => {
    report(el.tagName.toLowerCase() + " '" + el.textContent + "'", "clickable but not a button or link");
  });

  // Rule 4: links need text, and new tabs need rel="noopener noreferrer"
  document.querySelectorAll("a").forEach((a) => {
    if (a.textContent.trim() === "") report("a " + a.getAttribute("href"), "link has no text");
    if (a.target === "_blank" && !a.rel.includes("noopener")) {
      report("a '" + a.textContent + "'", "target=_blank without rel=noopener");
    }
  });

  // Rule 5: headings must not skip a level
  let last = 0;
  document.querySelectorAll("h1, h2, h3, h4, h5, h6").forEach((h) => {
    const level = Number(h.tagName[1]);
    if (last > 0 && level > last + 1) {
      report(h.tagName.toLowerCase() + " '" + h.textContent + "'", "skips from h" + last + " to h" + level);
    }
    last = level;
  });

  // Rule 6: the page must say what language it is in
  if (!document.documentElement.lang) report("html", "no lang attribute");

  console.table(problems);
  document.querySelector("#report").textContent =
    problems.length + " problems found - see the Console panel.";
</script>

The page says 7 problems found, and the Console table lists them in rule order:img #1 has no alt text; input#email has no label; the span 'Contact me' is clickable but not a button or link; a 'My GitHub' opens a new tab without rel=noopener; a cv.pdf has no text; h3 'Projects' skips from h1 to h3; and the html element has no lang. Fix one, press Run again, and watch the count drop. Real tools are the same idea with hundreds of rules.

Quick check: your site scores 100 for Accessibility in Lighthouse. Does that mean every user can use it?

No. Tools test only what a rule can measure: that an image has alt text, not that alt="image123" is useless; that a button has a name, not that the Tab order jumps around. A 100 means "no automatically detectable problems". Keyboard testing and a real person still matter.

Exam tip. Match the tool to the question. Is my HTML valid? — the W3C validator. How good is my page overall? — Lighthouse. Which accessibility rules does it break, and where? — axe or WAVE. Can a real person use it? — no tool; test it yourself.

77.8 Common misunderstandings

✗ "My JavaScript checks the age, so the server is protected."
The user controls the browser and can skip, edit or bypass your check.
✓ "Browser validation is for convenience; the server must validate again."
Two checks, two jobs: friendliness in the browser, safety on the server.
✗ "innerHTML is safe because inserted <script> tags do not run."
Event-handler attributes such as onerror on the elements it builds still run.
✓ "User and API data go in with textContent, or as text inside elements I create."
innerHTML is only for fixed markup you wrote yourself.
✗ "It works in Chrome on my laptop, so it works."
That is one cell of the matrix; in the slide's sample, none of the four bugs appeared there.
✓ "I tested three widths, the main browsers, the keyboard, a slow network and a real phone."
✗ "Lighthouse gave me 100, so the site is accessible."
Tools check only what a rule can measure; meaningless alt text and a chaotic Tab order still pass.
✓ "Automated tools first, then a keyboard-only run and a look with real eyes."
The tools find the easy problems fast, so your time goes on the hard ones.

Exam-style checks

Answer each one before opening it.

A comments page must display text typed by users. Which property should it use?L1
  • A. innerHTML
  • B. outerHTML
  • C. textContent
  • D. insertAdjacentHTML

Answer: C. textContent shows the text as characters, so HTML inside it never runs. A, B and D all parse their input as HTML, which is how XSS gets in.

A registration page contains if (age.value < 18) { return showError("Must be 18+"); }. Can a 15-year-old still register? Explain.L3

Answer: yes. They can turn JavaScript off, edit the check in DevTools, or send the request straight to the server (with curl, say). Client-side validation is not a security boundary; the server must check the age again.

A student's GitHub Pages site needs a secret key for a paid weather API. Where should the key be kept?L2
  • A. In a const at the top of app.js
  • B. In a hidden <input type="hidden"> field
  • C. Base64-encoded inside index.html
  • D. On a server or serverless function that calls the API and returns only the results

Answer: D. A, B and C all deliver the key to the browser, where DevTools shows it; base64 is an encoding anyone can reverse, not encryption.

What does this print? const box = document.createElement("div"); box.textContent = "<b>Hi</b>"; console.log(box.children.length, box.innerHTML);L3

Answer: 0 &lt;b&gt;Hi&lt;/b&gt;. textContent creates one text node, not a <b> element, so there are 0 child elements. Written back out as HTML, the angle brackets are escaped as &lt; and &gt;, which is why the text can never become a tag. The user sees the characters <b>Hi</b>, not a bold word.

A script in app.js runs box.innerHTML = '<script>console.log("A")</script><img src="x" onerror="console.log(\'B\')">'; and then appends box to the page. What appears in the Console?L3
  • A. A, then B
  • B. A only
  • C. B only
  • D. Nothing at all

Answer: C. A <script> inserted through innerHTML never runs, so no A. But the <img> is a real element; its image fails to load and its onerror attribute prints B. So "scripts do not run with innerHTML" is no defence against XSS.

What does rel="noopener" on a target="_blank" link protect against?L2
  • A. The opened page using window.opener to send your original tab to a fake page
  • B. Search engines indexing the link
  • C. The linked page loading over HTTP
  • D. The link being saved in the browser's history

Answer: A. Without it, older browsers give the new tab a handle on your tab, which a malicious page can use to swap your page for a lookalike login screen (reverse tabnabbing).

Which tool checks a page's markup against the HTML standard and reports unclosed tags and duplicate ids?L1
  • A. The Network panel
  • B. The W3C Markup Validation Service
  • C. WAVE
  • D. caniuse.com

Answer: B. validator.w3.org checks HTML against the standard. The Network panel shows requests, WAVE checks accessibility rules, and caniuse.com tells you which browsers support a feature.

Which of these is NOT one of the categories in a Lighthouse report?L1
  • A. Performance
  • B. Accessibility
  • C. SEO
  • D. Spelling and grammar

Answer: D. Lighthouse scores four categories: Performance, Accessibility, Best Practices and SEO. It does not check your writing.

In before.html, <div class="btn" onclick="send()">Send</div> works with a mouse. What is the main problem with it?L2
  • A. It cannot be reached with Tab or pressed with Enter, and screen readers do not announce it as a button
  • B. A div is not allowed to have an onclick attribute
  • C. It only works in Chrome
  • D. Its text is too short to be read

Answer: A. A div is not focusable (its tabIndex is −1) and has no button role. A real <button> is focusable, announced as a button, and turns Enter and Space into clicks. B and C are false: the div works, but only for mouse users.

Which comment is the most useful one to put next to const GST_RATE = 0.18;?L2
  • A. // a constant
  • B. // 18% GST on all items; change here if the rate changes
  • C. // set GST_RATE to 0.18
  • D. // do not touch

Answer: B. It says what the number means and why someone might change it, which the code cannot say. A and C only repeat the code; D gives an order with no reason.

A site's menu opens with a mouse click but not with the Enter key. Which test from the testing matrix would catch this?L2
  • A. Lighthouse Performance
  • B. The keyboard-only test
  • C. Throttling to Slow 4G
  • D. The W3C CSS validator

Answer: B. Only the keyboard test finds controls a mouse can use and a keyboard cannot. The likely cause is a clickable div; the fix is a real button.

A project works on http://localhost. Once deployed to https://asha.github.io/marks/, its fetch("http://api.example.com/marks") fails. Why, and what is the fix?L3

Answer: mixed content. A page loaded over HTTPS may not fetch from a plain http:// address, so the browser blocks the request (the Console says so). The fix is to call the API at its https:// address.

Quick revision

Key takeaways

  1. Best practices protect reliability, maintainability, accessibility, security and teamwork, and help search engines too.
  2. Semantic HTML: landmarks, ordered headings, alt, a <label> per input, <a> to go and <button> to act. A clickable div is invisible to the keyboard.
  3. Maintainable code: clear consistent names, named constants, reusable classes, small functions, no duplication, comments that explain why. A refactor never changes the output.
  4. The user can read and change everything sent to the browser: textContent for user and API data; validate again on the server; no secrets in front-end code; rotate leaked keys.
  5. HTTPS for the site, APIs and assets; rel="noopener noreferrer" on new-tab links; a CSP limits where scripts come from.
  6. Test a matrix: 375, 768, 1280 px; Chrome, Firefox, Safari, Edge; a real phone; keyboard only; Slow 4G and offline.
  7. W3C validator, Lighthouse, axe or WAVE — then a human test, because tools see only what rules can measure.
  8. The final checklist has ten areas, from functionality to verified deployment.
