Form Validation Basics

A form that accepts an empty name, a date of birth in the future or an email address without an @ is worse than no form at all. HTML5 lets you describe what a valid value looks like, and the browser checks it before anything is sent, with no JavaScript. This chapter covers every built-in constraint, what the browser does when one fails, how to switch validation off deliberately, and the one rule that never changes: the server must check everything again.

18.1 Two layers of validation

Validation happens in two places, and they have different jobs.

Client-side validation runs in the browser before the form is sent. It improves the user experience: the mistake is pointed out instantly, with no page reload. But it can be bypassed: a determined user can open DevTools, delete the required attribute and submit whatever they like, or send a request without using your form at all. So client-side checks are for convenience, not security.

Server-side validation runs in the backend code after the data arrives. It is called the final line of defence because it cannot be bypassed by the user: whatever reaches the server is checked there, regardless of what the browser did. It is not faster than client-side checks, it is not written in HTML, and it gives no instant feedback; it is simply the one that counts. Every serious application does both, and client-side validation never removes the need for server-side validation.

18.2 The built-in constraints

HTML5 calls this constraint validation: attributes on a control describe the valid values, and the browser enforces them when the form is submitted.

ConstraintFails whenExample
requiredThe field is empty (or no radio in the group is chosen, or a checkbox is unticked)<input type="email" required>
type="email", "url", "number", "date"The value is not in the format the type demandsstudent@college fails type="email": no domain part after the dot
min, maxThe value is below min or above max<input type="number" min="18" max="60">
stepThe value is not on the step gridstep="5" rejects 12
minlength, maxlengthToo few characters (maxlength usually cannot be exceeded at all: the browser stops typing)<input type="password" minlength="8">
patternThe value does not match the regular expression (the whole value must match)pattern="[A-Za-z]{3,}": at least three letters

pattern and title

pattern takes a regular expression that the entire value must match. Because the browser's default error message ("Please match the requested format") tells the user nothing, pair it with a title attribute: the title supplies the hint shown when the value fails the pattern. In <input type="text" pattern="[A-Za-z]{3,}" title="At least 3 letters">, the title is not the field's name for the server, not a default value and not a substitute for a label.

<form onsubmit="event.preventDefault(); alert('All constraints satisfied - the browser would now submit')">
  <p><label for="u">Username (letters only, 3+)</label><br>
     <input id="u" name="u" type="text" required pattern="[A-Za-z]{3,}" title="At least 3 letters, no digits"></p>
  <p><label for="e">Email</label><br>
     <input id="e" name="e" type="email" required value="student@college"></p>
  <p><label for="a">Age (18-60)</label><br>
     <input id="a" name="a" type="number" min="18" max="60" step="1" required></p>
  <p><label for="p">Password (8-20 characters)</label><br>
     <input id="p" name="p" type="password" minlength="8" maxlength="20" required></p>
  <p><label for="c">Course</label><br>
     <select id="c" name="c" required>
       <option value="">-- choose a course --</option>
       <option value="cse">Computer Science</option>
     </select></p>
  <p><label><input type="checkbox" name="t" required> I accept the rules</label></p>
  <button type="submit">Register</button>
</form>

Notice the email field: it is pre-filled with student@college. Press Register and the browser blocks submission because the value is not a valid email format: it does not submit normally, does not "correct" the value and does not silently drop the field. Add .edu and it passes.

18.3 What the browser does on submit

When a constraint fails, the browser stops the submission, moves focus to the first invalid control and shows a message bubble beside it. Valid and invalid controls can also be styled with the CSS pseudo-classes :valid and :invalid (Unit 3), which is how the red outline you see on many sites is done.

Switching validation off on purpose

  • novalidate on the <form> disables built-in validation for the whole form, for example when you handle all checks in JavaScript.
  • formnovalidate on a particular submit button makes the form skip built-in validation when that button is used: the classic case is a "Save draft" button beside "Submit", where a half-filled form is acceptable. It does not make the form unsubmittable, does not remove required from the markup, and does not move validation to the server.
<form onsubmit="event.preventDefault(); alert('Submitted via: ' + event.submitter.textContent)">
  <label for="t">Title</label> <input id="t" name="t" required>
  <button type="submit">Publish (validates)</button>
  <button type="submit" formnovalidate>Save draft (skips validation)</button>
</form>

18.4 Three things that confuse everyone

placeholder has nothing to do with validation

placeholder is a hint that shows in an empty field and vanishes when typing starts. It does not count as a value, so it never satisfies required; and required is not ignored when a placeholder is present. The two attributes can legally sit on the same element: required controls whether the form submits; placeholder only shows a hint and has no effect on validation.

A required select needs an empty option

A <select required> is satisfied by any selected option, and a select always has one selected by default (the first). The trick is to make the first option a placeholder with an empty value: <option value="">-- choose --</option>. Now the form will not submit until a non-empty option is chosen. The browser does not remove the empty option, does not ignore required on selects, and does not auto-select the first real option.

readonly and disabled fields are not validated

A control the user cannot change is never reported as invalid; a disabled control is not even submitted (Chapter 17).

18.5 A little JavaScript, for later

Unit 5 adds scripted validation on top of these constraints: checking that two password fields match, showing friendlier messages with setCustomValidity(), or validating as the user types. The HTML constraints remain the foundation, because they work with JavaScript disabled and they announce themselves correctly to assistive technology. And whatever you do in the browser, the server checks again.

Quick revision

Key takeaways

  1. Client-side validation (HTML constraints, JavaScript) gives instant feedback but can be bypassed; server-side validation cannot be bypassed and is the final line of defence. Use both.
  2. Constraints: required; type (email, url, number, date); min/max/step; minlength/maxlength; pattern with title as the failure hint.
  3. On submit the browser blocks invalid forms, focuses the first bad field and shows a message; :valid/:invalid style them.
  4. novalidate (form) and formnovalidate (a submit button, e.g. Save draft) switch built-in validation off deliberately.
  5. placeholder never satisfies required; a required select needs an empty first option; disabled fields are neither validated nor submitted.
