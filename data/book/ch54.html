Callback Functions

Some jobs finish at once. Others finish later: a timer runs out, a button is clicked, marks arrive from a server. JavaScript handles every "later" moment in the same way: you hand over a function and say "call this back when it happens". That function is a callback. This chapter shows how to write callbacks, when they run, and the tangle that Promises were invented to untie.

About 34 minutes · Course outcome CO5

Before you start — one-line reminders

  • A function is a value: greet is the function itself, greet() runs it, and a function can be handed to another function (Chapter 48).
  • An arrow function such as (m) => m + 5 is the short way to write a function expression (Chapter 48).
  • The call stack holds the function that is running right now, and it is empty once the last line of a script has run (Chapter 49).
  • forEach, map, filter and sort take a function and call it for you; they are higher-order functions (Chapter 53).

  • Explain, with the call stack, the waiting queue and the event loop, why a 0 ms timer still waits.

54.1 Call me back: what a callback is

In Chapter 48 you handed a whole function to another function: doTwice(cheer) gave cheer to doTwice, and doTwice ran it twice. In Chapter 53 you did it constantly, giving small arrow functions to forEach, map and filter. That pattern has a name, and your slides define it in one line.

Key idea. A callback is a function passed to another function, to be invoked by that function. The callback is the function being passed. The higher-order function is the function that receives it (or returns one).

Here is a function that accepts a callback, in the style of the slide's processUser example:

function processUser(name, callback) {
  console.log("Processing user:", name);
  callback(name);                    // the moment the function is "called back"
}

function greet(name) {
  console.log("Welcome, " + name + "!");
}

processUser("Asha", greet);
// Processing user: Asha
// Welcome, Asha!

Follow the handover. The call passes two arguments: a string, and the function greet itself, with no brackets. Inside, the parameter callback holds that function, just as name holds "Asha". processUser does its own work, then writes callback(name): brackets after a parameter that holds a function, so greet("Asha") runs. processUser is the higher-order function; greet is the callback. You hand a function over, and the receiver calls it back when it is ready.

A callback does not have to be a named function. These three calls hand over three different callbacks:

processUser("Rahul", greet);                                       // a named function
processUser("Meera", function (n) { console.log("Hi, " + n); });   // an anonymous function, written in place
processUser("Kabir", (n) => console.log("Hello, " + n));           // an arrow function: the usual choice

The arrow form is the one you will see most. A callback is usually short and used once, so it is written right inside the call.

No brackets when you hand it over. processUser("Asha", greet()) runs greet right now, with no argument, and prints "Welcome, undefined!". What is handed over is greet's return value, undefined. So when processUser reaches callback(name), it stops with TypeError: callback is not a function. Hand over the function: greet.

A callback is an ordinary function that you give to another function instead of calling it yourself. The other function keeps it in a parameter and runs it at the right moment, with whatever values it has to give.

Quick check: in checkResult(student.marks, (result) => { ... }), which is the higher-order function and which is the callback?

checkResult is the higher-order function, because it receives a function. The arrow function is the callback, because it is the function being passed. It receives "Pass" or "Fail" because checkResult calls it with that value.

54.2 Synchronous callbacks: called back at once

Every callback so far ran during the call that received it. processStudent called its callback before it finished, so by the time the next line of the program ran, the callback's work was done. The array methods of Chapter 53 behave in the same way:

const marks = [72, 85, 64];

console.log("Before");
marks.forEach((m) => console.log("Callback got", m));
console.log("After");

// Before
// Callback got 72
// Callback got 85
// Callback got 64
// After

forEach calls your arrow function three times, once per element, and only then returns (with undefined, because it has no answer to give). "After" cannot appear until all three calls are over. A callback that runs like this, inside the call and before the next line, is a synchronous callback. The compare function you give to sort is another. marks.sort((a, b) => a - b) calls it several times to decide which number goes first, and every one of those calls is over before sort hands back the sorted array. The functions you give to map, filter, find, some and every are synchronous too.

Synchronous callbacks customise a job. sort already knows how to sort; your callback tells it what "smaller" means. They are easy to follow, because the code runs in the order you read it. The next kind does not.

54.3 Asynchronous callbacks: called back later

The browser gives you a function called setTimeout. You hand it a callback and a number of milliseconds (1000 ms is one second), and it calls the callback once, after that time. Chapter 49 used it briefly. Predict what this prints:

console.log("1. Order placed");
setTimeout(() => {
  console.log("2. Food is ready");
}, 2000);
console.log("3. Find a table");

Reading top to bottom, you expect 1, 2, 3. The Console shows 1 and 3 at once, and 2 two seconds later. setTimeout does not sit and wait for two seconds. It books a timer with the browser, keeps your callback for later, and returns immediately, so line 3 runs straight away. Two seconds later the browser calls the callback back. A callback that runs later like this, after the code around it has moved on, is an asynchronous callback.

Picture this. At a busy food court you order a masala dosa. The cashier does not make you stand at the counter for ten minutes. She takes your order, hands you a buzzer and calls "Next!". You find a table while the dosa cooks, and when it is ready the buzzer goes off and you go back to collect it. Placing the order is the call to setTimeout; the buzzer is the callback you left behind; finding a table is line 3, which happens while the dosa is still cooking. One more detail: you collect at the same counter, and the cashier serves one person at a time. Even if your buzzer goes off the moment you sit down, you wait until she has finished with the person in front of you. Section 54.5 is about exactly that.

Timers are only the start. Every time a page waits for something outside your code, it uses an asynchronous callback:

A synchronous callback is called back before the next line runs. An asynchronous callback is called back after your code has carried on, when something happens: a timer ends, a button is clicked, data arrives. To tell them apart, ask: "is this function waiting for something?"

Quick check: is the function you give to addEventListener("click", ...) synchronous or asynchronous?

Asynchronous. Adding the listener only hands the function to the browser; the line after it runs at once. The callback runs later, each time the click happens, and it may never run at all if nobody clicks.

54.4 Timers: setTimeout and setInterval

The two timer functions are provided by the browser (they belong to the window object, Chapter 55), not by the JavaScript language itself, but every browser has them. Both take a callback, a delay in milliseconds, and optionally extra arguments that are passed on to the callback:

const id1 = setTimeout(callback, delay, arg1, arg2);    // call callback(arg1, arg2) ONCE, after delay ms
const id2 = setInterval(callback, delay, arg1, arg2);   // call it EVERY delay ms, until stopped

clearTimeout(id1);    // cancel the timeout, if it has not run yet
clearInterval(id2);   // stop the interval

Each one returns a timer ID, a number that names this particular timer. Keep it in a variable: it is your only way to cancel the timer, because clearTimeout and clearInterval take the ID, not the function. An interval that is never cleared keeps calling its callback until the page is closed.

The timer-ID line comes first, because it is ordinary synchronous code; the ID is just some whole number. Half a second later the reminder appears, with "CSE326" passed on by setTimeout. "You will never see this" never appears, because clearTimeout cancelled it in time. Then come four ticks, 4 down to 1, and on the fifth call the interval clears itself. Press Stop part-way and the ticks end at once.

Exam tip. setTimeout = once, setInterval = repeat. Both return an ID, and clearTimeout(id) or clearInterval(id) cancels with that ID. The delay is in milliseconds: three seconds is 3000, not 3.
Quick check: a slideshow changes picture with setInterval(nextSlide, 5000). How should the Pause button stop it?

Store the ID when the interval starts, const slideTimer = setInterval(nextSlide, 5000);, and call clearInterval(slideTimer) in the Pause button's callback. clearInterval(nextSlide) does nothing, because it needs the ID, not the function.

54.5 The event loop: who decides when a callback runs

JavaScript in a page has one call stack (Chapter 49), so it does exactly one thing at a time: it is single-threaded. So who counts the two seconds while your code carries on? Not JavaScript. The browser has helpers of its own, outside JavaScript, which keep timers, watch for clicks and wait for network replies (diagrams online often label them "Web APIs"). Three pieces work together:

  1. The call stack — the code running right now. Your script runs here from its first line to its last.
  2. The browser's helpers — setTimeout hands them your callback and the delay, and returns at once. They count the time while JavaScript runs the next lines.
  3. The waiting queue — when the time is up, or the click happens, the helper does not interrupt your code. It puts the callback at the back of the task queue (also called the callback queue).

Joining them is the event loop, a rule the browser repeats for as long as the page is open: if the call stack is empty, take the first callback from the queue and run it to the end; then check again.

That rule explains the most famous surprise in JavaScript. Trace this, with a delay of zero:

console.log("A");
setTimeout(() => console.log("B"), 0);
console.log("C");
// A
// C
// B
StepCall stackHelpers and queueConsole
1Runs console.log("A")EmptyA
2Runs setTimeout: hands the callback over and returns at onceThe 0 ms timer is up almost at once, so the callback joins the queueA
3Runs console.log("C")The callback is waitingA C
4The script has finished: emptyThe event loop moves the callback onto the stackA C
5Runs the callback, console.log("B")EmptyA C B

A delay of zero does not mean "now". It means "as soon as possible, after the running code has finished". The callback is ready almost at once, but the event loop will not move it while your script is still running: your buzzer went off, but the cashier was still serving someone. For the same reason the delay is only the least time to wait. If the stack is busy when the time is up, the callback waits longer.

Timers and clicks never interrupt your code. When one is ready, its callback joins a queue. Only when the running code has completely finished does the event loop take the next callback from the queue and run it, from start to end.

The same rule has a darker side. While your code keeps the call stack busy, nothing else can happen: no timer callback, no click handler, and the browser cannot even redraw the page. This example keeps JavaScript busy for one second with a loop that only watches the clock:

  body { font-family: system-ui, sans-serif; padding: 6px 14px; }

<script>
  const start = Date.now();            // the time now, in milliseconds (Chapter 62)
  console.log("1. Script starts and books a 0 ms timer");

  setTimeout(() => {
    console.log("3. The 0 ms timer finally ran, after", Date.now() - start, "ms");
  }, 0);

  // keep the call stack busy for one second
  while (Date.now() - start < 1000) {
    // nothing here: just keep checking the clock
  }
  console.log("2. Busy loop over, after", Date.now() - start, "ms");

Line 2 reports about 1000 ms, and the "0 ms" timer runs just after it, because the event loop had to wait for the busy loop to end. A page that does heavy work in one long piece feels frozen for exactly this reason, so real pages keep every callback short. (Chapter 65 adds one detail: promise callbacks have a queue of their own, served first. Still, nothing interrupts code that is already running.)

Exam tip. In "what does this print?" questions, every synchronous line prints first, whatever the delays say. Then the timer callbacks run in order of when their time is up: for timers booked together, the shortest delay first, and equal delays in the order they were booked.

54.6 Writing your own function that takes a callback

You are not limited to the browser's functions. Any function you write can accept a callback, and the pattern is always the same: take a function as a parameter, do your work, then call it with the results. Here is processMarks. It adds up a list of marks, works out the average, and calls back whoever asked, through a parameter named onDone:

function processMarks(marks, onDone) {
  let total = 0;
  for (const m of marks) {           // for...of, Chapter 52
    total = total + m;
  }
  const average = total / marks.length;
  onDone(total, average);            // call back with two results
}

processMarks([72, 85, 64, 91], (total, average) => {
  console.log("Total:", total, "Average:", average);   // Total: 312 Average: 78
});

Why not simply return the answers? For a quick calculation you could, and Chapter 48's advice still holds. A callback earns its place in two situations: when the caller should decide what happens with the result (log it, show it, save it), so one processMarks serves them all; and when the result is not ready yet. The second matters most, and ends this section.

Who chooses the callback's arguments?

The function that does the calling. processMarks calls onDone(total, average), so every callback you give it receives the total first and the average second. You choose the names, so (t, avg) works just as well, but the caller fixes the order (Chapter 48). The same holds for every function that takes a callback:

The functionCalls your callback with
processMarks(marks, cb)(total, average)
arr.forEach(cb)(element, index, array); name only the ones you need
setTimeout(cb, ms, a, b)(a, b), the extra arguments you gave it
btn.addEventListener("click", cb)(event), the details of the click (Chapter 57)
An error-first function (section 54.7)(error, data)

When you need to call a function with values the caller does not supply, wrap the call in an arrow function. The arrow function is the callback, and inside it you call your own function with whatever you like:

function remind(subject) {
  console.log("Reminder:", subject, "assignment is due today");
}

setTimeout(remind("CSE326"), 500);         // WRONG: remind runs NOW, and setTimeout gets undefined
setTimeout(() => remind("CSE326"), 500);   // right: the arrow is called back, and it calls remind
setTimeout(remind, 500, "CSE326");         // also right: setTimeout passes "CSE326" on

Results that arrive later

Now the real reason callbacks exist. Suppose the marks are on a server and take a second to arrive. You might try to return them:

function getMarks(rollNo) {
  setTimeout(() => {
    return [72, 85, 64, 91];       // returns to the timer, not to whoever called getMarks
  }, 1000);
}                                  // getMarks itself ends at once and returns nothing

const marks = getMarks(12);
console.log(marks);                // undefined: the data does not exist yet

getMarks finishes in a split second, long before the timer ends, and has no return of its own, so the caller gets undefined. The return inside the arrow function hands the array to whoever called the arrow function: the browser's timer, which throws it away. A value that does not exist yet cannot be returned. Instead, the caller hands over a callback, and the function calls it when the data is ready:

  #out { font-weight: 700; color: #0B2545; }

<script>

    let total = 0;
    for (const m of marks) {
      total = total + m;
    }

  // one processMarks, different callbacks

Four lines appear at once: Asha's total 312 and average 78, Rahul's average 38 "(below 40)", the request for roll 12, and "Meanwhile...", which comes before the marks because loadMarks returns as soon as its timer is booked. A second later the marks arrive and the page changes. Timers, addEventListener and geolocation still hand results over in exactly this way.

Quick check: why does getMarks(12) give undefined, when the arrow function inside it says return?

That return belongs to the arrow function, so it hands the array back to whoever called the arrow function: the browser's timer, a second later. getMarks itself has no return and finished long before, so its call gives undefined. The fix is to accept a callback and call it with the data, as loadMarks does.

54.7 When something goes wrong: error-first callbacks

Waiting for something means it can fail: there is no student with that roll number, or the network is down. A try...catch around loadMarks(...) cannot help, because the failure happens later, after the try has finished (Chapter 70). The callback itself must be told. A very common convention, a habit programmers agree on rather than a rule of the language, is the error-first callback: the callback's first parameter is an error, and the result comes second.

  • On failure, the function calls callback(new Error("what went wrong")).
  • On success, it calls callback(null, result). A null in first place means "no error".
function findStudent(rollNo, callback) {
  setTimeout(() => {
    const student = students.find((s) => s.roll === rollNo);   // find, Chapter 50
    if (student === undefined) {
      callback(new Error("No student with roll " + rollNo));   // failure: the error first
    } else {
      callback(null, student);                                 // success: null, then the data
    }
  }, 300);
}

findStudent(99, (err, student) => {
  if (err) {                           // always check the error first...
    console.log("Error:", err.message);
    return;                            // ...and stop: there is no student to use
  }
  console.log("Found", student.name);
});

The caller always checks err first, and returns early if there is one. new Error("...") makes an error object whose message holds the text (Chapter 70). Node.js, the JavaScript that runs on servers, uses this convention throughout its classic built-in functions, such as fs.readFile(path, (err, data) => { ... }). Browser features more often take separate success and failure callbacks (geolocation, Chapter 66), or return promises.

54.8 Callback hell, and why Promises were invented

A report card needs three steps, each waiting on the one before: find the student, work out the average of their marks, then turn the average into a grade. With callbacks, each next step can only start inside the previous step's callback, because that is the only place where its result exists. Watch the shape the code takes:

  function findStudent(rollNo, callback) {

      } else {
        let total = 0;
        for (const m of student.marks) {
          total = total + m;
        }
        callback(null, total / student.marks.length);
      }
    }, 300);
  }

  function getGrade(average, callback) {          // cannot fail, but keeps the same shape

      if (average >= 80) {
        callback(null, "A");
      } else if (average >= 60) {
        callback(null, "B");
      } else if (average >= 40) {
        callback(null, "C");
      } else {
        callback(null, "F");
      }
    }, 300);
  }

  function show(text) {
    document.getElementById("out").textContent = text;
    console.log(text);
  }

  // the pyramid: each step lives inside the previous step's callback
  function showReport(rollNo) {
    show("Working on roll " + rollNo + "...");
    findStudent(rollNo, (err, student) => {
      if (err) {
        show("Error: " + err.message);
        return;
      }
      getAverage(student, (err, average) => {
        if (err) {
          show("Error: " + err.message);
          return;
        }
        getGrade(average, (err, grade) => {
          if (err) {
            show("Error: " + err.message);
            return;
          }
          show(`${student.name}: average ${average}, grade ${grade}`);
        });
      });
    });
  }

  showReport(12);
  document.getElementById("r12").addEventListener("click", () => showReport(12));
  document.getElementById("r99").addEventListener("click", () => showReport(99));
  document.getElementById("r15").addEventListener("click", () => showReport(15));
</script>

Roll 12 prints "Working on roll 12..." and, 0.9 seconds later (three steps of 300 ms), "Asha: average 78, grade B". Roll 99 fails at step 1 and roll 15 at step 2. The innermost line can still use student and average, because each callback sits inside the ones around it (a closure again).

Now look at the shape. Each step pushes the code one level further right, and the closing brackets pile up at the bottom, }); three times over. This is callback hell, or the pyramid of doom. Three steps are bearable; real programs often had six or seven, and the problems grow with every level:

  • Hard to read. The steps happen top to bottom, but the code drifts sideways, and you must match brackets to see where each step ends.
  • Errors handled again and again. The same if (err) check sits at every level, and one forgotten check lets a failure slip through silently.
  • Hard to change. Adding a step in the middle means re-nesting everything.
  • Trust. You hand your code to someone else's function and hope it calls back exactly once: not never, and not twice.

Giving each callback a name and defining it separately flattens the pyramid a little, but not the repeated error checks. The real fix arrived in the language itself. In 2015 JavaScript gained Promises: a function hands back an object that stands for "the answer, when it comes", and you attach the next step with .then(). In 2017 came async and await, which let asynchronous steps be written like ordinary lines. Once the three helpers are rewritten to return promises, the same report reads like this:

// A preview of Chapter 65: the same three steps with promises and await
async function showReport(rollNo) {
  try {
    const student = await findStudent(rollNo);
    const average = await getAverage(student);
    const grade = await getGrade(average);
    show(`${student.name}: average ${average}, grade ${grade}`);
  } catch (err) {
    show("Error: " + err.message);
  }
}

The same three steps, top to bottom, with one try...catch for every error. Chapter 65 teaches promises, await and fetch properly. Underneath they still use callbacks and the event loop; they simply keep them in order.

Callbacks work. But when step 2 needs step 1's answer and step 3 needs step 2's, each step must be written inside the one before. The code becomes a deep, sideways pyramid that is hard to read and repeats its error checks. Promises and async/await were added to JavaScript to write the same steps in a straight line.

54.9 Common misunderstandings

✗ "A callback is a special kind of function."
Nothing in its definition is special.
✓ "Any function becomes a callback when it is passed to another function to be called."
greet is an ordinary function; it is a callback only in processUser("Asha", greet).
✗ "Every callback runs later."
The callbacks of forEach, map and sort run straight away.
✓ "Synchronous callbacks run during the call; asynchronous ones run when something happens."
Ask whether the function is waiting for something: a timer, a click, a reply.
✗ "setTimeout(fn, 0) runs fn immediately."
Its callback waits in the queue.
✓ "It runs as soon as possible after the current code has finished."
The event loop moves a callback onto the stack only when the stack is empty, which is also why any delay is a minimum, not an exact time.
✗ "I can return a value from inside a setTimeout callback to my function's caller."
That return goes to the timer, much later.
✓ "A result that arrives later is handed over through a callback (or a promise)."
Accept a callback and call it with the data once it exists.
✗ "setTimeout(greet("Asha"), 2000) greets Asha after two seconds."
The brackets run greet now and hand over its result.
✓ "Hand over a function: setTimeout(() => greet("Asha"), 2000)."
Or let setTimeout pass the value: setTimeout(greet, 2000, "Asha").

Exam-style checks

What is a callback function?L1
  • A. A function that calls itself again and again
  • B. A function passed to another function, to be called by that function
  • C. A function that runs automatically when the page loads
  • D. Any function that returns another function

Answer: B. That is the slide's definition. D describes one kind of higher-order function, not the callback; A is recursion.

In checkResult(72, showResult), where checkResult calls showResult with "Pass" or "Fail", which statement is correct?L2
  • A. showResult is the higher-order function and checkResult is the callback
  • B. Both are callbacks
  • C. checkResult is the higher-order function and showResult is the callback
  • D. Neither, because showResult is written without brackets

Answer: C. The function being passed is the callback; the function receiving it is the higher-order function. A has the roles backwards, and the missing brackets in D are exactly how a function is handed over.

What does this print? console.log("A"); setTimeout(() => console.log("B"), 0); console.log("C");L2
  • A. A C B
  • B. A B C
  • C. B A C
  • D. A C, and B never prints

Answer: A. Even with a 0 ms delay, the timer's callback waits in the queue until the script has finished, so C prints before B. B is the trap for anyone who reads 0 as "now"; in D, the callback does run, just last.

Predict every line, in order: console.log("start"); [1, 2].forEach((n) => { setTimeout(() => console.log(n), 0); }); console.log("end");L3

Answer: start, end, 1, 2. The forEach callback is synchronous and runs twice at once, but it only books two timers. Their callbacks wait until the script has printed "end", then run in the order they were booked.

A student writes setTimeout(greet("Asha"), 2000); where greet prints a greeting. What happens?L2
  • A. The greeting appears after 2 seconds
  • B. The greeting appears at once, and nothing useful happens after 2 seconds
  • C. A SyntaxError stops the script
  • D. The greeting appears twice

Answer: B. The brackets run greet("Asha") immediately, and setTimeout receives its return value, undefined, instead of a function. Write setTimeout(() => greet("Asha"), 2000) or setTimeout(greet, 2000, "Asha").

After const id = setInterval(tick, 1000);, which line stops the interval?L1
  • A. clearInterval(tick);
  • B. setInterval(tick, 0);
  • C. stopInterval(id);
  • D. clearInterval(id);

Answer: D. clearInterval takes the timer ID that setInterval returned. A passes the function, so it stops nothing; B starts a second interval; C does not exist.

What does this print? setTimeout(() => console.log("X"), 200); setTimeout(() => console.log("Y"), 100); console.log("Z");L3
  • A. X Y Z
  • B. Y X Z
  • C. Z X Y
  • D. Z Y X

Answer: D. The synchronous line Z prints first. Then the callbacks run as their time is up: Y after 100 ms, X after 200 ms. The delays decide the order, not the order the timers were written in.

Which of these callbacks is synchronous?L2
  • A. The compare function given to marks.sort(...)
  • B. The function given to setTimeout(..., 500)
  • C. The function given to btn.addEventListener("click", ...)
  • D. The function given to fetch(url).then(...)

Answer: A. sort calls its compare function during the call, and every comparison is done before sort returns. The other three wait for something: a timer, a click, a server reply.

In your own words: why does setTimeout(fn, 0) not run fn immediately?L2

Answer: setTimeout hands fn to the browser and returns at once. When the 0 ms are up, fn joins the waiting queue, and the event loop moves it onto the call stack only when the stack is empty: after the running code, usually the rest of the script, has finished.

An error-first callback is written (err, data) => { ... }. What does err hold when the operation succeeded?L2
  • A. An Error object with an empty message
  • B. The data
  • C. null, meaning "no error"
  • D. The string "ok"

Answer: C. By convention the function calls callback(null, result) on success and callback(new Error("...")) on failure. null is falsy, so if (err) is skipped when all went well.

Promises and async/await were added to JavaScript mainly to solve which problem?L2
  • A. Images loading slowly on mobile phones
  • B. Deeply nested callbacks with repeated error checks, known as callback hell
  • C. Functions that have no names
  • D. Loops that run too fast to see

Answer: B. Dependent asynchronous steps nest into a sideways pyramid with an if (err) at every level. Promises and await write the same steps in a straight line with one try...catch.

Predict every line: let n = 0; const id = setInterval(() => { n++; console.log("Tick", n); if (n === 3) { clearInterval(id); } }, 100); console.log("Started");L3

Answer: Started, Tick 1, Tick 2, Tick 3, and then nothing more. "Started" is synchronous, so it prints first. The interval's callback then runs every 100 ms. On the third call n is 3, so clearInterval(id) stops it, and no fourth tick ever runs.

Quick revision

Key takeaways

  1. A callback is a function passed to another function, to be called by it; the receiver is a higher-order function. Hand the callback over without brackets.
  2. Synchronous callbacks (forEach, map, the sort compare function) run during the call, before the next line. Asynchronous ones (timers, addEventListener, fetch(...).then) run later, when something happens.
  3. setTimeout runs once, setInterval repeats. Both return a timer ID for clearTimeout or clearInterval. The delay is in milliseconds, and it is a minimum.
  4. The event loop moves the first waiting callback onto the call stack only when the stack is empty, so a 0 ms timer still waits for the script, and a busy loop freezes the page.
  5. The caller of a callback chooses its arguments; wrap a call in an arrow function to pass your own. A result that arrives later cannot be returned, so it is handed to a callback.
  6. Error-first callbacks receive (err, data), with err as null on success. Check it first.
  7. Dependent asynchronous steps nest into callback hell; Promises (2015) and async/await (2017) straighten it out (Chapter 65).
