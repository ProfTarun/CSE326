Unit 6 · Chapter 73 · Code Organization

Code Organization

A page that works is only half the job. The other half is finding the button handler next month, fixing one bug without causing two more, and letting a friend work on the design while you work on the logic. This chapter shows how developers lay out a project: which file holds what, where each file lives, how to cut one giant function into small ones, and how ES modules let files share code safely.

About 32 minutes · Course outcome CO6

Before you start — one-line reminders

  • <script src="app.js"> loads JavaScript from its own file, and where the tag sits decides when the code runs (Chapter 41).
  • A function packs a job under a name: parameters go in, a return value comes out, and you can call it as often as you like (Chapter 48).
  • A well-designed app keeps structure, presentation, behaviour and data as separate layers, changed through one state and drawn by one render function (Chapter 72).
  • A relative path such as images/logo.png is read from the folder of the current page; ../ means "go up one folder" (Chapter 8).

By the end of this chapter you can

  • Name five problems one giant file causes.
  • Split a page into index.html, css/styles.css and js/app.js, connected with <link> and <script defer> in the head.
  • Lay out a project folder and name files so they work on a real server.
  • Refactor a do-everything handler into small single-job functions, with named constants at the top.
  • Write comments that explain why, and keep formatting consistent.
  • Share code with export, import and type="module", and explain why module pages need http://, not file://.
  • Import named and default exports correctly.

73.1 Why organise code?

Every project starts small: thirty lines in one index.html, a little CSS in a <style> block, a little JavaScript in a <script> block. Then you add a search box, a dark theme, a friend's login form. A month later the file looks like this:

<!-- index.html - 1,214 lines -->
<!DOCTYPE html>
<html>
<head>
  <style>
    /* 380 lines of CSS */
    .card { ... }  .btn-new { ... }  .btn-new2 { ... }
  </style>
</head>
<body>
  <!-- 450 lines of HTML -->
  <script>
    // 384 lines of JavaScript
    let x = 0; let data2; let temp;
    function doStuff()  { /* 140 lines */ }
    function doStuff2() { /* a copy of doStuff with two changes */ }
  </script>
</body>
</html>

Nothing here is broken. The trouble starts the moment anyone has to change it:

ProblemWhat it looks like in the 1,214-line file
ReadabilityYou scroll a thousand lines to find one button handler.
DebuggingThe error is on line 873. Which feature is that?
TeamworkTwo students edit the same file and their changes collide (a merge conflict — Chapter 75).
ReusabilityformatDate() is buried in this page, so the next page gets a copy that slowly drifts apart.
MaintenanceYou change one style for the search box and three unrelated parts change with it.

Code organisation is the set of habits that prevents all five: separate files for separate jobs, a predictable folder layout, small functions with clear names, comments that explain decisions, and modules that share code on purpose. None of it changes what the page does. Reorganising working code without changing its behaviour is called refactoring; you will do a full refactor in section 73.9.

Picture this. A kitchen where rice, salt, spoons, electricity bills and medicines all live in one enormous drawer. You can still cook, but every meal starts with ten minutes of digging, and a guest cannot help without asking where things are. Now picture labelled jars on labelled shelves: spices on one, grains on another, utensils in their own drawer. Same food, same recipes — but anyone, including you a month from now, finds the salt in five seconds. Organising code is labelling the jars.
Key idea. Organisation makes the next change cheap. You read code far more often than you write it, so arranging it pays back every time someone opens the file.

73.2 Three languages, three files

You met the first rule in Chapter 1: HTML gives structure, CSS presentation, JavaScript behaviour. Keeping those jobs apart is called separation of concerns. An organised project puts each job in its own file, and each kind of file in its own folder:

File or folderHoldsTypical contents
index.htmlStructure and contentHeadings, cards, forms, buttons. The entry page servers look for.
css/styles.cssPresentationColours, fonts, layout, spacing, responsive rules.
js/app.jsBehaviourEvent listeners, state, rendering, fetch calls.
images/, assets/Static filesLogos, photos, icons, fonts, PDFs.

Separation also means no smuggling: a colour or a click handler typed into an HTML tag is CSS or JavaScript hiding inside the structure file. Compare:

<!-- MIXED: presentation and behaviour hiding inside the HTML -->
<button style="background:#0B2545; color:#fff" onclick="addTask()">Add</button>

<!-- SEPARATED: index.html only says what the thing is -->
<button class="btn" id="addBtn">Add</button>

/* css/styles.css says how it looks */
.btn { background: #0B2545; color: #fff; }

// js/app.js says what it does
document.querySelector("#addBtn").addEventListener("click", addTask);

The separated version is two lines longer, and worth it:

BenefitOne fileSeparated files
Finding codeScroll and searchOpen the file that owns it
ReuseEvery page carries its own CSSTen pages link one styles.css: change a colour once, every page follows
TeamworkEveryone edits index.htmlThe designer edits CSS while the developer edits JavaScript
CachingEverything is downloaded againThe browser keeps styles.css and app.js for the next page (Chapter 74)

HTML says what is there, CSS says how it looks, JavaScript says what it does — each in its own file. If you catch yourself typing a colour or an onclick="..." into a tag, move it to the file whose job it is.

73.3 Connecting the files: link and script

Separate files do nothing until index.html tells the browser to fetch them. Two tags do it, both in the <head>:

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Student Dashboard</title>
  <link rel="stylesheet" href="./css/styles.css">
  <script src="./js/app.js" defer></script>
</head>
<body>
  ...
</body>
</html>
PieceMeaning
rel="stylesheet"What kind of link this is. Without it, nothing is styled.
href="./css/styles.css"Where the CSS is. ./ means "from this page's folder".
src="./js/app.js"Where the JavaScript is. The tag itself stays empty.
deferDownload now, run only after the whole HTML is read, in the order written.

Why the stylesheet goes in the head. The browser will not draw the page until the CSS it knows about has arrived. Linked in the head, it is fetched first, so the page is styled from the first frame instead of flashing up as plain text.

Why the script needs defer

The browser reads your HTML from top to bottom, building the page as it goes; the part that does this reading is the parser. When it meets an ordinary <script src>, it stops: it waits for the file to download, runs it, and only then reads on. So the page sits half-built during the download, and the script runs before the elements below it exist: document.querySelector("#addBtn") returns null.

Watch the "too early" problem happen: two inline scripts look for the same paragraph, one in the head, one at the end of the body.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <title>When does a script run?</title>
  <style>
    body { font-family: system-ui, sans-serif; padding: 6px 14px; }
    #status { background: #FFF1E0; padding: 10px 14px; border-radius: 8px; }
  </style>
  <script>
    // Script A sits in the head. The parser has not reached the body yet.
    const early = document.querySelector("#status");
    console.log("Script A (in the head) found:", early);
  </script>
</head>
<body>
  <p id="status">Waiting for a script...</p>
  <script>
    // Script B sits after the paragraph, so the paragraph already exists.
    const late = document.querySelector("#status");
    console.log("Script B (end of body) found:", late);
    late.textContent = "Script B found me and changed this text.";
  </script>
</body>
</html>

The Console shows Script A (in the head) found: null and then Script B (end of body) found: <p id="status">. Now add early.addEventListener("click", () => {}); at the end of Script A and press Run again: the Console reports Uncaught TypeError: Cannot read properties of null (reading 'addEventListener') — the most common beginner error, and the heart of Chapter 69's TechFest case study.

A script can only find elements the browser has already read. defer means "fetch this file now, but run it only after reading the whole page". So a deferred script in the head always finds every element, and the page never waits for it.

Every way to load a script, compared

How it is writtenDownloadsRunsUse it for
<script src> in the headAt once, page pausedAt once; elements below missingAlmost never
<script src> at the end of the bodyNear the end (browsers often start a little earlier)After the HTML above itOlder sites; still works
<script src defer> in the headAt once, in parallelAfter parsing, in the order writtenYour own app code
<script src async>At once, in parallelOn arrival, in any orderIndependent extras (analytics)
<script type="module" src>At once, in parallelAfter parsing, in order (deferred automatically)Modules (section 73.8)

"In the order written" matters once you have two files: if app.js uses a function from utils.js, write utils.js's tag first, and two deferred scripts always run in tag order. async makes no such promise, so it is wrong for code that depends on other code.

defer only works with src. On an inline script — <script defer> ...code... </script> — the browser ignores defer and runs the code immediately. That is why the example above could not simply add defer to Script A. Put inline code at the end of the body; in real projects, move it into a file.
Quick check: <script src="js/app.js"></script> sits in the head with no defer, and its first line is document.querySelector("#addBtn").addEventListener("click", addTask);. What happens, and what is the one-word fix?

The script runs before the parser reaches the button, so querySelector returns null and the line throws TypeError: Cannot read properties of null (reading 'addEventListener'). The fix: defer.

Paths between the files

href and src hold relative paths, read from the page's own folder (Chapter 8):

Written asMeans
css/styles.css or ./css/styles.cssThe css folder next to this page; the two forms are identical.
../css/styles.cssUp one folder, then into css: needed from a page in a subfolder, such as pages/about.html.

73.4 A project folder, and names that never break

Once a project has a few files, give each kind its own folder. There is no single law, but most small projects use this layout, so anyone opening it knows where to look:

student-dashboard/            the project folder (the repository, in Chapter 75)
├── index.html                the home page - always at the top level
├── about.html                any other pages sit beside it
├── css/
│   └── styles.css            all the presentation
├── js/
│   ├── app.js                the entry point: wires the page together
│   └── utils.js              small helpers shared by other files
├── images/
│   ├── logo.png
│   └── campus-gate.jpg
└── assets/
    ├── fonts/
    └── docs/timetable.pdf

Three rules make this layout work:

  1. index.html lives at the top level. When an address ends at a folder — https://asha.github.io/student-dashboard/ — the server sends that folder's index.html. Name the home page anything else and visitors get a 404 or a bare file list.
  2. One folder per kind of file. css/ for stylesheets, js/ for scripts, images/ for pictures, assets/ for other files served as-is (fonts, icons, PDFs). Some teams put images/ inside assets/, as the course slides do; either is fine if the whole team agrees.
  3. Names are lowercase, words are joined with hyphens, and there are no spaces. This style is called kebab-case: campus-gate.jpg, student-card.js.

The third rule is not fussiness; it prevents two common "works on my laptop, broken online" bugs.

Capital letters. Windows and macOS normally treat Logo.png and logo.png as the same file, so on your laptop a mismatch goes unnoticed. The Linux servers that host most websites, GitHub Pages included, are case-sensitive: the HTML asks for logo.png, the server has only Logo.png, and the visitor sees a broken image and a 404. All-lowercase names make the mismatch impossible.

Spaces. A URL cannot contain a space, so my photo.jpg travels as my%20photo.jpg: easy to mistype, ugly to share, and awkward in command lines. A hyphen costs nothing.

AvoidPreferWhy
Home Page.htmlindex.htmlServers look for index.html; no space
My Photo.JPGmy-photo.jpgLowercase, hyphen, lowercase extension
StyleSheet FINAL(2).cssstyles.cssNo versions in names; Git keeps versions (Chapter 75)
script1.js, new.jssearch.js, cart.jsA name says what is inside
IMG_20261012_0931.jpgcampus-gate.jpgDescribes the picture, not when it was taken
Quick check: the logo shows on Rahul's laptop but not on his GitHub Pages site. His HTML says images/logo.png; the file in the folder is images/Logo.PNG. Why?

His laptop ignores the difference between capital and small letters; the server does not. To the server, logo.png and Logo.PNG are different files, so the request gets a 404. Renaming the file to logo.png fixes it for good.

73.5 Organising JavaScript: small functions with one job

Splitting files is the easy half; the harder half happens inside app.js. Here is the live search from Chapter 71, written the way almost everyone writes it the first time:

// app.js - one function does everything
searchInput.addEventListener("input", async () => {
  const res = await fetch("students.json");          // every key press!
  const data = await res.json();
  const list = document.querySelector("#list");
  list.innerHTML = "";
  for (const s of data) {
    const q = searchInput.value.toLowerCase();
    if (s.name.toLowerCase().includes(q)) {
      const li = document.createElement("li");
      li.textContent = s.name + " - " + s.course;
      list.appendChild(li);
    }
  }
  document.querySelector("#msg").textContent = list.children.length + " found";
});

It works. Read it as a reviewer: this one handler (1) loads the data, (2) filters it by the search text, (3) builds the list and (4) updates the message. The tangle hides a real problem: the network request runs on every key press. Type "Meera" and the browser downloads the same file five times; on a slow phone the list lags behind the typing.

The tangle also means you cannot test the filtering without typing into a box, cannot reuse it for a second search box, and must edit the middle of an event handler if the server address changes.

The reorganised version gives each job its own, well-named function. Run it, then type in the box. The data comes from a pretend server inside the example, because the classroom network may be offline; in a real project DATA_URL would simply be "students.json".

<style>
  body { font-family: system-ui, sans-serif; padding: 8px 14px; }
  input { padding: 6px 10px; font-size: 15px; }
  #msg { color: #6B7A90; font-size: 14px; }
  li { margin: 3px 0; }
</style>
<label for="search">Search students</label>
<input id="search" type="search" placeholder="Try: ra">
<p id="msg">Loading...</p>
<ul id="list"></ul>
<script>
  // ---- pretend server: in a real project this is the file students.json ----
  const data = [
    { name: "Asha Verma", course: "CSE326" },
    { name: "Rahul Singh", course: "CSE305" },
    { name: "Meera Iyer", course: "CSE326" },
    { name: "Arjun Nair", course: "CSE201" },
    { name: "Kavya Rao", course: "CSE326" }
  ];
  const DATA_URL = URL.createObjectURL(
    new Blob([JSON.stringify(data)], { type: "application/json" }));

  // ---- elements, looked up once ----
  const searchInput = document.querySelector("#search");
  const list = document.querySelector("#list");
  const msg = document.querySelector("#msg");

  // ---- state ----
  let students = [];
  let fetchCount = 0;

  // ---- one job each ----
  async function loadStudents() {
    const res = await fetch(DATA_URL);
    students = await res.json();
    fetchCount++;
  }

  function filterStudents(query) {
    const q = query.trim().toLowerCase();
    return students.filter((s) => s.name.toLowerCase().includes(q));
  }

  function renderStudents(items) {
    list.replaceChildren();                    // clear the old items
    items.forEach((s) => {
      const li = document.createElement("li");
      li.textContent = `${s.name} - ${s.course}`;
      list.append(li);
    });
  }

  function showMessage(text) {
    msg.textContent = text;
  }

  // ---- wiring: the handler now reads like a sentence ----
  searchInput.addEventListener("input", () => {
    const matches = filterStudents(searchInput.value);
    renderStudents(matches);
    showMessage(`${matches.length} found`);
    console.log(`"${searchInput.value}": ${matches.length} found (fetches so far: ${fetchCount})`);
  });

  // ---- start-up: load once, then show everyone ----
  loadStudents().then(() => {
    renderStudents(students);
    showMessage(`${students.length} students`);
    console.log("Loaded", students.length, "students with", fetchCount, "fetch");
    console.log('filterStudents("ra") returns', filterStudents("ra").map((s) => s.name));
  });
</script>

On Run the Console prints Loaded 5 students with 1 fetch and filterStudents("ra") returns ['Rahul Singh', 'Meera Iyer', 'Kavya Rao'] — the filter answered without anyone typing, which makes it testable. Type a few letters and every line ends fetches so far: 1: typing only filters now.

One job, one reason to change

The principle behind the split is single responsibility: each function does one job, so it has one reason to change. A new server address changes only loadStudents; a new list design, only renderStudents; matching course codes too, only filterStudents. Nothing else is opened, so nothing else can break by accident.

Good names do half the work: functions are verb phrases, data is nouns, true/false values read like a question:

Kind of nameGoodAvoid
Functions: verb + thingloadStudents, calculateTotal, formatRupeesdoStuff, process2
Data: nounsstudents, totalPrice, searchInputdata2, temp, x
True/false: a questionisOpen, hasError, canSubmitflag, status

Describe each function in one sentence. If the sentence needs "and" — "it loads the data and filters it and draws the list" — the function is doing more than one job and should probably be split.

73.6 Inside one file: constants first, grouped by feature, no stray globals

Functions are the rooms; the file is the house, and it needs a floor plan. Well-kept JavaScript files follow the same top-to-bottom order, so a reader always knows where to look. Here it is for the notebook order calculator from Chapter 68:

// js/app.js - notebook order calculator

// ===== 1. Settings: fixed values, named once =====
const PRICE = 250;          // rupees per notebook
const TAX_RATE = 0.05;      // 5% tax
const MAX_QTY = 20;         // the shop sells at most 20 per order

// ===== 2. Elements, looked up once =====
const qtyInput = document.querySelector("#qty");
const calcBtn = document.querySelector("#calcBtn");
const totalEl = document.querySelector("#total");

// ===== 3. Calculations (no DOM in here) =====
function calculateTotal(qty) {
  const subtotal = qty * PRICE;
  return subtotal * (1 + TAX_RATE);
}

// ===== 4. Display =====
function showTotal(total) {
  totalEl.textContent = `Total: ₹${total.toFixed(2)}`;
}

// ===== 5. Event handlers =====
function handleCalculate() {
  const qty = Math.min(Number(qtyInput.value), MAX_QTY);
  showTotal(calculateTotal(qty));
}

// ===== 6. Wiring and start-up =====
calcBtn.addEventListener("click", handleCalculate);
showTotal(0);

A quantity of 2 shows Total: ₹525.00, as in Chapter 68's debugging challenge. Three habits are visible.

Constants at the top. A bare number inside a calculation — total = qty * 250 * 1.05; — is a magic number: nobody knows what 250 or 1.05 mean, and a price change means hunting for every copy. Name each fixed value once, at the top, in UPPER_SNAKE_CASE, and the calculation explains itself: qty * PRICE * (1 + TAX_RATE).

Grouped by feature. Calculations, display functions and handlers each sit together. A group big enough to scroll past is ready to become its own file — cart.js, search.js — which is what modules are for (section 73.8). The calculation group never touches the page, so calculateTotal can be tested without any HTML.

No stray globals. A global variable is declared outside every function, at the top level of a script. Every ordinary script on a page shares one global space (Chapter 49), so two files written by two people can quietly overwrite each other's names. Watch it happen:

<style>
  body { font-family: system-ui, sans-serif; padding: 6px 14px; }
</style>
<p>Two scripts written by two students, loaded on one page. Read the Console.</p>
<script>
  // ---- counter.js, written by Asha ----
  var total = 0;
  function reset() { total = 0; console.log("Asha's reset: counter back to 0"); }
  total = total + 3;
  console.log("Asha's counter after 3 clicks:", total);
</script>
<script>
  // ---- cart.js, written by Rahul: same names, different meaning ----
  var total = 500;
  function reset() { total = 500; console.log("Rahul's reset: cart back to 500"); }
  console.log("Rahul's cart total:", total);
</script>
<script>
  // ---- back in Asha's code, one more click ----
  total = total + 1;
  console.log("Asha expects 4, gets:", total);
  reset();   // whose reset runs?
</script>

The Console shows Asha's counter after 3 clicks: 3, Rahul's cart total: 500, Asha expects 4, gets: 501 and Rahul's reset: cart back to 500. Rahul's file silently replaced both Asha's total and her reset, with no error to warn anyone — which is what makes this bug so expensive to find.

Three habits keep globals under control:

  • Declare variables inside the function that uses them whenever you can; other files cannot see them.
  • Use const and let, never var. Had both files used let total, the second script would stop with SyntaxError: Identifier 'total' has already been declared: still broken, but loudly and at once — far better than a wrong number nobody notices.
  • Give each file its own private space with modules — the real cure, in section 73.8.
Quick check: in the example above, why did reset() in the third script run Rahul's version?

Ordinary scripts on one page share a single global space. The second script declared a function with the same name, reset, which replaced Asha's, so only Rahul's existed when the third script called it.

73.7 Comments that explain why, and formatting that never varies

The code already says what it does. A comment earns its place by saying what the code cannot: why it is written this way, which rule it follows, what trap it avoids.

// NOT USEFUL: these repeat the code in English
i = i + 1;                 // add 1 to i
const t = 0.05;            // t is 0.05

// USEFUL: these explain a reason the code cannot show
const GROUP_SIZE = 3;      // fest committee rule: 10% off from 3 tickets, not 4
li.textContent = s.name;   // textContent, not innerHTML: names come from users

// Load once at start-up: fetching on every key press made search lag on phones.
loadStudents();

const month = 9;           // Date months start at 0, so 9 means October

A few working rules:

  • One header comment per file: // js/search.js - filters the student list as the user types.
  • A short comment above a function when its name does not say everything. For functions other files use, write a documentation comment; VS Code shows it when you hover over the name:
/**
 * Adds a tip to a bill.
 * @param {number} bill        the bill in rupees
 * @param {number} tipPercent  the tip as a percentage, e.g. 10 for 10%
 * @returns {number}           the bill plus the tip, in rupees
 */
function calculateTotal(bill, tipPercent) {
  return bill * (1 + tipPercent / 100);
}
  • Delete commented-out code. Old versions belong in Git's history (Chapter 75), not at the bottom of the file.
  • Keep comments true. Change the comment when you change the code; readers believe a wrong comment.
  • // TODO: marks a known gap: // TODO: show a message when the list is empty.

Code tells you how; a good comment tells you why. If a comment only translates the line beside it into English, delete it. Where a future reader would ask "why is it done like this?", a comment belongs.

Formatting: same shape everywhere

These two pieces of code are identical to the computer. Only one is pleasant to debug:

// squashed

calc.addEventListener("click",()=>{const b=Number(bill.value),t=Number(tip.value)
result.textContent='Total: '+formatRupees(calculateTotal(b,t))})

// formatted

  return bill * (1 + tipPercent / 100);
}

  const b = Number(bill.value);
  const t = Number(tip.value);

Consistent formatting means the same indentation everywhere (two spaces is common), one statement per line, spaces around operators and after commas, a semicolon after each statement, one kind of quote, and a blank line between groups. You need not do it by hand: VS Code's Format Document (Shift+Alt+F on Windows, Shift+Option+F on a Mac) reformats the whole file, and the Prettier extension with "Format on Save" does it on every save.

Names need a consistent style too. Most JavaScript projects follow these conventions:

Which style matters less than everyone using the same one. On Chapter 69's TechFest page the HTML said id="buyBtn", the JavaScript asked for #buy-btn, and the Buy button did nothing — a bug one agreed naming style makes far less likely.

73.8 ES modules: files that share on purpose

Ordinary scripts have two weaknesses: they share one global space, and they must be listed in the right order so each one's helpers exist in time. ES modules (ES is short for ECMAScript, the official name of the JavaScript standard) fix both. A module is a JavaScript file loaded as a module. Each gets its own private space: nothing inside is visible to another file unless the module exports it and that file imports it.

Here is the smallest example, from the course slides:

module-demo/
├── index.html
├── app.js
└── utils.js

// ---- utils.js: export marks what other files may use ----
export function formatName(name) {
  return name.trim();
}

// ---- app.js: import says what this file needs, and from where ----
import { formatName } from "./utils.js";
console.log(formatName("  Rahul  "));     // Rahul

<!-- ---- index.html: only the entry file is mentioned ---- -->
<script type="module" src="./app.js"></script>

Served from a local web server, the Console shows Rahul. utils.js offers formatName; app.js asks for it; index.html loads app.js as a module, and the browser fetches utils.js itself because app.js imports it.

The rules, one at a time

  1. export goes in front of what you want to share — a function, a const, a class. Everything else stays private to its file.
  2. import { name } from "./file.js"; uses curly braces and the exact exported name. In the browser the path must start with ./, ../ or / (or be a full https:// address) and give the exact file name, .js included; the browser never guesses. (Bare names such as "utils" work only with an import map, which this course does not use.)
  3. Import lines sit at the top level of the file, never inside a function or an if, and by habit at the very top.
  4. Only the entry file needs type="module" in the HTML. Every file it imports, and every file those import, is fetched automatically.
  5. Module scripts are deferred automatically: no defer needed.
  6. Module code runs in strict mode, so mistakes ordinary scripts let slide, such as assigning to an undeclared variable, become visible errors.
  7. Each module runs once, however many files import it, and the page must be served over http:// or https:// (below).

Seeing the module rules for yourself

Importing needs several real files, which one example frame cannot hold. But a module written inside the page (an inline module) follows the same rules about timing, strict mode and privacy:

<style>
  body { font-family: system-ui, sans-serif; padding: 6px 14px; }
  h2 { font-size: 16px; }
</style>
<p>Press <b>Run</b>, then read the Console. The numbers show the real order.</p>

<script type="module">
  // A MODULE script, written FIRST on the page.
  const heading = document.querySelector("#below");
  console.log("2. The module runs after parsing, so it finds the heading below it:", heading !== null);

  const courseCode = "CSE326";      // private to this module

  try {
    marks = 95;                     // oops: no const or let
  } catch (err) {
    console.log("3. Strict mode turns the typo into an error:", err.name + ": " + err.message);
  }
</script>

<h2 id="below">I am written below the module script</h2>

<script>
  // An ORDINARY script, written LAST - but it runs the moment the parser reaches it.
  console.log("1. The ordinary script runs first, even though it is written last");

  document.addEventListener("DOMContentLoaded", () => {
    console.log("4. Can the ordinary script see courseCode?", typeof courseCode);
  });
</script>

The Console prints four lines in this order:

1. The ordinary script runs first, even though it is written last
2. The module runs after parsing, so it finds the heading below it: true
3. Strict mode turns the typo into an error: ReferenceError: marks is not defined
4. Can the ordinary script see courseCode? undefined

Line 2 shows the module was deferred: written above the heading, it still ran after the page was read. Line 3 shows strict mode: in an ordinary script marks = 95 would quietly create a global; in a module it is a ReferenceError. Line 4 shows privacy: courseCode never left the module (typeof gives "undefined" for a missing name instead of throwing). As modules, Asha's and Rahul's two total variables would never have met.

A module is a file with a locked door. export puts something on the doorstep for others to collect; import collects it from a named doorstep. Everything else stays inside.

Why double-clicking index.html is not enough

Double-click index.html and the address bar shows file:///C:/Users/.../index.html: the page came from your disk, not a server. Browsers fetch module files with the same safety check they use for other websites' data (the CORS check), which a file:// page fails. Chrome and Edge show a red error like this:

Access to script at 'file:///C:/Users/Meera/tip-calculator/js/app.js' from origin 'null'
has been blocked by CORS policy

The fix is to run a small web server on your own computer and open the page through it:

  • VS Code Live Server: right-click index.html → Open with Live Server. The address becomes http://127.0.0.1:5500/index.html.
  • Node.js installed: in the project folder, run npx serve.
  • Python installed: in the project folder, run python -m http.server, then open http://localhost:8000.
"Works on Live Server, blank when double-clicked." Not a bug in your code: it is the file:// rule. On GitHub Pages (Chapter 76) the site is served over https:// and modules load normally.

Named exports and default exports

Everything so far used named exports: the import must use the exported name inside curly braces, and a file can have as many as it likes. A file can also have one default export, its "main thing", imported without braces under any name you choose.

// ---- money.js: two NAMED exports ----
export const CURRENCY = "₹";
export function formatRupees(n) {
  return CURRENCY + n.toFixed(2);
}

// ---- greet.js: one DEFAULT export ----
export default function greet(name) {
  return `Namaste, ${name}!`;
}

// ---- app.js ----
import { formatRupees, CURRENCY } from "./money.js";   // named: braces, exact names
import greet from "./greet.js";                         // default: no braces

console.log(formatRupees(99));     // ₹99.00
console.log(greet("Asha"));        // Namaste, Asha!
You want to...Write
Rename a named importimport { formatRupees as rupees } from "./money.js";
Import a default under another nameimport sayHello from "./greet.js";
Import everything as one objectimport * as money from "./money.js"; then money.formatRupees(99)
Export a list at the bottom of a fileexport { formatRupees, CURRENCY };
Exam tip. Braces mean named; no braces means default. A named import must match the exported name exactly (or rename it with as); a default import can be called anything. Many named exports per file, but only one default.
Quick check: utils.js contains export default function formatName(name) { ... }. app.js says import { formatName } from "./utils.js";. What happens?

It fails: SyntaxError: The requested module './utils.js' does not provide an export named 'formatName'. The braces ask for a named export, but formatName is the default. Drop the braces — import formatName from "./utils.js"; — or remove default from the export.

73.10 Common misunderstandings

✗ "defer works on any script tag."
It is ignored on inline scripts, which run immediately wherever they sit.
✓ "defer works only with src."
Load a file with <script src="js/app.js" defer>, or use type="module", which is deferred automatically.
✗ "If the images show on my laptop, my file names are fine."
Windows and macOS ignore capital letters in file names, so mismatches stay hidden until you deploy.
✓ "Servers are case-sensitive, so I name everything in lowercase."
On GitHub Pages Logo.png and logo.png are different files.
✗ "Double-clicking index.html is a fine way to test a module page."
A file:// page cannot load module files; Chrome and Edge block them with a CORS error.
✓ "Module pages are tested through a local server."
Live Server, npx serve or python -m http.server, so the address starts with http://.
✗ "Splitting into many small functions makes the program slower."
Calling a function costs a tiny fraction of a millisecond.
✓ "Small functions make the program easier to read, test and change."
Real speed problems come from things like downloading data on every key press, which organising helps you spot (Chapter 74).

Exam-style checks

Which attribute lets an external script download during HTML parsing and run only after parsing finishes, in the order the scripts are written?L1
  • A. async
  • B. defer
  • C. type="text/javascript"
  • D. lazy

Answer: B. async also downloads in parallel, but runs each script on arrival, in any order, possibly before parsing ends. type="text/javascript" is the old default and changes nothing; lazy is not a script attribute.

Which file name is the safest choice for an image in a web project?L1
  • A. Campus Photo.JPG
  • B. campus_photo final.jpg
  • C. campus-photo.jpg
  • D. CampusPhoto.JPG

Answer: C. Lowercase, hyphen-joined, no spaces. A and B contain spaces (%20 in URLs); A and D mix capitals, which break on case-sensitive servers when the HTML spells the name differently.

Why is <link rel="stylesheet"> normally placed in the <head>?L2
  • A. So the CSS arrives before the page is first drawn, and it never flashes up unstyled
  • B. A stylesheet link in the body is a syntax error
  • C. So the CSS runs after the JavaScript
  • D. Browsers ignore CSS linked from the body

Answer: A. The browser waits for the CSS it knows about before drawing, so linking it early gives a styled first frame. B and D are false: a stylesheet linked lower down is still applied, but content above it may show unstyled first. C makes no sense: CSS does not "run".

Three ordinary scripts are loaded on one page, in this order. What does the Console show?
<script> var count = 10; function show() { console.log("A:", count); } </script>
<script> var count = 99; function show() { console.log("B:", count); } </script>
<script> show(); </script>L3

Answer: B: 99. Ordinary scripts share one global space. The second script's var count overwrote the first, and its show replaced the first, so the third script finds only the second versions. As modules, neither name would leak out.

utils.js contains export default function formatRupees(n) { ... }. Which line in app.js imports it correctly?L2
  • A. import { formatRupees } from "./utils.js";
  • B. import formatRupees from "./utils.js";
  • C. import formatRupees from "utils";
  • D. import default from "./utils.js";

Answer: B. A default export is imported without braces. A asks for a named export and fails ("does not provide an export named 'formatRupees'"); C lacks ./ and .js, so the browser cannot resolve it; D is invalid, because default is a reserved word.

Meera double-clicks index.html. The address bar shows file:///C:/Users/Meera/tip-calculator/index.html and the Console says the module js/app.js "has been blocked by CORS policy". What should she do?L3
  • A. Rename app.js to app.mjs
  • B. Remove type="module" from the script tag
  • C. Move the script tag to the end of the body
  • D. Open the folder through a local web server such as Live Server, so the page loads over http://

Answer: D. Module files cannot be loaded into a page opened from file://. B swaps that error for "Cannot use import statement outside a module"; A and C do not change where the page was loaded from.

Which comment is the most useful?L2
  • A. count = count + 1; // add one to count
  • B. const TAX = 0.05; // TAX is 0.05
  • C. const GROUP_SIZE = 3; // fest rule: 10% off from 3 tickets, not 4
  • D. // function, written above a function

Answer: C. It records a rule the code cannot explain, and warns the next reader off the tempting change to 4. A and B repeat the code in English; D says nothing.

One input handler fetches students.json, filters the students, builds the list items and updates a message. Which change is the best reorganisation?L2
  • A. Split it into loadStudents, filterStudents, renderStudents and showMessage; load once at start-up; the handler only filters, renders and shows
  • B. Add a comment above each part of the handler
  • C. Move the handler, still one function, into another file
  • D. Rename the handler doEverything

Answer: A. Each function gets one job and one reason to change, the filter can be tested alone, and the data is no longer downloaded on every key press. B and C leave every problem in place; D only names it.

The page loads app.js with type="module" and is served by Live Server. What does the Console show?
utils.js: export function double(n) { return n * 2; } and const SECRET = 42;
app.js: import { double } from "./utils.js"; console.log(double(21)); console.log(typeof SECRET);L3

Answer: 42, then undefined. double was exported and imported, so double(21) is 42. SECRET was never exported, so it stays private to utils.js; in app.js the name does not exist, and typeof then gives "undefined" instead of an error.

The Console shows Uncaught SyntaxError: Cannot use import statement outside a module. What is the most likely cause?L2
  • A. utils.js does not export anything
  • B. The import path is missing ./
  • C. The page was opened from file://
  • D. The <script> tag that loads app.js is missing type="module"

Answer: D. Without type="module", app.js is an ordinary script, where import is not allowed. A gives "does not provide an export named ...", B "Failed to resolve module specifier", C a CORS error.

Which statement about <script type="module"> is FALSE?L2
  • A. It is deferred automatically, so it runs after the page is parsed
  • B. Its code runs in strict mode
  • C. Its top-level variables become global variables that every other script can use
  • D. The module files it loads must come over http:// or https://, not file://

Answer: C. The opposite is true: a module's top-level names stay private unless exported and imported — the main reason to use modules.

Why is calculateTotal(bill, tipPercent) in the refactored tip calculator easier to test than the original click handler, and what does formatRupees(calculateTotal(800, 25)) return?L3

Answer: it is a pure function — numbers in, a number out, no page — so you can call it with values whose answers you know, with no typing or clicking. calculateTotal(800, 25) is 800 × 1.25 = 1000, and formatRupees(1000) returns "₹1000.00".

Quick revision

Key takeaways

  1. Organising code does not change what it does; it makes the next change cheap.
  2. HTML in index.html, CSS in css/styles.css, JavaScript in js/app.js; link the CSS and load the script with defer, both in the head.
  3. defer downloads in parallel and runs after parsing, in order. It works only with src.
  4. index.html at the top level, one folder per kind of file, lowercase hyphenated names with no spaces: servers are case-sensitive.
  5. Small single-job functions with verb names; named constants instead of magic numbers; related code grouped; few globals.
  6. Comments explain why; formatting is the same everywhere, and a formatter can do it.
  7. ES modules: export to share, import { x } from "./file.js" to use, type="module" on the entry script. Modules are deferred, strict and private, and need http://, not file://.
  8. Named exports: braces, exact names, many per file. Default export: no braces, any name, one per file.
