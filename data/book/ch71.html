Interactive User Interface Development

A notice board shows the same sheet until somebody walks up and pins a new one. The pages you use every day behave differently: they answer every click and keystroke at once, show you what they are doing, and let you take a mistake back. This chapter joins up everything Unit 5 taught about events and the DOM into four small, complete apps, and the habits that keep such code tidy.

About 35 minutes · Course outcome CO6

Before you start — one-line reminders

  • addEventListener("click", fn) leaves a function with the browser to call later, and one listener on a parent can serve all its children (Chapter 57).
  • A render() function turns an array into page content with createElement and textContent; user text never goes into innerHTML (Chapter 58).
  • In a submit handler, event.preventDefault() stops the page reloading so your script can check the form (Chapter 60).
  • array.filter(fn) keeps only the items for which fn returns true (Chapter 53).

By the end of this chapter you can

  • Say what makes an interface interactive — feedback, responsiveness and state you can see — and name the common interactive components.
  • Trace the event-driven chain: user action, browser event, handler, state change, updated screen.
  • Write an event listener correctly, and explain why addEventListener("click", greet()) is a bug.
  • Build a counter, a live search and a form with live error messages, all with the pattern event → change state → render().
  • Pick the right feedback for an action: a disabled button, loading text, a success message or an undo.
  • Apply six DOM habits: select once, textContent for text, classes not styles, delegation, no inline handlers, data as the source of truth.
  • Build the task manager: add, complete, delete, search, count and an empty state.

71.1 What makes an interface interactive

Open the university exam notice: a heading, some paragraphs, a table of dates. You can only read it, and the one way to see something different is to load a different page. That is a static interface. Now open a course list with buttons for All, CSE and ECE and a search box. Press CSE and the list changes at once; type two letters and it narrows while you type. Nothing reloaded. That is an interactive interface: it answers what the user does, immediately, inside the same page.

You use eight interactive components every day:

ComponentWhat it does
ButtonsTrigger an action: save, add, like
Navigation menusA hamburger icon opens the menu on a phone
TabsSwitch views without reloading
FormsCheck what you type as you type it
Search fieldsFilter results live
ModalsA dialog over the page: "Delete this file?"
Expandable panelsA question opens to show its answer
Dynamic listsItems added, removed, re-ordered

Every good one of these shares three qualities:

  1. Feedback. Every action gets a visible answer. A button changes, a number moves, a message appears.
  2. Responsiveness. The answer comes at once. About a tenth of a second feels instant; anything slower than a second needs a sign that work is going on.
  3. State you can see. The screen always shows the current situation: which tab is open, how many items are in the cart, whether something is still saving. The data that describes that situation is the page's state.
Picture this. You press the call button for the lift on the ground floor of your block. A good lift answers you three ways: the button lights up the moment you touch it (feedback: "I heard you"), the panel over the door counts down the floors as the lift comes (state you can see), and then the doors open (the result). Now picture a button that does not light up. People press it again, and again, ten times — not because they are impatient, but because nothing told them the first press worked. A web page without feedback gets the same treatment: a Submit button pressed three times, three orders, three payments.
Quick check: a Save button saves the data correctly but nothing on the screen changes. Which of the three qualities is missing?

Feedback. The work was done, but the user cannot tell, so they will press it again or assume it failed. A message such as "Saved" or a button that briefly says "Saving..." fixes it.

71.2 The event-driven model: wait, react, update

A program you might imagine runs from its first line to its last and stops. Browser JavaScript is different. When the page loads, your script runs once, top to bottom: it finds the elements it needs, registers its handlers, and draws the starting screen. Then it has nothing more to do. The page sits there, waiting. Only when the user does something does the browser wake a piece of your code up. This style is called event-driven programming, and every interactive page follows the same five-step chain:

The function that runs in step 3 is the event handler. It does two things: it changes the data, then it updates the page from that data. The browser repaints the screen once your handler has finished. Five events cover nearly everything in this chapter:

EventFires when…Typical use
clickAn element is clicked or tapped (or Enter/Space is pressed on a focused button)Buttons, menu toggles, cards
inputThe value of a box changes — every keystroke, paste or clearLive search, character counters
changeA value is committed: a select or checkbox is changed, or a text box is left after editingDropdown filters, tick boxes
submitA form is sent, by its submit button or by Enter in one of its fieldsChecking a form before it goes
keydownA key is pressed downShortcuts, Escape to close a dialog

Your script is not a film that plays from start to finish. It is a set of notes left with the browser: "when this happens, run that". The browser watches; your functions run only when their moment comes, change the data, and redraw the page.

71.3 Event listener syntax, one more time

Every listener in this chapter has the same three parts:

const button = document.querySelector("#myButton");

button.addEventListener("click", () => {
  console.log("Button clicked");
});
PartWhat it is
querySelector("#myButton")The selector. Finds the first element matching the CSS selector — or gives null if there is none.
"click"The event type, a string naming what to listen for.
() => { ... }The callback. The browser stores this function and calls it each time the event happens.

The first trap is null. If the <script> tag sits in the <head>, it runs before the browser has read the button, so querySelector finds nothing and the next line fails with TypeError: Cannot read properties of null (reading 'addEventListener'). Put the script at the end of the <body>, or write <script src="app.js" defer></script> so it waits until the HTML has been read.

The second trap is the most common beginner bug in this whole unit: calling a function when you meant to pass it. greet is the function itself, a recipe handed over to be used later. greet() means "run it now", and what you hand over is whatever it returns — here, undefined. The browser quietly accepts undefined and simply has nothing to run when the click comes. Predict what this page does before you press Run:

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  button { padding: 8px 14px; margin-right: 6px; cursor: pointer; }
</style>
<button id="broken">Broken button</button>
<button id="fixed">Fixed button</button>
<p id="out">Clicks so far: 0</p>

<script>
  const brokenBtn = document.querySelector("#broken");
  const fixedBtn = document.querySelector("#fixed");
  const out = document.querySelector("#out");
  let clicks = 0;

  function greet() {
    clicks++;
    out.textContent = `Clicks so far: ${clicks}`;
    console.log("Hi!");
  }

  brokenBtn.addEventListener("click", greet());   // BUG: greet() runs NOW
  fixedBtn.addEventListener("click", greet);      // right: hand the function over
  console.log("Listeners attached. clicks =", clicks);
</script>

The Console shows Hi! and then Listeners attached. clicks = 1, and the page already says Clicks so far: 1 — before you have touched anything. That one Hi! came from greet() running while the listener was being set up. Click Broken button as often as you like: nothing happens. Click Fixed button: Hi! again and Clicks so far: 2. When a handler needs arguments, wrap the call in a new arrow function, which is passed and not called: btn.addEventListener("click", () => greet("Asha"));

Quick check: a page has btn.addEventListener("click", showMenu()); where showMenu opens a menu. What does the user see?

The menu opens once by itself as the page loads (because showMenu() ran then), and clicking the button afterwards does nothing. The fix is btn.addEventListener("click", showMenu); — no brackets.

71.4 Build 1: the interactive counter

Chapter 57 built a counter; here is the lecture's version, laid out the way a real project is, plus the lab task. The structure comes first:

<!-- index.html -->
<main class="counter">
  <h1>Click Counter</h1>
  <p id="count" class="count" aria-live="polite">0</p>
  <div class="actions">
    <button id="decrement">&minus;</button>
    <button id="reset">Reset</button>
    <button id="increment">+</button>
  </div>
</main>
<script src="counter.js" defer></script>

/* styles.css (the part that matters) */
.count          { font-size: 4rem; font-weight: 700; }
.count.negative { color: #dc2626; }

Three decisions in this HTML are worth copying into every project:

  • One source of truth. The number lives in a JavaScript variable; #count only displays it.
  • Real <button> elements. Tab, Enter, Space and screen-reader support come free; a clickable <div> has none of them (Chapter 59).
  • Style by class. JavaScript adds or removes the class negative; the CSS decides that negative means red. aria-live="polite" asks screen readers to announce the new number whenever it changes.

The lecture's counter.js grabs the elements once, keeps let count = 0 as the state, and puts every page update into one render(). Each handler changes the state, then calls render(), so the screen can never disagree with the data. Here it is with the lab task done — a +5 button, and a floor at −10:

<style>
  .counter { max-width: 320px; margin: 10px auto; text-align: center;
             font-family: system-ui, sans-serif; }
  .count { font-size: 4rem; font-weight: 700; margin: 6px 0; }
  .count.negative { color: #dc2626; }
  .actions { display: flex; gap: 8px; justify-content: center; }
  button { padding: 8px 16px; font-size: 1.25rem; cursor: pointer; }
  .note { color: #64748b; font-size: 14px; min-height: 20px; }
</style>
<main class="counter">
  <h1>Click Counter</h1>
  <p id="count" class="count" aria-live="polite">0</p>
  <div class="actions">
    <button id="decrement" aria-label="Decrease">&minus;</button>
    <button id="reset">Reset</button>
    <button id="increment" aria-label="Increase">+</button>
    <button id="plus5">+5</button>
  </div>
  <p id="note" class="note"></p>
</main>

<script>
  const MIN = -10;                                 // the lab task: the floor
  const countEl  = document.querySelector("#count");
  const noteEl   = document.querySelector("#note");
  const incBtn   = document.querySelector("#increment");
  const decBtn   = document.querySelector("#decrement");
  const resetBtn = document.querySelector("#reset");
  const plus5Btn = document.querySelector("#plus5");

  let count = 0;                                   // the state

  function render() {                              // state -> screen, nothing else
    countEl.textContent = count;
    countEl.classList.toggle("negative", count < 0);
    decBtn.disabled = count <= MIN;                // feedback: you cannot go lower
    noteEl.textContent = count <= MIN ? `Lowest allowed is ${MIN}.` : "";
    console.log("count =", count);
  }

  function change(step) {
    count = Math.max(MIN, count + step);           // the data can never pass the floor
    render();
  }

  incBtn.addEventListener("click", () => change(1));
  decBtn.addEventListener("click", () => change(-1));
  plus5Btn.addEventListener("click", () => change(5));
  resetBtn.addEventListener("click", () => { count = 0; render(); });

  render();                                        // draw the starting state
</script>

On Run, the last line draws the starting state and the Console shows count = 0. Press +5 twice (count = 5, count = 10), then Reset (count = 0). Now press − repeatedly: at count = -1 the number turns red, and at count = -10 the − button greys out and the note says Lowest allowed is -10.

classList.toggle("negative", count < 0) takes a second argument: when it is true the class is added, when false it is removed. The floor has two guards doing two jobs: decBtn.disabled tells the user they have reached the end, and Math.max(MIN, count + step) protects the data — Math.max(-10, -11) is -10 — even if some other code calls change(-1).

Key idea. The pattern to remember for every interactive page: event → change state → render(). Handlers never touch the page directly; only render() does.

71.5 Build 2: live search

A live search narrows a list while you type. Four steps run on every keystroke:

The HTML is a labelled search box and an empty list: <label for="search">Search students</label>, <input id="search" type="search">, <ul id="results"></ul>. Here is the lecture's code, with one addition — a status line that counts the matches:

<style>
  body { font-family: system-ui, sans-serif; padding: 14px; }
  label { display: block; font-weight: 600; margin-bottom: 4px; }
  input { font-size: 15px; padding: 6px 8px; width: 240px; max-width: 100%; }
  #status { color: #475569; font-size: 14px; }
</style>
<label for="search">Search students</label>
<input id="search" type="search">
<p id="status" role="status"></p>
<ul id="results"></ul>

<script>
  // The data
  const students = [
    "Aarav Sharma", "Diya Patel", "Ishaan Gupta", "Kavya Nair",
    "Rohan Mehta", "Saanvi Iyer", "Vivaan Singh",
  ];
  const input = document.querySelector("#search");
  const list = document.querySelector("#results");
  const statusEl = document.querySelector("#status");

  // Draws whatever array it is given - it does not care where the array came from
  function renderStudents(items) {
    list.replaceChildren();                        // clear the list
    if (items.length === 0) {
      const li = document.createElement("li");
      li.textContent = "No students found";
      list.append(li);
      return;
    }
    items.forEach((name) => {
      const li = document.createElement("li");
      li.textContent = name;
      list.append(li);
    });
  }

  // Works out the matches, then asks renderStudents to draw them
  function search() {
    const query = input.value.trim().toLowerCase();
    const matches = students.filter((name) => name.toLowerCase().includes(query));
    renderStudents(matches);
    statusEl.textContent = query === ""
      ? `All ${students.length} students`
      : `${matches.length} of ${students.length} students match "${query}"`;
    console.log(`search "${query}":`, matches.length, "of", students.length);
  }

  input.addEventListener("input", search);
  search();                                        // show everyone at the start
</script>

On Run the Console shows search "": 7 of 7 and all seven names appear. Why does an empty box match everyone? Because every string includes the empty string: "Diya Patel".includes("") is true. That is exactly what you want — clear the box and the whole list comes back with no special code.

Type an: search "an": 4 of 7, showing Ishaan Gupta, Rohan Mehta, Saanvi Iyer and Vivaan Singh (Kavya Nair is left out: its a and n have a space between them). Type xyz: search "xyz": 0 of 7, and the list shows No students found. That message is the list's empty state; without it the user sees a blank box and assumes the page is broken.

Each keystroke: read the box, tidy it (strip spaces, make it small letters), keep only the names containing it, and redraw the list from those names. Lower-casing both sides is what makes AN, An and an all find Ishaan.

list.replaceChildren() with empty brackets removes every child of the list in one call. And the work is split on purpose: renderStudents only draws an array, search only works out which array. Each can be tested alone, and renderStudents could draw a list from a server tomorrow unchanged.

Quick check: Meera types SH (capitals) into the box. Which names are shown, and what does the status line say?

The query becomes "sh". It is inside Aarav Sharma and inside Ishaan Gupta (i-sh-aan), so two names show and the status says 2 of 7 students match "sh". Vivaan Singh does not match: s is followed by i, not h.

71.6 Build 3: form validation feedback

The third build is a registration form that tells the user, in plain words and right under the field, what is wrong. The HTML gives every field three things: a real <label> (clicking it focuses the box), the input, and its own empty error paragraph. novalidate on the form switches off the browser's own pop-up bubbles, so your messages look the same in every browser. A role="status" paragraph at the bottom reports the overall result.

The JavaScript has two parts. getError(field, value) holds all the rules in one place and returns a message, or an empty string when the value is fine. The submit handler stops the page reloading, checks every field (so the user sees all the problems at once, not one per attempt), writes each message under its field, marks the field with aria-invalid so screen readers say "invalid entry", and reports success only when everything passes.

The lecture checks only on Submit. One small addition makes the feedback real-time: once a field is showing an error, it is re-checked on every keystroke, so the red message disappears the instant the user fixes it. Chapter 60 calls this late to complain, quick to forgive: never scold someone for a half-typed email, but never leave a message up after the mistake is fixed.

<style>
  body { font-family: system-ui, sans-serif; padding: 14px; }
  label { display: block; font-weight: 600; margin-top: 10px; }
  input { font-size: 15px; padding: 6px 8px; width: 240px; max-width: 100%;
          border: 2px solid #94a3b8; border-radius: 6px; }
  input[aria-invalid="true"] { border-color: #dc2626; }
  .error { color: #dc2626; font-size: 14px; margin: 3px 0 0; min-height: 18px; }
  button { margin-top: 12px; padding: 8px 14px; cursor: pointer; }
</style>
<form id="registerForm" novalidate>
  <label for="name">Full name</label>
  <input id="name" autocomplete="name">
  <p class="error" id="name-error"></p>

  <label for="email">Email</label>
  <input id="email" type="email">
  <p class="error" id="email-error"></p>

  <label for="password">Password</label>
  <input id="password" type="password">
  <p class="error" id="password-error"></p>

  <button type="submit">Create account</button>
  <p id="form-status" role="status"></p>
</form>

<script>
  const form = document.querySelector("#registerForm");
  const statusEl = document.querySelector("#form-status");
  const fields = ["name", "email", "password"];

  // The rules, in one place: a message, or "" when the value is fine
  function getError(field, value) {
    if (field === "name" && value.length < 2) return "Enter at least 2 characters.";
    if (field === "email" && !value.includes("@")) return "Enter a valid email address.";
    if (field === "password" && value.length < 8) return "Use at least 8 characters.";
    return "";                                     // no problem
  }

  // Check one field, show the result under it, say whether it passed
  function checkField(field) {
    const input = document.querySelector(`#${field}`);
    const errorEl = document.querySelector(`#${field}-error`);
    const message = getError(field, input.value.trim());
    errorEl.textContent = message;
    input.setAttribute("aria-invalid", message !== "");
    return message === "";
  }

  form.addEventListener("submit", (event) => {
    event.preventDefault();                        // stay on this page
    let valid = true;
    fields.forEach((field) => {                    // check EVERY field
      if (!checkField(field)) valid = false;
    });
    statusEl.textContent = valid
      ? "Account created! (demo — nothing was sent)"
      : "Please fix the errors above.";
    console.log("Submit pressed. valid =", valid);
  });

  // Real-time: a field that is showing an error is re-checked on every key
  fields.forEach((field) => {
    const input = document.querySelector(`#${field}`);
    input.addEventListener("input", () => {
      if (input.getAttribute("aria-invalid") === "true") checkField(field);
    });
  });

  // The rules can be tested with no clicking at all
  console.log("Rule test 1:", getError("email", "ravi.college.edu"));
  console.log("Rule test 2:", getError("email", "ravi@college.edu") === "" ? "(no error)" : "error");
</script>

On Run, the two test lines prove the rules work on their own: Rule test 1: Enter a valid email address. and Rule test 2: (no error). Now press Create account with everything empty. All three messages appear at once, three borders turn red, the status says Please fix the errors above. and the Console logs Submit pressed. valid = false.

Type A into Full name: the message stays (one character is still too short). Type a second letter and it vanishes on that keystroke, because the field was marked invalid and the input listener re-checked it. Fill in a real email and an 8-character password, press the button again, and you get Account created! and valid = true.

setAttribute turns the true/false into the text "true" or "false", and the CSS rule input[aria-invalid="true"] paints the red border: one attribute serves screen readers and the styling together.

Not a security check. Anyone can switch JavaScript off, edit your code in DevTools, or send data straight to the server without using your form. Browser validation exists for instant, friendly feedback. When a real server receives the data, it must check every rule again.

71.7 Feedback patterns: busy, done, and undo

The three builds each answered the user at once. Some actions cannot finish at once — sending a form to a server can take seconds — and some actions are dangerous, like deleting. Four patterns cover these cases:

PatternUse it whenIn code
Disabled button while busyAn action takes time and must not run twice (submit, pay, send)btn.disabled = true; until the work finishes
Loading textThe wait is long enough to notice (about a second or more)btn.textContent = "Submitting..."; or a status line
Success messageThe action worked and nothing else shows itText in a role="status" element: "Submitted"
UndoThe action destroys something (delete, archive)Do it at once, keep a copy for a few seconds, offer an Undo button

Undo is kinder than an "Are you sure?" box. People click OK on confirmation boxes without reading them; an undo lets them act quickly and still recover. It usually appears as a toast: "Deleted 'Email the mentor'. Undo". Error messages are the fifth pattern, and Chapter 70 covers them.

<style>
  body { font-family: system-ui, sans-serif; padding: 14px; }
  h3 { margin: 10px 0 6px; font-size: 16px; }
  button { padding: 6px 12px; cursor: pointer; }
  button:disabled { cursor: wait; opacity: 0.6; }
  li { margin: 4px 0; }
  #toast { background: #0B2545; color: #fff; padding: 8px 12px; border-radius: 8px;
           display: inline-block; }
  #toast[hidden] { display: none; }
</style>
<h3>1. Busy, then success</h3>
<button id="saveBtn">Submit assignment</button>
<p id="saveMsg" role="status"></p>

<h3>2. Delete with undo</h3>
<ul id="notes"></ul>
<p id="toast" role="status" hidden>
  <span id="toastText"></span> <button id="undoBtn">Undo</button>
</p>

<script>
  // ---- 1. Busy, then success ----
  const saveBtn = document.querySelector("#saveBtn");
  const saveMsg = document.querySelector("#saveMsg");

  saveBtn.addEventListener("click", () => {
    saveBtn.disabled = true;                      // a second click cannot start a second submit
    saveBtn.textContent = "Submitting...";        // loading text
    saveMsg.textContent = "";
    console.log("Busy: button disabled");
    setTimeout(() => {                            // pretend the server takes 1.5 seconds
      saveBtn.disabled = false;
      saveBtn.textContent = "Submit assignment";
      saveMsg.textContent = "Submitted. You can close this page.";   // success
      console.log("Done: button enabled again");
    }, 1500);
  });

  // ---- 2. Delete with undo ----
  let notes = ["Buy lab record", "Email the mentor", "Revise Unit 5"];
  let lastDeleted = null;                         // { note, index } kept for undo
  let toastTimer = null;
  const list = document.querySelector("#notes");
  const toast = document.querySelector("#toast");
  const toastText = document.querySelector("#toastText");

  function render() {
    list.replaceChildren();
    notes.forEach((note, i) => {
      const li = document.createElement("li");
      li.textContent = note + " ";
      const btn = document.createElement("button");
      btn.textContent = "Delete";
      btn.dataset.index = i;                      // which note this button belongs to
      li.append(btn);
      list.append(li);
    });
    console.log("notes:", notes.join(" | "));
  }

  list.addEventListener("click", (event) => {     // one listener for every Delete
    const btn = event.target.closest("button");
    if (!btn) return;
    const index = Number(btn.dataset.index);
    lastDeleted = { note: notes[index], index };
    notes.splice(index, 1);                       // delete at once - no "Are you sure?"
    render();
    toastText.textContent = `Deleted "${lastDeleted.note}".`;
    toast.hidden = false;
    clearTimeout(toastTimer);                     // restart the 5-second clock
    toastTimer = setTimeout(() => {
      toast.hidden = true;
      lastDeleted = null;                         // too late to undo now
    }, 5000);
  });

  document.querySelector("#undoBtn").addEventListener("click", () => {
    if (!lastDeleted) return;
    notes.splice(lastDeleted.index, 0, lastDeleted.note);   // put it back in its old place
    lastDeleted = null;
    toast.hidden = true;
    render();
  });

  render();
</script>

On Run the Console lists notes: Buy lab record | Email the mentor | Revise Unit 5. Press Submit assignment: the button greys out and says Submitting..., the Console says Busy: button disabled, and 1.5 seconds later Done: button enabled again with the success line on the page. Try to click it twice during the wait — you cannot.

Now delete Email the mentor: it goes at once (notes: Buy lab record | Revise Unit 5) and the toast appears. Press Undo within five seconds and it returns to the middle, because splice(index, 0, note) inserts at the old position, and the Console lists all three again. Wait longer and the toast leaves, taking the undo with it.

While something is working, say so and stop a second click. When it is done, say that too. When something is destroyed, keep a copy for a few seconds and offer it back. The user should never have to guess what the page is doing.

71.8 DOM manipulation best practices

Six DOM tools did all the work in this chapter:

MethodUse it to…
querySelector()Find one element with a CSS selector
createElement()Make a new element in memory, not yet on the page
textContentSet text safely — it is never treated as HTML
append()Insert elements or text (appendChild takes exactly one node)
classListadd, remove or toggle CSS classes
addEventListener()Attach behaviour without writing onclick in the HTML

Six habits turn those tools into code that stays correct as it grows.

1. Select once, reuse the result

Find each element once, near the top, and keep it in a const. Searching inside a handler repeats the search on every keystroke and scatters "#results" strings through the file.

2. textContent for anything the user typed

innerHTML reads its text as HTML. Put a visitor's comment into it and the browser obeys any tags inside. If an attacker types this as a "comment", the broken image's onerror runs their script in the browser of everyone who views the page:

// UNSAFE: the text is parsed as HTML
item.innerHTML = input.value;

// The attacker types:  <img src=x onerror="alert('hacked')">
// innerHTML builds a real <img>, it fails to load, onerror runs the script.

// SAFE: the same text is shown as plain characters
item.textContent = input.value;

Running an attacker's text as code in another user's browser is called XSS. The rule from Chapter 58: user data and data from a server go in with textContent; innerHTML is only for fixed markup you wrote yourself.

3. Toggle classes, do not set styles

countEl.style.color = "red" hard-codes the look inside JavaScript. countEl.classList.toggle("negative", count < 0) says only what is true; the CSS decides how that looks, so a designer can change red to orange without touching your script.

4. Event delegation for lists

A list whose items come and go should not get one listener per item. Put one listener on the parent that never changes, and ask which child was hit with event.target.closest(...). This is event delegation (Chapter 57). It matters even more with render(): every redraw throws the old items away together with any listeners on them, but the listener on the parent survives every redraw.

5. No inline handlers

An inline handler such as <button onclick="addTask()"> mixes behaviour into the HTML, works only with global functions, and is blocked outright by sites that use a strict security policy. Keep the HTML for structure and attach every behaviour with addEventListener in the script.

6. Keep the data as the source of truth

Never read your state back out of the page. count = Number(countEl.textContent) + 1 works until the display changes to "Count: 3", and then gives NaN. Counting tasks with listEl.children.length breaks as soon as a search hides some. The data lives in variables; the page is only a picture of it.

Find things once. Put user text in with textContent. Let CSS classes decide looks. Give a list one listener on its parent. Keep JavaScript out of the HTML. And treat the page as a picture of your data, never as the data itself.

Quick check: a task list adds a click listener to each Delete button inside render(). Why is one listener on the ul better?

The ul is never rebuilt, so its single listener is attached once and keeps working for every button, including ones added later. Per-button listeners must be attached again on every redraw, and forgetting once leaves buttons that do nothing.

71.9 The task-manager challenge, step by step

The lab for this module brings everything together: a small to-do app. Try it yourself for 30–45 minutes before reading the solution. The feature checklist:

FeatureWhat it must do
Add taskWith the Enter key or the button; ignore empty text
Mark completedA checkbox toggles a strike-through
Delete taskRemoves only that task
Search tasksLive filter while typing
Empty state"No tasks yet — add your first one above."
Counter"X of Y done"
AccessibleLabels, real buttons, everything works with the keyboard
BonusSave to localStorage

The lecture's hint is the whole design in one line: let tasks = [{ id, title, done }] → render(). Build it in six steps.

Step 1 — the HTML. Put the new-task box and its button inside a <form>. Enter in a form field submits the form, so one submit listener handles both Enter and the button. Add a labelled search box, an empty <ul>, a paragraph for the empty state and a role="status" paragraph for the counter.

Step 2 — the state and render(). The state is the tasks array plus the search word, query. render() filters the tasks by query, builds one <li> per visible task (a checkbox and the title inside a label, plus a Delete button), and fills in the empty state and the counter. Each <li> carries data-id, so an event can find its task.

Step 3 — add. In the submit handler: preventDefault(), trim() the text, return if it is empty, push a new task object, clear the box, render.

Step 4 — complete and delete, with delegation. Two listeners on the <ul>: a change listener for the checkboxes and a click listener for the Delete buttons. Each one climbs from the element that was hit to its <li> with closest("li"), reads data-id, and finds the task in the array. Then it changes the array — never the page — and renders.

Step 5 — search. An input listener on the search box sets query and renders. It is the live search from 71.5, applied to task titles.

Step 6 — the bonus. save() writes JSON.stringify(tasks) to localStorage after every change; load() reads it back at start-up, with sample tasks as the default (Chapter 64). In this book's Run frame storage starts empty each Run; opened with Live Server, the tasks survive a reload.

<script>
  const addForm   = document.querySelector("#addForm");
  const newTask   = document.querySelector("#newTask");
  const searchBox = document.querySelector("#search");
  const listEl    = document.querySelector("#taskList");
  const emptyEl   = document.querySelector("#empty");
  const counterEl = document.querySelector("#counter");

  // ---- The state: the single source of truth ----
  let tasks = load();
  let query = "";

  function load() {                                // bonus: read saved tasks, or use samples
    try {
      const saved = JSON.parse(localStorage.getItem("tasks"));
      if (Array.isArray(saved)) return saved;
    } catch (err) {
      console.warn("Saved tasks were unreadable - starting fresh");
    }
    return [
      { id: 1, title: "Submit DBMS assignment", done: true },
      { id: 2, title: "Read chapter 4 - Networks", done: false },
      { id: 3, title: "Push portfolio to GitHub", done: false },
    ];
  }

  function save() {                                // bonus: write the state after each change
    try {
      localStorage.setItem("tasks", JSON.stringify(tasks));
    } catch (err) {
      console.warn("Could not save:", err.message);
    }
  }

  // ---- render(): the only code that draws ----
  function render() {
    const visible = tasks.filter((t) => t.title.toLowerCase().includes(query));
    listEl.replaceChildren();
    visible.forEach((task) => {
      const li = document.createElement("li");
      li.dataset.id = task.id;
      li.classList.toggle("done", task.done);

      const label = document.createElement("label");
      const box = document.createElement("input");
      box.type = "checkbox";
      box.checked = task.done;
      const title = document.createElement("span");
      title.textContent = task.title;              // user text: textContent, never innerHTML
      label.append(box, " ", title);

      const del = document.createElement("button");
      del.type = "button";
      del.className = "delete";
      del.textContent = "Delete";
      del.setAttribute("aria-label", `Delete ${task.title}`);

      li.append(label, del);
      listEl.append(li);
    });

    if (tasks.length === 0) {
      emptyEl.textContent = "No tasks yet — add your first one above.";
    } else if (visible.length === 0) {
      emptyEl.textContent = `No tasks match "${query}".`;
    } else {
      emptyEl.textContent = "";
    }
    const doneCount = tasks.filter((t) => t.done).length;
    counterEl.textContent = `${doneCount} of ${tasks.length} done`;
    console.log(`render: ${visible.length} shown, ${doneCount} of ${tasks.length} done`);
  }

  // Which task does this element (inside a list item) belong to?
  function taskFor(element) {
    const id = Number(element.closest("li").dataset.id);
    return tasks.find((t) => t.id === id);
  }

  // ---- Events: change the state, save, render ----
  addForm.addEventListener("submit", (event) => {  // the button AND the Enter key
    event.preventDefault();
    const title = newTask.value.trim();
    if (title === "") return;                      // ignore empty text
    tasks.push({ id: Date.now(), title, done: false });
    newTask.value = "";
    save();
    render();
  });

  listEl.addEventListener("change", (event) => {   // delegation: any checkbox in the list
    if (event.target.type !== "checkbox") return;
    const task = taskFor(event.target);
    task.done = event.target.checked;
    save();
    render();
    listEl.querySelector(`li[data-id="${task.id}"] input`).focus();   // keep keyboard focus
  });

  listEl.addEventListener("click", (event) => {    // delegation: any Delete button
    const del = event.target.closest("button.delete");
    if (!del) return;
    const task = taskFor(del);
    tasks = tasks.filter((t) => t.id !== task.id);
    save();
    render();
    newTask.focus();                               // its button is gone: move focus somewhere useful
  });

  searchBox.addEventListener("input", () => {
    query = searchBox.value.trim().toLowerCase();
    render();
  });

  render();                                        // draw the starting state
</script>

On Run, load() finds nothing saved (JSON.parse(null) is null, which is not an array), returns the three sample tasks, and the Console shows render: 3 shown, 1 of 3 done. The page matches the lecture's mock-up, with the first task struck through. Follow this path and check each Console line:

The counter counts tasks, not visible: while you search for unit it still says 2 of 4 done, because searching hides tasks without finishing any. The two empty-state messages differ on purpose: "no tasks yet" invites the user to add one; "no tasks match" says the search is why the list looks empty.

The rest of the checklist: Date.now(), the current time in milliseconds, gives each new task a different id. The label wraps the checkbox and title, so clicking the text ticks the box. Each Delete button's aria-label names its task, so a screen reader says "Delete Push portfolio to GitHub", not four identical "Delete"s. And since render() replaces the elements, the code puts keyboard focus back on purpose after a tick or a delete.

71.10 Common misunderstandings

✗ "addEventListener("click", save()) attaches save to the button."
The brackets run save immediately, once, and hand the browser its return value, usually undefined.
✓ "Pass the function: addEventListener("click", save)."
For arguments, pass a new arrow function: () => save(task).
✗ "The handler should change the page; the data can catch up later."
Then the page and the data drift apart, and the next redraw undoes the change.
✓ "Event → change state → render()."
Only render() touches the page, and it always draws from the data.
✗ "After render() rebuilds the list, the old click listeners on the items still work."
The old elements are thrown away together with their listeners; the new ones have none.
✓ "One listener on the parent, which is never rebuilt."
Delegation with event.target.closest(...) works for every item, old or new.
✗ "innerHTML is fine for user text if the text is short."
One short <img onerror> tag is enough to run an attacker's script.
✓ "User and server data go in with textContent."
innerHTML is only for fixed markup you wrote yourself.
✗ "My JavaScript validation keeps bad data away from the server."
Anyone can switch it off or skip the form entirely.
✓ "Browser validation is for friendly feedback; the server checks again."
✗ "If the action worked, the user knows it worked."
Without a visible answer they press again, or assume it failed.
✓ "Every action gets feedback."
Disable and relabel while busy, confirm when done, offer undo after a delete.

Exam-style checks

Answer each one before opening it.

A live search must update when the user types, pastes or clears the box. Which event should it listen for?L1
  • A. click
  • B. change
  • C. input
  • D. submit

Answer: C. input fires on every change to the value. change (B) is the tempting one, but for a text box it fires only when the user leaves the box after editing — far too late for a live search.

What does the Console show when this page loads, and what happens when the button is clicked twice? function greet() { console.log("Hi!"); } btn.addEventListener("click", greet());L3

Answer: Hi! is printed once, on page load, and the two clicks print nothing. greet() ran while the listener was being set up, and its return value, undefined, was registered instead of a function. Fix: btn.addEventListener("click", greet);

document.querySelector("#myButton") returns null although the button exists in the HTML. The most likely cause is:L2
  • A. The script is in the head without defer, so it ran before the button was read
  • B. querySelector only works with class names
  • C. The button needs an onclick attribute first
  • D. Buttons cannot have ids

Answer: A. The script ran before the browser had reached the button. Move the script to the end of the body or add defer. B is false: # selects by id.

What does this print? const names = ["Asha", "Rahul", "Meera"]; console.log(names.filter((n) => n.toLowerCase().includes("ra")));L3

Answer: ["Rahul", "Meera"]. Lower-cased, rahul starts with "ra" and meera ends with it; asha has no "r". The order of the original array is kept.

After countEl.classList.toggle("negative", count < 0) runs with count equal to 3, the element:L2
  • A. Gains the class negative
  • B. Does not have the class negative, whether or not it had it before
  • C. Switches the class to the opposite of what it was
  • D. Throws an error because 3 is not a boolean

Answer: B. With a second argument, toggle adds the class when it is true and removes it when false; 3 < 0 is false. C describes toggle without the second argument.

A comment box shows visitors' comments. Why must it use textContent rather than innerHTML?L2
  • A. textContent is the only way to show text
  • B. innerHTML cannot show more than 100 characters
  • C. innerHTML would run any tags an attacker typed, such as an img with an onerror script
  • D. textContent makes the page load faster

Answer: C. innerHTML parses its text as HTML, so attacker-written markup becomes real elements and can run script — cross-site scripting (XSS). textContent shows the same characters harmlessly.

Pressing "Place order" takes three seconds to reach the server, and some users press it again. The best fix is to:L2
  • A. Show an alert telling users to press only once
  • B. Disable the button and show "Placing order..." until the reply arrives
  • C. Hide the button forever after the first press
  • D. Add a second Place order button

Answer: B. The disabled button stops a second order, and the loading text is the feedback that the first press worked. C stops a retry even if the order fails.

A task list is rebuilt by render() after every change. Why put one click listener on the <ul> instead of one on each Delete button?L2
  • A. Buttons inside a list cannot have listeners
  • B. A listener on the ul runs before the button is drawn
  • C. It makes the Delete buttons keyboard-accessible
  • D. The ul is never rebuilt, so its listener survives every redraw and covers buttons added later

Answer: D. This is event delegation: the click bubbles up from the button to the ul, and event.target.closest(...) finds which button it was. C is wrong: real buttons are keyboard-accessible either way.

Which line breaks the rule "keep the data as the source of truth"?L3
  • A. count++; render();
  • B. tasks = tasks.filter((t) => t.id !== id); render();
  • C. count = Number(countEl.textContent) + 1;
  • D. query = searchBox.value.trim().toLowerCase(); render();

Answer: C. It reads the state back out of the page. The moment the display changes (say to "Count: 3"), Number(...) gives NaN. A, B and D all change the data and then let render() draw it.

In the registration form, why does the submit handler use forEach to check every field instead of stopping at the first error?L2

Answer: So the user sees all the problems after one press and can fix them together. Stopping at the first error would show one message per attempt, and a form with three mistakes would need three failed submits to discover them.

Quick revision

Key takeaways

  1. An interactive interface answers the user inside the same page with feedback, responsiveness and state you can see.
  2. Browser JavaScript is event-driven: set up once, then wait. Each action runs the chain user action → event → handler → state change and render → new screen.
  3. A listener has three parts: selector, event type, callback. Pass the function (greet), never its call (greet()); put scripts at the end of the body or use defer.
  4. The pattern for every build: event → change state → render(). Only render() touches the page.
  5. Live search: input event, trim().toLowerCase(), filter with includes, redraw, and always an empty state.
  6. Form feedback: rules in one function, check every field on submit, message under each field, aria-invalid, re-check an invalid field as the user types. The server must check again.
  7. Busy actions: disable the button and show loading text; finish with a success message; follow a delete with undo.
  8. Habits: select once, textContent for user text, classes not styles, delegation for lists, no inline handlers, data as the source of truth.
