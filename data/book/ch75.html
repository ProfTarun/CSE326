GitHub Repository Management

The night before a deadline, yesterday's change has broken the page and your only backup is a file called index-final-2.html. Git ends that problem: it keeps every saved state of your project and lets you go back to any of them. GitHub keeps a copy online where your teacher, your teammates and future employers can see the work.

About 30 minutes · Course outcome CO6

Before you start — one-line reminders

  • A project is one folder: index.html at the top, css/, js/ and images/ inside, names lowercase with hyphens (Chapter 73).
  • The HTML links its files with relative paths such as css/styles.css (Chapter 73).
  • A server is a computer that stores files and answers requests over the Internet (Chapter 2).
  • Anything sent to a browser can be read by anyone, so secrets never belong in front-end code (Chapter 1).

By the end of this chapter you can

  • Explain version control, and tell Git (a tool) apart from GitHub (a website).
  • Name the four places work lives and the command that moves it between them.
  • Use init, status, add, commit, log and diff, and read their output.
  • Write clear commit messages.
  • Connect a project to GitHub with remote add and push -u; use pull and clone.
  • Write a useful README.md and a .gitignore that keeps dependencies, clutter and secrets out.
  • Create and merge a branch, settle a simple conflict and describe a pull request.

75.1 A time machine for your project

Open the folder of almost any first-year project and you will find something like this:

index.html
index-old.html
index-final.html
index-final-2.html
index-final-REALLY-final.html
project-backup-15-oct.zip

Each copy was made for a good reason ("let me keep the working version before I try something risky"), but a week later nobody knows which is the latest, what changed between them, or which one your partner has. And when tonight's change breaks the page, you cannot ask the folder to "show me how you looked at six o'clock yesterday."

Version control is the cure: a system that records every saved state of a project, each with a note about what changed, so you can look back at any of them and bring any of them back. The one almost every developer uses is Git. Learn its definition word for word:

Key idea. Git is a distributed version-control system: it tracks every change to your files as named snapshots, so you can review history, work in parallel and undo mistakes.

Each saved state is a commit: a snapshot of the whole project at one moment, with an id (a short code such as 7d3b5f0), a message you write (Add projects section), the author and the time.

The story of the broken theme

Asha has made three commits on her portfolio. The third added a dark theme, and it broke the layout. She has no backup copy, and she does not need one.

$ git log --oneline
e93a114 (HEAD -> main) New dark theme
7d3b5f0 Add projects section
a1c09e2 Initial portfolio

$ git restore --source=7d3b5f0 css/styles.css

The first command lists her history, newest at the top. The second brings back css/styles.css as it was in commit 7d3b5f0, when the layout worked. She saves the repaired state as a fourth commit, Restore working CSS. (You will type these yourself by section 75.6.)

Distributed means every copy — Asha's laptop, her partner's, GitHub — holds the complete history. If the Internet goes down Git keeps working; if a laptop is stolen, any other copy has every commit.

Why developers use it

  • History: who changed what, when, and why.
  • Undo: restore a file or revert a commit.
  • Experiment safely on a branch.
  • Collaborate without emailing zip files.

Git is a save button with a memory: each press keeps a snapshot of the whole folder with your note under it, and you can pull any old file out of any snapshot later.

75.2 Git and GitHub: a tool and a website

The names sound alike, and beginners (and exam questions) mix them up. They are different things.

GitGitHub
What it isA program: the version-control toolA website hosting Git repositories
Where it livesInstalled on your computerOn GitHub's servers, opened in a browser
Needs the Internet?No — works fully offlineYes
What it doesRecords commits, keeps history, manages branchesKeeps an online copy and adds pull requests, issues, code review and GitHub Pages
Commandsinit, add, commit, branch, logReached with git push, pull, clone, or its web pages

In one sentence: Git is the tool on your computer; GitHub is a website that hosts Git repositories and adds collaboration. You can use Git without GitHub, but GitHub always uses Git underneath. GitLab and Bitbucket do the same job.

Wrong on purpose. "GitHub is the version-control system I install on my laptop." No — you install Git; GitHub is a service you visit. An exam option that swaps them, or calls them the same, is wrong.

The words you will use every day

WordMeaning
Repository (repo)A project folder plus its full history, e.g. student-dashboard
CommitA saved snapshot with an id and a message: 7d3b5f0 Add projects section
BranchA separate line of work, e.g. feature/contact-form
RemoteA copy of the repository on a server, usually nicknamed origin
Pull requestA request on GitHub to merge a branch, with review and discussion
CloneA full copy of a repository, history included, downloaded to a computer
HEADGit's "you are here" marker: normally the newest commit of your current branch
Quick check: can you use Git on a laptop with no Internet connection?

Yes. Commits, history and branches all work offline. Only push, pull and clone, which talk to GitHub, need the Internet.

75.3 Setting up once

Three jobs, done once per computer: install Git, tell it your name, and make a GitHub account.

Install Git

On Windows, install Git for Windows from git-scm.com, accepting the suggested answers (choose main if asked for a default branch name). It brings Git, Git Bash (a command window) and the Git Credential Manager, which handles signing in to GitHub. On a Mac, git --version in Terminal offers to install it; on Linux, sudo apt install git.

Open a terminal

Git is used by typing commands into a terminal. In VS Code, open your project folder and choose Terminal → New Terminal (Ctrl+`); it opens inside the project folder, where Git commands must be typed. A line starting with $ is what you type (without the $); other lines are Git's reply.

$ git --version
git version 2.47.1.windows.1

Your number will differ. If you see 'git' is not recognized or command not found, Git is not installed, or the terminal was open while you installed it: close VS Code completely and reopen it.

Tell Git who you are

$ git config --global user.name "Asha Verma"
$ git config --global user.email "asha.verma@example.com"
$ git config --global init.defaultBranch main
$ git config --global --list
user.name=Asha Verma
user.email=asha.verma@example.com
init.defaultbranch=main

Every commit is stamped with this name and email, which are public on GitHub. --global means "for every project on this computer", so you do it once. Use your GitHub email (or the private no-reply address in GitHub's Settings → Emails) so commits link to your profile. The third line names every new project's first branch main, as GitHub does (older setups say master; section 75.7 renames it).

On a shared lab computer, git config --global user.name with no name prints the name Git is using, often the previous student's. Set your own before you commit, or set it without --global inside your repository, for that project only.

Make a GitHub account

Sign up at github.com (free). Your username appears in every address (github.com/USERNAME/student-dashboard, and in Chapter 76 USERNAME.github.io), so choose one fit for a CV, and turn on two-factor sign-in.

75.4 Three places your work lives

Get this picture right and every Git command becomes obvious.

  1. Working directory — the files you edit. Git watches them but saves nothing on its own.
  2. Staging area — a waiting list of changes chosen for the next commit (Git's manual also calls it the index).
  3. Local repository — the commits, kept in a hidden .git folder inside your project.
  4. Remote — a copy on a server, usually GitHub, nicknamed origin.

Why a waiting list? Say you fixed a typo in index.html and half-built a search feature in js/app.js. git add index.html stages only the typo fix, so you can commit Fix heading typo now and the search later. Each commit tells one clean story.

Always in this order: add chooses, commit saves on your computer, push uploads to GitHub. Until you commit, Git has saved nothing; until you push, GitHub knows nothing.

Picture this. A photographer at a family wedding. Guests wander round the hall all evening — your working directory. For each picture the photographer calls onto the stage only the people who belong in it — git add. Click: the moment is fixed, with a caption underneath — git commit. The print goes into the album at home (your local repository), and a copy is posted to the relatives' album in another city (git push).

Four states a file can be in

StateMeaningHow it gets theregit status lists it under
UntrackedNew; Git has never saved itYou create itUntracked files
ModifiedChanged since the last commit, not yet chosenYou edit and save itChanges not staged for commit
StagedOn the waiting list for the next commitgit addChanges to be committed

Quick check: you edit index.html and run git add index.html. Is the change on GitHub now?

No. git status shows Changes to be committed: modified: index.html: staged, not committed, not pushed. It reaches GitHub only after git commit and git push.

// A toy model of Git. Each file has a draft number: v1, then v2 after an edit...
const working = { "css/styles.css": 1, "index.html": 1 };
const staged = {};        // what "git add" has chosen for the next commit
let snapshot = {};        // every file as it was in the latest commit
const commits = [];       // oldest first: { id, message }
let pushed = 0;           // how many of those commits GitHub has
// Real Git calculates each id from the snapshot; this toy takes the next one.
const ids = ["3f2a9c1", "5a7c2e1", "9be1d40", "c41e8a2", "e07d3b9", "a62f915"];

function show(listId, lines) {
  const box = document.getElementById(listId);
  box.textContent = "";
  for (const line of lines.length ? lines : ["(empty)"]) {
    const p = document.createElement("p");
    p.textContent = line;
    box.appendChild(p);
  }
}

function render() {
  show("wdList", Object.keys(working).map(f => f + " v" + working[f]));
  show("stList", Object.keys(staged).map(f => f + " v" + staged[f]));
  show("repoList", commits.map(c => c.id + " " + c.message).reverse());
  show("ghList", commits.slice(0, pushed).map(c => c.id + " " + c.message).reverse());
}

function gitStatus() {
  const ready = [], changed = [], untracked = [];
  for (const file of Object.keys(working)) {
    const inCommit = snapshot[file];   // undefined if never committed
    const inStage = staged[file];      // undefined if not staged
    if (inStage !== undefined) {
      ready.push((inCommit === undefined ? "new file:   " : "modified:   ") + file);
    }
    const known = inStage !== undefined ? inStage : inCommit;
    if (known === undefined) untracked.push(file);
    else if (working[file] !== known) changed.push("modified:   " + file);
  }
  const out = ["$ git status", "On branch main"];
  if (commits.length === 0) out.push("No commits yet");
  if (pushed > 0) {
    const ahead = commits.length - pushed;
    out.push(ahead === 0 ? "Your branch is up to date with 'origin/main'."
      : "Your branch is ahead of 'origin/main' by " + ahead + (ahead === 1 ? " commit." : " commits."));
  }
  if (ready.length) out.push("Changes to be committed:", ...ready.map(t => "    " + t));
  if (changed.length) out.push("Changes not staged for commit:", ...changed.map(t => "    " + t));
  if (untracked.length) out.push("Untracked files:", ...untracked.map(t => "    " + t));
  if (ready.length + changed.length + untracked.length === 0) {
    out.push("nothing to commit, working tree clean");
  }
  console.log(out.join("\n"));
}

function gitAdd() {
  for (const file of Object.keys(working)) {
    if (working[file] !== snapshot[file]) staged[file] = working[file];
  }
  console.log("$ git add .");
  render();
}

function gitCommit() {
  const message = document.getElementById("msg").value.trim();
  console.log('$ git commit -m "' + message + '"');
  const files = Object.keys(staged);
  if (message === "") {
    console.log("Aborting commit due to empty commit message.");
    return;
  }
  if (files.length === 0) {
    console.log('nothing to commit (use "git add" to stage your changes first)');
    return;
  }
  const id = ids[commits.length] || Math.random().toString(16).slice(2, 9);
  const root = commits.length === 0 ? " (root-commit)" : "";
  commits.push({ id: id, message: message });
  snapshot = { ...snapshot, ...staged };
  for (const file of files) delete staged[file];
  const count = files.length === 1 ? "1 file changed" : files.length + " files changed";
  console.log("[main" + root + " " + id + "] " + message + "\n " + count);
  render();
}

function gitLog() {
  const out = ["$ git log --oneline"];
  if (commits.length === 0) {
    out.push("fatal: your current branch 'main' does not have any commits yet");
  }
  for (let i = commits.length - 1; i >= 0; i--) {     // newest first
    const labels = [];
    if (i === commits.length - 1) labels.push("HEAD -> main");
    if (i === pushed - 1) labels.push("origin/main");
    const tag = labels.length ? " (" + labels.join(", ") + ") " : " ";
    out.push(commits[i].id + tag + commits[i].message);
  }
  console.log(out.join("\n"));
}

function gitPush() {
  const out = ["$ git push"];
  if (commits.length === 0) {
    out.push("error: src refspec main does not match any");
  } else if (pushed === commits.length) {
    out.push("Everything up-to-date");
  } else {
    out.push("To https://github.com/asha-verma/student-dashboard.git");
    if (pushed === 0) out.push(" * [new branch]      main -> main");
    else out.push("   " + commits[pushed - 1].id + ".." + commits[commits.length - 1].id + "  main -> main");
    pushed = commits.length;
  }
  console.log(out.join("\n"));
  render();
}

document.querySelectorAll("[data-edit]").forEach(button => {

    console.log("(you edited " + file + " and saved it: it is now v" + working[file] + ")");
    render();
  });
});

75.5 Your first repository, command by command

Asha's Chapter 73 project, student-dashboard, holds index.html, css/styles.css and js/app.js. In a VS Code terminal, five commands give it a first commit.

1. git init — start tracking this folder

$ git init
Initialized empty Git repository in C:/Users/asha/Documents/student-dashboard/.git/

That created a hidden folder, .git. That folder is the repository: every commit is stored inside it. Run git init once per project, inside the project folder — never in your whole Documents folder.

2. git status — what is going on?

$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        css/
        index.html
        js/

nothing added to commit but untracked files present (use "git add" to track)

You are on the branch main, there are no commits yet, and three things are untracked: Git sees them but has never saved them (an untracked folder is shown once, as css/). git status changes nothing, so run it before and after every other command.

3. git add — choose what goes into the snapshot

$ git add .
$ git status
On branch main

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
        new file:   css/styles.css
        new file:   index.html
        new file:   js/app.js

The dot means "this folder and everything in it"; git add index.html stages one file. git add printed nothing: silence means success.

A warning, not an error. On Windows you may see warning: in the working copy of 'index.html', LF will be replaced by CRLF the next time Git touches it. Windows and Mac/Linux end lines with different invisible characters; your files are fine.

4. git commit -m — save the snapshot

$ git commit -m "Add page layout"
[main (root-commit) be8b983] Add page layout
 3 files changed, 14 insertions(+)
 create mode 100644 css/styles.css
 create mode 100644 index.html
 create mode 100644 js/app.js

main is the branch, and (root-commit) marks the very first commit. be8b983 is the commit's id, a hash; yours will differ, because it is calculated from the contents, your name and the time. create mode 100644 just means "ordinary file".

-m means "the message follows". Forget it and Git opens a text editor; if it is a black screen of ~ marks (Vim), press Esc, type :q! and Enter to cancel, then run the command again with -m.

5. git log --oneline — read the history

$ git log --oneline
be8b983 (HEAD -> main) Add page layout

$ git branch
* main

HEAD -> main means "you are here, on the branch main". git branch lists the branches; the star marks the one you are on.

Commit messages people can read

A history of update, fix, final2 tells you nothing; Add search box, Fix email check in contact form is a diary. Four rules:

  1. A command: Add, Fix, Remove, not Added. It should complete "If applied, this commit will ___."
  2. One commit, one idea: a bug fix and a new feature are two commits.
  3. Short: about 50 characters, capital first letter, no full stop. GitHub cuts first lines over 72 characters.
  4. Explaining why? A second -m adds a description: git commit -m "Fix email check" -m "Addresses with a + sign were rejected."

const vague = ["update", "updates", "changes", "stuff", "fix", "misc", "wip", "asdf", "final"];
const notCommands = ["added", "adding", "fixed", "fixing", "updated", "updating",
                     "changed", "changing", "removed", "removing", "created", "creating"];

function checkMessage(message) {
  const subject = message.trim();
  if (subject === "") return ["the message is empty"];
  const problems = [];
  const words = subject.split(/\s+/);
  if (vague.includes(subject.toLowerCase())) {
    problems.push("too vague: say WHAT changed");
  } else if (words.length < 2) {
    problems.push("too short: say what changed");
  }
  if (notCommands.includes(words[0].toLowerCase())) {
    problems.push('write it as a command: "Add", not "Added"');
  }
  if (subject[0] !== subject[0].toUpperCase()) problems.push("start with a capital letter");
  if (subject.endsWith(".")) problems.push("no full stop at the end");
  if (subject.length > 50) {
    problems.push("keep it to about 50 characters (this one has " + subject.length + ")");
  }
  return problems;
}

  li.textContent = `${verdict} "${message}"${why}`;

}

Exam tip. The best commit message names one specific change as a short command: Add search box to assignment list. update, changes or final are always wrong.

75.6 Looking back, and going back

Asha adds a search box to index.html and saves:

$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   index.html

no changes added to commit (use "git add" and/or "git commit -a")

git diff — exactly what changed?

$ git diff
diff --git a/index.html b/index.html
index 37368a2..cff73d3 100644
--- a/index.html
+++ b/index.html
@@ -7,6 +7,7 @@
 </head>
 <body>
   <h1>Student Dashboard</h1>
+  <input type="search" id="search" placeholder="Search assignments">
   <script src="js/app.js" defer></script>
 </body>
 </html>

The first four lines name the file (a/ old, b/ new). @@ -7,6 +7,7 @@ says where: "from line 7, six lines became seven". A line starting with + was added (green in a terminal), - was removed (red), and a space marks an unchanged neighbour shown for context. A changed line appears as a - line then a + line.

git diff is "spot the difference" done for you: plus added, minus removed. Read it before every commit.

Plain git diff shows unstaged changes; after git add, git diff --staged shows what will be committed.

$ git add index.html
$ git commit -m "Add search box"
[main 92ae75c] Add search box

$ git log --oneline

History is listed newest first. Plain git log adds the full 40-character id, author and date (+0530 is IST). A long log shows a screen at a time: Space for more, q to quit.

Going back

You want to…CommandWhat happens
Throw away edits you have not committedgit restore index.htmlThe file goes back to its last committed (or staged) version. The edits are gone for good.
Take a file off the waiting list, keeping your editgit restore --staged index.htmlThe change is unstaged; the file on disk is untouched.
Bring back one file from an older commitgit restore --source=7d3b5f0 css/styles.cssThe file becomes that old version; check it, then add and commit (Figure 75.1).
Undo a whole commitgit revert --no-edit e93a114Git makes a new commit, Revert "New dark theme", that does the exact opposite of the old one.

None of these rewrites history: restore changes files and revert adds a commit. Older tutorials write git checkout -- index.html for git restore index.html.

Two ways to lose work. Deleting the .git folder throws away every commit; git reset --hard throws away every uncommitted change to tracked files, with no undo.

// A tiny Markdown reader: # headings, - and 1. lists, [text](url) links, paragraphs.
function withLinks(tag, text) {
  const el = document.createElement(tag);
  // "See [demo](https://x.io) now" splits into ["See ", "demo", "https://x.io", " now"]
  const parts = text.split(/\[([^\]]+)\]\(([^)]+)\)/);
  parts.forEach((part, i) => {
    if (i % 3 === 0) {
      el.append(part);                         // ordinary text
    } else if (i % 3 === 1) {
      const a = document.createElement("a");   // the link text...
      a.textContent = part;
      a.href = parts[i + 1];                   // ...and the address after it
      el.append(a);
    }
  });
  return el;
}

function renderMarkdown(source) {
  const out = document.getElementById("preview");
  out.textContent = "";
  let list = null;
  for (const raw of source.split("\n")) {
    const line = raw.trim();
    if (line === "") { list = null; continue; }
    const bullet = line.match(/^(- |\d+\. )/);
    if (bullet) {
      const type = bullet[1] === "- " ? "UL" : "OL";
      if (!list || list.tagName !== type) {
        list = document.createElement(type);
        out.appendChild(list);
      }
      list.appendChild(withLinks("li", line.slice(bullet[1].length)));
      continue;
    }
    list = null;
    const hashes = line.match(/^(#{1,3}) /);
    if (hashes) {
      out.appendChild(withLinks("h" + hashes[1].length, line.slice(hashes[0].length)));
    } else {
      out.appendChild(withLinks("p", line));
    }
  }
}

.gitignore is a plain text file with exactly that name, in the project's top folder. Each line is a pattern; a new file that matches stays untracked: git status does not list it and git add . skips it. The file from the slides:

node_modules/The project's dependencies: thousands of files that npm install re-downloads from package.json
dist/Build output: can be regenerated, and would bury your real changes
.envSecrets (passwords, keys): pushed, they are no longer secret

The rules: a name ending in / means a folder of that name, anywhere; a plain name like .env matches exactly that name at any depth; * means "any characters" (*.log matches debug.log); # starts a comment. Create .gitignore before your first commit, because it does not affect files Git already tracks; for those, run git rm -r --cached node_modules (the files stay on disk) and commit.

// Keep only the real rules: drop blank lines and # comments.
function readRules(text) {
  return text.split("\n")
    .map(line => line.trim())
    .filter(line => line !== "" && !line.startsWith("#"));
}

// Does one rule match one name? Understands a single * such as "*.log".
function nameMatches(rule, name) {
  if (!rule.includes("*")) return rule === name;
  const [start, end] = rule.split("*");
  return name.length >= start.length + end.length &&
         name.startsWith(start) && name.endsWith(end);
}

// Returns the rule that ignores this path, or null if Git will track it.
function ignoredBy(path, rules) {
  const parts = path.split("/");          // "js/old/error.log" -> 3 parts
  const folders = parts.slice(0, -1);     // every part except the file name
  for (const rule of rules) {
    if (rule.endsWith("/")) {             // "dist/" means a FOLDER called dist
      const folder = rule.slice(0, -1);
      if (folders.some(f => nameMatches(folder, f))) return rule;
    } else if (parts.some(p => nameMatches(rule, p))) {
      return rule;                        // a plain name matches at any depth
    }
  }
  return null;
}

function check() {
  const rules = readRules(document.getElementById("rules").value);
  const list = document.getElementById("list");
  list.textContent = "";
  const rows = [];
  for (const file of files) {
    const rule = ignoredBy(file, rules);
    rows.push({ file: file, git: rule ? "ignored by " + rule : "tracked" });
    const li = document.createElement("li");

Quick check: the .gitignore contains the line .env. Will a file called .env.example be committed?

Yes. A plain name matches only that exact name. That is deliberate: .env.example is a template with the setting names and fake values, so teammates know what to put in their own .env.

Never commit a secret

A secret lets someone act as you or spend your money: passwords, tokens, private keys, and the API keys that maps, AI and payment services issue. Programs scan public repositories for leaked keys, often within minutes. Keep secrets in an ignored .env file and commit a harmless template:

# .env  - listed in .gitignore, stays on your computer
WEATHER_API_KEY=7f3a9c0e5b2d4f81a6c3e9d0b4f7a2c1

# .env.example  - committed, so others know which settings exist
WEATHER_API_KEY=your-key-here

One more catch: front-end code has no safe place for a secret key at all, because every file is sent to the visitor's browser (Chapter 1). Such keys belong on a server (Chapter 77).

Already committed a secret? Deleting the file in a new commit is not enough: the old commit still contains it. Treat the key as stolen: revoke or rotate it (cancel it and get a new one) at the service that issued it, immediately. Then add the file to .gitignore, run git rm --cached .env, and commit.

75.9 Branches and pull requests

In Chapter 76 the dashboard goes live from main. To try a contact form safely, Asha makes a branch, a separate line of work. If the form works she merges it in; if not, she deletes the branch.

$ git switch -c feature/contact-form
Switched to a new branch 'feature/contact-form'

$ git branch
* feature/contact-form
  main

git switch -c creates a branch and moves you onto it; the star has moved. Older tutorials write git checkout -b and git checkout main for git switch -c and git switch main. She commits the form, then switches back:

$ git add index.html
$ git commit -m "Add contact form"
[feature/contact-form 67bf32e] Add contact form
 1 file changed, 1 insertion(+)

$ git switch main
Switched to branch 'main'

Look at index.html now: the contact form has vanished. Nothing is lost — Git swapped the files to match the current branch. Commit before you switch: Git refuses if an uncommitted change would be overwritten, and otherwise carries it across.

Merging the branch in

You always merge into the branch you are on, so Asha is on main when she brings the form in:

$ git merge feature/contact-form
Updating 34a6310..67bf32e
Fast-forward
 index.html | 1 +
 1 file changed, 1 insertion(+)

$ git branch -d feature/contact-form
Deleted branch feature/contact-form (was 67bf32e).

This was a fast-forward: main had not moved since the branch began, so Git slid the label forward. When both lines have new commits, Git makes a merge commit joining them (Figure 75.3). Deleting a merged branch removes only its name.

A branch is a named bookmark that moves forward with each commit made on it. Merging means "bring that line of work into this one".

Quick check: git branch prints " feature/contact-form" and "* main". Which branch are you on, and where will your next commit go?

On main (the star marks it), so the next commit goes to main. Run git switch feature/contact-form first if you meant to work on the form.

Merge conflicts

Git merges changes to different lines by itself. If both branches changed the same line differently, it stops and asks. Here main made the heading CSE326 Dashboard and feature/title made it My Assignments:

$ git merge feature/title
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.

Git has written both versions into the file, between conflict markers:

<body>
<<<<<<< HEAD
  <h1>CSE326 Dashboard</h1>
=======
  <h1>My Assignments</h1>
>>>>>>> feature/title
  <input type="search" id="search" placeholder="Search assignments">

Between <<<<<<< HEAD and ======= is the version on your current branch (main); after ======= comes the incoming one. To resolve it:

  1. Edit the file to say what you want (one version, the other, or a mix) and delete the three marker lines. VS Code's Accept Current / Incoming / Both buttons do this for you.
  2. Save, check the page, then git add index.html and git commit -m "Merge feature/title, keep CSE326 heading".

git merge --abort undoes the whole attempt. A conflict is Git asking a human to decide, not a sign you broke anything.

Pull requests: merging with a review

On teams, people push the branch and open a pull request (PR) on GitHub — "please pull my branch into main" — a page where teammates read every changed line, comment, and merge with one button:

  1. git push -u origin feature/contact-form, then click Compare & pull request on the repository page.
  2. Check the direction (base: main ← compare: feature/contact-form), describe what changed and why, and click Create pull request.
  3. Reviewers read Files changed, comment, and approve or ask for changes; new commits on the branch join the PR automatically.
  4. Click Merge pull request, Confirm merge, Delete branch. On your laptop: git switch main, git pull, git branch -d feature/contact-form.

For someone else's project, where you cannot push, first fork it (your own GitHub copy) and open the PR from the fork.

75.10 The practical Git challenge

The twenty-minute task from your slides, on any small project of your own. The goal: a public repository with a sensible structure, a README that renders, and three meaningful commits.

75.11 Common misunderstandings

✗ "git add saves my work."
It only puts changes on the waiting list.
✓ "add chooses, commit saves, push uploads."
Until git commit, nothing is in the history.
✗ "I committed, so it's on GitHub."
A commit is stored only on your computer.
✓ "It's on GitHub after git push."
Ahead of 'origin/main' by 1 commit means you still need to push.
✗ "I deleted the file with my API key and committed, so the key is gone."
Every older commit still contains it.
✓ "A leaked key must be revoked and replaced at once."
Prevention is .env in .gitignore from day one.
✗ "A merge conflict means I broke something."
Nothing is broken or lost.
✓ "Git needs me to choose between two edits of the same line."
Edit, delete the markers, add, commit — or git merge --abort.

  • D. Downloads feature/contact-form from GitHub

Answer: B. -c means create (old spelling: git checkout -b). Deleting is git branch -d; merging is git merge.

After git merge feature/title the file contains:
<<<<<<< HEAD
<h1>CSE326 Dashboard</h1>
=======
<h1>My Assignments</h1>
>>>>>>> feature/title
What do the two parts mean, and how do you finish the merge?L3

Answer: a merge conflict. The HEAD part is the version on your current branch; the part after ======= is the incoming one from feature/title. Edit to the heading you want, delete the three marker lines, then git add index.html and git commit.

Your first git push -u origin main is rejected with (fetch first). You had ticked "Add a README" on GitHub. Cause and fix?L3
  • A. Your password is wrong; type it again
  • B. The branch must be called master; rename it
  • C. GitHub has a README commit your computer lacks; run git pull --rebase origin main, then push
  • D. The repository is private; make it public

Answer: C. Git refuses to overwrite GitHub's commit; --rebase puts your commits on top of it. A wrong password gives a sign-in error, not this rejection.

Which command makes a full copy of a GitHub repository, with its whole history, on a computer that has never had it?L1
  • A. git pull
  • B. git init
  • C. git push
  • D. git clone

Answer: D. git pull only updates a copy you already have; git init starts an empty repository.

Quick revision

Key takeaways

  1. Git is a distributed version-control system: every copy holds the full history of commits (id, message, author, time).
  2. Git is an offline tool on your computer; GitHub is a website hosting Git repositories, with pull requests, issues and Pages.
  3. Working directory → (add) staging area → (commit) local repository → (push) remote; pull brings commits down.
  4. Set user.name and user.email once; run git status constantly; read git diff before committing.
  5. Commit messages are short commands about one change: Add search box, not update.
  6. To publish: create an empty GitHub repository, then remote add origin URL and push -u origin main. Never put a password or key in a file.
  7. README.md is the front page; .gitignore keeps out node_modules/, build output, .env and OS clutter. A leaked secret must be revoked.
  8. Branches let you experiment safely; merge them back, settle conflicts by editing the markers, and use pull requests to review.
