Client-Server Architecture

Every web page you have ever seen arrived through the same four-step conversation. This chapter slows that conversation down so you can see each part: the client that asks, the server that answers, the URL that names what is wanted, the HTTP request and response that carry it, and the status codes that report how it went.

About 19 minutes · Course outcome CO1 · Builds on Chapter 1

By the end of this chapter you can

  • Describe the roles of client and server and the request–response cycle in order.
  • Split any URL into protocol, domain, path and query string.
  • Read an HTTP request and response and name their parts.
  • Interpret status codes by their first digit (2xx, 3xx, 4xx, 5xx).
  • Explain ports 80 and 443, DNS, HTTPS/TLS, and what "HTTP is stateless" means.

2.1 Two roles: client and server

The Web is built on a pattern called the client–server model. A client is a program that asks for something; a server is a program that waits for requests and answers them. On the Web the client is almost always a browser (or a mobile app doing the same job), and the server is a program running in a data centre that stores the site's files and data, runs its logic and sends back responses.

The food-delivery app on your phone is the cleanest everyday example. Your phone is the client: it shows menus and takes your taps. The company's server holds the restaurant list, prices and your order history, works out delivery times, and replies to whatever the app asks. The app never has the whole database; it asks for one restaurant's menu at a time, and the server answers each request.

Keep the two jobs distinct, because exam questions probe exactly that boundary:

  • The client (the browser) renders HTML into pixels for the user and sends the HTTP request. It never stores the site's database.
  • The server stores data, runs logic and responds to requests. It does not type the URL, does not render pixels for the user, and does not encrypt your keyboard.

2.2 The request–response cycle

Picture yourself clicking "View Result" on the university portal. Here is everything that happens, in order. The order is the whole point: the browser cannot receive a response before it has sent a request, and the server cannot process a request before it arrives.

  1. Click. You type a URL or click a link. The browser reads the domain name from it.
  2. DNS lookup. Computers find each other by IP address, not by name, so the browser asks the Domain Name System to translate portal.lpu.in into an address such as 203.0.113.7. Think of DNS as the phone book of the Internet.
  3. Request. The browser opens a connection to that address (on port 443 for HTTPS, port 80 for plain HTTP) and sends an HTTP request for the path it wants.
  4. Processing. The server receives the request. For a plain file it just reads it from disk; for a dynamic page it runs code, checks who you are, queries the database and builds the HTML.
  5. Response. The server sends back an HTTP response: a status code and the content, typically HTML for a page or JSON for data.
  6. Render. The browser parses the HTML, requests the CSS, images and scripts it refers to (each one its own request–response), and draws the page.
Why one page means many requests. The HTML arrives first. Every <link>, <img>, <script> and <video> in it triggers a further request. A typical page today makes 50–100 requests. Open DevTools (F12) and the Network tab on any site and watch them.

2.3 Anatomy of a URL

A URL (Uniform Resource Locator) is the address the browser sends its request to. Learn to split one into parts on sight, because questions ask "which part is the path?" or "what is ?id=257 called?".

Protocol (scheme): https
How the browser should fetch the resource. http and https are the ones you will use; mailto and tel (Chapter 8) are others. In https://www.example.com/index.html the part https is the protocol.
Domain (host): portal.lpu.in
Which server to ask. DNS converts it to an IP address. In https://portal.lpu.in/results the domain is portal.lpu.in, not in (that is only the top-level domain) and not /results.
Path: /courses/web.html
Which resource on that server, written like a folder path. In https://portal.lpu.in/courses/web.html?id=257 the path is /courses/web.html.
Query string: ?id=257
Extra parameters sent to the server as name=value pairs, separated by &: ?id=257&year=2026. In https://shop.example.com/items?id=257 the part ?id=257 is the query string. Form submissions with method="get" put their fields here (Chapter 16).
Port (optional): :8080
A number after the domain choosing which "door" on the server to knock on. It is usually omitted because every protocol has a default: HTTP uses port 80 and HTTPS uses port 443. (Ports 21 and 25 belong to FTP and email, not the Web.)
Fragment (optional): #contact
A position inside the page, matched to an element's id. It is handled by the browser and never sent to the server (Chapter 8).

Absolute and relative URLs

An absolute URL contains the protocol and the domain (https://portal.lpu.in/courses/web.html) and therefore means the same thing wherever it is written. A relative URL leaves those out (web.html, ../index.html) and is resolved against the current page's address: the browser fills in the missing parts from the page you are on. Relative URLs are shorter and let a whole site be moved to another domain without editing every link; Chapter 8 shows the rules for ../ and /.

2.4 Inside an HTTP request and response

HTTP messages are plain text. That is worth seeing once, because it demystifies the whole thing. When the browser asks for the results page it sends something like this:

GET /results HTTP/1.1          ← request line: method, path, version
Host: portal.lpu.in            ← headers: name: value, one per line
Accept: text/html
Cookie: session=8f3a9c
                               ← blank line ends the headers
(no body for a GET request)

And the server replies:

HTTP/1.1 200 OK                ← status line: version, status code, reason
Content-Type: text/html; charset=UTF-8
Content-Length: 5120
                               ← blank line
<!DOCTYPE html>                ← body: the HTML text
<html lang="en"> ...

Three ideas to take from this:

  • The method says what kind of request it is. GET asks for a resource and carries its parameters in the URL's query string. POST sends data (a form, an upload) in the request body. Chapter 16 explains when a form should use each.
  • Headers carry information about the message: what type of content is inside, how long it is, which cookies the browser holds, what language the user prefers.
  • The body of a response is the content itself: HTML for a page, or JSON, an image, a PDF.

HTTP is stateless

Each request is handled on its own; the server does not remember you between requests. That is what "HTTP is stateless" means. It does not mean pages cannot store data or that only one user can connect. Because real sites need to remember that you logged in, they work around statelessness with cookies (small labels the browser sends back with every request, like the Cookie: session=8f3a9c line above) and tokens.

2.5 Status codes: how the server says how it went

Every response starts with a three-digit status code. You only need the meaning of the first digit, plus a few famous individuals.

RangeMeaningFamous examples
1xxInformational: still working on it100 Continue
2xxSuccess: here is what you asked for200 OK, 201 Created
3xxRedirection: it is somewhere else, go there301 Moved Permanently, 302 Found, 304 Not Modified (use your cached copy)
4xxClient error: your request was bad or not allowed400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found
5xxServer error: your request was fine, the server failed500 Internal Server Error, 503 Service Unavailable

So a status in the 400–499 range indicates a client error, such as a mistyped address (404) or a request without permission (401, 403); it is not a success, not a redirection and not a failure inside the server. The 500s are the server's fault.

2.6 HTTPS: the same conversation, in a sealed envelope

Plain HTTP travels as readable text, so anyone operating a router on the path (a café Wi-Fi, an ISP) could read your password or change the page on its way to you. HTTPS wraps the identical HTTP messages in TLS (Transport Layer Security), which encrypts them and also proves, through a certificate, that the server really is portal.lpu.in and not an impostor. The padlock in the address bar means TLS is in use. HTTPS does not make files smaller, does not adjust layouts for mobiles and has nothing to do with server-side scripting; its one job is encryption and authentication of the data in transit. It uses port 443 by default instead of HTTP's port 80.

Exam tip. Memorise the pairs: HTTP = port 80, HTTPS = port 443, HTTPS = HTTP + TLS encryption. Distractors like port 21 (FTP) and port 25 (SMTP email) are real ports for other services.

2.7 Worked example: reading a portal URL

Take https://portal.lpu.in/results/view.html?reg=12345&sem=3#marks and label it:

PartValueJob
ProtocolhttpsFetch over HTTP with TLS encryption, port 443
Domainportal.lpu.inWhich server; DNS resolves it to an IP address
Path/results/view.htmlWhich resource on the server
Query string?reg=12345&sem=3Two parameters for the server: reg and sem
Fragment#marksScroll to the element with id="marks"; not sent to the server

Now the round trip in one sentence: the browser (client) resolves the domain, sends a GET request for the path with the query string to port 443 over TLS, the server checks the registration number, reads the marks from its database, and responds with 200 OK and an HTML page, which the browser renders and scrolls to the marks section. If you can say that, you understand client–server architecture.

Exam-style checks

In a client–server exchange, which component sends the HTTP request?L1
  • A. The web server
  • B. The browser acting as the client
  • C. The DNS root server
  • D. The database engine

Answer: B. The client asks; the server answers. DNS only translates names and the database only answers the server.

In the client–server model, the server's role is to:L2
  • A. Render HTML into pixels for the user
  • B. Type the URL into the address bar
  • C. Store data, run logic and respond to requests
  • D. Encrypt the user's keyboard input

Answer: C. Rendering (A) is the browser's job; B is the user's; D is nonsense.

After a server processes a request, what does it typically send back?L2
  • A. The user's keystrokes
  • B. A copy of the browser's cache
  • C. A newly registered domain name
  • D. A response containing HTML or JSON

Answer: D. The response body is the content: HTML for a page, JSON for data.

In the URL https://portal.lpu.in/courses/web.html?id=257, which part is the path?L2
  • A. https://
  • B. portal.lpu.in
  • C. ?id=257
  • D. /courses/web.html

Answer: D. Protocol, then domain, then path, then query string.

In https://shop.example.com/items?id=257, the part ?id=257 is called the:L2
  • A. Protocol
  • B. Query string
  • C. Path
  • D. Domain

Answer: B. Everything from the ? onward is the query string: name=value parameters for the server.

In https://www.example.com/index.html, the part https is the:L1

Answer: the protocol (scheme). It tells the browser how to fetch the resource.

In https://portal.lpu.in/results, which part is the domain?L1
  • A. portal.lpu.in
  • B. https
  • C. /results
  • D. in

Answer: A. The full host name is the domain. in alone is only the top-level domain; /results is the path.

What distinguishes an absolute URL from a relative URL?L2
  • A. An absolute URL is always shorter
  • B. An absolute URL includes the protocol and domain; a relative URL is resolved against the current page
  • C. A relative URL can only point to images
  • D. An absolute URL may not contain a query string

Answer: B. Absolute URLs are self-contained; relative ones borrow the missing parts from the page they appear on.

HTTP is best described as:L1
  • A. The physical cabling that carries Internet traffic
  • B. A language for querying databases
  • C. A markup language for structuring web pages
  • D. The protocol used to exchange web requests and responses

Answer: D. HTTP is the set of rules for requests and responses. Cabling is infrastructure, SQL queries databases, HTML is the markup language.

The statement "HTTP is stateless" means:L2
  • A. Pages cannot store data
  • B. The server does not remember you between requests
  • C. HTTP cannot send images
  • D. Only one user can connect at a time

Answer: B. Each request stands alone; cookies and tokens exist to work around this.

An HTTP status code in the 400–499 range indicates:L2
  • A. A client error, such as a bad or unauthorised request
  • B. A successful response
  • C. A redirection to another resource
  • D. A failure inside the server

Answer: A. 2xx is success, 3xx redirection, 4xx client error, 5xx server error.

Which port number does unencrypted HTTP use by default?L2
  • A. 25
  • B. 443
  • C. 21
  • D. 80

Answer: D. HTTP is port 80; HTTPS is 443; 21 is FTP; 25 is SMTP email.

A student says the browser is the server because it "serves the page to my eyes". What is wrong?L3

Answer: The roles are defined by who asks and who answers on the network, not by who shows pixels. The browser requests the page, so it is the client; the program that stores the page and responds is the server. Rendering to the screen is part of the client's job.

Quick revision

Key takeaways

  1. Client asks, server answers. The browser is the client; the server stores data, runs logic and responds; the database sits behind the server.
  2. Cycle: click, DNS lookup, request, server processes, response, render. Every image, stylesheet and script is a further request.
  3. URL = protocol :// domain / path ? query string, plus optional port and #fragment.
  4. HTTP messages are text: a request line or status line, headers, a blank line, then the body. GET carries parameters in the URL; POST carries them in the body.
  5. HTTP is stateless: the server does not remember you between requests, so cookies do the remembering.
  6. Status codes by first digit: 2 success, 3 redirect, 4 client error (404 Not Found), 5 server error.
  7. HTTPS = HTTP + TLS encryption and authentication; port 443. Plain HTTP is port 80.
