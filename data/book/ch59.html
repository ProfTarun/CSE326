Unit 5 · Chapter 59 · JavaScript Accessibility Practices

JavaScript Accessibility Practices

Good HTML is already mostly accessible. Then JavaScript makes a box clickable, changes a number, opens a panel — and each of those can quietly shut out a keyboard or screen-reader user while everything looks perfect with a mouse. This chapter gives you the handful of habits that let your scripts add behaviour without taking anybody's access away.

About 32 minutes · Course outcome CO5

Before you start — one-line reminders

  • Native controls such as <button> work with the keyboard for free; role, aria-label, tabindex="0" and tabindex="-1"; the first rule of ARIA is native first (Chapter 15).
  • WCAG's four principles, POUR, and the 4.5:1 contrast rule for normal text (Chapter 20).
  • addEventListener("click", fn) and "keydown" run code when something happens; event.key names the key that was pressed (Chapter 57).
  • textContent, setAttribute and getAttribute read and change an element from JavaScript (Chapter 56).

By the end of this chapter you can

  • Name the ways a script can lock out keyboard and screen-reader users.
  • Choose the native element for a job, and when there is no choice, turn a div into a working button.
  • Move focus with focus() when something opens, closes, shows an error or disappears.
  • Announce changes with aria-live="polite", role="status" and role="alert".
  • Keep aria-expanded, aria-pressed and aria-invalid true to what the screen shows.
  • Hide content with the right tool: hidden, display: none, a visually-hidden class or aria-hidden.
  • Respect prefers-reduced-motion from JavaScript, and test a page with the keyboard alone.

59.1 What a script can break

Web accessibility means designing websites so that people with different abilities can perceive, understand, navigate and interact with them. That is the lecture's definition, and Chapter 15 started from the same place. It benefits keyboard users, screen-reader users and people with visual impairments — and also people with temporary or situational limitations: a student with a fractured wrist, someone reading a phone in bright sunlight, a parent holding a baby in one arm and the phone in the other.

So far HTML has done most of the work: a <button> can be reached with the keyboard, a <label> names its field. JavaScript changes the page after it has loaded, and that is where the trouble starts. People who cannot use a mouse or see the screen reach the page through assistive technology, and a script can leave that technology knowing nothing about what just happened.

The script…A mouse user seesA keyboard or screen-reader user gets
makes a div clickableA working buttonNothing: Tab skips it, Enter does nothing, it is read as plain text
changes a message or a numberThe new textSilence: the screen reader is busy elsewhere and is never told
opens, closes or removes part of the pageThe panel appearing or goingTheir place lost: focus left behind, or dropped to the top
animates or slides contentA lively pageFor some people, dizziness or nausea

The mouse user never sees a problem, which is why these bugs survive: the developer tests with a mouse, everything works, and the page ships. Each section of this chapter fixes one row.

Key idea. Your script must tell assistive technology everything it shows the eyes: what a control is, what state it is in, what just changed, and where the user is now.

59.2 Native elements first

A real <button> comes with a contract that the browser keeps for you, on every device, at no cost:

  • It sits in the Tab order and shows a focus ring when it is reached.
  • Enter and Space press it. The browser turns the key press into a click event, so one click listener serves mouse, keyboard and voice control alike.
  • It is announced as "button", with its text as its name.
  • It can be disabled, and inside a form it submits (write type="button" when it should not).

How does a screen reader know any of that? Alongside the DOM, the browser builds a second, simpler tree called the accessibility tree. For every element it records its name (what it is called), its role (what kind of thing it is) and its state (pressed, expanded, invalid, checked). Screen readers read that tree, never the pixels.

A screen reader cannot see colours, shapes or positions. It knows only what the browser writes in the accessibility tree: name, role, state. A real button writes all three for you. A div writes only its text, however many click listeners you attach to it.

So before writing any code, pick the element that already does the job:

The jobUseNot
Do something on this page: save, open, delete<button type="button"><div> or <span> with a click listener
Go to another page or place<a href="...">A button that changes location; an <a> with no href (it is not even focusable)
Type text<input> with a <label>A div that listens for key presses
Yes or no; one of severalCheckbox; radio buttons or <select>Boxes that change colour when clicked
Show or hide a block<details>, or a button with aria-expanded (59.6)A clickable heading
A dialog box<dialog> (59.4)A positioned div, unless you manage focus yourself

A rule that settles most arguments: links go, buttons do. The lecture's list also names <nav> and <main>: these landmarks (Chapter 15) let a screen-reader user jump straight to the menu or the content, so keep them when a script redraws the page. And when your script builds elements (Chapter 58), the same rules apply: createElement("button"), not a div; an alt on every informative image it creates; a label for every input.

59.3 When you must build a custom control

Sometimes you inherit a page full of clickable divs, or a design no native element can produce. Chapter 15's flowchart gave the recipe; this is its JavaScript half. A div that is to behave as a button needs four things, and leaving out any one breaks it for somebody:

  1. role="button", so it is announced as a button.
  2. An accessible name: its own text, or aria-label if it shows only an icon.
  3. tabindex="0", so Tab can reach it.
  4. A keydown listener that runs the action for Enter and Space, because the browser turns key presses into clicks only for native controls such as a real button.
<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  .pay { display: inline-block; background: #0B2545; color: #fff; border: 0;
         padding: 10px 16px; margin: 0 8px 10px 0; border-radius: 8px;
         font: inherit; font-weight: 700; cursor: pointer; }
  .pay:focus-visible { outline: 3px solid #E07B1E; outline-offset: 3px; }
  #log { background: #F1F5F9; border-radius: 8px; padding: 8px 12px; }
</style>
<div class="pay" id="fake">Pay (plain div)</div>
<div class="pay" id="fixed" role="button" tabindex="0">Pay (repaired div)</div>
<button class="pay" id="real" type="button">Pay (button)</button>
<p id="log">Nothing paid yet.</p>

<script>
  const log = document.getElementById("log");

  function pay(who, how) {
    log.textContent = `${who} worked (${how})`;
    console.log(`${who} worked (${how})`);
  }

  // 1. The plain div: a click listener and nothing else
  document.getElementById("fake").addEventListener("click", () => pay("Plain div", "click"));

  // 2. The repaired div: role and tabindex are in the HTML; the keys are here
  const fixed = document.getElementById("fixed");
  fixed.addEventListener("click", () => pay("Repaired div", "click"));
  fixed.addEventListener("keydown", (event) => {
    if (event.key === "Enter" || event.key === " ") {
      event.preventDefault();               // stop Space from scrolling the page
      pay("Repaired div", `key "${event.key}"`);
    }
  });

  // 3. The real button: one line, and the keys come free
  document.getElementById("real").addEventListener("click", () => pay("Button", "click"));
</script>

Click once inside the preview so the keys go to it, then press Tab. Focus lands on the repaired div, then the real button, and never on the plain div. Press Enter on the repaired div: Repaired div worked (key "Enter"). Press Space: Repaired div worked (key " ") — the space bar's key value is a single space, " ", not the word "Space". On the real button both keys print Button worked (click): the browser turned your key press into a click.

event.preventDefault() matters too: Space normally scrolls the page, so the listener cancels that default, just as Chapter 57 cancelled a form's submit.

Now count the cost. The repaired div needed two attributes and a seven-line listener, and it still ignores disabled and cannot submit a form. The real button needed one line. So use a button, and keep this recipe for when you truly cannot (Chapter 77's best-practice checklist says the same).

Exam tip. "Which makes a div work as an accessible button?" The complete answer has all of role="button", tabindex="0" and Enter/Space key handling. An option with only one of them is the trap: role alone changes what is announced, never what the element does.
Quick check: your keydown listener tests event.key === "Space". What happens when the user presses the space bar?

Nothing runs, because event.key for the space bar is " ", a single space. Worse, the page scrolls, because preventDefault() is never reached. Test event.key === " ".

59.4 Managing focus

At any moment at most one element on the page has focus: the element that receives the next key press. Keyboard users move focus with Tab; screen-reader users hear whatever it lands on. JavaScript can read it with document.activeElement (which gives the <body> when nothing is focused) and move it with element.focus().

Normally the user moves focus. Your script must move it whenever the script itself changes the page around the user:

When your script…Move focus toBecause otherwise
opens a panel or dialogInside it: its heading or first fieldThe user is still on the opener and never learns it opened
closes itBack to the control that opened itFocus falls to the page body; the user's place is lost
shows an errorThe wrong field (Chapter 60 does this for whole forms)The user hears nothing about what to fix, or where
deletes, hides or disables the focused elementThe next sensible elementSuch an element cannot hold focus, so focus is thrown away

Whenever your script makes something appear, move focus to it. Whenever it makes the focused thing disappear, move focus somewhere sensible — usually back where the user came from. The user should never have to hunt for their place.

Two details make this work. First, focus() only works on elements that can take focus: links with an href, buttons, form controls and anything with a tabindex. On a plain <h2> it silently does nothing. To focus a heading or panel from a script without adding it to the Tab order, give it tabindex="-1" (Chapter 15). Second, if your script leads focus into something, it must also let the user out: Escape should close it. A place the keyboard can enter but never leave is a keyboard trap, and it fails WCAG.

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  #panel { max-width: 360px; margin-top: 12px; padding: 10px 14px;
           border: 2px solid #0B2545; border-radius: 10px; }
  #panel h2 { margin: 0 0 6px; font-size: 18px; }
  button, input { font: inherit; padding: 6px 10px; }
</style>
<button id="open" type="button">Exam help</button>

<div id="panel" role="dialog" aria-labelledby="help-title" hidden>
  <h2 id="help-title" tabindex="-1">Exam help</h2>
  <p>The MTT is on 14 March at 10:00 IST in Block 34. Bring your ID card.</p>
  <label for="q">Your question</label>
  <input id="q" type="text">
  <button id="close" type="button">Close</button>
</div>

<script>
  const openBtn = document.getElementById("open");
  const panel = document.getElementById("panel");
  const title = document.getElementById("help-title");

  function report(step) {
    console.log(step, "- focus is on:", document.activeElement);
  }

  function openPanel() {
    panel.hidden = false;
    title.focus();               // 1. move focus INTO what just opened
    report("Opened");
  }

  function closePanel() {
    panel.hidden = true;
    openBtn.focus();             // 2. give focus BACK to the opener
    report("Closed");
  }

  openBtn.addEventListener("click", openPanel);
  document.getElementById("close").addEventListener("click", closePanel);
  panel.addEventListener("keydown", (event) => {
    if (event.key === "Escape") closePanel();      // a way out, always
  });
</script>

Press Exam help, with the mouse or with Tab and Enter. The Console prints Opened - focus is on: <h2 id="help-title">: focus sits on the heading, so a screen reader announces "Exam help, dialog" (from role="dialog" and aria-labelledby) and reads on. Tab to the field and Close, then press Escape: Closed - focus is on: <button id="open">. The user is back where they began.

Without openBtn.focus(), closing would hide the Close button while it had focus. Focus would drop to the page body and a screen reader would lose its place.

For a true modal dialog — one that blocks the page behind it — use the native <dialog> and open it with showModal(). The browser moves focus in, closes it on Escape, makes the page behind unreachable and, in current browsers, returns focus to the opener on close. Native first, again.

<button id="open" type="button">Exam help</button>
<dialog id="help" aria-labelledby="help-title">
  <h2 id="help-title">Exam help</h2>
  <button id="close" type="button">Close</button>
</dialog>
<script>
  const help = document.getElementById("help");
  document.getElementById("open").addEventListener("click", () => help.showModal());
  document.getElementById("close").addEventListener("click", () => help.close());
</script>

One more habit from the lecture's list: provide visible focus indicators. The focus ring is the keyboard user's cursor; never remove it with outline: none without a replacement such as :focus-visible (Chapter 32).

59.5 Announcing changes: live regions

A screen reader reads what has focus, or what the user asks it to read. When your script changes text somewhere else — a count, a "Saved" message, search results — nothing tells the user. On screen the change is obvious; in the user's ears it never happened.

Picture this. At Ludhiana Junction the departure board flips to show the Shatabdi on platform 3. Sighted passengers glance up and walk; a blind passenger beside them learns nothing — until the announcer speaks. A routine announcement waits until the current one has finished; an emergency announcement cuts in mid-sentence. And the loudspeaker has to be fitted before the train arrives: nobody can announce through a speaker that is still being installed.

The page's loudspeaker is a live region: an element marked so that screen readers read out its new text automatically, wherever the focus is.

MarkupAnnouncesUse it for
aria-live="polite"When the screen reader finishes what it is sayingCounts, "Saved", "12 results found"
role="status"The same as polite; the role also says "this is a status message"Status and result messages (Chapter 70 uses it after a failed fetch)
role="alert"At once, interrupting whatever is being readOnly urgent messages: "Payment failed", "Session ends in 1 minute"

Two rules make live regions reliable. The region must already be in the page before its text changes: put it in the HTML, empty or with its starting text, and afterwards change only its textContent. A region created a moment before its message is often missed — the speaker still being installed. And write whole messages: the region is read without the page around it, so "Seats booked: 3" says something; "3" says almost nothing.

Mark a message area as live once, in the HTML. After that, every time your script changes its text, the screen reader reads the new text aloud. Polite waits its turn; alert interrupts — so use alert rarely, the way a station uses its emergency announcements.

Here is the lecture's interactive counter from Chapter 57, made to be heard as well as seen:

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  .row { display: flex; gap: 8px; align-items: center; }
  .sym { font-size: 22px; width: 44px; height: 44px; }
  #status { font-size: 22px; font-weight: 800; color: #0B2545; margin: 0 6px; }
  #msg { color: #B42318; font-weight: 700; min-height: 1.4em; }
</style>
<h3>CSE326 lab: book a seat</h3>
<div class="row">
  <button class="sym" id="minus" type="button" aria-label="Cancel a seat">&minus;</button>
  <p id="status" aria-live="polite">Seats booked: 0</p>
  <button class="sym" id="plus" type="button" aria-label="Book a seat">+</button>
  <button id="reset" type="button">Reset</button>
</div>
<p id="msg" role="alert"></p>

<script>
  const MAX = 5;
  let count = 0;
  const statusBox = document.getElementById("status");
  const msg = document.getElementById("msg");

  function update() {
    statusBox.textContent = `Seats booked: ${count}`;   // polite: read when the reader pauses
    msg.textContent = "";                               // clear any old warning
    console.log("Screen reader would say (polite):", statusBox.textContent);
  }

  function warn(text) {
    msg.textContent = text;                             // alert: read at once
    console.log("Screen reader would say (alert):", text);
  }

  document.getElementById("plus").addEventListener("click", () => {
    if (count === MAX) { warn(`All ${MAX} seats are booked.`); return; }
    count++;
    update();
  });
  document.getElementById("minus").addEventListener("click", () => {
    if (count === 0) { warn("There are no seats to cancel."); return; }
    count--;
    update();
  });
  document.getElementById("reset").addEventListener("click", () => {
    count = 0;
    update();
  });
</script>

Nothing is logged at first: a live region announces changes, not its starting text. Press + and the Console shows Screen reader would say (polite): Seats booked: 1, then 2, 3, 4, 5. A sixth press gives Screen reader would say (alert): All 5 seats are booked. Press −: Seats booked: 4, and the warning is cleared. (The Console stands in for the screen reader you cannot hear in a preview frame.)

Two smaller choices are worth copying. The symbol buttons have aria-labels, because "plus" and "minus" say nothing about seats. And at the limit the counter does not disable the + button: disabling the focused button throws focus away (59.4). A message keeps the user in place and says why.

Quick check: under a search box, "12 results" updates as the user types. Polite or alert?

Polite (aria-live="polite" or role="status"). The count is useful but not urgent. An alert on every key press would keep interrupting the user's own typing.

59.6 Keeping ARIA states true

Chapter 15 used ARIA to name and describe things. Some ARIA attributes describe a state that changes while the page is used. Only your script knows when it changes, so your script must update the attribute every time. A stale state is worse than none: it tells the user something false.

AttributeGoes onA screen reader says, roughly
aria-expanded="true" / "false"The button that shows and hides a panel, not the panel"Syllabus, button, collapsed"
aria-pressed="true" / "false"A toggle button that stays on or off"Mute alerts, toggle button, not pressed"
aria-invalid="true"A form field whose value is wrong"Roll number, edit, invalid entry"
aria-describedby="id"The same field, pointing at the error text"… Error: a roll number has exactly 8 digits"

Three habits keep states honest:

  1. ARIA values are text. getAttribute("aria-expanded") gives the string "true" or "false", so if (btn.getAttribute("aria-expanded")) is always true: "false" is a non-empty string (you will meet the same trap with a stored "false" in Chapter 64). Compare with === "true".
  2. Change the state and the screen together, in the same function.
  3. Let CSS style from the attribute. With [aria-pressed="true"] { ... } (attribute selectors, Chapter 34) the look comes from the state itself, so what is seen and what is heard cannot drift apart.

When the screen changes, the attribute must change in the same breath. Read ARIA values as words ("true", "false"), not as true and false, and style from them so the picture and the announcement always agree.

With aria-pressed, keep the label fixed ("Mute alerts") and let the state say on or off. If you would rather swap the label ("Play" / "Pause"), leave aria-pressed out: one or the other, never both.

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  button, input { font: inherit; padding: 6px 10px; margin: 4px 0; }
  .arrow { display: inline-block; }
  [aria-expanded="true"] .arrow { transform: rotate(90deg); }
  [aria-pressed="true"] { background: #0B2545; color: #fff; }
  input[aria-invalid="true"] { border: 2px solid #B42318; }
  .err { color: #B42318; font-weight: 700; }
</style>
<button id="more" type="button" aria-expanded="false" aria-controls="syllabus">
  <span class="arrow" aria-hidden="true">&#9656;</span> Syllabus
</button>
<ul id="syllabus" hidden>
  <li>Unit 4: JavaScript fundamentals</li>
  <li>Unit 5: Interactive web development</li>
</ul>

<p><button id="mute" type="button" aria-pressed="false">Mute alerts</button></p>

<label for="roll">Roll number</label>
<input id="roll" type="text">
<button id="check" type="button">Check</button>
<p id="roll-err" class="err" hidden>Error: a roll number has exactly 8 digits.</p>

<script>
  // 1. Disclosure: aria-expanded on the button, hidden on the panel
  const more = document.getElementById("more");
  const syllabus = document.getElementById("syllabus");
  more.addEventListener("click", () => {
    const isOpen = more.getAttribute("aria-expanded") === "true";   // compare text!
    more.setAttribute("aria-expanded", String(!isOpen));
    syllabus.hidden = isOpen;              // it was open, so hide it (and vice versa)
    console.log("Syllabus: aria-expanded =", more.getAttribute("aria-expanded"));
  });

  // 2. Toggle button: aria-pressed, label never changes
  const mute = document.getElementById("mute");
  mute.addEventListener("click", () => {
    const isOn = mute.getAttribute("aria-pressed") === "true";
    mute.setAttribute("aria-pressed", String(!isOn));
    console.log("Mute alerts: aria-pressed =", mute.getAttribute("aria-pressed"));
  });

  // 3. An error: aria-invalid + aria-describedby, and focus to the field
  const roll = document.getElementById("roll");
  const rollErr = document.getElementById("roll-err");
  document.getElementById("check").addEventListener("click", () => {
    const ok = roll.value.trim().length === 8;
    if (ok) {
      roll.removeAttribute("aria-invalid");
      roll.removeAttribute("aria-describedby");
      rollErr.hidden = true;
    } else {
      roll.setAttribute("aria-invalid", "true");
      roll.setAttribute("aria-describedby", "roll-err");
      rollErr.hidden = false;
      roll.focus();
    }
    console.log("Roll number", ok ? "accepted" : "rejected",
                "| aria-invalid =", roll.getAttribute("aria-invalid"));
  });
</script>

Press Syllabus twice: the Console shows Syllabus: aria-expanded = true, then false, and the arrow turns because the CSS reads the same attribute. Mute alerts goes dark when aria-pressed = true, again straight from the CSS. Type 123 and press Check: Roll number rejected | aria-invalid = true. The field is marked invalid, the message appears, linked by aria-describedby, and focus moves to the field, so a screen reader says "Roll number, edit, invalid entry, Error: a roll number has exactly 8 digits." Type 12345678 and Check again: Roll number accepted | aria-invalid = null, because getAttribute gives null for an attribute that is not there. Chapter 60 grows this into full form validation.

59.7 Hiding content the right way

Scripts hide and show things all day: panels, error messages, the "Loading…" line. There are several ways to hide something, and they hide it from different people.

TechniqueSeen?Read by screen readers?Reached by Tab?Use it for
hidden attribute, el.hidden = trueNoNoNoClosed panels, messages not needed yet
display: noneNoNoNoThe same, when CSS decides (a class, a media query)
visibility: hiddenNo (the space stays)NoNoRarely: hiding while keeping the gap
A .visually-hidden classNoYesOnly if focusableExtra words for screen readers: "Delete Pay hostel fee", "(opens in a new tab)"
aria-hidden="true"YesNoYes, if focusable — a trapDecoration beside real text: an arrow, an icon
opacity: 0NoYesYesAlmost never on its own: an invisible, clickable trap

hidden means gone for everyone. A visually-hidden class means gone for the eyes only. aria-hidden means gone for the screen reader only. Choose by asking: who must not get this?

From JavaScript the everyday choice is the hidden attribute, as in 59.4 and 59.6: panel.hidden = true hides the panel and everything in it, Tab stops included; false brings it back.

hidden can lose to your own CSS. Browsers implement hidden as a built-in display: none, and any rule of yours that sets display beats it: 
.panel { display: flex; }                 /* this rule wins...            */
<div class="panel" hidden>...</div>     <!-- ...so this is still visible -->

[hidden] { display: none !important; }   /* add once: hidden always hides */

The visually-hidden class does the opposite job: it hides words from the eyes but keeps them for screen readers. This book uses it (under the name sr-only): every link under Reference material ends with a hidden "(opens in a new tab)". The CSS is the standard one, used unchanged across the web:

.visually-hidden {
  position: absolute; width: 1px; height: 1px; padding: 0; margin: -1px;
  overflow: hidden; clip: rect(0, 0, 0, 0); white-space: nowrap; border: 0;
}

Use it for words a sighted user can work out from the layout, such as which item a Delete button belongs to. Never put aria-hidden="true" on anything focusable: the keyboard would land on a control that the screen reader refuses to describe.

Quick check: the words "(opens in a new tab)" after a link should be heard but not seen. hidden, aria-hidden or visually-hidden?

The visually-hidden class. hidden would remove the words for everyone, and aria-hidden would do the exact opposite of what is wanted: keep them visible and silence them.

59.8 Colour, hover and motion

Three more habits from the lecture's list, each with a JavaScript twist.

Never colour alone

When a script marks something right or wrong, colour is the first thing you reach for: a red border, a green tick. About one man in twelve has some colour-vision deficiency, and a screen reader hears no colour at all. Always add words ("Error:", "Saved") or a shape, as 59.6's roll-number message does. And when JavaScript switches colours, as a dark-mode toggle does, check the new pairs still reach 4.5:1 (Chapter 20).

Never hover alone

mouseenter and mouseover need a mouse. Touch screens have no real hover (a tap may fake one, unreliably), and a keyboard user never "hovers". Anything a script shows on hover, such as a hint or a menu, must also appear on focus or on a click:

// Hover only: keyboard and touch users never see the hint
infoBtn.addEventListener("mouseenter", showHint);
infoBtn.addEventListener("mouseleave", hideHint);

// Add these two, so reaching the button with Tab shows it too
infoBtn.addEventListener("focus", showHint);
infoBtn.addEventListener("blur", hideHint);

Less motion, when the user asks

Chapter 38 used the CSS media query prefers-reduced-motion to switch off transitions for people who have asked their device for less movement, many of them people with a vestibular disorder. CSS cannot reach motion that JavaScript creates: smooth scrolling, an auto-advancing slideshow, a number that counts up. For those, ask the same question in JavaScript. window.matchMedia takes the text you would write after @media and returns an object whose .matches is true or false right now; its change event fires if the user changes the setting while the page is open.

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  #list { position: relative; height: 140px; overflow-y: auto; margin: 10px 0 0;
          padding: 0 12px; list-style: none;
          border: 1px solid #CBD5E1; border-radius: 8px; }
  #list li { padding: 8px 0; border-bottom: 1px solid #E2E8F0; }
  #list li:focus { outline: 3px solid #E07B1E; outline-offset: -3px; }
  #mode { margin: 8px 0 0; }
</style>
<button id="jump" type="button">Jump to the latest notice</button>
<p id="mode"></p>
<ul id="list"></ul>

<script>
  const list = document.getElementById("list");
  for (let i = 1; i <= 20; i++) {
    const li = document.createElement("li");
    li.textContent = `Notice ${i}: routine update`;
    list.append(li);
  }
  const latest = list.lastElementChild;
  latest.textContent = "Notice 20 (latest): MTT seating plan is out";
  latest.tabIndex = -1;                       // focusable by script, not by Tab

  const motion = window.matchMedia("(prefers-reduced-motion: reduce)");

  function showMode() {
    document.getElementById("mode").textContent = motion.matches
      ? "Reduced motion is ON: the jump is instant."
      : "Reduced motion is off: the jump glides.";
    console.log("prefers-reduced-motion: reduce ->", motion.matches);
  }
  showMode();
  motion.addEventListener("change", showMode);   // the user may switch it any time

  document.getElementById("jump").addEventListener("click", () => {
    list.scrollTo({ top: latest.offsetTop, behavior: motion.matches ? "auto" : "smooth" });
    latest.focus({ preventScroll: true });       // keyboard users carry on from here
    console.log("Jumped", motion.matches ? "instantly" : "smoothly");
  });
</script>

On most computers the Console prints prefers-reduced-motion: reduce -> false, and the jump glides (Jumped smoothly). To see the other path, turn the setting on: on Windows, Settings → Accessibility → Visual effects → Animation effects off; on Android, Remove animations; or in Chrome DevTools, open the Rendering panel and set Emulate CSS media feature prefers-reduced-motion to reduce. The change listener notices at once and the next jump is instant.

The jump also moves focus to the latest notice (it has tabIndex = -1), so a keyboard user carries on from there. preventScroll: true stops focus() making its own sudden jump, so the scroll line alone decides how the list moves.

59.9 Build it: an accessible reminder list

One small page that uses nearly everything: real buttons, extra words for screen readers, a live region, and focus put somewhere sensible after a delete.

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  .visually-hidden { position: absolute; width: 1px; height: 1px; padding: 0;
    margin: -1px; overflow: hidden; clip: rect(0, 0, 0, 0);
    white-space: nowrap; border: 0; }
  #list { list-style: none; padding: 0; max-width: 380px; }
  #list li { display: flex; justify-content: space-between; align-items: center;
    padding: 8px 10px; margin-bottom: 6px;
    border: 1px solid #CBD5E1; border-radius: 8px; }
  h2:focus, button:focus-visible { outline: 3px solid #E07B1E; outline-offset: 2px; }
  #status { color: #14532D; font-weight: 600; }
</style>
<h2 id="heading" tabindex="-1">My reminders</h2>
<ul id="list"></ul>
<p id="status" role="status"></p>

<script>
  const reminders = ["Submit lab record", "Pay hostel fee", "Revise Unit 5"];
  const list = document.getElementById("list");
  const statusBox = document.getElementById("status");
  const heading = document.getElementById("heading");

  function render() {
    list.innerHTML = "";
    if (reminders.length === 0) {
      const li = document.createElement("li");
      li.textContent = "Nothing left. Well done!";
      list.append(li);
      return;
    }
    reminders.forEach((text, i) => {
      const li = document.createElement("li");
      const label = document.createElement("span");
      label.textContent = text;

      const del = document.createElement("button");
      del.type = "button";
      del.textContent = "Delete";
      const extra = document.createElement("span");
      extra.className = "visually-hidden";
      extra.textContent = " " + text;        // heard, not seen: "Delete Pay hostel fee"
      del.append(extra);
      del.addEventListener("click", () => removeAt(i));

      li.append(label, del);
      list.append(li);
    });
  }

  function removeAt(i) {
    const gone = reminders[i];
    reminders.splice(i, 1);
    render();                                 // the focused button no longer exists

    const buttons = list.querySelectorAll("button");
    const next = buttons[i] || buttons[i - 1] || heading;
    next.focus();
    statusBox.textContent = `Deleted "${gone}". ${reminders.length} left.`;
    console.log(statusBox.textContent, "| focus on:", document.activeElement.textContent);
  }

  render();
</script>

Click once inside the preview, Tab to the second Delete and press Enter. The Console prints Deleted "Pay hostel fee". 2 left. | focus on: Delete Revise Unit 5. Three things happened that a sighted user takes for granted:

  • Every button says what it deletes. On screen, three "Delete" buttons are clear because each sits beside its reminder; read aloud they would be three identical words. The visually-hidden span names each one: "Delete Submit lab record", "Delete Pay hostel fee"…
  • Focus survived the delete. render() destroyed the button that had focus. next.focus() picks the button now in the same position, or the one before it if the last item went, or the heading (tabindex="-1") when nothing is left. Keep pressing Enter: Deleted "Revise Unit 5". 1 left. | focus on: Delete Submit lab record (the last item went, so focus stepped back one), then Deleted "Submit lab record". 0 left. | focus on: My reminders.
  • The result was announced. The role="status" paragraph was in the HTML from the start, so each message is read out politely, after the newly focused button is named.

59.10 Testing with the keyboard only

Automated checkers such as Lighthouse and axe (Chapter 20) find missing labels and low contrast, but miss most of this chapter: a div with a click listener is valid HTML. Your hands find these bugs. Put the mouse out of reach and work through the page:

KeyWhat should happen
Tab / Shift+TabFocus moves forward or back through every link and control, in reading order, with a ring you can always see
EnterFollows a link; presses a button
SpacePresses a button or ticks a checkbox, without scrolling the page
EscapeCloses the panel, dialog or popup you are in, and focus returns to its opener
Arrow keysMove within radio groups, select boxes and sliders

After every action, ask three questions: Where is focus now? Did anything change that I was not told about? Can I get out of where I am?

Then look at what assistive technology receives. In Chrome DevTools, select an element in the Elements panel and open its Accessibility tab: it lists the element's name, role and states, such as expanded: false — the accessibility tree of 59.2, live. Finally, listen. Windows has Narrator built in (Ctrl+Windows+Enter) and NVDA is free; Android has TalkBack; Macs and iPhones have VoiceOver. Ten minutes with your eyes closed teaches more than any checklist.

59.11 Common misunderstandings

✗ "role="button" makes a div work like a button."
ARIA changes only what is announced. The div still ignores Tab, Enter and Space.
✓ "A custom button needs role, tabindex="0" and key handling — or should be a <button>."
The real button does it all in one line.
✗ "If it changed on the screen, everybody knows."
A screen reader announces only what gets focus and what is in a live region.
✓ "Messages go in a live region that is already in the HTML."
aria-live="polite" or role="status" for most; role="alert" only when it is urgent.
✗ "aria-hidden="true" hides an element."
It stays on the screen; only the screen reader stops reading it.
✓ "To hide from everyone, use hidden; to hide from the eyes only, use a visually-hidden class."
And never put aria-hidden on something focusable.
✗ "if (btn.getAttribute("aria-expanded")) tells me whether it is open."
It is always true: "false" is a non-empty string.
✓ "Compare the text: getAttribute("aria-expanded") === "true"."
And write the value with String(...) or a literal "true" / "false".
✗ "Hiding or deleting the focused element is harmless."
Focus drops to the page body and the user loses their place.
✓ "Move focus first: to the opener, the next item, or a heading with tabindex="-1"."
The same applies when you disable the button the user just pressed.

Exam-style checks

Answer each one before opening it. Most have four options and one correct answer; three ask what a piece of code does.

Which element should be used for a control that saves a form draft on the same page?L1
  • A. <div onclick="save()">
  • B. <a> with no href
  • C. <button type="button">
  • D. <span role="link">

Answer: C. Saving is an action on this page, and buttons do. A and B cannot even be reached with Tab; D has the wrong role and no keyboard support.

A developer must turn a <div> into a custom button. Which set is complete?L2
  • A. role="button", tabindex="0", and a keydown listener for Enter and Space
  • B. role="button" only
  • C. tabindex="0" and a click listener
  • D. aria-label and a click listener

Answer: A. The role for the announcement, tabindex for reaching it, the key listener for working. B is the classic trap: ARIA changes the announcement, not the behaviour. With C, Enter and Space still do nothing.

What happens when the user presses the space bar on this element? box.addEventListener("keydown", (e) => { if (e.key === "Space") console.log("pressed"); });L3

Answer: nothing is printed, and the page scrolls. event.key for the space bar is " ", so the test is false. Fix: e.key === " ", plus preventDefault().

A help panel opened by a button is now closed with the Escape key. Where should focus go?L2
  • A. To the page body
  • B. To the first link on the page
  • C. Nowhere; the browser decides
  • D. Back to the button that opened the panel

Answer: D. The user is back exactly where they were. A and C are what happens when the script forgets; B sends the user back to the start of the page.

Which attribute makes a screen reader read out an element's new text when it changes, without interrupting?L1
  • A. aria-hidden="true"
  • B. aria-live="polite"
  • C. tabindex="-1"
  • D. aria-label

Answer: B. A hides the element from screen readers, C makes it focusable by script, D only names it.

A payment has just failed and the user must know immediately. Which region suits the message best?L2
  • A. role="status"
  • B. A visually-hidden class
  • C. role="alert"
  • D. aria-describedby

Answer: C. An alert interrupts at once, right for an urgent failure. A waits politely, which suits routine messages such as "Saved"; B announces nothing by itself, and D only adds a description that is read when its field gets focus.

What does this print? btn.setAttribute("aria-expanded", "false"); if (btn.getAttribute("aria-expanded")) { console.log("open"); } else { console.log("closed"); }L3

Answer: open. getAttribute returns the string "false", and a non-empty string counts as true. Test === "true" and it prints closed.

Text must be hidden from the screen but still read by screen readers. Which technique does that?L2
  • A. The hidden attribute
  • B. display: none
  • C. aria-hidden="true"
  • D. A visually-hidden (sr-only) class

Answer: D. The text is clipped to a 1-pixel box: invisible, but still in the accessibility tree. A and B hide it from everyone; C is the reverse.

A script shows a wrong roll number only by turning the field's border red. What is the best fix?L3
  • A. Use a brighter red
  • B. Add an "Error: ..." message, link it with aria-describedby, set aria-invalid="true" and focus the field
  • C. Show the message only when the mouse hovers over the field
  • D. Make the border flash

Answer: B. It adds words, connects them to the field and takes the user there. C fails keyboard and touch users; D adds motion, not meaning.

Which code tells a script that the user has asked their device for less motion?L2
  • A. window.matchMedia("(prefers-reduced-motion: reduce)").matches
  • B. navigator.reducedMotion
  • C. document.motion === "reduce"
  • D. screen.prefersReducedMotion

Answer: A. matchMedia takes the same media query CSS uses. B, C and D do not exist.

Which test is most likely to find a clickable <div> that keyboard users cannot reach?L2
  • A. The W3C HTML validator
  • B. Checking the colour contrast
  • C. Putting the mouse away and moving through the page with Tab, Enter and Space
  • D. Reading the page source

Answer: C. The div is valid HTML, so the validator passes it. Only the keyboard shows that Tab skips it.

The page has <h2>Exam help</h2> with no tabindex, and nothing is focused. What does this print? document.querySelector("h2").focus(); console.log(document.activeElement.tagName);L3

Answer: BODY. A plain heading cannot take focus, so focus() does nothing and the body stays active. With tabindex="-1" it prints H2.

Quick revision

Key takeaways

  1. Scripts break accessibility in ways a mouse user never sees: fake controls, silent changes, lost focus, unwanted motion.
  2. Native first; links go, buttons do. A custom control needs role, a name, tabindex="0" and Enter/Space handling (event.key === " " for Space).
  3. Move focus when the script changes the page: into what opens, back to the opener on close, to a wrong field, onwards after a delete. tabindex="-1" lets a script focus a heading; Escape always gets the user out.
  4. aria-live="polite" and role="status" announce changes in turn; role="alert" interrupts. The region must be in the HTML before its text changes.
  5. Update aria-expanded, aria-pressed and aria-invalid with the screen. Their values are the strings "true" / "false".
  6. hidden hides from everyone, a visually-hidden class from the eyes only, aria-hidden from screen readers only.
  7. Never colour alone, never hover alone; check prefers-reduced-motion with matchMedia before JavaScript motion; test with the keyboard.
