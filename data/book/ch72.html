Unit 6 · Chapter 72 · Client-Side Application Design

Client-Side Application Design

So far you have built features one at a time: a counter, a live search, a form that checks itself. An application is many such features sharing one screen and one set of data without tripping over each other. This chapter is about the thinking you do before the first line of code: what the browser should be responsible for, how to split the work into layers, what to sketch on paper, which screens nobody remembers to design, and how one state object keeps the whole page telling the same story.

About 34 minutes · Course outcome CO6

Before you start — one-line reminders

  • The viewport meta tag and min-width media queries let one page fit every screen, starting from the phone (Chapter 21).
  • A render() function can redraw a list from an array of objects, and textContent is the safe way to put text on the page (Chapter 58).
  • localStorage keeps only strings, so objects go in with JSON.stringify and come out with JSON.parse (Chapter 64).
  • An interactive page waits for an event, reacts to it, and updates what the user sees (Chapter 71).

By the end of this chapter you can

  • Say which jobs belong in the browser and which must stay on the server, and explain why the browser cannot be trusted for security.
  • Name the four layers of a client-side application and what each one is allowed to touch.
  • Turn a user goal into a user journey and a low-fidelity wireframe before writing code.
  • Write mobile-first CSS and apply an accessibility checklist from the first day.
  • List the states a data screen needs — loading, success, empty, error, partial, disabled, validation — and design each one.
  • Build a page around one state object: events change the state, render() redraws, and localStorage remembers what should survive a reload.

72.1 What the browser is responsible for

Every web application is split between two places. The client is the browser on the user's phone or laptop. The server is a computer the college or company runs somewhere else, which every user's browser talks to. Client-side application design means deciding, before you build, what the browser part will do and how its code will be arranged.

The browser has four jobs:

JobWhat it meansDashboard example
Presents informationTurns data into readable, accessible screensAssignment cards with titles and due dates
Responds to actionsClicks, typing and swipes get immediate feedbackTyping "DBMS" narrows the list at once
Validates inputCatches mistakes early, before anything is sent"Enter a complete email" appears under the box
Manages UI stateRemembers which tab is open, what is filtered, what is loadingThe "Due soon" filter stays selected

Everything else belongs to the server:

Client side (browser)Server side
Layout, styling, animationStoring data for all users
Show / hide, filter, sortAuthentication (who you are) and permissions (what you may do)
Instant input checksFinal, trusted validation
Remembering UI preferencesPayments, secrets, API keys
Calling APIs and showing the resultsSending email, running scheduled jobs
The design rule. Anything a user could change in their own browser — your JavaScript, localStorage, form values, even a disabled attribute — cannot be trusted for security. Every file you send is readable with View Source, and every line can be edited in DevTools before it runs. Keep trust decisions on the server.

That is why a form checks the email in the browser and the server checks it again. The browser check is a courtesy: the user hears about the mistake in a split second instead of after a round trip. The server check is the lock on the door. Someone who switches off JavaScript skips your JavaScript check, and someone who sends a request straight to the server without your page at all skips every browser check — but neither can skip the server's.

The browser is the shop window part of the app: it shows things, reacts and helps. The server is the part that decides: who is allowed in, what is true, what gets saved for everybody. If a fact must be trusted or shared between users, it lives on the server.

Quick check: a quiz page checks the answers in JavaScript and shows the score. Can the teacher use that score as the official mark?

No. The correct answers had to be sent to the browser for JavaScript to compare them, so a student can read them in the page source, or simply edit the score in DevTools. Official marking must happen on the server.

72.2 The layers of a client-side application

You already know three jobs by their file types: HTML gives structure, CSS gives presentation, JavaScript gives behaviour. An application adds a fourth thing that a plain page barely has: data that changes while you watch — which assignments exist, which ones are done, what the user has typed in the search box. Organised properly, a student dashboard has four layers:

LayerMade ofIn the dashboard
1. PresentationHTML + CSSThe header, the assignment cards, the progress bar
2. UI interaction and stateEvent handlers, one state object, render()state = { student, assignments, filter }
3. Data access and API communicationA file such as api.jsfetchAssignments() returns JSON and handles loading and errors
4. Backend services (where there is one)Server + databaseThe REST API, logging in, the stored submissions

Layer 3 talks to an API; layer 4 is whatever answers it. When you publish on GitHub Pages (Chapter 76) you have no server of your own, so the bottom layer is somebody else's API or a static JSON file sitting next to your HTML.

The arrows are the whole point. The presentation layer never fetches anything; the data layer never touches the page. That buys you two promises:

  • If the API changes — a new address, a renamed field — only the data layer changes.
  • If the design changes — cards become a table — only the presentation layer and render() change. The data code does not know or care.

HTML says what is on the page. CSS says how it looks. JavaScript says what happens. The state says what is true right now. Keep those four apart and you can change any one of them without breaking the other three.

72.3 Plan before coding: goals, journeys and wireframes

The most expensive way to design a screen is to code it, show it to someone, and code it again. The cheap way is to answer three questions on paper first.

  1. What is the user's goal? Not "use the dashboard", but something they actually want done: Ananya wants to see what is due this week and submit her DBMS lab.
  2. What is the user journey? The steps from opening the app to finishing that goal:
    Open dashboard → search "DBMS" → open the assignment → upload the file → see "Submitted ✓".
  3. What does each screen look like? A rough sketch of every screen on that journey.

A journey with its branches is a user flow: what happens if the search finds nothing, or the upload fails? Each branch is a screen you will have to design (section 72.5 lists them), so you want to find them now, not after the code is written.

The sketch is a wireframe. A low-fidelity wireframe is deliberately rough — grey boxes, squiggles for text, no colours, no fonts, no real images — because it is meant to be argued over and redrawn in a minute. It decides four things:

DecisionQuestion it answers
LayoutWhere does each block sit?
NavigationHow does the user move between pages?
HierarchyWhat is most important — biggest, first, highest on the screen?
User journeyWhich steps finish the task, and is each step easy to find?

Agree on the wireframe first, then build. Moving a box on paper takes seconds; moving it in finished HTML, CSS and JavaScript takes an afternoon.

Quick check: why is a wireframe drawn without colours or real images?

So that everyone discusses layout, navigation, hierarchy and the journey — the decisions that are expensive to change later — instead of arguing about shades of blue. It also keeps the sketch cheap enough to throw away and redraw.

72.4 Responsive and accessible from the start

Two decisions belong in the plan, not in a "fix it later" list: how the layout changes with screen size, and how people who do not use a mouse or cannot see the screen will use it. Both are cheap on day one and expensive afterwards.

Mobile-first layout

Mobile-first means the plain CSS, with no media query around it, is the phone layout: one column. Then each min-width media query adds columns once the screen is wide enough. The width where the layout changes is called a breakpoint.

/* styles.css - mobile-first */
.cards { display: grid; gap: 16px; grid-template-columns: 1fr; }   /* mobile: one column */

@media (min-width: 600px) {                                     /* tablet */
  .cards { grid-template-columns: 1fr 1fr; }
}
@media (min-width: 1000px) {                                    /* desktop */
  .cards { grid-template-columns: repeat(3, 1fr); }
}

Read it as a staircase: under 600px, one column; from 600px, two; from 1000px, three. min-width: 600px is true when the width is 600px or more, so exactly 600px already gets two columns. The phone layout is the simplest one, so starting there means each step only adds; you never have to undo a desktop layout to squeeze it onto a phone.

The accessibility checklist

Accessibility means that keyboard users, screen reader users and people with weak eyesight can use the same app as everyone else. Put this checklist into the plan:

CheckWhat it means in practice
Semantic HTML<header>, <nav>, <main>, <button> — not a <div> pretending to be each
Readable typeBody text 16px or larger, line height about 1.5
Colour contrastAt least 4.5 : 1 between body text and its background
KeyboardThe Tab key reaches every link, button and input, in a sensible order
Visible focusA clear :focus-visible outline shows where the keyboard is
Flexible layout%, fr, rem — no fixed pixel widths on containers
LabelsEvery input has a <label for="...">
Viewport meta tag<meta name="viewport" content="width=device-width, initial-scale=1"> in every page's <head>

Why decide this up front? Because a real <button> is reachable with Tab, works with Enter and Space, and is announced as "button" by a screen reader — all for free. A clickable <div> chosen on day one has none of that, and adding it later means a tabindex, a role and key handlers on every one of them.

Build the phone version first and widen it. Use the HTML element that already means what you want. Then the app works for small screens, keyboards and screen readers without a rescue job at the end.

72.5 Design every state, not just the happy one

Designers often draw one picture of a screen: the one where the data has arrived and everything is fine. Users meet many more. Take a screen that loads a directory of users from an API. Here are the states it can be in:

StateWhat the user seesWhat they can do next
LoadingGrey placeholder rows ("skeletons") or "Loading…" while the request travelsWait, knowing something is happening
SuccessThe list, plus a summary: "10 users loaded"Read, search, open one
Empty"No users match 'zzz'. Try a different name."Change the search
Error"Couldn't load users. Check your connection." and a Retry buttonRetry, instead of reloading the whole page
PartialSome data arrived and some did not: "Showing 4 of 5 courses. One could not be loaded."Use what is there; retry the missing part
DisabledThe Save button greyed out, saying "Saving…"Nothing yet — which prevents a double submission
Validation"⚠ Enter a complete email, e.g. name@college.edu" beside the boxFix that one field

Notice the difference between empty and error. Empty means the request worked and the honest answer is "nothing"; error means the request itself failed. A screen that shows a blank white area for both leaves the user guessing which one happened. For every state ask two questions: what does the user see, and what can they do next? If the answer to the second is "nothing" for anything except a brief loading or saving moment, the design is not finished.

This is what user feedback means: every action gets a visible response straight away — a highlighted button, a spinner, a message — so the user never wonders whether the click registered. Put status messages in an element with role="status" (Chapter 70) so screen readers announce them too.

The example keeps the current state in a field called status and lets render() draw whichever state that is. The data layer is a pretend server, so it runs with no internet.

<style>
  body { font-family: system-ui, sans-serif; padding: 12px; }
  .bar { display: flex; gap: 8px; flex-wrap: wrap; align-items: center; }
  .skel { height: 14px; width: 70%; background: #E3E9F0; border-radius: 6px; }
  .err { color: #B91C1C; }
  .muted { color: #475569; }
</style>
<div class="bar">
  <button id="good">Load users</button>
  <button id="bad">Load while offline</button>
  <label for="q">Search</label> <input id="q" type="search">
</div>
<div id="out" role="status"></div>
<script>
  // ---- data layer: a pretend server, so this runs with no internet ----
  const names = ["Leanne Graham", "Ervin Howell", "Clementine Bauch",
                 "Patricia Lebsack", "Chelsey Dietrich"];
  const goodUrl = URL.createObjectURL(
    new Blob([JSON.stringify(names)], { type: "application/json" }));
  const deadUrl = URL.createObjectURL(new Blob(["gone"]));
  URL.revokeObjectURL(deadUrl);              // fetching it now fails, like having no Wi-Fi
  const wait = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

  async function fetchUsers(offline) {
    await wait(800);                         // a real network takes time too
    const response = await fetch(offline ? deadUrl : goodUrl);
    if (!response.ok) throw new Error("HTTP " + response.status);
    return response.json();
  }

  // ---- state: what is true right now ----
  const state = { status: "idle", users: [], query: "" };

  // ---- presentation: draw the screen from the state, nothing else ----
  const out = document.querySelector("#out");
  const goodBtn = document.querySelector("#good");
  const badBtn = document.querySelector("#bad");

  function line(text, cls) {
    const p = document.createElement("p");
    p.textContent = text;
    p.className = cls;
    return p;
  }

  function render() {
    const shown = state.users.filter((u) => u.toLowerCase().includes(state.query));
    const screen = state.status === "success" && shown.length === 0 ? "empty" : state.status;
    goodBtn.disabled = badBtn.disabled = state.status === "loading";   // disabled state
    out.replaceChildren();
    if (screen === "idle") {
      out.append(line("Press a button to load the directory.", "muted"));
    } else if (screen === "loading") {
      for (let i = 0; i < 3; i++) out.append(line("", "skel"));
    } else if (screen === "error") {
      out.append(line("Couldn't load users. Check your connection.", "err"));
      const retry = document.createElement("button");
      retry.textContent = "Retry";
      retry.addEventListener("click", () => load(false));
      out.append(retry);
    } else if (screen === "empty") {
      out.append(line(`No users match "${state.query}". Try a different name.`, "muted"));
    } else {
      shown.forEach((name) => out.append(line("● " + name, "")));
      out.append(line(`${shown.length} of ${state.users.length} users shown`, "muted"));
    }
    console.log("render() drew the", screen, "state");
  }

  // ---- events: change the state, then render ----
  async function load(offline) {
    state.status = "loading";
    render();
    try {
      state.users = await fetchUsers(offline);
      state.status = "success";
    } catch (err) {
      console.error("Load failed:", err.message);
      state.status = "error";
    }
    render();
  }
  goodBtn.addEventListener("click", () => load(false));
  badBtn.addEventListener("click", () => load(true));
  document.querySelector("#q").addEventListener("input", (e) => {
    state.query = e.target.value.trim().toLowerCase();
    render();
  });
  render();
</script>

Run it and the console says render() drew the idle state. Press Load users: loading appears at once, with both buttons disabled so a second click cannot start a second request, then success 0.8 seconds later. Type zzz and every keystroke draws the empty state. Press Load while offline and you get a red Load failed: line (the browser's own wording follows it, such as "Failed to fetch" in Chrome), then the error state with a Retry button.

The code never "shows the spinner" or "hides the error" by hand. It only sets state.status and calls render(), and render() draws whichever state is true. That is how every state gets designed: it has to appear in render(), or it cannot appear at all.

72.6 State: one source of truth

State is the data that describes what the screen should show right now: the list of assignments, which ones are submitted, the word in the search box, the chosen filter, whether something is loading. A well-designed app keeps all of it in one object, which is the app's single source of truth. The page on screen is only a picture of that object.

Picture this. At a cricket ground the official scorer writes every ball in the scorebook. The big scoreboard is never changed by someone in the crowd guessing the total; whoever works it copies from the book. If the board and the book ever disagree, the book wins and the board is corrected from it. In your app the state object is the scorebook, the screen is the scoreboard, and render() is the person copying from one to the other.

Three rules turn that idea into code:

  1. Every fact lives in the state. Not in a CSS class you read back, not in the text of a badge, not in a second variable that has to be kept in step with the first.
  2. Only render() draws. It reads the state and rebuilds the screen from it.
  3. Every event does two things: update the state, then call render().

Here is the dashboard's version of that loop:

// dashboard.js
const state = { assignments: [], filter: "" };

function render() {
  const visible = state.assignments.filter((a) =>
    a.title.toLowerCase().includes(state.filter));
  list.replaceChildren();                      // empty the list
  visible.forEach((a) => list.append(makeCard(a)));
}

search.addEventListener("input", () => {
  state.filter = search.value.toLowerCase();   // 1. update the state
  render();                                    // 2. redraw from it
});

Now predict: somewhere else in the code, a new task arrives and this line runs, with no render() after it. What does the user see?

state.assignments.push(newTask);   // no render() call

Nothing changes on screen. The data has the new task, but the page is only rebuilt when render() runs. This is the most common bug in hand-written state code. Try both versions:

It starts with Start - in state: 3 | on screen: 3. Press the first button and you get Pushed, no render() - in state: 4 | on screen: 3: the data and the screen now disagree. Press the second and both catch up: Pushed, then render() - in state: 5 | on screen: 5, because render() draws everything in the state, including the task the first button added. Type lab in the search and the quiz disappears while every "Lab" card stays.

Libraries such as React and Vue are built around exactly this loop; their main job is to call the re-render for you whenever the state changes. In plain JavaScript you call render() yourself, which is why you must never forget it.

Quick check: the dashboard shows "4 of 6 submitted". Where does the true number of submitted assignments live — in that text, or somewhere else?

In the state. The text is a picture drawn by render(), which counts the assignments whose submitted is true. Nobody reads the number back from the page; if the two disagree, the state is right and the screen is out of date.

72.7 Remembering state with localStorage

Because everything lives in one object, making some of it persist across a reload needs just two small functions. save() writes the part worth keeping to localStorage after each change; load() reads it back once, when the page starts.

const KEY = "edutrack-v1";

function save() {
  localStorage.setItem(KEY, JSON.stringify({ filter: state.filter }));
}

function load() {
  try {
    const saved = JSON.parse(localStorage.getItem(KEY));   // null if nothing saved yet
    if (saved) state.filter = saved.filter;
  } catch (err) {
    console.warn("Saved data was damaged, starting fresh");  // never let bad data crash the app
  }
}

// every event now: update the state, save, render
function setFilter(value) {
  state.filter = value;
  save();
  render();
}

load();     // once, at start-up
render();

Two details are worth slowing down for. getItem returns null when nothing has been saved yet, and JSON.parse(null) quietly returns null, so the if (saved) line covers a first visit. And if someone has left a broken string under that key, JSON.parse throws a SyntaxError, and the try...catch (Chapter 70) means the app simply starts with its defaults instead of showing a blank page.

Deciding what to save is a design decision, and section 72.1 already gave you the rule:

Save in localStorageDo not save there
UI preferences: the chosen filter, the open tab, dark modeShort-lived flags such as status: "loading" — after a reload nothing is loading
An unsent draft the user would hate to loseData the server owns, such as which assignments are submitted; fetch it fresh
Passwords, tokens, or anything the app must be able to trust

Every change follows the same three steps: change the state, save it, draw it. Only the pieces that are the user's own choices get saved; facts come back from the server each time.

About the Run button in this book. The preview frames have no web address of their own, so their localStorage is a temporary stand-in: it works while you click, but Run again starts it empty. On a real site, such as your own page opened with VS Code Live Server, the saved data survives reloads and browser restarts.

From the sketch to a state object

Now read your wireframe as a programmer and ask of every box: what in here can change? The answers are the state.

const state = {
  student: { name: "Ananya", roll: "12215678", semester: 3 },   // student info box
  assignments: [                                               // the cards
    { id: 1, title: "DBMS Lab 4", course: "CSE305", dueInDays: 1, submitted: false }
    // ...one object per card
  ],
  filter: "all",    // "all" | "due" | "submitted"   - the filter buttons
  search: ""        // the search box
};

Look at what is not in it. The progress figure "3 of 6" is not stored: render() counts it from assignments every time. The most urgent assignment is not stored either: it is the unsubmitted one with the smallest dueInDays. Storing either would create a second copy of a fact that could drift out of step with the first, which is exactly what one source of truth forbids.

        { id: 2, title: "Web Project", course: "CSE326", dueInDays: 3, submitted: false },
        { id: 3, title: "OS Quiz 2",   course: "CSE316", dueInDays: 6, submitted: false },
        { id: 4, title: "Web Lab 5",   course: "CSE326", dueInDays: 0, submitted: true },
        { id: 5, title: "Maths Sheet", course: "MTH166", dueInDays: 2, submitted: true },
        { id: 6, title: "DBMS Lab 3",  course: "CSE305", dueInDays: 0, submitted: true }
      ],
      filter: "all",
      search: ""
    };
  }
  let state = freshState();

  // ---- data: keep only the user's own choice ----
  function save() {
    localStorage.setItem(KEY, JSON.stringify({ filter: state.filter }));
  }
  function load() {
    try {
      const saved = JSON.parse(localStorage.getItem(KEY));
      if (saved) state.filter = saved.filter;
    } catch (err) {
      console.warn("Saved data was damaged, starting fresh");
    }
  }

  // ---- values worked out from the state, never stored ----
  function matchesFilter(a) {
    if (state.filter === "due") return !a.submitted && a.dueInDays <= 3;
    if (state.filter === "submitted") return a.submitted;
    return true;                                     // "all"
  }
  function visibleAssignments() {
    const words = state.search.trim().toLowerCase();
    return state.assignments
      .filter(matchesFilter)
      .filter((a) => a.title.toLowerCase().includes(words))
      .sort((a, b) => a.submitted - b.submitted || a.dueInDays - b.dueInDays);
  }
  function mostUrgent() {
    const open = state.assignments.filter((a) => !a.submitted);
    open.sort((a, b) => a.dueInDays - b.dueInDays);
    return open[0];                                  // undefined once all are submitted
  }
  function dueText(days) {
    if (days === 0) return "Due today";
    if (days === 1) return "Due tomorrow";
    return `Due in ${days} days`;
  }

  // ---- presentation ----
  function renderCards() {
    const box = $("#cards");
    const list = visibleAssignments();
    const urgent = mostUrgent();
    box.replaceChildren();
    if (list.length === 0) {                         // the empty state
      const p = document.createElement("p");
      p.textContent = "Nothing here. Try another filter or search.";
      box.append(p);
      return;
    }
    list.forEach((a) => {
      const card = document.createElement("article");
      card.className = a === urgent ? "card urgent" : "card";
      const h = document.createElement("h3");
      h.textContent = a.title;
      const info = document.createElement("p");
      info.textContent = a.course + " · " + (a.submitted ? "Submitted ✓" : dueText(a.dueInDays));
      const btn = document.createElement("button");
      btn.textContent = a.submitted ? "Undo" : "Mark submitted";
      btn.addEventListener("click", () => toggleSubmitted(a.id));
      if (a === urgent) {
        const badge = document.createElement("p");
        badge.className = "badge";
        badge.textContent = "Most urgent";
        card.append(badge);
      }
      card.append(h, info, btn);
      box.append(card);
    });
  }
  function render() {
    const s = state.student;
    const done = state.assignments.filter((a) => a.submitted).length;
    const total = state.assignments.length;
    $("#hello").textContent = `Hi, ${s.name} (roll ${s.roll}, semester ${s.semester})`;
    $("#bar").max = total;
    $("#bar").value = done;
    $("#count").textContent = `${done} of ${total} submitted`;
    if ($("#search").value !== state.search) $("#search").value = state.search;
    document.querySelectorAll("[data-filter]").forEach((b) => {
      b.setAttribute("aria-pressed", b.dataset.filter === state.filter);
    });
    renderCards();
    console.log(`render(): filter=${state.filter}, ${done} of ${total} submitted`);
  }

  // ---- interaction: update the state, save if needed, render ----
  function setFilter(value) {
    state.filter = value;
    save();
    render();
  }
  function toggleSubmitted(id) {
    const a = state.assignments.find((x) => x.id === id);
    a.submitted = !a.submitted;                      // a real app would tell the server
    render();
  }
  document.querySelectorAll("[data-filter]").forEach((b) => {
    b.addEventListener("click", () => setFilter(b.dataset.filter));
  });
  $("#search").addEventListener("input", (e) => {
    state.search = e.target.value;
    render();
  });
  $("#reload").addEventListener("click", () => {
    console.log("--- pretend reload: state rebuilt from scratch ---");
    state = freshState();
    load();
    render();
  });

  load();
  render();
</script>

Trace it once. The console starts with render(): filter=all, 3 of 6 submitted, and DBMS Lab 4 carries the "Most urgent" badge because it is the open assignment due soonest. Press Due soon: render(): filter=due, 3 of 6 submitted, and only DBMS Lab 4 and the Web Project remain. Mark DBMS Lab 4 submitted: render(): filter=due, 4 of 6 submitted; it leaves the list, the progress bar grows, and the badge moves to the Web Project. Nobody wrote code to move the badge — render() simply worked it out again.

Now press Simulate a page reload. After --- pretend reload: state rebuilt from scratch --- comes render(): filter=due, 3 of 6 submitted. The filter survived because it was saved; the tick did not, because submissions belong to the server (section 72.1), and in the real app the fresh data from the server would already include it. That is the whole chapter in one button: the user's choices in localStorage, the facts from the server, and one render() drawing the result.

72.9 Common misunderstandings

✗ "My JavaScript checks it, so it is safe."
Anyone can read, edit or skip your JavaScript, or send a request to the server without your page at all.
✓ "The browser checks for convenience; the server checks for security."
Validate in both places; trust only the server.
✗ "When I change the data, the page updates itself."
In plain JavaScript the page changes only when your code changes it. A push with no render() leaves the screen out of date.
✓ "Update the state, then call render() — every time."
Libraries such as React automate that second step; the idea is the same.
✗ "I will design the screen with the data on it. The other states can wait."
Users meet loading, empty and error screens every day, often before they ever see the success screen.
✓ "For each state: what does the user see, and what can they do next?"
If a state is not in render(), it cannot appear at all.
✗ "Mobile-first means designing only for phones."
It is about the order you write the CSS in, not about which devices you support.
✓ "The phone layout is the default; min-width queries add to it for wider screens."
Every screen size is designed; the simplest one comes first.

Exam-style checks

Which of these jobs must be done on the server rather than in the browser?L1
  • A. Hiding a panel when a button is clicked
  • B. Warning instantly that an email address has no @
  • C. Deciding whether a student is allowed to submit after the deadline
  • D. Remembering that the user chose dark mode

Answer: C. It is a permission decision, and anything decided in the browser can be changed by the user. The instant email warning (B) is fine in the browser as a convenience, but the server must check the email again before trusting it.

In the four-layer dashboard, which layer contains fetchAssignments()?L2
  • A. Data access and API communication
  • B. UI interaction and state
  • C. Presentation
  • D. Backend services

Answer: A. The data layer talks to the API, returns JSON and handles loading and errors. It is not the backend (D): the backend is the server that answers the request, which on GitHub Pages is not yours at all.

What is a low-fidelity wireframe?L1
  • A. The finished design, with the real colours and fonts
  • B. A quick sketch of layout and hierarchy, with no colours or real images
  • C. The HTML skeleton of the page, without CSS
  • D. A diagram of the server's database tables

Answer: B. It is drawn before any code, to agree on layout, navigation, hierarchy and the user journey while changes are still cheap. HTML without CSS (C) is already code.

With the mobile-first CSS of section 72.4 (one column; two from min-width: 600px; three from min-width: 1000px), how many columns are shown at a width of 400px, 800px and exactly 1000px?L3

1, 2 and 3. At 400px neither query matches, so the default single column applies. At 800px only the 600px query matches. At exactly 1000px both match, because min-width includes the value itself, and the later rule wins: three columns.

A user searches the directory for "zzz". The request worked, but no names match. Which state should the screen show?L2
  • A. Error
  • B. Loading
  • C. Disabled
  • D. Empty

Answer: D. Nothing failed; the honest answer is simply "no matches", with a next step such as "Try a different name". Showing the error state (A) would wrongly suggest something broke.

Why is a Save button disabled and relabelled "Saving…" while its request is in flight?L2
  • A. To prevent a second click sending the same data twice, and to show that the click registered
  • B. Because a browser cannot send two requests at once
  • C. To stop the server from validating the data
  • D. Because the button cannot keep its focus outline while saving

Answer: A. It is user feedback and protection against double submission. Browsers can send several requests at once (B is false), which is exactly why the second click must be blocked.

The dashboard's search handler is shown in section 72.6. Elsewhere, state.assignments.push(newTask); runs with no render() after it. What does the user see?L3

No change on screen. The state now holds the new task, but the page is rebuilt only when render() runs. The task appears the next time something calls render() — for example the user typing in the search box. The fix is to call render() after every state change.

What does this code print?L3
const state = { done: 1, total: 4 };
function render() {
  console.log(`${state.done} of ${state.total} submitted`);
}
render();
state.done = state.done + 2;
state.total++;
render();

1 of 4 submitted, then 3 of 5 submitted. The first render() runs before any change. Then done becomes 3 and total becomes 5, and the second render() draws the new state. The screen (here, the console) shows only what render() drew.

What does "single source of truth" mean in a client-side app?L2
  • A. All the code is kept in a single file
  • B. Every fact is stored once, in the state object, and the screen is drawn from it
  • C. Only one user may use the app at a time
  • D. The DOM is the master copy and the state is read back from it

Answer: B. One place holds each fact; everything else, including the screen, is derived from it. D is exactly backwards: reading facts back out of the page is what this rule exists to prevent.

On a first visit, nothing has been saved yet. What does JSON.parse(localStorage.getItem("edutrack-v1")) return?L3
  • A. undefined
  • B. An empty object {}
  • C. null
  • D. It throws a SyntaxError

Answer: C. getItem returns null for a missing key, and JSON.parse(null) turns it into the text "null", which parses to null. That is why load() checks if (saved). A SyntaxError (D) happens only when a string that is not valid JSON was saved.

The accessibility checklist sets a minimum contrast ratio between body text and its background. What is it?L1
  • A. 2 : 1
  • B. 3 : 1
  • C. 3.5 : 1
  • D. 4.5 : 1

Answer: D. 4.5 : 1 is the WCAG level AA minimum for normal-sized text. For text, the lower 3 : 1 (B) is allowed only when it is large, such as big headings.

Quick revision

Key takeaways

  1. The browser presents, responds, validates early and manages UI state. Anything that must be trusted or shared — permissions, final validation, payments, secrets — stays on the server.
  2. Four layers: presentation (HTML + CSS), UI interaction and state (JavaScript), data access (the API calls), backend. Each talks only to its neighbour.
  3. Plan first: the user's goal, the journey that reaches it, and a low-fidelity wireframe that settles layout, navigation and hierarchy.
  4. Mobile-first CSS: one column by default, min-width queries add columns. Decide semantic HTML, labels, contrast, keyboard access and visible focus at the start.
  5. Design every state — loading, success, empty, error, partial, disabled, validation — and for each, what the user sees and can do next.
  6. One state object is the single source of truth. Every event: update the state, then call render(). Forget render() and the screen goes stale.
  7. Persist only the user's own choices with save() after each change and load() at start-up, wrapped in try...catch.
