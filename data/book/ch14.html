Page Structure and Layout

Chapter 13 gave you the vocabulary; this chapter is about assembling a whole page with it. You will learn to see a page as a tree, to turn a sketch of a layout into an HTML skeleton, to keep the structure independent of how it will eventually be styled, and to recognise the layout mistakes (tables, line breaks, fake headings) that break a page for everyone but the person who wrote it.

About 12 minutes · Course outcome CO2

By the end of this chapter you can

  • Draw the tree of a typical page from html down to its landmarks.
  • Convert a wireframe into a semantic HTML skeleton.
  • Explain "structure first, style later" and logical source order.
  • Place headings, headers and footers correctly inside sections and articles.
  • Identify layout built with tables, breaks or styled divs and replace it.

14.1 The page as a hierarchy

Every page is a tree. At the root is html, which holds the invisible head and the visible body. Inside the body the semantic regions form the next level; inside them, sections and articles; inside those, headings, paragraphs, lists, images and forms. Reading a page as this tree is the skill that makes every structure question easy.

Three facts about the tree that questions probe: head holds information about the document and body holds what is displayed; the semantic regions are children of body; and article and aside normally live inside main, never inside head, header or footer.

14.2 From wireframe to skeleton

Designers sketch pages as boxes: a banner across the top, a menu, a wide content column, a narrow sidebar, a footer. Each box maps to a semantic element. Draw the boxes, label them, and the HTML skeleton writes itself.

Here is that skeleton as a complete, valid page. It is HTML only, no CSS, and it already has everything a screen reader or search engine needs.

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>School of Computing and AI</title>
</head>
<body>
  <header>
    <h1>School of Computing and AI</h1>
    <p>Lovely Professional University</p>
  </header>
  <nav aria-label="Main navigation">
    <ul>
      <li><a href="index.html">Home</a></li>
      <li><a href="courses.html">Courses</a></li>
      <li><a href="contact.html">Contact</a></li>
    </ul>
  </nav>
  <main>
    <section>
      <h2>About Us</h2>
      <p>Welcome to our school.</p>
    </section>
    <section>
      <h2>Latest News</h2>
      <article>
        <h3>AI Workshop</h3>
        <p>Workshop conducted for students.</p>
      </article>
    </section>
    <aside>
      <h2>Quick Links</h2>
      <a href="admissions.html">Admissions</a>
    </aside>
  </main>
  <footer>
    <p>&copy; 2026 School of Computing and AI</p>
  </footer>
</body>
</html>

14.3 Structure first, style later

Notice that the page above has no layout at all: everything stacks top to bottom in the order it was written. That is correct. HTML provides the logical structure; CSS, written afterwards, decides how that structure is arranged on a desktop, a tablet or a phone (Unit 3 covers Flexbox, Grid and media queries). The habit that makes this work is logical source order: write the elements in the order a reader should encounter them, header, navigation, main content, related content, footer, and let CSS move them into columns. A screen reader, a search engine and a phone with no CSS all read the source order, so it must make sense on its own.

Two habits that prepare HTML for responsive layout before any CSS exists: a logical source order and flexible, scalable media (images and videos that can shrink to their container, Chapter 21). Two habits that fight it: hard-coding width="800" on containers, and nesting layout tables.

14.4 Headings, headers and footers inside regions

The heading outline (Chapter 6) and the landmark structure work together. The page's single h1 usually sits in the page header. Each section starts with an h2; each article inside it with an h3. An aside gets a heading too. The result is an outline that matches the regions, so a screen-reader user can navigate by either.

Regions can nest their own sub-regions. An article may open with its own header (title, author, date) and close with its own footer (tags, share links); a long article may contain sections. What must not happen: a second main, a main inside an article, or a section with no heading.

<article>
  <header>
    <h2>Why semantic HTML matters</h2>
    <p>By Asha Kumar · <time datetime="2026-09-01">1 September 2026</time></p>
  </header>
  <section>
    <h3>Screen readers</h3>
    <p>Landmarks let users jump straight to the content.</p>
  </section>
  <section>
    <h3>Search engines</h3>
    <p>Structure tells them what is content and what is navigation.</p>
  </section>
  <footer><p>Tags: HTML, accessibility</p></footer>
</article>

14.5 Layout mistakes to unlearn

Tables for layout
Before CSS, pages were laid out in invisible tables. Today it breaks accessibility and responsiveness: a screen reader announces a data table with rows and columns that mean nothing, and a fixed grid cannot reflow on a phone. Tables are for tabular data (Chapter 19). Browsers still support <table>, tables can hold images, and they are not slower; those are not the reasons.
Line breaks for structure
<br> means a line break in text. Stacks of <br> to create space between blocks are not a layout system; use semantic containers and CSS margins.
Styled divs instead of headings
<div class="h2">Results</div> looks like a heading and loses the document outline, so heading navigation cannot find it. Use a real h2 and style it.
Fixed pixel dimensions on containers
width="800" and fixed heights fight every screen that is not 800 pixels wide. Let containers be fluid and let media scale.
Everything in divs
A page that is only divs has no landmarks and no outline; the user hears the whole menu on every load. Use the regions.

14.6 Three common page shapes

Most pages you will build are one of these, and the skeleton for each is short.

ShapeRegions in orderTypical use
Single columnheader (h1, nav), main (sections), footerProfile page, landing page, documentation
Content + sidebarheader, nav, main (sections/articles) + aside, footerBlog, news site, course page
Form pageheader, main (one section holding the form), footerRegistration, login, feedback

A checklist for any skeleton: one h1; header, nav, main, footer present; every section has a heading; articles and asides inside main; no layout tables, no br stacks; source order reads correctly with no CSS; viewport meta tag in the head.

Exam-style checks

In a well-formed page skeleton, where do <article> and <aside> normally sit?L3
  • A. Inside <header>
  • B. Inside <footer>
  • C. Inside <main>
  • D. Directly inside <head>

Answer: C.

Which is the correct nesting order: header > nav then main > section, or main > header > nav?L2

Answer: header > nav, then main > section. The nav belongs in the header; sections belong in main.

Why should every <section> contain a heading?L2
  • A. So assistive technology can summarise and navigate the section
  • B. Without one the section will not render
  • C. Headings are required before CSS can be applied
  • D. It prevents the section from being indexed

Answer: A.

Why should tables not be used to lay out an entire web page today?L3
  • A. Tables cannot contain images
  • B. It breaks accessibility and responsiveness; tables are for tabular data
  • C. Browsers no longer support the <table> element
  • D. Tables always load more slowly than <div> elements

Answer: B.

Which habit best prepares HTML for a responsive layout before any CSS is written?L3
  • A. Hardcoding width="800" on every container
  • B. Nesting layout tables three levels deep
  • C. Using a logical source order and flexible, scalable media
  • D. Setting fixed pixel heights on all sections

Answer: C.

A developer styles a section heading as <div class="h2">Results</div>. What is lost?L3

Answer: the document outline, so heading navigation by assistive technology no longer finds it. CSS, placement inside a section and rendering are all unaffected.

Which element should appear exactly once per page, and can a <footer> appear inside an <article>?L2

Answer: <main> appears once. Yes, a footer can close an article or section as well as the page.

What is the difference between <head> and <header> in the page tree?L2

Answer: head is a child of html holding invisible metadata; header is a child of body (or of a section/article) holding visible introductory content.

Quick revision

Key takeaways

  1. The page is a tree: html > head + body; body > header, nav, main, footer; main > sections, articles, aside.
  2. Wireframe boxes map to semantic elements; write them in logical source order.
  3. HTML supplies structure; CSS later arranges it for each screen. The source must read correctly with no CSS at all.
  4. One h1 in the header; h2 per section; h3 per article; sections and articles may carry their own header and footer; never a second main.
  5. Do not lay out with tables, br stacks, styled divs or fixed widths.
