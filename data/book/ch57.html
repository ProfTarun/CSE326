Unit 5 · Chapter 57 · Event Handling

Event Handling

Until now your scripts ran once, top to bottom, and then stopped. A real page does something different: it sits and waits, and the moment you click, type, press a key or send a form, a piece of your code springs to life. This chapter shows how to tell the browser "when this happens, run that", what the browser tells you about each happening, and how one small idea — events travel up the page — lets a single line of code look after a hundred buttons.

About 35 minutes · Course outcome CO5

Before you start — one-line reminders

  • A function's name without brackets, greet, is the function itself; with brackets, greet(), it runs now (Chapter 48).
  • A callback is a function you hand to someone else to call later, when the time comes (Chapter 54).
  • The page is a tree: every element sits inside a parent, up to <body>, <html> and document (Chapter 55).
  • getElementById finds an element, textContent and classList change it, and dataset reads its data-* attributes (Chapter 56).

By the end of this chapter you can

  • Name the common events (click, input, change, submit, keydown, mouseover, focus, blur, load, DOMContentLoaded) and say when each one fires.
  • Attach a handler in all three ways, and explain why addEventListener is the one to use.
  • Read the event object: type, target, currentTarget, key and target.value.
  • Stop a form submit or a link with preventDefault(), and stop an event travelling with stopPropagation().
  • Predict the order in which nested elements hear a click (capturing, target, bubbling).
  • Handle a whole list of buttons with one delegated listener that reads data-* attributes.
  • Remove a listener correctly, and build the interactive counter with mouse and keyboard support.

57.1 What is an event?

An event is something that happens in the browser which your code can respond to. Most events are caused by the person using the page: they click a button, type a letter, move the mouse over a picture, press Enter in a form. Some are caused by the browser itself: the page has finished loading, a video has reached its end. The browser notices every one of them. Your job is only to say which ones you care about, and what should happen.

Here are the events you will use most often. The name in the first column is exactly the text you will type in your code, in lowercase.

EventFires whenA typical use
clickAn element is clicked or tapped — or a focused button is activated with Enter or SpaceButtons of every kind
inputThe value of a text box changes: every letter typed, pasted or deletedLive search, a character counter
changeA value is committed: a checkbox ticked, a dropdown option chosen, or a text box left after editingDropdowns, checkboxes
submitA form is sent, by its submit button or by Enter in one of its boxesChecking a form before it goes
keydown / keyupA key goes down / comes back upKeyboard shortcuts, games
mouseover / mouseoutThe mouse pointer moves onto / off an elementShowing a hint, highlighting a card
focus / blurAn element gets / loses the keyboard's attention (clicked into, or reached with Tab)Showing help next to the box being filled
DOMContentLoadedOn document: the HTML has been read and the tree is builtStarting a script placed in the head (Chapter 55)
loadOn window: the page and all its images and stylesheets have arrivedCode that needs image sizes

Such a page works in a loop: it waits, something happens, your code reacts by changing the page, and the page waits again. This is called event-driven programming. The function you hand over is an event listener (or event handler; the names mean the same here). It is a callback, as in Chapter 54: you never call it yourself; the browser calls it every time the event happens.

Picture this. At the hostel gate sits a watchman with a notebook. You tell him once: "When a courier comes for room 204, ring my phone," and go back to studying — he does the waiting. When a courier arrives he finds your line and rings you, handing over a slip saying who came and with what. Your roommate can leave a line for the same courier too, and the watchman rings you both, in the order the lines were written. You can cross your line out — but only by pointing to the exact line you wrote. The browser is the watchman, the courier is the event, your line is the listener, and the slip is the event object.
Quick check: a student types "Hi" into a search box. Which event fires twice, and which fires only when she clicks somewhere else?

input fires twice, once for each letter. change fires once, when she leaves the box, because that is when a text box's value is committed.

57.2 Three ways to attach a handler

The lecture slides show three ways of connecting a function to an event. All three still work in every browser, and you will meet all three in other people's code, so you must be able to read them. Only one should go into code you write.

<!-- 1. Inline event handler: JavaScript inside an HTML attribute -->
<button onclick="alert('Hello!')">Click Me</button>

// 2. DOM property: store a function in the element's onclick property
button.onclick = function () { alert("Button clicked!"); };

// 3. addEventListener() - the recommended approach
document.getElementById("btn").addEventListener("click", () => {
  alert("Button clicked!");
});

Way 1, the oldest, puts JavaScript as text inside an HTML attribute: two languages in one line, hard to read, hard to reuse, and blocked outright by many real websites for security reasons. Way 2 keeps the code in JavaScript, but an element has exactly one onclick property, and like any variable it holds one value: assign a second function and the first is silently thrown away. Way 3, addEventListener, adds a listener to a list the browser keeps for that element and event. Add three, and all three run.

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  button { display: block; margin: 8px 0; padding: 8px 14px; cursor: pointer; }
</style>
<button id="b1" onclick="console.log('Way 1: the onclick attribute ran')">Way 1: onclick attribute</button>
<button id="b2">Way 2: onclick property</button>
<button id="b3">Way 3: addEventListener</button>

<script>
  // Way 2: the property holds ONE function
  const b2 = document.getElementById("b2");
  b2.onclick = function () { console.log("Way 2: first handler"); };
  b2.onclick = function () { console.log("Way 2: second handler"); };  // replaces the first!

  // Way 3: every addEventListener call ADDS one more listener
  const b3 = document.getElementById("b3");
  b3.addEventListener("click", () => console.log("Way 3: first listener"));
  b3.addEventListener("click", () => console.log("Way 3: second listener"));

  console.log("Handlers attached. Now click each button.");
</script>

On Run the Console shows only Handlers attached. Now click each button. — nothing else, because no handler runs until its event happens. Then, click by click:

  • Way 1 prints Way 1: the onclick attribute ran.
  • Way 2 prints only Way 2: second handler. The first function was overwritten before anyone clicked.
  • Way 3 prints Way 3: first listener and then Way 3: second listener: both kept, in the order they were added.

Three ways, one winner. The onclick attribute mixes JavaScript into HTML. The onclick property can hold only one function, so a second one wipes out the first. addEventListener keeps HTML and JavaScript apart, lets many listeners share one event, and lets you take any of them away again.

Exam tip. "Why is addEventListener preferred?" has three marks waiting in it: (1) it allows several listeners for the same event, (2) a listener can be removed, and (3) it keeps JavaScript separate from HTML. A fourth point, if you have room: it offers options such as the capturing phase.

57.3 addEventListener up close

Every call has the same shape: which element, a dot, addEventListener, and two things in the brackets.

saveBtn.addEventListener("click", saveNotes);
//  |                      |        |
//  element to watch       event    function to run each time it happens

The event name is a string, without "on". Write "click", never "onclick". The browser has no event called onclick, so addEventListener("onclick", fn) waits for something that never happens: no error, no click, just silence.

The function goes in without brackets. This is the bug every beginner writes at least once:

function saveNotes() { console.log("Saved!"); }

saveBtn.addEventListener("click", saveNotes);     // right: hands over the function
saveBtn.addEventListener("click", saveNotes());   // wrong: runs it NOW, hands over undefined

With brackets, saveNotes() runs immediately, while the page loads, and prints Saved! once. Its result, undefined, is what gets handed over, and a listener of undefined is quietly ignored, so later clicks do nothing. You told the watchman "ring me" and then rang yourself on the spot. You can also write the function in place; both of these are fine:

saveBtn.addEventListener("click", function () { console.log("Saved!"); });
saveBtn.addEventListener("click", () => console.log("Saved!"));

Taking a listener away again

removeEventListener takes the same two things and crosses that line out of the browser's list. The catch is in the watchman story: you must point to the exact line you wrote. The browser compares the function by its reference — is it the very same function object? — not by whether the code looks the same.

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  button { padding: 8px 14px; margin-right: 6px; cursor: pointer; }
</style>
<button id="hello">Say hello</button>
<button id="stop">Stop counting</button>
<p id="out">Clicks counted: 0</p>

<script>
  const hello = document.getElementById("hello");
  const out = document.getElementById("out");
  let clicks = 0;

  function greet() {
    console.log("greet: Hello!");
  }
  function countClick() {
    clicks++;
    out.textContent = `Clicks counted: ${clicks}`;
    console.log("countClick: clicks =", clicks);
  }

  hello.addEventListener("click", greet);        // listener 1
  hello.addEventListener("click", countClick);   // listener 2
  hello.addEventListener("click", () => console.log("arrow: still here"));  // listener 3

  // Trying to remove listener 3: this arrow is a NEW function, so nothing matches
  hello.removeEventListener("click", () => console.log("arrow: still here"));

  document.getElementById("stop").addEventListener("click", () => {
    hello.removeEventListener("click", countClick);   // same name = same function
    console.log("countClick removed. The other two stay.");
  });

  console.log("Three listeners on Say hello. Click it.");
</script>

Click Say hello once and the Console shows three lines in order: greet: Hello!, countClick: clicks = 1, arrow: still here. The attempt to remove the arrow failed: the arrow written inside removeEventListener looks identical, but it is a brand-new function, a second sheet of paper with the same words on it. Now press Stop counting (countClick removed. The other two stay.) and Say hello again: only greet: Hello! and arrow: still here. The counter on the page freezes at 1, because countClick was named, so the browser could find that exact function and cross it out.

If you will ever need to remove a listener, give its function a name and use that name in both calls. A function written straight into the brackets has no name to point to, so it can never be removed.

For the common case "run this only the first time", there is a shortcut that removes the listener for you: a third argument of options, btn.addEventListener("click", showWelcome, { once: true }).

Quick check: why does hello.removeEventListener("click", greet) work, while removing an arrow function written out again does not?

greet names one particular function, the same one that was added, so the browser finds it in its list. Writing the arrow out again creates a new function that merely looks the same; it was never added, so there is nothing to remove.

57.4 The event object: the slip the browser hands you

Every time the browser calls one of your listeners, it passes it one argument: an event object describing what just happened. To receive it, give your function a parameter. Any name works; event, evt and e are the usual choices.

nameBox.addEventListener("input", (event) => {
  console.log(event.type);           // "input"
  console.log(event.target.value);   // whatever is in the box right now
});
Property or methodWhat it tells you, or does
event.typeThe kind of event, as a string: "click", "input", "keydown" …
event.targetThe element where the event started — the exact thing clicked or typed into
event.target.valueFor a text box, dropdown or similar: its current value (always a string)
event.currentTargetThe element whose listener is running now (57.6 shows when this differs from target)
event.keyKeyboard events only: the key pressed, such as "a", "A", "Enter", "ArrowUp", " "
event.preventDefault()Stops the browser's usual action for this event (57.5)
event.stopPropagation()Stops the event travelling on to other elements (57.6)

The lecture's example is a box that greets you as you type. Try it, and then press Tab or click outside the box.

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  input { font: inherit; padding: 6px 8px; }
  #mirror { font-size: 20px; font-weight: 700; color: #0B2545; }
  #keyInfo { color: #64748B; }
</style>
<label for="nameBox">Your name</label>
<input id="nameBox" type="text" placeholder="Type here">
<p id="mirror">Hello, stranger!</p>
<p id="keyInfo">Last key: (none yet)</p>

<script>
  const nameBox = document.getElementById("nameBox");
  const mirror = document.getElementById("mirror");
  const keyInfo = document.getElementById("keyInfo");

  nameBox.addEventListener("focus", () => console.log("focus: the box is ready"));

  nameBox.addEventListener("keydown", (event) => {
    keyInfo.textContent = `Last key: "${event.key}"`;
    console.log(event.type, "| key:", event.key);
  });

  nameBox.addEventListener("input", (event) => {
    const typed = event.target.value;
    mirror.textContent = `Hello, ${typed || "stranger"}!`;
    console.log(event.type, "| value:", typed);
  });

  nameBox.addEventListener("change", (event) => {
    console.log("change | committed:", event.target.value);
  });

  nameBox.addEventListener("blur", () => console.log("blur: you left the box"));

  console.log("Click in the box and type a name.");
</script>

Click in the box and type asha, in small letters. The Console shows focus: the box is ready, then for each letter a pair: keydown | key: a, then input | value: a; keydown | key: s, then input | value: as, and so on. The order teaches something: keydown fires before the letter reaches the box, and input fires after the value has changed. That is why a key listener asks event.key and an input listener asks event.target.value.

Press Shift on its own and you get keydown | key: Shift but no input line: a key went down, but the value did not change. (Type a capital letter and you see both: key: Shift, then key: A.) Finally click outside the box: change | committed: asha, then blur: you left the box. The page greets you letter by letter because it listens to input; had it listened to change, the greeting would appear only once you left the box.

Quick check: you want a character counter under a feedback box that updates as the student types. input or change?

input. It fires on every change to the value. change fires only when the box is left, so the counter would lag behind until the student clicked somewhere else.

57.5 preventDefault: stopping the browser's usual action

Many events come with a default action: something the browser does by itself after your listeners have run. Click a link and the browser goes to its address. Submit a form and the browser sends the data and loads a new page — for a form with no action address, that means loading the same page again, fresh and empty. Calling event.preventDefault() inside a listener cancels that default action for this one event.

The most common use by far is a form you want to handle with JavaScript. Listen for submit on the form, not click on the button: the form fires submit whether the user clicks the button or presses Enter in a box, so one listener catches both.

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; }
  input, button { font: inherit; padding: 6px 10px; }
  #msg { font-weight: 700; color: #138808; min-height: 1.4em; }
</style>
<form id="joinForm">
  <label for="who">Name</label>
  <input id="who" type="text" placeholder="e.g. Rahul">
  <button type="submit">Join the coding club</button>
</form>
<p id="msg"></p>
<p><a id="lpuLink" href="https://www.lpu.in">Visit lpu.in</a></p>

<script>
  const form = document.getElementById("joinForm");
  const who = document.getElementById("who");
  const msg = document.getElementById("msg");
  const link = document.getElementById("lpuLink");

  form.addEventListener("submit", (event) => {
    event.preventDefault();                 // no sending, no page reload
    const name = who.value.trim() || "friend";
    msg.textContent = `Welcome to the club, ${name}! (The page did not reload.)`;
    console.log("submit stopped | name:", name);
  });

  link.addEventListener("click", (event) => {
    event.preventDefault();                 // the browser does not follow the link
    console.log("link stopped | it would have opened", link.getAttribute("href"));
  });

  console.log("Ready. Submit the form, then click the link.");
</script>

Type Rahul and press Enter (or click the button): the message appears, the name stays in the box, and the Console says submit stopped | name: Rahul. Click the link: you stay where you are, and the Console says link stopped | it would have opened https://www.lpu.in. Delete the preventDefault() line from the form listener and try again: the browser sends the form, the preview is replaced by a new page, and your message and the typed name are gone (at most the message flickers for an instant). Chapter 60 builds proper form validation on exactly this pattern.

preventDefault is not "stop everything". It cancels only the browser's own action. Your other listeners still run, and the event still travels up the page as the next section describes. Stopping that travel is a different method, stopPropagation(). Mixing the two up is one of the most common exam mistakes.

57.6 Bubbling and capturing: how an event travels

Here is a puzzle. A button sits inside a <div>, which sits inside <body>. You click the button. Did you also click the div? And the body? From the user's point of view, yes: the button is part of the div, the way your hand is part of your arm. The browser agrees, and so a click is not delivered to one element only. It travels through the tree in three phases, together called propagation:

  1. Capturing phase — the event travels down from the top (window, then document), through every ancestor, towards the element that was clicked.
  2. Target phase — it arrives at the element that was clicked: event.target.
  3. Bubbling phase — it travels back up through every ancestor to document and finally window, like a bubble rising through water.

A listener added the normal way runs on the way up, during bubbling. So a click on the inner element is heard first by its own listeners, then by its parent's, then by the grandparent's. To have a listener run on the way down instead, pass true as the third argument (or { capture: true }); to remove such a listener later, pass true to removeEventListener as well. You will rarely need capturing; you will use bubbling every day.

Now event.currentTarget earns its place. During the journey, target never changes: it is always the innermost element, where the click started. currentTarget is whichever element's listener is running at this moment, so it changes at every stop. Inside a listener on the outer box, target might be the inner box while currentTarget is the outer box.

<style>
  body { font-family: system-ui, sans-serif; padding: 12px; }
  #outer, #middle, #inner { border: 2px solid #0B2545; border-radius: 10px; padding: 14px; }
  #outer  { background: #FFFFFF; }
  #middle { background: #EEF2FF; }
  #inner  { background: #FFF1E0; text-align: center; cursor: pointer; }
</style>
<label><input type="checkbox" id="stopBox"> inner calls stopPropagation()</label>
<div id="outer">outer
  <div id="middle">middle
    <div id="inner">inner (click me)</div>
  </div>
</div>

<script>
  const stopBox = document.getElementById("stopBox");

  function report(event) {
    console.log(`${event.currentTarget.id} heard it (target: ${event.target.id})`);
    if (stopBox.checked && event.currentTarget.id === "inner") {
      event.stopPropagation();
      console.log("inner called stopPropagation() - no more bubbling");
    }
  }

  // Ordinary listeners: they run while the event bubbles UP
  document.getElementById("inner").addEventListener("click", report);
  document.getElementById("middle").addEventListener("click", report);
  document.getElementById("outer").addEventListener("click", report);

  // One capturing listener (third argument true): it runs on the way DOWN
  document.getElementById("outer").addEventListener("click", (event) => {
    console.log(`--- outer, capturing on the way down (target: ${event.target.id})`);
  }, true);

  console.log("Listeners on outer, middle and inner. Click a box.");
</script>

Click the inner box. Four lines appear:

--- outer, capturing on the way down (target: inner)
inner heard it (target: inner)
middle heard it (target: inner)
outer heard it (target: inner)

Trace it against Figure 57.2. On the way down only the capturing listener on outer is listening, so it speaks first, although outer is the furthest box from the click. Then the event bubbles up: inner, middle, outer. target stays inner throughout, while currentTarget walks outwards.

Click the middle box (on the word "middle"): the capturing line says target: middle, then middle heard it and outer heard it. Inner is not on the path at all; the event starts at middle and travels up. Now tick the checkbox and click inner again: the capturing line, inner heard it, inner called stopPropagation() - no more bubbling — and nothing from middle or outer. The capturing listener had already run, because it was earlier on the trip.

A click belongs to the element you clicked and to every element around it. The browser first walks down to the clicked element, then walks back up, and normal listeners hear it on the way up: innermost first, outermost last. target is where the click happened; currentTarget is who is listening right now. stopPropagation() says "nobody further up needs to hear this".

Use stopPropagation() sparingly: a listener higher up, such as one that closes a menu when you click elsewhere, may need to hear every click. Most events bubble: click, input, change, submit, keydown and mouseover all do. A few do not bubble: focus and blur (their bubbling twins are focusin and focusout), and mouseenter and mouseleave (the bubbling versions are mouseover and mouseout).

A trap with this. In older code you will see this inside a listener. In a listener written with the function keyword, this is the same as event.currentTarget. In an arrow function it is not — arrows do not get their own this. Write event.currentTarget and the question never comes up.

57.7 Event delegation: one listener for many buttons

Bubbling makes possible one of the most useful patterns on the web. Suppose a course list has an Enrol button beside each of fifty courses. Instead of fifty listeners, add one to the list that contains them all. Every click on any button bubbles up to the list, where your listener asks event.target which button it came from. This is event delegation. There is one listener to maintain instead of fifty, and it works for buttons that did not exist yet when it was added: a course added later sits inside the same parent, so its clicks bubble to the same listener.

The listener still needs to know which course a button is for. Write that on the button itself, in data-* attributes (Chapter 56): <button data-code="CSE326" data-credits="4">, read back as button.dataset.code. dataset values are always strings, so convert numbers with Number(); and a hyphenated name becomes camelCase: data-course-name is dataset.courseName.

One line in the code below needs a word first. event.target is the innermost element clicked, which may not be a button at all: click the course name and the target is the <li>. element.closest("button") answers "is this element, or anything it sits inside, a button? If so, which one?" It returns that button, or null if there is none. Chapter 58 uses the same line again.

<style>
  body { font-family: system-ui, sans-serif; padding: 12px; }
  #courses { list-style: none; padding: 0; max-width: 420px; }
  #courses li { display: flex; justify-content: space-between; align-items: center;
                padding: 6px 10px; margin-bottom: 6px;
                border: 1px solid #CBD5E1; border-radius: 8px; }
  button { padding: 4px 12px; cursor: pointer; }
  #total { font-weight: 700; }
</style>
<h3>Choose your electives</h3>
<ul id="courses">
  <li>CSE326 Internet Programming <button data-code="CSE326" data-credits="4">Enrol</button></li>
  <li>MTH174 Engineering Maths <button data-code="MTH174" data-credits="4">Enrol</button></li>
  <li>PEL121 Communication Skills <button data-code="PEL121" data-credits="2">Enrol</button></li>
</ul>
<button id="addCourse">Add CSE121 to the list</button>
<p id="total">Credits chosen: 0</p>

<script>
  const list = document.getElementById("courses");
  const total = document.getElementById("total");
  const addCourse = document.getElementById("addCourse");
  let credits = 0;

  // ONE listener, on the list, for every Enrol button - now and later
  list.addEventListener("click", (event) => {
    const btn = event.target.closest("button");
    if (btn === null) {
      console.log("Clicked", event.target.tagName, "- not a button, ignored");
      return;
    }
    if (btn.disabled) return;                       // already enrolled
    const code = btn.dataset.code;                  // "CSE326"
    const add = Number(btn.dataset.credits);        // "4" -> 4
    credits += add;
    btn.textContent = "Enrolled";
    btn.disabled = true;                            // greyed out: one enrolment each
    total.textContent = `Credits chosen: ${credits}`;
    console.log(`Enrolled in ${code} (+${add}) | total ${credits}`);
  });

  addCourse.addEventListener("click", () => {
    const li = document.createElement("li");
    li.innerHTML = 'CSE121 Programming in C <button data-code="CSE121" data-credits="3">Enrol</button>';
    list.append(li);
    addCourse.disabled = true;
    console.log("CSE121 added - no new listener was needed");
  });

  console.log("Buttons in the list:", list.querySelectorAll("button").length, "| listeners on them: 0");
</script>

On Run: Buttons in the list: 3 | listeners on them: 0. Enrol in CSE326 and PEL121: Enrolled in CSE326 (+4) | total 4, then Enrolled in PEL121 (+2) | total 6. Click the words Engineering Maths: Clicked LI - not a button, ignored. Press Add CSE121 to the list (CSE121 added - no new listener was needed) and enrol in it: Enrolled in CSE121 (+3) | total 9. That button was born after the listener was attached, and it works anyway, because its click bubbles to the list like all the others.

Without Number(), the first enrolment would make credits the string "04" — zero joined to the text "4" — and the next would make it "042". Data attributes are text, always.

Quick check: a delegated listener is on a ul. The user clicks an Enrol button inside an li. What are event.target and event.currentTarget?

event.target is the button, where the click started. event.currentTarget is the ul, because that is the element whose listener is running.

57.8 Keyboard events and accessibility

Not everyone uses a mouse. Some people use only a keyboard, blind users drive a screen reader with keys, and a phone has no mouse at all. Your choice of events decides who can use your page, so three habits matter from day one.

1. Listen for click on a real <button>. A <button> can be reached with Tab, and pressing Enter or Space on it fires click. So one click listener already serves mouse, touch and keyboard users alike. A <div> styled to look like a button gets none of this: it cannot be reached with Tab, and keys do nothing to it. Chapter 59 shows what it takes to rescue such a "fake button" — and why it is easier to use the real one.

2. Use keydown and event.key for keyboard shortcuts. keydown fires when a key goes down, and again and again while it is held. keyup fires when it is released. event.key names the key as the user sees it:

The user pressesevent.key is
A letter, digit or symbolThat character: "a", "A" (with Shift), "7", "+"
Enter, Escape, Tab, Backspace"Enter", "Escape", "Tab", "Backspace"
The arrow keys"ArrowUp", "ArrowDown", "ArrowLeft", "ArrowRight"
The space bar" " — a string holding one space

You may meet an old event called keypress, and an old property event.keyCode holding numbers like 13 for Enter. Both are outdated; use keydown and event.key. A shortcut on the whole page goes on document, where every key press ends up by bubbling. If a key already has a job — the arrow keys scroll the page — call preventDefault() when your shortcut uses it.

3. Never make the mouse the only way. Something that appears only on mouseover — a hint, a hidden menu — is invisible to keyboard and touch users. Show it on focus as well, or better, behind a button they can click.

Use a real button and listen for click: that one listener works for mouse, finger and keyboard. Add keydown shortcuts as a bonus, never as the only way. And whatever a mouse can reveal, a keyboard must be able to reveal too.

57.9 Build it: the interactive counter

The lecture ends with an interactive counter: a number and three buttons, +, − and Reset. It has the shape of every interactive page: one piece of state (the number), and one function, render(), whose only job is to make the page show that state. Every listener changes the state, then calls render(). This version also turns the number red below zero and adds keyboard shortcuts.

<style>
  body { font-family: system-ui, sans-serif; padding: 16px; text-align: center; }
  #count { font-size: 56px; font-weight: 800; margin: 8px 0; color: #0B2545; }
  #count.negative { color: #B42318; }
  button { font-size: 20px; min-width: 56px; padding: 8px 14px; margin: 0 4px; cursor: pointer; }
  .hint { color: #64748B; font-size: 14px; }
</style>
<h3>Interactive counter</h3>
<p id="count">0</p>
<button id="minus" type="button" aria-label="Decrease">&minus;</button>
<button id="reset" type="button">Reset</button>
<button id="plus" type="button" aria-label="Increase">+</button>
<p class="hint">Keyboard: + or ArrowUp adds, - or ArrowDown subtracts, 0 resets.</p>

<script>
  let count = 0;                                     // the state: one number
  const countBox = document.getElementById("count");
  const plusBtn  = document.getElementById("plus");
  const minusBtn = document.getElementById("minus");
  const resetBtn = document.getElementById("reset");

  function render() {                                // state -> page
    countBox.textContent = count;
    countBox.classList.toggle("negative", count < 0);   // add the class only below zero
    console.log("count =", count);
  }

  // Mouse, touch, and Enter/Space on a focused button all fire "click"
  plusBtn.addEventListener("click", () => { count++; render(); });
  minusBtn.addEventListener("click", () => { count--; render(); });
  resetBtn.addEventListener("click", () => { count = 0; render(); });

  // Shortcuts for the whole page: every key press bubbles up to document
  document.addEventListener("keydown", (event) => {
    if (event.key === "+" || event.key === "ArrowUp") {
      count++;
    } else if (event.key === "-" || event.key === "ArrowDown") {
      count--;
    } else if (event.key === "0") {
      count = 0;
    } else {
      return;                                        // any other key: not ours
    }
    event.preventDefault();                          // stop the arrows scrolling
    render();
  });

  render();                                          // show the starting value
</script>

On Run, the last line calls render() once, so the Console starts with count = 0. Press + three times: count = 1, count = 2, count = 3. Press − four times and watch the number turn red at count = -1: classList.toggle("negative", count < 0) adds the class when the condition is true and removes it when it is false. Reset gives count = 0 and the colour goes back. Now click once in the empty part of the preview (so the keyboard is talking to it), and press ArrowUp twice: count = 1, count = 2, and the frame does not scroll.

PartWhy it is there
let count = 0The state. let, because it changes.
render()The only code that touches the page, so the number shown can never disagree with count.
Three click listenersChange the state, then render(). Real buttons make them keyboard-friendly for free.

With delegation and data-*, the three button listeners become one. Each button carries its step:

<div id="controls">
  <button type="button" data-step="-1">&minus;</button>
  <button type="button" data-step="0">Reset</button>
  <button type="button" data-step="1">+</button>
</div>

<script>
  // count and render() as in the counter above
  document.getElementById("controls").addEventListener("click", (event) => {
    const btn = event.target.closest("button");
    if (btn === null) return;
    const step = Number(btn.dataset.step);
    count = step === 0 ? 0 : count + step;   // 0 means reset
    render();
  });
</script>

Add a +5 button now and it needs one line of HTML, data-step="5", and no JavaScript at all. Chapter 58 grows this same state-and-render() idea from one number into whole lists, and Chapter 59 makes this counter announce itself to screen readers.

57.10 Common misunderstandings

✗ "btn.addEventListener("click", show()) runs show on every click."
The brackets run show once, at once, and hand its result (undefined) to the browser.
✓ "Pass the function, don't call it: addEventListener("click", show)."
The browser adds the brackets itself, later, each time the event happens.
✗ "event.target is always the element I put the listener on."
Only when the click happened on that very element.
✓ "target is where the event started; currentTarget is where the listener is."
With a listener on a parent, target is usually a child inside it.
✗ "preventDefault() stops the event going any further."
It cancels only the browser's own action, such as following a link or submitting a form.
✓ "preventDefault stops the default action; stopPropagation stops the travel."
They are independent: you can use either one, or both.
✗ "To remove a listener, write the same code again in removeEventListener."
Code that looks the same is a new function, and nothing is removed.
✓ "Removing needs the very same function: name it."
Pass the same name to addEventListener and removeEventListener, with the same event name.
✗ "For a form, listen for click on the submit button."
That misses the user who presses Enter in a text box.
✓ "Listen for submit on the form."
It fires for the button and for Enter alike, and preventDefault() there stops the reload.

Exam-style checks

Answer each one before opening it. Most have four options and exactly one correct answer; three ask you to predict what the code prints.

Which line runs showMenu every time btn is clicked?L1
  • A. btn.addEventListener("onclick", showMenu);
  • B. btn.addEventListener("click", showMenu());
  • C. btn.addEventListener("click", showMenu);
  • D. btn.addEventListener(click, showMenu);

Answer: C. The event name is the string "click" and the function is passed without brackets. A listens for an event that does not exist; B runs showMenu once at load and passes undefined; D uses an undeclared variable click, which throws a ReferenceError.

What does one click on the button print? btn.onclick = () => console.log("A"); btn.onclick = () => console.log("B"); btn.addEventListener("click", () => console.log("C"));L3

Answer: B, then C. The onclick property holds one function, so the second assignment replaced the first and A never prints. addEventListener adds a separate listener, which runs as well.

Which is NOT a reason to prefer addEventListener over the onclick attribute?L2
  • A. Several listeners can handle the same event
  • B. It makes the event fire faster
  • C. A listener can be removed with removeEventListener
  • D. It keeps JavaScript out of the HTML

Answer: B. Events fire at the same moment however the handler was attached. A, C and D are the three standard reasons.

A listener is on a <ul>. The user clicks a <button> inside one of its <li>s. Inside the listener, event.currentTarget is:L2
  • A. The ul
  • B. The button
  • C. The li
  • D. document

Answer: A. currentTarget is the element whose listener is running, the ul. The button (B) is event.target, where the click started — the tempting swap.

Three nested divs, outer > middle > inner, each with addEventListener("click", e => console.log(e.currentTarget.id)); middle's listener also calls e.stopPropagation(). What does a click on inner print?L3

Answer: inner, then middle. Ordinary listeners run while the event bubbles up: inner first, then middle. Middle stops the propagation, so outer never hears it.

What does event.preventDefault() do inside a form's submit listener?L2
  • A. Deletes everything typed in the form
  • B. Stops the event bubbling to the form's parents
  • C. Removes the submit listener
  • D. Stops the browser sending the form and reloading the page

Answer: D. It cancels the default action, which for a form is sending it and loading a new page. B describes stopPropagation(), a different method.

Why does btn.removeEventListener("click", () => alert("Hi")) fail to remove a listener that was added as btn.addEventListener("click", () => alert("Hi"))?L2
  • A. Arrow functions can never be listeners
  • B. The second arrow is a different function object, so nothing matches
  • C. removeEventListener only works on the onclick property
  • D. Listeners can only be removed after the event has fired

Answer: B. The browser matches the exact function, not code that looks the same. Store the function in a name and pass that name to both calls.

Which event fires on every letter typed into a text box?L1
  • A. change
  • B. submit
  • C. input
  • D. blur

Answer: C. input fires on every change to the value. change (A) waits until the value is committed, which for a text box means when the box is left.

What is the main advantage of event delegation for a list of buttons?L2
  • A. One listener on the parent handles every button, including buttons added later
  • B. It stops events bubbling
  • C. It makes each button fire its own separate event
  • D. It is the only way to read data-* attributes

Answer: A. Delegation depends on bubbling (so B is backwards): clicks on the buttons travel up to the parent's single listener, and new buttons inside the parent are covered automatically.

What does this print when the button is clicked? <button id="b" data-credits="4"> with b.addEventListener("click", e => console.log(e.target.dataset.credits + 1));L3

Answer: 41. Every dataset value is a string, so "4" + 1 joins them as text. Number(e.target.dataset.credits) + 1 gives 5.

A "button" is made from a <div> with a click listener. Who cannot use it?L2
  • A. Mouse users
  • B. Touch-screen users
  • C. Keyboard-only users
  • D. Nobody — a click listener works for everyone

Answer: C. A div cannot be reached with Tab, and Enter or Space does nothing to it. A real <button> fires click for the keyboard too, which is why it is the right element.

Quick revision

Key takeaways

  1. An event is something that happens (click, input, change, submit, keydown, mouseover, focus, blur, load, DOMContentLoaded). A listener is a callback the browser runs each time it happens.
  2. Three ways to attach: the onclick attribute, the onclick property (one function only; a new one replaces the old) and addEventListener — several listeners, removable, JavaScript kept out of the HTML. Use the last.
  3. Write addEventListener("click", fn): the event name without "on", the function without brackets. removeEventListener needs the very same function, so name it.
  4. The event object: type, target (where it started), currentTarget (whose listener is running), target.value, key.
  5. preventDefault() cancels the browser's own action (form submit, following a link). stopPropagation() stops the event travelling further. They are different.
  6. An event travels down (capturing), reaches the target, then bubbles up. Ordinary listeners run on the way up, innermost first.
  7. Delegation: one listener on a parent, event.target.closest(...) to find the child, dataset to read its data (as strings). It covers children added later.
  8. For access: real buttons plus click serve mouse, touch and keyboard; keydown with event.key adds shortcuts; nothing should be mouse-only.
