Unit 4 · Chapter 49 · Scope

Scope

Every variable you create lives somewhere. Make it inside a function and only that function can see it; make it at the top of the file and the whole page can. These rules, called scope, explain most "but I did define it!" errors, and two famous surprises: using a variable before the line that creates it, and a function that remembers things after it has finished.

About 30 minutes · Course outcome CO4

Before you start — one-line reminders

  • let and const create variables; var is the older keyword you will still meet in old code and in exam questions (Chapter 42).
  • The curly braces { } after an if or else group the lines that run together (Chapter 47).
  • A function is a named, reusable piece of code; you call it with (), and its parameters receive the values you pass in (Chapter 48).
  • A function can also be stored in a variable, as a function expression or an arrow function written with => (Chapter 48).

By the end of this chapter you can

  • Say which parts of a program can see a variable, using the words global, function and block scope.
  • Predict what var, let and const do inside an if block and a for loop.
  • Follow the scope chain to work out which variable a name refers to, including when one name shadows another.
  • Predict the output of code that uses a variable or a function before its line (hoisting and the temporal dead zone).
  • Describe the creation and execution phases and draw the call stack for nested function calls.
  • Write a closure, such as a counter or a private wallet balance, and explain why it remembers.
  • Explain why global variables are risky, and fix the classic var-in-a-loop bug.

49.1 Where can a name be seen?

In Chapter 42 you learned that let marks = 85; creates a name, marks, and attaches a value to it. So far, every name you have made could be used on any later line of your program. That stops being true the moment a variable is created inside a function. Read this and predict the last line before you read on:

function calculate() {
  const total = 85 + 90;
  console.log("Inside:", total);     // Inside: 175
}

calculate();
console.log("Outside:", total);      // ReferenceError: total is not defined

Inside calculate, total works perfectly. On the last line JavaScript stops with an error: the variable was simply never visible from out there. The region of a program where a name can be seen and used is called its scope. The scope of total is the function calculate, and the last line is outside it.

The error is a ReferenceError. It is JavaScript saying: you referred to a name, and from where you are standing I cannot find it. You will meet it often in this chapter, always for a reason you can predict.

Picture this. An LPU hostel has notice boards at three levels: one on the door of your room, one in your hostel block's lobby, and the big board at the main gate. When you want the mess timings, you check your own door first, then the block lobby, then the main gate, and you stop at the first notice you find. A notice pinned inside Room 204 can never be read by someone standing at the main gate. JavaScript's scopes work the same way: every function and block has its own board, code reads outward from where it stands, it can never read inward, and a closer notice with the same title hides a farther one.

Why hide variables on purpose? Because it makes big programs possible:

  • No trampling. Ten functions can each have their own total without disturbing one another.
  • No meddling. Outside code cannot reach in and change a function's working values by accident.
  • No clutter. When a function finishes, its variables can normally be thrown away (section 49.8 shows the exception).

49.2 Three kinds of scope: global, function and block

In an ordinary script a variable can live in one of three places. (A file loaded as a module gets a fourth, module scope; that belongs to Code Organization in Chapter 73.)

ScopeYou get it by declaring…Who can see the name
Global scopeoutside every function and every block, at the top level of the scriptEveryone: the rest of the script, and the inside of every function
Function scope (also called local scope)inside a function's braces; the function's parameters count tooOnly code inside that function, including functions written inside it
Block scopewith let or const inside any other pair of braces: the block of an if, else, for or whileOnly code inside that block

A block is simply a stretch of code between a pair of curly braces { }. You have been writing blocks since Chapter 47 every time you wrote an if. Here is one program that uses all three kinds of scope:

const college = "LPU";                     // global scope

function showRoom(dept) {                  // the parameter dept: function scope
  const floor = 2;                         // function scope
  if (floor > 1) {
    let room = "34-201";                   // block scope
    console.log(college, dept, floor, room);   // LPU CSE 2 34-201
  }
  console.log(college, dept, floor);       // LPU CSE 2
  console.log(room);                       // ReferenceError: room is not defined
}

showRoom("CSE");

Read it from the inside out. The line inside the if block sees all four names. The line after the block sees three, because room ended at its block's closing brace. Code outside showRoom could see only college. The parameter dept behaves like a variable declared at the top of the function: local to it, and made afresh for every call.

Key idea. Where a variable is declared decides where it can be used. The nearest pair of curly braces around the declaration is the variable's home. The one exception, var, is the subject of the next section.

49.3 var is function-scoped; let and const are block-scoped

Your slides put it in two lines. Variables declared with var have function-level scope: they are visible throughout the whole function, whatever blocks they sit in. Variables declared with let and const have block-level scope: they are limited to the block that declares them. The slides' own example:

function exampleFunction() {
  if (true) {
    var functionScopedVar = "I am function-scoped";
  }
  console.log(functionScopedVar);    // I am function-scoped
}

exampleFunction();
console.log(functionScopedVar);      // ReferenceError: functionScopedVar is not defined

var ignores the braces of the if, so the line after it can still read the variable. But it does notice the function's braces: outside exampleFunction the name is not defined. Swap var for let (or const) and the variable stays inside the if block:

function exampleFunction() {
  if (true) {
    let blockScopedVar = "I am block-scoped";
  }
  console.log(blockScopedVar);       // ReferenceError: blockScopedVar is not defined
}

exampleFunction();

The same rule applies to the counter of a for loop (loops get their own Chapter 52). for (let i = 1; i <= 3; i++) { ... } means: start i at 1; while i is at most 3, run the block; after each run, add 1 to i. The block runs with 1, 2 and 3, and the loop stops when i becomes 4. Declared with let, i disappears when the loop ends. Declared with var, it leaks out, still holding the 4 that stopped the loop.

To show an error and carry on, the examples use try { ... } catch (err) { ... }: try this block; if it throws, do not stop, hand the error to the catch block as err. err.name is the kind of error and err.message its text. Error handling proper is Chapter 70.

var only notices the walls of a function. let and const notice every pair of curly braces. That is the whole difference between function scope and block scope, and it is why you should write const by default, let when the value must change, and var only when you are reading someone else's old code.

Quick check: a var is declared inside an if block inside a function. Can the line straight after the if block read it? Can code outside the function?

The line after the block: yes, because var belongs to the whole function, not to the block. Code outside the function: no, because var still stops at the function's walls, so it gets ReferenceError: ... is not defined.

49.4 The scope chain: looking outward, never inward

Scopes sit inside one another like boxes inside boxes: a block inside a function, a function inside the global scope. When a line uses a name, JavaScript searches in a fixed order:

  1. the scope the line is in;
  2. if the name is not there, the scope around that one;
  3. and so on, one level further out each time, up to the global scope;
  4. if the global scope does not have it either, the search fails with a ReferenceError.

The search stops at the first match. This inside-to-outside path is the scope chain, and it runs one way only: inner code sees outer names, outer code never sees inner names, just like the notice boards in section 49.1.

The first three lines are the scope chain at work. The last needs a closer look. sayWho was called from inside caller, which has its own who, yet it printed the global one. The scope chain follows where a function is written, not where it is called from. sayWho is written at the top level, so the box around it is the global scope. This rule is lexical scope (lexical means "to do with the written text"), and JavaScript always uses it.

A function always looks outward from the spot where it was written, wherever it is called from. Put your finger on the function's own code and look at the boxes around it.

Exam tip. "What does this print?" questions love to put a same-named variable inside the calling function. Ignore it.

49.5 Shadowing: same name, different variable

You may declare a variable inside a function with the same name as one outside it. You then get two different variables that share a name. Inside the inner scope the inner one wins, because the scope chain stops at the first match; the outer one is hidden there but unharmed. This is shadowing: the local variable casts a shadow over the global one. Your slides show it with var:

var shadowedVar = "I am global";

function exampleFunction() {
  var shadowedVar = "I am local";
  console.log(shadowedVar);    // I am local
}

exampleFunction();
console.log(shadowedVar);      // I am global

It works the same with let and const, and with blocks. The example shadows one name twice, in a function and in a block inside it, then shows something that looks similar but is not shadowing at all.

One word makes all the difference. let score = 15; inside a function creates a new local variable that shadows the outer one. score = 15; with no keyword declares nothing: JavaScript walks the scope chain, finds the outer score, and changes it. If it finds no score anywhere, a normal script quietly creates a brand-new global variable, which section 49.9 explains is a real problem.

Shadowing is legal, but same-named variables in nearby scopes are easy to confuse; when you can, give them different names.

Quick check: let points = 5; is global. A function contains the single line points = 8; and is called once. What is points afterwards? What if the line had been let points = 8;?

Without let, the line changes the global variable, so points is 8. With let, the function gets its own local points that shadows the global one, and the global points is still 5.

49.6 Hoisting: using a name before its line

Your slides define hoisting as declarations being treated as if moved to the top of their scope before the code runs, so a name can be used before the line that declares it. The key detail: only the declarations are hoisted, not the initialisations.

Nothing is literally moved. Before running the first line of a scope, JavaScript reads the whole scope and notes every name declared in it. That is hoisting. What a name holds before its own line depends on how it was declared, and that is what the exam asks about.

var: hoisted, holding undefined

console.log(x);   // undefined
var x = 5;
console.log(x);   // 5

The first line prints undefined, not an error. var x was noted in advance with the starting value undefined; the assignment x = 5 stays where it was written. It behaves as if you had written:

var x;            // the declaration, noted before anything runs
console.log(x);   // undefined
x = 5;            // the initialisation happens on its own line
console.log(x);   // 5

A var is hoisted to the top of its function (or of the script, if it is outside every function), not to the top of its block, which matches what you saw in section 49.3.

let and const: hoisted, but not ready

console.log(y);   // ReferenceError: Cannot access 'y' before initialization
let y = 10;
console.log(y);   // 10

let and const are hoisted too, but not given a starting value. From the top of its scope until its declaration line runs, the name is in the temporal dead zone (TDZ). Touching it there throws a ReferenceError with a particular message, Cannot access 'y' before initialization: the name does exist, it just is not ready. Compare y is not defined, which means no such name exists at all. (Firefox says "can't access lexical declaration 'y' before initialization"; same error.)

How can we be sure let is really hoisted, not just ignored until its line? This program proves it:

let city = "Delhi";

function showCity() {
  console.log(city);      // ReferenceError: Cannot access 'city' before initialization
  let city = "Phagwara";
}

showCity();

If the inner let city were not hoisted, the first line would walk out along the scope chain and print "Delhi". Instead it throws, because JavaScript knows from the top of the function that it has its own city, still in its dead zone.

Functions: declarations are hoisted whole, expressions are not

hello();                       // Hello, world!

function hello() {
  console.log("Hello, world!");
}

A function declaration is hoisted with its whole body, so this slide example works. A function expression or arrow function is just a value stored in a variable, so it follows the rules of that variable's keyword. With var, the name holds undefined early, and calling undefined gives TypeError: greet is not a function. With let or const, the name is in its dead zone, and you get a ReferenceError.

Your slides end with good advice: declare variables at the top of their scope, so nobody has to think about hoisting. Used too early, a var gives a silent undefined, while let stops you with an error on the exact line: a loud error beats a silent wrong answer.

49.7 Execution context and the call stack

The machinery behind hoisting is simple. Whenever JavaScript runs a piece of code, it first sets up an execution context: a private workspace holding that code's variables and a note of which line it has reached. A script starts with the global execution context; every function call gets a new one of its own.

Each execution context is set up in two phases:

  1. Creation phase. JavaScript reads the code without running it and makes room for every declared name: var names get undefined, function declarations get the whole function, let and const names are noted but left uninitialised (their dead zone), and, for a function call, each parameter receives the argument that was passed in.
  2. Execution phase. JavaScript runs the lines from top to bottom, assigning values and calling functions as it reaches them.

That is all hoisting is: the creation phase finishes before the execution phase begins (Figure 49.2 pictures both phases).

The call stack

A function can call another, which can call a third. JavaScript tracks whose turn it is with the call stack, a pile of execution contexts with the newest on top. A call puts its context on top, and only the top one runs. When the function returns, its context is removed and the one underneath carries on from the line where it paused.

welcome and greet each have a parameter called name, and they do not clash, because each call has its own context. Likewise, a local variable that starts at 0 starts at 0 again on every call. A function that calls itself forever grows the stack until the browser gives up (Chrome says RangeError: Maximum call stack size exceeded; Firefox, too much recursion): the call stack has overflowed.

Every function call gets a fresh workspace: first the names are filled in, then the lines run. Workspaces pile up as functions call functions; only the top one runs, and when it finishes it is cleared away, normally taking its local variables with it.

49.8 Closures: a function that remembers

Section 49.7 said local variables "normally" go. Here is the exception. Suppose a function creates another function inside itself and hands it back with return. The outer function finishes and its context leaves the stack, but the inner function is still alive, and it uses one of the outer function's variables.

function makeCounter() {
  let count = 0;
  return function () {
    count = count + 1;
    return count;
  };
}

const counterA = makeCounter();
console.log(counterA());   // 1
console.log(counterA());   // 2

Follow it slowly. Calling makeCounter() creates count set to 0, creates a small function that adds 1 to it, and returns that function, which we store in counterA. makeCounter has now finished, yet every call of counterA() finds count and adds 1: 1, then 2. The variable was not thrown away, because a living function still needs it.

A function together with the outside variables it remembers is a closure. Every function remembers the scope it was written in (lexical scope, section 49.4); you only notice it when the function outlives the place that made it. Two facts matter more than any definition:

  • It is a live link, not a copy. The inner function holds on to the variable itself, not a snapshot of its value, so it sees every change.
  • Each call of the outer function makes a new set of variables. Call makeCounter() twice and you get two counters, each with its own count.

Closures keep data private

Code outside makeCounter cannot read or change count directly; the only way in is the function it was given. That makes closures JavaScript's natural tool for private data. The example builds a wallet whose balance can be read and topped up only through two functions, and the top-up refuses bad amounts. The two functions come out inside a small object (a bundle of named values, Chapter 51), used with a dot: rahul.addMoney(50).

A function never forgets where it was born. A variable it uses from the function that made it stays alive as long as it does, even after the maker has finished. Each run of the maker makes fresh variables, so every function it hands out has its own private memory.

A function that returns another function is one kind of higher-order function; Chapter 53 builds on exactly this idea.

Quick check: after the example above, you write const counterC = makeCounter(); and call counterC() once. What does it return, and does it change counterA's count?

It returns 1. The third call of makeCounter() creates a brand-new count starting at 0, so counterA's count (4) is untouched.

49.9 Why global variables are risky

A global variable is the easiest kind to make, and every function can use it. That convenience is exactly the problem: on a real site, with several script files written by several people, globals cause some of the hardest bugs to find.

  • Anyone can change it. If a global holds the wrong value, any line in any file might be responsible.
  • Names collide. All ordinary script files on one page share a single global scope. Two files that each pick a common name like total will fight over it.
  • A missing let makes a new one (section 49.5), as shown below.
  • It lives for the life of the page. A local variable is cleared when its function finishes; a global sits in memory until the tab is closed.

Here is a name collision. A page loads two scripts, and both declare total at the top level:

<!-- index.html -->
<script src="marks.js"></script>
<script src="quiz.js"></script>

// marks.js
let total = 0;

// quiz.js, written by a classmate
let total = 10;    // SyntaxError: Identifier 'total' has already been declared
                   // and NOTHING in quiz.js runs

With let the clash is at least loud. If both files had used var, there would be no error at all: quiz.js would silently replace the value, and the marks page would show wrong totals with nothing to warn you.

Here is the accidental global, created by a typing mistake:

function setTotal() {
  totl = 500;          // typo, and no let: a normal script quietly creates a GLOBAL totl
}

setTotal();
console.log(totl);     // 500: a stray global now exists

You can make JavaScript refuse to do this. Put the line "use strict"; at the very top of the file and the script runs in strict mode, where assigning to an undeclared name is an error instead of a silent new global. Modules (Chapter 73) are always strict, without the line.

"use strict";

function setTotal() {
  totl = 500;          // ReferenceError: totl is not defined
}

setTotal();

There is one more trap. In a browser, a top-level var (or function declaration) also becomes a property of the window object, the browser's own global object, where it can bump into names the browser already uses. A top-level let or const is still global, but it does not become a window property:

var city = "Jalandhar";
let state = "Punjab";

console.log(window.city);    // Jalandhar: the top-level var became a property of window
console.log(window.state);   // undefined: the top-level let did not

The cure is a handful of habits:

  • Declare every variable with const or let, and never assign to a name you have not declared.
  • Keep each variable in the smallest scope that works: declare it inside the function, or the block, that actually uses it.
  • Pass values in as parameters and send results out with return, instead of having functions share a global.
  • Keep data that must be protected in a closure (section 49.8) or a module (Chapter 73).

49.10 The classic bug: var in a loop

This bug, an interview and exam favourite, brings the whole chapter together. A loop schedules three small tasks to run a moment later, and each task prints the loop counter. The only new tool is setTimeout(task, ms), which means "run this task once, after ms milliseconds". Timers and callbacks are explained in Chapter 54; all you need here is that the loop finishes long before any task runs.

<style>
  body { font-family: system-ui, sans-serif; padding: 6px 14px; }
</style>
<p>Press <b>Run</b>, then watch the Console panel for a moment.</p>
<script>
  // setTimeout(task, ms) means: "run task once, ms milliseconds from now".
  // Both loops finish in a split second; the tasks run afterwards.

  for (var i = 1; i <= 3; i++) {
    setTimeout(function () {
      console.log("var loop says:", i);
    }, 100);
  }

  for (let j = 1; j <= 3; j++) {
    setTimeout(function () {
      console.log("let loop says:", j);
    }, 200);
  }

  console.log("Both loops have finished. Now wait for the tasks...");
</script>
Both loops have finished. Now wait for the tasks...
var loop says: 4
var loop says: 4
var loop says: 4
let loop says: 1
let loop says: 2
let loop says: 3

Most people expect 1, 2, 3 from the first loop. Here is why it prints 4 three times:

  • Each task is a function written inside the loop, so it is a closure: it uses the variable i from outside itself (section 49.8).
  • var ignores the loop's braces (section 49.3), so there is only one i for the whole loop, and all three tasks are linked to that same variable.
  • A closure holds a live link, not a copy. By the time the tasks run, the loop has long finished and that single i holds 4, the value that stopped the loop. All three tasks read the same 4.

With let, the loop makes a fresh j for every lap, starting from the previous lap's value. Each task is linked to the j of its own lap, which nothing changes afterwards, so they print 1, 2 and 3. Changing one keyword fixes the bug, and this was one of the main reasons let was added to the language in 2015.

49.11 Common misunderstandings

✗ "Hoisting physically moves my code to the top of the file."
Nothing moves, and assignments certainly stay where you wrote them.
✓ "Before running a scope, JavaScript notes every name declared in it."
That is the creation phase; only what each name holds early differs.
✗ "let and const are not hoisted."
Then the showCity example in section 49.6 would have printed "Delhi".
✓ "let and const are hoisted but left uninitialised: the temporal dead zone."
The message Cannot access 'x' before initialization proves the name already exists.
✗ "A variable declared inside an if block is always private to that block."
Not if it was declared with var.
✓ "let and const stay in their block; var belongs to the whole function."
And a var outside every function becomes global, block or no block.
✗ "Writing x = 5 inside a function makes a new local x."
Only a declaration (let, const or var) makes a new variable.
✓ "A plain assignment changes the nearest x it can find along the scope chain."
If there is none, a normal script creates an accidental global; strict mode throws a ReferenceError.
✗ "A function can see the variables of whoever calls it."
The caller's local variables are invisible to it.
✓ "A function sees the scopes around the place where it was written."
That is lexical scope.
✗ "A closure takes a copy of the outer variable when it is created."
Then the counter would return 1 every time, and the var loop would print 1, 2, 3.
✓ "A closure keeps a live link to the variable itself."
It sees every later change, which is why the counter counts and why the var loop prints 4, 4, 4.

Answer each one before opening it. For the "what does this print?" questions, trace the code line by line on paper first.

Which keyword declares a variable that ignores the braces of an if block and belongs to the whole enclosing function?L1
  • A. let
  • B. const
  • C. var
  • D. static

Answer: C. var is function-scoped. let and const are block-scoped, so they stay inside the if block; static is not a way to declare a variable in JavaScript.

What does this print?

Answer: B. a is a var, so it belongs to the whole function and prints 1. b is a let, which ended at the block's closing brace, so the second line throws. A forgets that let is block-scoped.

When JavaScript cannot find a name in the scope of the current line, what does it do next?L1
  • A. Looks in the scope that encloses it, then further outward until the global scope
  • B. Looks inside the functions that the current function contains
  • C. Throws a ReferenceError at once
  • D. Creates the name with the value undefined

Answer: A. That outward search is the scope chain. It never looks inward (B), and it throws a ReferenceError (C) only after even the global scope has failed.

What does this print?

  • B. outer
  • C. ReferenceError: level is not defined
  • D. undefined

Answer: B. Scope is lexical: show is written at the top level, so it looks outward from there and finds the global level. The level inside run, the caller, is invisible to it. A is the trap.

Predict both lines:

console.log(x);L2

Answer: local, then global. The let inside f creates a second variable that shadows the global one inside the function. The global x is never touched, so the last line prints "global".

What does this print, and which one-word change makes it print 0 1 2?

Answer: D. Even with a delay of 0, the tasks run after the loop has finished. There is one shared var i, and by then it holds 3, the value that stopped the loop. Change var to let: each lap then gets its own i, and the output becomes 0 1 2.

Function a calls b, and b calls c. While c is running, what does the call stack look like?L2
  • A. c's context is on top, with b, a and the global context below it
  • B. a's context is on top, with c at the bottom
  • C. Only c's context is on the stack
  • D. The global context is on top, because it started first

Answer: A. Each call puts a new execution context on top, so the newest call, c, is on top and the global context is at the bottom; b and a are paused below it.

What does this print?
function makeCounter() {
  let count = 0;
  return () => { count = count + 1; return count; };
}

const c2 = makeCounter();
console.log(c1(), c1(), c2(), c1());L3

Answer: 1 2 1 3. Each call of makeCounter() creates its own count, and each returned arrow function is a closure over its own one. c1 goes 1, 2, 3; c2, with its separate count, starts again at 1.

  • A. ReferenceError: marks is not defined

  • C. undefined, because marks was local to setMarks
  • D. SyntaxError, because marks was never declared

Answer: B. No let, const or var means nothing was declared, so a normal script makes an accidental global. With "use strict"; at the top, the assignment would instead throw A's ReferenceError, which is why strict mode is safer.

Quick revision

Key takeaways

  1. Scope is where a name can be seen. There are three kinds in a script: global, function (local) and block.
  2. var is function-scoped and leaks out of if and for blocks; let and const are block-scoped. Use const by default, let when the value changes.
  3. The scope chain searches outward from where the code is written (lexical scope), stops at the first match, and never looks inward. Not found anywhere means a ReferenceError.
  4. Shadowing: an inner declaration with the same name makes a second variable that hides the outer one inside its scope. A plain assignment without a keyword changes the outer one instead.
  5. Hoisting: var names start as undefined; let/const names sit in the temporal dead zone (ReferenceError); function declarations are hoisted whole; function expressions and arrows follow their variable's keyword.
  6. Every run of code gets an execution context: a creation phase sets up the names, then an execution phase runs the lines. Function calls pile up on the call stack; only the top one runs.
  7. A closure is a function that keeps a live link to the variables of the scope that created it, even after that scope has finished. It gives counters memory and keeps data private.
  8. Globals are risky: anyone can change them, names collide, and a missing let creates them by accident. let in a loop gives each lap its own variable, which fixes the classic bug.
